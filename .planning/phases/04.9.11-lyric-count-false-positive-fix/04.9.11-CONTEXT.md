# Phase 4.9.11: Staff Alignment — Lyric-Count False Positive Fix - Context

**Gathered:** 2026-05-29
**Status:** Ready for planning

<domain>
## Phase Boundary

Fix the Playwright UAT checker which gave false-positive PASS results (it detected bare `<tspan class="abcjs-lyric">` elements regardless of text content), then investigate and fix the underlying alignment bugs that the false positives were masking — estimated 72/144 tunes where phrase 4 has more note heads than real syllable tokens. Expand the checker to comprehensively validate staff psalm pages: correct phrase/sub-staff structure and full lyric coverage under every note head.

</domain>

<decisions>
## Implementation Decisions

### Playwright Checker Fix
- **D-01:** The immediate bug is that `ng.querySelector('.abcjs-lyric')` matches even when the tspan has empty or whitespace-only text. Fix by checking `el.textContent.trim() !== ''`.
- **D-02:** After the fix, the checker must be broadened beyond just trailing-empty detection. It should validate: (a) every note-head on every sub-staff has a non-empty lyric text or a legitimate continuation/melisma marker; (b) no unexpected "no notation available" fallbacks for tunes that should have ABC.
- **D-03:** The checker should report the true pass/fail picture after fix, forming the baseline for the alignment fix work.

### Phrase-4 Root Cause Investigation
- **D-04:** Root cause is unknown going into this phase. Investigation is Plan 1 (or combined with the checker fix plan). Approach: for each failing tune after the fixed sweep, log (a) note-head count per phrase from the DB ABC, (b) token count of the w: line, (c) whether `padWLineToNoteCount` padding was applied and how many `_` tokens were added.
- **D-05:** Three candidate root causes to test: (i) hardcoded split points [8, 14, 22] don't fit tunes with >28 notes; (ii) `countNoteHeads` in NotationRenderer undercounts phrase 4 body; (iii) `buildWLineFromSolfa` / `syllabifyForAbc` produces too few tokens for phrase 4.
- **D-06:** The fix approach (annotation script re-run, NotationRenderer change, or w:-builder patch) is determined by investigation findings — not prescribed in advance.

### Scope of Staff Page Validation
- **D-07:** The user wants comprehensive staff page validation, not just trailing-empty detection. The enhanced checker should verify the full alignment contract: notations correctly split across staves, lyrics correctly placed under all note heads.
- **D-08:** Success bar: fix checker, diagnose root cause, fix it, re-verify until 135+/139 tunes pass the comprehensive checker (11 data-gap/meter-n1 tunes are documented exceptions and remain SKIPped).

### Claude's Discretion
- Whether the comprehensive checker is implemented as an enhanced version of `verify-staff-alignment.js` or a separate script (leaning toward enhancing the existing one to avoid proliferating scripts).
- Exact threshold for "legitimate continuation vs spurious _ padding" — melisma marks from `buildWLineFromSolfa` are legitimate; `padWLineToNoteCount`-added `_` tokens for structural overflow are not.

</decisions>

## Specific Ideas

- User wants the checker to validate **everything on the staff psalm pages**: correct note-staff split structure, all lyrics correctly placed under all note heads — not just trailing-empty detection.
- Expand from "trailingEmpty > tolerance" to a comprehensive per-note check: every `g.abcjs-note` must have a `text.abcjs-lyric` child with non-empty `textContent.trim()` (unless it's a legitimate melisma continuation, which abcjs renders as an extender line, not an empty tspan).
- The investigation should produce a per-tune failure table (tune name, phrase index, note count, token count, gap size) to make the fix scope concrete before writing code.
