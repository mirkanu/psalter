## Summary

Phase 4.9.11 has two tightly coupled goals: (1) fix the Playwright checker false positive, then (2) use the fixed checker to surface and fix real alignment bugs in the underlying tunes.

The false positive is already precisely diagnosed. `ng.querySelector('.abcjs-lyric')` returns an element even when the `<tspan>` has empty `textContent` — abcjs renders an empty `<text class="abcjs-lyric">` placeholder for every note position in the row, populating it only when a lyric token covers that position. The current check never inspects `.textContent`, so `trailingEmpty=0` is reported for every psalm even when tunes have real alignment gaps at the end of phrases. The 150/150 "pass" from Phase 4.9.10 is entirely a false positive: every psalm has at least one non-empty lyric tspan somewhere in the row, which terminates the trailing scan immediately.

The real alignment problem is structural: `padWLineToNoteCount` pads short w: lines with `_` tokens, and abcjs renders each `_` as an empty-text lyric tspan — visually correct (the note has a "lyric" per the DOM, but the tspan is blank). The comprehension gap is: the DOM check sees a `.abcjs-lyric` element exists, but never reads its text. Once text is checked, the `_`-padded positions are exposed as gaps.

The estimated 72/144 phrase-4 failures identified in the Context document are the tunes where `padWLineToNoteCount` is being called to add `_` tokens for phrase 4, indicating a systematic token-count underproduction. Three candidate root causes (split-point mismatch, `countNoteHeads` undercount, `buildWLineFromSolfa` underproduction) need investigation per-tune before choosing a fix strategy.

**Primary recommendation:** Two-plan phase — Plan 1 fixes the checker and runs the investigation sweep, Plan 2 implements and verifies the alignment fix.

## Architecture Patterns

### abcjs DOM Structure (VERIFIED: live codebase read + inline comment in verify-staff-alignment.js line 44-52)

```
g.abcjs-staff-wrapper.abcjs-l<N>   — one per rendered staff row
  g.abcjs-note.abcjs-n<N>          — one per note position (syllable slot)
    text.abcjs-lyric                — ALWAYS present per note (even when empty)
      tspan                         — text content is "" when no lyric assigned
```

**Critical insight:** abcjs 6.6.3 renders a `<text class="abcjs-lyric">` element for every note group in every row. When no lyric token covers a note, the `<text>` element exists but its `textContent` is `""` (empty string). The current checker calls `ng.querySelector('.abcjs-lyric')` which returns the element regardless of content — so the check always succeeds and `trailingEmpty` is always 0.

**Melisma underscores:** abcjs renders `_` lyric tokens (ABC melisma extension) as non-empty tspans with text content `"_"` (or a rendered extender dash). These are legitimate: they mark held notes. The checker should treat `_` as valid lyric coverage.

### False Positive Fix Pattern (VERIFIED: code at verify-staff-alignment.js line 84-91)

Current (broken):
```javascript
if (noteGroups[i].querySelector('.abcjs-lyric')) {
  break  // stops scan — but element exists even when empty
}
```

Fixed:
```javascript
const lyricEl = noteGroups[i].querySelector('.abcjs-lyric')
if (lyricEl && lyricEl.textContent.trim() !== '') {
  break  // only stops when there is real text content
}
```

Apply this fix in both locations in `inspectStaff`: line 85 (trailing scan) and line 91 (notesWithLyric count).

### Comprehensive Alignment Check Pattern

The enhanced check should classify each note group in each sub-staff:

```javascript
for (const ng of noteGroups) {
  const lyricEl = ng.querySelector('.abcjs-lyric')
  const text = lyricEl ? lyricEl.textContent.trim() : ''
  if (text === '') {
    notesWithoutLyric++
  } else if (text === '_' || text === '–' || text === '-') {
    // Melisma continuation — legitimate, counts as covered
    notesWithLyric++
  } else {
    notesWithLyric++
  }
}
```

For the trailing scan (the primary pass/fail signal), empty text = not covered.

### Investigation Script Pattern (VERIFIED: established patterns in annotate-phrase-breaks.ts + NotationRenderer.tsx)

The per-tune investigation query should:
1. Load every tune from DB with `abc_notation IS NOT NULL`
2. Split on `% PHRASE_BREAK` to get phrase bodies
3. Call `countNoteHeads(phraseBody)` for each phrase  
4. Compare to expected syllable counts from `getSplitPointsForMeter` (the deltas between split points)
5. Flag tunes where phrase 4's note count > expected (indicates wrong PHRASE_BREAK placement) or where phrase 4's note count < expected (indicates undercount in `countNoteHeads`)

Expected syllable counts per phrase (from `getSplitPointsForMeter`):

- LM n=4: [8, 8, 8, 8] (split points [8, 16, 24])
- SM n=4: [6, 6, 8, 6] (split points [6, 12, 20])

## Common Pitfalls

### Pitfall 1: textContent vs innerHTML for abcjs lyric check
**What goes wrong:** `textContent` on a `<text>` SVG element includes all descendant text nodes. If abcjs nests multiple `<tspan>` elements per note (for multiple stanzas), `textContent` concatenates all of them. This is actually correct behavior for our check — we want to know if ANY stanza has a lyric at this note position.
**Why it happens:** SVG `<text>` can contain multiple `<tspan>` children (one per stanza line stacked vertically).
**How to avoid:** Use `textContent.trim()` not `innerHTML`. `textContent` is correct here.
**Warning signs:** Checker reports pass for multi-stanza psalms but fail for single-stanza — signals that the check is evaluating individual tspans rather than the parent text element.

### Pitfall 2: `_` tokens are legitimate melisma markers — not alignment gaps
**What goes wrong:** Over-strict checker treats every `_` tspan as an empty note → marks tuned-melisma psalms as FAIL incorrectly.
**Why it happens:** In ABC notation, `_` in a `w:` field is an explicit melisma extender. abcjs renders it as a non-empty element (text is `_` or an extender dash character). The lyrics.ts `syllabifyForAbc` produces `_` for multi-note syllables. `buildWLineFromSolfa` produces `_` for passing notes.
**How to avoid:** Only flag a note as misaligned when `textContent.trim() === ''` (truly empty). Do NOT flag `_`, `-`, or `–` as alignment failures.
**Warning signs:** If the enhanced checker fails every psalm with solfège OCR data, the `_`-as-failure bug is present.

### Pitfall 3: `padWLineToNoteCount`-added `_` vs. `buildWLineFromSolfa`-produced `_`
**What goes wrong:** Both produce `_` tokens, but they have different semantic meaning. `buildWLineFromSolfa` `_` = intentional melisma (note held over). `padWLineToNoteCount` `_` = structural padding because token count was short.
**Why it happens:** Both are rendered identically by abcjs (empty or near-empty tspan text). The DOM cannot distinguish them.
**How to avoid:** For investigation purposes, use the DB-side analysis (note-head count vs. token count) rather than DOM inspection to identify `padWLineToNoteCount` over-padding. The DOM check alone cannot diagnose root cause — it can only confirm presence of a gap.
**Warning signs:** Investigation shows expected-tokens > actual-tokens for phrase 4 even before padding → confirms upstream underproduction.

### Pitfall 4: Fresh browser per psalm is required (memory constraint)
**What goes wrong:** Running a single browser instance for all 150 psalms causes earlyoom to kill the Chromium process mid-sweep (~psalm 52 and ~122 historically).
**Why it happens:** VPS has 3.7GB RAM with ~1.9GB at baseline. Chromium accumulates memory across page navigations.
**How to avoid:** Keep the existing pattern from Phase 4.9.10: `launchBrowser()` per psalm (fresh chromium instance), `browser.close()` after each psalm, no `--single-process` flag (causes crash-on-close). This is already in `verify-staff-alignment.js`.
**Warning signs:** `page.evaluate: Target crashed` error — earlyoom killed the process; psalm will pass on retry.

### Pitfall 5: 50-minute timeout is tight for a comprehensive check
**What goes wrong:** The current script has a 50-minute hard timeout. Adding a per-note DOM inspection loop for all 4+ sub-staves per psalm makes each psalm slightly slower.
**Why it happens:** 150 psalms × fresh browser launch + page load + 800ms settle + DOM walk.
**How to avoid:** Benchmark a few psalms before committing to 150-psalm sweeps. If per-psalm time increases significantly, raise the timeout to 60-70 minutes in the script header. The 50-minute figure is already conservative for the Phase 4.9.10 run.
**Warning signs:** `TIMEOUT: verify-staff-alignment exceeded 50 min` at end of run.

### Investigation script skeleton (Node.js + tsx)
```typescript
// scripts/investigate-phrase4-alignment.ts
import 'dotenv/config'
import { drizzle } from 'drizzle-orm/postgres-js'
import postgres from 'postgres'
import * as schema from '../src/db/schema'
import { countNoteHeads, getSplitPointsForMeter } from './annotate-phrase-breaks'
import { phrasesForMeter } from '../src/lib/abc-phrase-meter-map'
import { isNotNull } from 'drizzle-orm'

const pgClient = postgres(process.env.DATABASE_URL!)
const db = drizzle({ client: pgClient, schema })

const tunes = await db.select().from(schema.tunes).where(isNotNull(schema.tunes.abcNotation))

for (const tune of tunes) {
  const n = phrasesForMeter(tune.meter)
  if (n <= 1) continue
  
  const abc = tune.abcNotation!
  const phrases = abc.split('% PHRASE_BREAK').map(p => p.trim())
  if (phrases.length !== n) {
    console.log(`MARKER_MISMATCH ${tune.name}: expected ${n} phrases, got ${phrases.length}`)
    continue
  }
  
  const splitPoints = getSplitPointsForMeter(tune.meter, n)
  const expected = splitPoints
    ? [splitPoints[0], ...splitPoints.slice(1).map((sp, i) => sp - splitPoints[i]), 
       // last phrase = total minus last split point
      ].slice(0, n)  // approx — compute properly
    : null
  
  for (let i = 0; i < phrases.length; i++) {
    const noteCount = countNoteHeads(phrases[i])
    console.log(`${tune.name} phrase${i}: noteHeads=${noteCount}`)
  }
}
await pgClient.end()
```

## Open Questions

1. **Why does the false positive produce 150/150 exactly?**
   - What we know: `ng.querySelector('.abcjs-lyric')` returns a non-null element for every note group in every row because abcjs always renders the `<text class="abcjs-lyric">` placeholder
   - What's clear: the trailing scan terminates at the very first note (index 0 from the end has an element) for every row — so `trailingEmpty` is always 0
   - Resolution: confirmed by code inspection; no ambiguity

2. **Will 72/144 tunes actually fail the fixed checker?**
   - What we know: Context document estimates 72 from prior analysis; the exact count is unknown until the fixed sweep runs
   - What's unclear: whether the failure count is actually phrase-4-specific or spread across phrases
   - Recommendation: Run the fixed checker on a spot sample (5-10 psalms) in Plan 1 to calibrate before full 150-psalm sweep

3. **Is `padWLineToNoteCount` always the proximate cause of `_` padding in phrase 4?**
   - What we know: `padWLineToNoteCount` is a safety net that adds `_` tokens when token count < note count; it is always called for every phrase/sub-staff combination
   - What's unclear: whether the padding is due to (i) split-point placement putting too many notes in phrase 4, (ii) `buildWLineFromSolfa` undercounting phrase 4 tokens, or (iii) `countNoteHeads` overcounting phrase 4 notes
   - Recommendation: Investigation script should log per-phrase: `noteCount`, `tokenCount` (before padding), `padCount` (tokens added), `splitPointExpected` — to distinguish root causes
