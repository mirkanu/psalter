## Implementation Decisions

### Phrase-Splitting Strategy

- **D-01: Phrase boundaries calculated at ABC import time** — Pre-computed during Phase 4.9 OCR/ABC generation, not at render time. This allows consistent phrase structure across all rendering contexts (pages, fullscreen, API, etc.).
- **D-02: Phrase breaks marked with ABC comment markers** — Use inline comments like `% PHRASE_BREAK` at phrase boundaries in the ABC string. Non-invasive, parseable by simple regex, doesn't alter ABC semantics.
- **D-03: Meter-dependent phrase lengths via predefined mapping** — Maintain a lookup table (CM → 2 phrases, LM → 2 phrases, SM → 2 phrases, double-CM → 4 phrases, etc.) rather than computing algorithmically. Simple, consistent, manually verifiable.
- **D-04: Phrase structure follows lyrical meter, not tune meter alone** — Critical clarification: phrases split where the lyric *lines* break. For CM (8.6.8.6 syllable structure), split after the first 8+6 syllables (line break), then after the next 8+6. Each stanza's 4 lyric lines map to the corresponding phrase structure. Preserves visual alignment of lyrics with staff lines.

### Font Sizing Architecture

- **D-05: Font sizing via CSS custom property `--staff-base-size`** — Set on a root container or the NotationRenderer element. All sizing derives from this: staff SVG `staffscale` (abcjs rendering), inline lyric text, and verse stanza text all scale proportionally. Cleaner than React state, no re-renders on size changes.
- **D-06: Font size range 12px–18px in 2px increments** — Four sizes: 12px (small), 14px (default/medium), 16px (large), 18px (x-large). Matches UI-SPEC baseline and provides accessibility without overwhelming options.
- **D-07: Font size persists to localStorage** — Save user's chosen size; restore on page reload. Better UX for repeat users (e.g., precentors who always want larger text).

### Component Organization

- **D-08: Create new NotationRenderer component** — High-level component replacing PsalmNotationPlayer. Owns phrase navigation state, renders one phrase at a time, composes AbcRenderer for the current phrase. Cleaner separation of concerns than extending AbcPlayer.
- **D-09: NotationRenderer manages phrase state internally** — Component owns `currentPhrase` state and prev/next handlers. Parent (psalm detail page) passes `abc`, `lyrics`, `tuneName`, etc., but doesn't manage phrase index. Simpler API for consumers.
- **D-10: Render one phrase at a time** — NotationRenderer displays the current phrase only; navigation swaps which phrase is rendered. Lighter DOM, matches UI-SPEC fullscreen layout (all phrases never visible at once). User navigates via Prev/Next buttons.

### Syllable Alignment Strategy

- **D-11: Syllabify on render, not pre-computed** — When NotationRenderer mounts or when lyrics change, apply syllabification logic to embed `w:` lines into the ABC before passing to abcjs. No changes needed to existing ABC in DB; keeps logic in the rendering layer.
- **D-12: Enhance lib/lyrics.ts with syllable embedding** — Add a function like `buildAbcWithSyllables(baseAbc: string, lyrics: string[], phraseIndex: number)` that syllabifies the relevant stanza(s) and injects `w:` lines. Keeps all lyrics-related logic in one place.
- **D-13: Generate w: lines for current phrase only** — Only syllabify the stanzas visible in the current phrase. Reduces computation, matches what user sees, allows easy swapping between phrases.

### Claude's Discretion

- **D-14: Solfège rendering strategy** — User did not specify; recommend rendering original solfège JPEG (from `solfegeJpgUrl`) as fallback when toggled to Solfège mode. Generating a dynamic solfège display is deferred per UI-SPEC note ("reserved for future enhancement").
- **D-15: Fullscreen implementation** — User did not specify; recommend CSS `position: fixed` layout with sticky bottom navigation (Prev/Next/Exit), not a separate Portal component. Simpler state management, inline with rest of component.
