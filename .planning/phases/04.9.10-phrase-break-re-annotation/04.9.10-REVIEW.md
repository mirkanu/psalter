Two source files (`annotate-phrase-breaks.ts`, `fix-stracathro-rimington.ts`) and the UAT harness (`verify-staff-alignment.js`) were reviewed at standard depth.

## Critical Issues

### CR-01: Off-by-one in Path B splice-index formula silently skips annotation

**File:** `scripts/annotate-phrase-breaks.ts:361`

**Issue:** The index computation `Math.floor((internalBars.length * k) / n) - 1` is off by one. For a tune whose body is on a single line with exactly `n-1` internal bars (the minimum that passes the guard at line 354), the formula generates duplicate index values that collapse after deduplication at line 368, causing `unique.length < n-1` at line 369 and an early `return abc` — the tune is silently skipped.

Verified with concrete values: `n=4`, `barCount=3` (minimum allowed):
- Raw indices: `[0, 0, 1]` → after dedup `[0, 1]` → length 2 < 3 → returns unchanged.

With the corrected formula (`Math.floor((internalBars.length * k) / n)`, no `-1`):
- Raw indices: `[0, 1, 2]` → after dedup `[0, 1, 2]` → length 3 = 3 → annotates correctly.

The `-1` is unexplained in the comment; it appears to be a mistaken attempt to convert a 1-based index to 0-based, but `Math.floor(len * k / n)` already produces a 0-based index.

**Fix:**
```typescript
// Line 361 — remove the `- 1`
const idx = Math.floor((internalBars.length * k) / n)
```

## Warnings

### WR-01: OVERWRITE mode permanently destroys `w:` lyric lines from ABC source

**File:** `scripts/annotate-phrase-breaks.ts:452-453`

**Issue:** When `--overwrite` is passed, the script strips all `w:` lines from the ABC source before re-annotating:

```typescript
source = source
  .replace(/^\s*%\s*PHRASE_BREAK\s*$/gm, '')
  .replace(/^w:.*$/gm, '')          // <-- destructive
  .replace(/\n\n+/g, '\n')
```

The comment says "pre-existing `w:` lines (Old 100th)" but the strip is unconditional — every tune with `w:` lyrics in its ABC gets those lines permanently deleted when the updated ABC is written back to the database at lines 70-74. Old 100th is the only tune named, but there may be others. This is a one-way data-loss operation with no recovery path within the script.

**Fix:** Either restrict the `w:` strip to specific tune names, or do not strip `w:` lines at all and instead make `insertPhraseBreaks` tolerate them (it already filters info-field lines from music-line detection, so `w:` lines won't interfere with split logic).

```typescript
// Safer: only strip PHRASE_BREAK markers; leave w: lines intact
source = source
  .replace(/^\s*%\s*PHRASE_BREAK\s*$/gm, '')
  .replace(/\n\n+/g, '\n')
```

If `w:` lines genuinely cause double-annotation issues for specific tunes, handle them explicitly by name.

### WR-02: UAT harness inflates `passed` count by including image-fallback psalms

**File:** `scripts/uat/verify-staff-alignment.js:155-160`

**Issue:** Psalms where no abcjs SVG is rendered (image fallback or missing notation data) are counted as `passed++` at line 160. The sweep log shows 10 such psalms (25, 45, 67, 70, 71, 99, 103, 104, 124, 136, 143). The `staff-alignment-report.json` reports `passed: 150, failed: 0`, making it appear all 150 psalms were positively verified — but 10 of those are unverified (no notation rendered at all). A consumer of the report cannot tell alignment was never checked for those psalms.

**Fix:** Track image-fallback psalms separately in the report summary:

```javascript
// Separate counters
let passed = 0
let failed = 0
let skipped = 0   // image fallback / no notation

// In the image-fallback branch:
console.log(`SKIP psalm ${num}: image fallback or no notation data`)
skipped++
return

// In the summary object:
const summary = {
  ...,
  passed,
  failed,
  skipped,
  failures: failureDetails,
}
```

### WR-03: `staff-alignment-report.json` is inconsistent with the sweep log

**File:** `scripts/output/staff-alignment-report.json` (artefact), `scripts/uat/verify-staff-alignment.js:231-233`

**Issue:** The sweep log at `staff-alignment-sweep-04.9.10.log` shows `Results: 148 passed, 2 failed` (psalm 75 crashed as "Target crashed" and was subsequently retried and passed). However `staff-alignment-report.json` shows `passed: 150, failed: 0, failures: []` — a clean result. These are from different script runs. The report JSON is from a later re-run where psalm 75 passed, but the checked-in sweep log captures the earlier run that had 2 failures including the unresolved psalm 75 crash.

The root cause is that the script always overwrites the same `REPORT_PATH` file. If a re-run cleans up failures, the historical evidence of the crash is gone from the report but remains visible in the log. This is a data-integrity gap for anyone auditing the artefacts: the summary in the report and the checked-in log contradict each other.

**Fix:** Either append a timestamp to the report filename so each run is preserved, or add a `runLog` field in the report that captures per-psalm results so the report is self-contained. At minimum, document in `VERIFICATION.md` that the report and the sweep log are from different runs.

### WR-04: `insertPhraseBreaks` double-newline collapse can corrupt source ABC

**File:** `scripts/annotate-phrase-breaks.ts:297`

**Issue:** After splicing `\n% PHRASE_BREAK\n` into the body string, the code collapses all runs of 2+ newlines:

```typescript
spliced = spliced.replace(/\n{2,}/g, '\n')
```

This is intended to clean up artefacts from inserting at line-end positions. However, ABC notation allows blank lines as tune separators and (in some dialects) as section dividers within a tune. If any source tune uses a blank line in its body, this replacement silently removes it, producing a different ABC string than the original — it changes tunes that do not need PHRASE_BREAK injection at all (since the function returns early if the tune already has markers). In the OVERWRITE path the strip at line 454 already removes `\n\n+`, so the body passed to `insertPhraseBreaks` won't have blank lines; but if called externally (the function is exported), the invariant does not hold.

**Fix:** Only collapse double-newlines that are adjacent to the newly inserted marker, not globally:

```typescript
spliced = spliced.replace(/\n% PHRASE_BREAK\n\n/g, '\n% PHRASE_BREAK\n')
spliced = spliced.replace(/\n\n% PHRASE_BREAK\n/g, '\n% PHRASE_BREAK\n')
```

### WR-05: `fix-stracathro-rimington.ts` hardcodes ABC header as 6 lines

**File:** `scripts/fix-stracathro-rimington.ts:59`

**Issue:** The note-count estimate uses `.split('\n').slice(6)` to skip the ABC header:

```typescript
const musicLines = abc.split('\n').slice(6).join(' ')
```

ABC headers generated by `solFaToAbc` may not always be exactly 6 lines (the generator could add optional fields such as `C:`, `S:`, `Q:` composer/source/tempo). If `solFaToAbc` ever produces a 7-line header, the note count includes one header line, and if it produces a 5-line header, one music line is skipped. This value is used only for `console.log` output, so it does not affect DB correctness — but it would produce a misleading count that could mask ABC generation regressions during diagnosis.

**Fix:** Use the same logic as `insertPhraseBreaks` to find the K: line dynamically:

```typescript
const abcLines = abc.split('\n')
const kIdx = abcLines.findIndex((l) => /^K:/.test(l.trim()))
const musicLines = kIdx >= 0 ? abcLines.slice(kIdx + 1).join(' ') : ''
const noteCount = (musicLines.match(/[A-Ga-g]/g) ?? []).length
```

### IN-02: Connection leak risk when `annotate-phrase-breaks.ts` is imported as a module

**File:** `scripts/annotate-phrase-breaks.ts:410-412`

**Issue:** The `postgres` client and drizzle instance are created inside `main()`, which is only called when the file is the entry point (`isEntry` guard). The exported functions (`countNoteHeads`, `getSplitPointsForMeter`, `insertPhraseBreaks`) do not touch the DB. However, if a future test or caller ever invokes `main()` directly (e.g. programmatic dry-run), `pgClient.end()` at line 482 will only be reached if the loop completes without throwing. If an unhandled error in the `for` loop bypasses the `await pgClient.end()` call (since it has no `finally`), the connection pool leaks.

**Fix:** Wrap the `main` body in a try/finally:

```typescript
async function main() {
  if (!process.env.DATABASE_URL) throw new Error('DATABASE_URL not set')
  const pgClient = postgres(process.env.DATABASE_URL!)
  const db = drizzle({ client: pgClient, schema })
  try {
    // ... all existing logic ...
  } finally {
    await pgClient.end()
  }
}
```

### IN-03: `--tunes` filter uses case-insensitive match but log output prints original case

**File:** `scripts/annotate-phrase-breaks.ts:428-431`

**Issue:** Minor inconsistency: the log line at 431 prints `TUNES_FILTER.join(', ')` (original case) but the DB query matches `lower(name)` against `lowered`. If a caller passes `--tunes=CRIMOND` and the tune is stored as "Crimond", the log says `Filter --tunes: CRIMOND` but the match succeeds silently. This is misleading during dry-runs when checking which tunes were targeted.

**Fix:** Print the normalised (lowered) form, or both:

```typescript
console.log(`Filter --tunes: ${TUNES_FILTER.join(', ')} (matched case-insensitively)`)
```
