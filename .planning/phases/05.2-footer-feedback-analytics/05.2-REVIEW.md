# Phase 05.2: Code Review Report

**Reviewed:** 2026-06-20
**Depth:** standard
**Files Reviewed:** 9
**Status:** issues_found

## Summary

This phase adds a site footer with About/Copyright/Feedback modals, a public feedback submission API, an admin view of submissions, and Umami analytics. The UI components are clean and the admin auth guard is correctly implemented. The primary concerns are in the public API route: it has no rate limiting, no input length caps, no email format validation, and no error handling on the DB insert — making it a trivial denial-of-service and data-quality target. The schema also has no length constraints on the feedback columns, so DB-side protection is also absent. Two secondary bugs affect the admin display and UAT reliability.

---

## Critical Issues

### CR-01: Feedback API has no input length limits — unbounded DB writes from any caller

**File:** `src/app/api/feedback/route.ts:20-25`
**Issue:** The `message`, `name`, `email`, and `pageUrl` fields are inserted into the database without any maximum-length check. A single POST with a multi-megabyte `message` body will be stored verbatim. The route is unauthenticated and publicly reachable. Combined with the absence of rate limiting, any caller can rapidly fill the `feedback_submissions` table and the PostgreSQL tablespace. The schema (`src/db/schema.ts:522-528`) also defines these columns as unbounded `text` with no DB-level constraints, so there is no safety net below the application layer.

**Fix:**
```typescript
const MAX_MESSAGE = 5000
const MAX_SHORT = 200

const message = typeof body.message === 'string' ? body.message.trim() : ''
if (!message) {
  return NextResponse.json({ error: 'message is required' }, { status: 400 })
}
if (message.length > MAX_MESSAGE) {
  return NextResponse.json({ error: 'message too long' }, { status: 400 })
}

const name = typeof body.name === 'string' ? body.name.trim().slice(0, MAX_SHORT) || null : null
const email = typeof body.email === 'string' ? body.email.trim().slice(0, MAX_SHORT) || null : null
const pageUrl = typeof body.pageUrl === 'string' ? body.pageUrl.trim().slice(0, 2048) || null : null
```

For schema defence-in-depth, add `varchar` column widths or a `CHECK (char_length(message) <= 5000)` constraint in the next migration.

### CR-02: Feedback API has no error handling on the DB insert — unhandled rejection returns stack trace

**File:** `src/app/api/feedback/route.ts:20`
**Issue:** `await db.insert(feedbackSubmissions).values(...)` is not wrapped in a try/catch. Any DB error (connection lost, constraint violation, disk full) will throw an unhandled exception that Next.js converts to a 500 response, potentially with a stack trace in development mode. More importantly, the caller (`FeedbackModal`) treats any non-`ok` response as a generic error and the client sees `status='error'` — but the root cause is invisible and cannot be distinguished from a transient network failure.

**Fix:**
```typescript
try {
  await db.insert(feedbackSubmissions).values({ message, name, email, pageUrl })
} catch (err) {
  console.error('[feedback] DB insert failed:', err)
  return NextResponse.json({ error: 'internal error' }, { status: 500 })
}

return NextResponse.json({ ok: true })
```

### CR-03: Email field accepted without format validation — malformed values stored permanently

**File:** `src/app/api/feedback/route.ts:23`
**Issue:** The `email` field is stored as any non-empty string. The client-side `<input type="email">` provides browser-level validation, but the API has no corresponding server-side check. Any direct POST (curl, scripts, the UAT runner itself) can store `"not-an-email"` or `"x@"` in the `email` column. The admin display renders this value verbatim with no sanitisation, and if any future code attempts to send email to stored addresses, it will fail with hard bounces on bad data.

**Fix:**
```typescript
const emailRaw = typeof body.email === 'string' ? body.email.trim() : ''
const emailValid = /^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(emailRaw)
const email = emailRaw && emailValid ? emailRaw : null
// Optionally: return 400 if emailRaw is non-empty but invalid
```

## Warnings

### WR-01: Admin feedback page — `createdAt.toLocaleString` will silently produce wrong output if Drizzle returns a string

**File:** `src/app/admin-only/feedback/page.tsx:40`
**Issue:** `row.createdAt.toLocaleString('en-GB')` assumes `createdAt` is a `Date` object. Drizzle maps `timestamp` columns to `Date` objects when using the `postgres.js` driver — which is correct for this project. However, `String.prototype.toLocaleString` also exists and does not format dates: if the value were ever a string (e.g. after a raw `sql\`\`` query or a future driver change), the column would display as a raw ISO string without any error. Explicitly guard this:

**Fix:**
```typescript
<TableCell>
  {row.createdAt instanceof Date
    ? row.createdAt.toLocaleString('en-GB')
    : new Date(row.createdAt).toLocaleString('en-GB')}
</TableCell>
```

### WR-02: FeedbackModal error catch silently discards the error — debugging impossible in production

**File:** `src/components/FeedbackModal.tsx:47`
**Issue:** The `catch` block discards the thrown error entirely:
```typescript
} catch {
  setStatus('error')
}
```
Network errors, JSON parse failures, and server-side errors all collapse into the same user-visible message `"Something went wrong."`. There is no logging, so a recurring API failure (e.g. the DB insert bug in CR-02) will not appear in any log stream.

**Fix:**
```typescript
} catch (err) {
  console.error('[FeedbackModal] submission failed:', err)
  setStatus('error')
}
```

### WR-03: UAT `checkFOOT04FeedbackModal` does not verify the submission was persisted — shallow test

**File:** `scripts/uat/phase-05.2-uat.js:157-221`
**Issue:** The test generates a unique `marker` string, fills the textarea, and checks for a `"Thank you for your feedback"` heading after the POST. But it never verifies the marker was actually written to the database (e.g. by checking the admin page at `/admin-only/feedback`). The test would pass even if the API returned `ok: true` without writing to the DB (e.g. due to a silenced error). This makes FOOT-04 a UI-flow test, not a persistence test.

**Fix:** After verifying the success heading, make an authenticated request to the admin endpoint and confirm the marker text appears in the response, or add a separate admin-authenticated check to the test suite.

### WR-04: `SiteFooter` — About and Copyright dialog content is always rendered in the DOM

**File:** `src/components/SiteFooter.tsx:23-47`
**Issue:** Both `<Dialog>` blocks render their `<DialogContent>` unconditionally — they are in the React tree at all times, only visually hidden when `open=false`. The shadcn `Dialog` implementation uses a portal but still mounts content. This means all link text and paragraph text inside the dialogs is always present in the DOM, which creates duplicate content for screen readers (who encounter the footer text, then encounter the same links and text again in hidden dialog content), and contributes to accessibility tree pollution.

**Fix:** Use conditional rendering or `<DialogContent>` inside a `<Dialog>` that only renders its children when open. Alternatively, restructure to use the `open` state as a guard before rendering content:
```tsx
{open === 'about' && (
  <Dialog open onOpenChange={(v) => !v && setOpen(null)}>
    <DialogContent>...</DialogContent>
  </Dialog>
)}
```

### WR-05: UAT script error-branch function-name parsing is garbled for FOOT/UMAMI identifiers

**File:** `scripts/uat/phase-05.2-uat.js:313`
**Issue:**
```js
const name = check.name.replace(/^check/, '').replace(/([A-Z])/g, ' $1').trim()
```
Applied to `checkFOOT01Footer`, this produces `" F O O T01 Footer"` — every capital letter gets a space inserted. Acronym names (`FOOT`, `UMAMI`) are unreadable in error output.

**Fix:** Use the function name directly or add a `label` property to each check result at the call site rather than parsing the function name:
```js
results.push({ name: check.name, pass: false, detail: `Exception: ${e.message}` })
```
Or store a human-readable label alongside each check function.

### IN-01: `NEXT_PUBLIC_PSALTER_UMAMI_WEBSITE_ID` absence silently suppresses analytics — UAT dependency undocumented

**File:** `src/app/layout.tsx:42-48`
**Issue:** The Umami script is conditionally rendered only when `NEXT_PUBLIC_PSALTER_UMAMI_WEBSITE_ID` is set. This is intentional (suppresses tracking in local dev). However, the UAT script `checkUMAMI01Script` will hard-fail (`FAIL scriptExists=false`) in any environment where this env var is absent — including CI runs or staging deployments — with no indication that the failure is an environment configuration issue rather than a code bug.

**Fix:** Add a comment to the UAT script near `checkUMAMI01Script` noting the env-var dependency:
```js
// UMAMI-01 requires NEXT_PUBLIC_PSALTER_UMAMI_WEBSITE_ID to be set in the
// deployment environment. This check will FAIL in envs where analytics is
// intentionally disabled (local dev, CI without the var set).
```

### IN-02: `pageUrl` stores the raw `window.location.href` including hash and query string — no normalisation

**File:** `src/components/FeedbackModal.tsx:43`
**Issue:** `pageUrl: includeUrl ? window.location.href : null` captures the full URL including fragment identifiers (`#section`) and query parameters. For pages with dynamic search state in the URL (e.g. `/explore?q=...`), this is useful context. However, it also means that two submissions from the same page with different query strings are stored as different URLs, making it harder to aggregate feedback by page in the admin view.

This is acceptable as-is for current usage; raise it if feedback volume grows and aggregation becomes needed.
