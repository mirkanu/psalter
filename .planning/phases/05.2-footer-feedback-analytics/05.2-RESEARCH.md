## Summary

Phase 05.2 adds three independent capabilities to the psalter: a persistent site footer (present on every page via root layout), a feedback form stored in a new PostgreSQL table, and a Umami analytics snippet in the root layout. All three are well-understood patterns with verified implementation references in this codebase and sibling projects.

The footer and modals are purely additive — they attach to `src/app/layout.tsx` after `<Toaster />` and require no structural changes to existing routes. All required shadcn components are already installed (`Dialog`, `Button`, `Input`, `Label`, `Checkbox`, `Table`, `Separator`, `Skeleton`) except `Textarea`, which must be added via `npx shadcn add textarea`. The feedback submission API route is unauthenticated (public form), writes to a new `feedback_submissions` table, and requires one `drizzle-kit push` to provision the table. The `/admin/feedback` page follows the exact same auth-gate pattern as `/dev/accounts` (RSC-level `auth.api.getSession` + redirect), placed at `src/app/admin-only/feedback/page.tsx`.

For Umami: no psalter website ID exists yet in the Umami instance at `umami.gsdlabs.dev` (verified by API). The website must be provisioned via the Umami REST API (one POST request), the returned ID stored as `NEXT_PUBLIC_PSALTER_UMAMI_WEBSITE_ID` in `/data/home/psalter/.env` and `/home/services/.env.production`, and a `<Script>` tag added to the root layout following the exact pattern used in the debates project.

**Primary recommendation:** Three-wave plan — (Wave 0) provision Umami website + add `Textarea` shadcn component + add feedback schema + drizzle-kit push; (Wave 1) build `SiteFooter` component + three Dialog modals + API route; (Wave 2) build `/admin/feedback` page + wire Umami `<Script>` + Playwright UAT.

### Pattern 2: Feedback API Route (unauthenticated)

```typescript
// Source: established pattern from /src/app/api/precent/route.ts
// src/app/api/feedback/route.ts
import { NextResponse } from 'next/server'
import { db } from '@/db'
import { feedbackSubmissions } from '@/db/schema'

export async function POST(req: Request) {
  let body: Record<string, unknown>
  try {
    body = await req.json()
  } catch {
    return NextResponse.json({ error: 'invalid JSON body' }, { status: 400 })
  }

  const message = typeof body.message === 'string' ? body.message.trim() : ''
  if (!message) {
    return NextResponse.json({ error: 'message is required' }, { status: 400 })
  }

  await db.insert(feedbackSubmissions).values({
    message,
    name: typeof body.name === 'string' ? body.name.trim() || null : null,
    email: typeof body.email === 'string' ? body.email.trim() || null : null,
    pageUrl: typeof body.pageUrl === 'string' ? body.pageUrl.trim() || null : null,
  })

  return NextResponse.json({ ok: true })
}
```

### Anti-Patterns to Avoid

- **Server Component footer:** The footer needs `useState` for dialog open states. It must be `'use client'`. Do NOT attempt to split triggers and dialogs across RSC/client boundaries.
- **`<script>` tag instead of `<Script>`:** Raw `<script>` in Next.js App Router layout is ejected from the `<head>` in unpredictable ways. Always use `next/script` with `strategy="afterInteractive"`.
- **Hardcoding the website ID:** The Umami website ID belongs in `.env` as `NEXT_PUBLIC_PSALTER_UMAMI_WEBSITE_ID` — it's not a secret (it's embedded in client JS), but it should not be hardcoded in source.
- **Middleware protection for /admin-only/feedback:** The existing middleware only covers `/dev/*` and `/precent/*`. The admin page uses RSC-level auth guard (`auth.api.getSession` + redirect). Do NOT add `/admin-only/*` to the middleware matcher without understanding the performance implication (DB call on every request). Use RSC guard instead — already established pattern.
- **Closing the Feedback modal on success:** UI-SPEC explicitly says "Do not close modal automatically." Show success state in-place.

## Common Pitfalls

### Pitfall 1: NEXT_PUBLIC_ env vars require rebuild
**What goes wrong:** Adding `NEXT_PUBLIC_PSALTER_UMAMI_WEBSITE_ID` to `.env` after the app is already built does nothing — Next.js bakes NEXT_PUBLIC_ vars into the bundle at build time.
**Why it happens:** `NEXT_PUBLIC_` vars are inlined at compile time, not resolved at runtime.
**How to avoid:** Add the env var to `.env`, then run `npm run build` + `pm2 restart psalter`. The Wave 0 plan must provision the Umami website ID first, then the build step in the final wave will embed it.
**Warning signs:** Script tag renders with `data-website-id=""` in page source.

### Pitfall 2: Umami provisioning must happen before the build
**What goes wrong:** If the Umami website ID doesn't exist in `.env` at build time, the `<Script>` renders with an empty `data-website-id` and Umami records nothing.
**How to avoid:** Wave 0 creates the Umami website, stores the ID in `.env`. All other waves depend on Wave 0 completing.

### Pitfall 3: Textarea not yet installed
**What goes wrong:** `import { Textarea } from '@/components/ui/textarea'` fails at compile time — `textarea.tsx` does not exist in `src/components/ui/`.
**How to avoid:** Wave 0 must run `npx shadcn add textarea` before any component that imports it.

### Pitfall 4: `export const dynamic = 'force-dynamic'` on admin page
**What goes wrong:** Without this export, Next.js may attempt to statically render `/admin-only/feedback/page.tsx` at build time, which fails because `auth.api.getSession` requires request headers.
**How to avoid:** Add `export const dynamic = 'force-dynamic'` as the first line of the admin page — exactly as done in `/dev/accounts/page.tsx`.

### Pitfall 5: Footer outside Providers
**What goes wrong:** If `<SiteFooter />` is placed outside `<Providers>` in `layout.tsx`, it won't have access to theme context (dark mode via `next-themes`).
**How to avoid:** Insert `<SiteFooter />` inside `<Providers>`, after `<Toaster richColors />` but before `</Providers>`.
