# Phase 04.9.13: Code Review Report

**Reviewed:** 2026-06-28T12:00:00Z
**Depth:** standard
**Files Reviewed:** 9
**Status:** issues_found

## Summary

The single-psalm singing view is a substantial UI streamlining that consolidates notation rendering, audio playback, stanza navigation, and view-mode switching into a single chromeless fullscreen-style layout. The component architecture is clean: `SingingView` owns all lifted state and delegates to focused child components (`GlassBottomBar`, `PlayMiniBar`, `GearPopover`, `PsalmTopBar`). The `NotationRenderer` is correctly wrapped in a `dynamic({ ssr: false })` + `Suspense` boundary for abcjs.

Four warnings surfaced: a missing `phraseShapeOverride` column in the alternate-tunes query (so tune-switcher selections lose phrase-shape override behavior), an ABC source selection inconsistency between the singing view and the tune detail page, a size-range clamp mismatch between `GlassBottomBar` and `NotationRenderer`, and an unnecessary type cast on `melismaPositions` in `SingingView`. Three informational items note dead code, a redundant cast, and a suppressed eslint dependency warning that could mask future bugs.

## Warnings

### WR-01: `phraseShapeOverride` not selected in `fetchTunesByMeter` — alternate tunes lose phrase-shape override

**File:** `src/db/queries/tunes.ts:111-129` (consumed via `src/app/psalms/[id]/page.tsx:105`)
**Issue:** The `fetchTunesByMeter` query selects 12 tune columns but omits `phraseShapeOverride`. When a user switches to an alternate tune via the TuneSwitcherSheet, the `phraseShapeOverride` field is `undefined` on the alternate tune object. In `SingingView.tsx:360`, the cast `(activeTune as { phraseShapeOverride?: number[] | null } | undefined)?.phraseShapeOverride` therefore resolves to `undefined`, which falls back to `?? null`. The renderer then uses the meter-derived phrase count instead of the authored override. For tunes like Abbeyville (`[8,6,8,6,6]`) this collapses the 5-phrase layout back to the meter default, re-introducing the last-line-repeat bug that `phraseShapeOverride` was designed to fix.

The `primaryTune` path works correctly because `fetchPsalmDetail` uses `tune: true` (all columns), and `page.tsx:131` explicitly copies `phraseShapeOverride` into the reconstructed object. But any tune reached via the switcher is missing it.

**Fix:**
```typescript
// In fetchTunesByMeter (src/db/queries/tunes.ts), add to columns:
columns: {
  id: true,
  name: true,
  meter: true,
  abcNotation: true,
  abcSatb: true,
  scoreJpgUrl: true,
  solfegeJpgUrl: true,
  soundcloudUrl: true,
  youtubeUrl: true,
  doubleLength: true,
  solfegeOcrText: true,
  melismaPositions: true,
  phraseShapeOverride: true,   // <-- add this
},
```

Also add `phraseShapeOverride: number[] | null` to the `AlternateTune` interface so the type cast at `SingingView.tsx:360` is no longer needed.

### WR-02: SingingView uses `abcNotation` directly instead of `pickAbcWithMarkers(abcSatb, abcNotation)`

**File:** `src/components/singing/SingingView.tsx:312`
**Issue:** The singing view derives its ABC source as `const abc = activeTune?.abcNotation ?? ''`. The tune detail page (`src/app/tunes/[id]/page.tsx:83`) uses `pickAbcWithMarkers(tune.abcSatb, tune.abcNotation)` to prefer whichever source has `% PHRASE_BREAK` markers. The singing view does not.

The current ingestion pipeline adds markers to `abcNotation`, so this works in practice today. But the `pickAbcWithMarkers` function exists specifically to handle the case where markers are in `abcSatb` but not `abcNotation` (or vice versa). By not using it, the singing view is fragile against future ingestion changes and inconsistent with the tune page. Additionally, `sopranoOnly` is never called on the ABC source, so if `abcNotation` is SATB-format for any tune, the singing view would render all four voices.

**Fix:**
```typescript
// In SingingView.tsx, replace line 312:
import { pickAbcWithMarkers, sopranoOnly } from '@/lib/utils'
const rawAbc = pickAbcWithMarkers(
  (activeTune as { abcSatb?: string | null } | undefined)?.abcSatb ?? null,
  activeTune?.abcNotation ?? null,
)
const abc = rawAbc ? sopranoOnly(rawAbc) : ''
```

### WR-03: `GlassBottomBar` clamps baseSize to [8, 40] while `NotationRenderer` allows [4, 120]

**File:** `src/components/singing/GlassBottomBar.tsx:65,73`
**Issue:** The A-/A+ buttons in `GlassBottomBar` hard-code their clamp range as `Math.max(8, ...)` and `Math.min(40, ...)`. Meanwhile, `NotationRenderer` defines `MIN_SIZE = 4` and `MAX_SIZE = 120`. The `SingingView` passes `handleBaseSizeChange` (which calls `setBaseSize` with no additional clamping) to both components. The result: the bottom bar's A+ button becomes a no-op at size 40, even though the renderer would support sizes up to 120. Conversely, if the renderer's internal controls (in non-chromeless mode) set a size below 8, the bottom bar would display that size but its A- button would clamp back to 8 on the next press.

This is a minor UX inconsistency but could confuse users who expect A+ to keep working past 40.

**Fix:** Extract the clamp constants to a shared location or reference `NotationRenderer`'s exported bounds. At minimum, align the bottom bar to the same range:
```typescript
// In GlassBottomBar.tsx, import or define:
const MIN_BASE_SIZE = 4
const MAX_BASE_SIZE = 120
// ...
onClick={() => onBaseSizeChange(Math.max(MIN_BASE_SIZE, baseSize - 1))}
// ...
onClick={() => onBaseSizeChange(Math.min(MAX_BASE_SIZE, baseSize + 1))}
```

### WR-04: `unifiedAbc` memo has suppressed eslint-disable with incomplete dependency list

**File:** `src/components/notation/NotationRenderer.tsx:1001-1003`
**Issue:** The `unifiedAbc` useMemo has `// eslint-disable-next-line react-hooks/exhaustive-deps` with a comment that "wLinesForPhrase depends on visibleCycles, captured by closure." The explicit dependency list is `[split, visiblePhraseIndices, visibleCycles, tuneMeter, showLyrics, phraseSubdivisions, chromeless, solfegeVoices, melismaPositions]`.

The function `wLinesForPhrase` (called inside the memo body) closes over `phraseShapeOverride` and `tuneMeter`. While `visiblePhraseIndices` does change when `phraseShapeOverride.length` changes (triggering memo recomputation), a change to the *contents* of `phraseShapeOverride` without a length change would NOT trigger recomputation. This is unlikely in practice (phrase shape is authored per-tune and doesn't change at runtime), but the suppressed eslint warning makes it easy to miss future regressions if the closure captures additional variables.

**Fix:** Add `phraseShapeOverride` to the explicit dependency list and remove the eslint-disable:
```typescript
}, [split, visiblePhraseIndices, visibleCycles, tuneMeter, showLyrics, phraseSubdivisions, chromeless, solfegeVoices, melismaPositions, phraseShapeOverride])
```

### IN-01: Unnecessary type cast on `melismaPositions` in SingingView

**File:** `src/components/singing/SingingView.tsx:365`
**Issue:** `melismaPositions` is accessed via `(activeTune as { melismaPositions?: number[][] | null } | undefined)?.melismaPositions`. Since `AlternateTune` (the `TuneOption` type) already declares `melismaPositions: number[][] | null`, this cast is redundant. The cast on `phraseShapeOverride` (line 360) IS needed because that field is missing from `AlternateTune`, but the `melismaPositions` cast adds noise.

**Fix:**
```typescript
melismaPositions={activeTune?.melismaPositions ?? null}
```
