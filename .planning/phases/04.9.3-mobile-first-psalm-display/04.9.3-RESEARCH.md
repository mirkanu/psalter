# Phase 04.9.3: Mobile-first Psalm Display — Research

**Researched:** 2026-05-16
**Domain:** Mobile-first single-page singing UI on top of Next.js 15 App Router + abcjs client-only renderer + shadcn primitives
**Confidence:** HIGH (most decisions locked by UI-SPEC; verification focused on what the planner must touch in code)

---

## Summary

This phase replaces the legacy tabbed psalm detail page (`src/app/psalms/[id]/page.tsx` → `<PsalmTabs>`) with a singing-instrument layout: a sticky top bar (`← Psalm N →`), sub-bar (`Tune (M): TuneName [Edit]`), full-viewport notation body, and one FAB that opens a bottom Sheet containing view-switcher / audio / metadata. It also closes out the abcjs overflow class of bugs by hard-clamping the container and deriving `staffwidth` from `offsetWidth`.

Crucially, **most of the infrastructure already exists** — the staffwidth-from-`outerRef` pattern is already wired in `AbcPlayer.tsx` (`useLayoutEffect` + `ResizeObserver`); the abcjs client-only wrapper (`NotationRendererClient`) is already in place; sheet/dialog primitives are installed; prev/next neighbor lib (`getPsalmNeighbors`) is already implemented. This phase is therefore primarily **assembly + targeted bug fixes**, not new infrastructure.

**Primary recommendation:** Build new chrome components (PsalmTopBar / TuneSubBar / PsalmActionsFAB / PsalmSelectorSheet / TuneSwitcherSheet) as thin presentational wrappers over existing primitives and the existing `NotationRenderer`. Strip `NotationRenderer`'s internal controlBar in the new layout (controls move into FAB sheet) but reuse its view-mode + size state via props. Fix the abc overflow by (a) adding `overflow-x: hidden` + `max-w-full px-2` on the AbcPlayer outer container, (b) keeping the existing `staffwidth = clientWidth` derivation, and (c) lowering the mobile default `--staff-base-size` to 13px as locked by UI-SPEC.

## User Constraints (from UI-SPEC — treated as LOCKED)

The UI-SPEC at `.planning/phases/04.9.3-mobile-first-psalm-display/04.9.3-UI-SPEC.md` is an APPROVED design contract. There is no CONTEXT.md for this phase; UI-SPEC is the binding upstream artifact.

### Locked Decisions

- **Pattern:** Bottom Sheet (shadcn `Sheet side="bottom"`), NOT speed-dial radial menu, for FAB expansion.
- **Layout heights:** Top bar 48 / 56 px; sub-bar 40 / 44 px; FAB 56×56 at `bottom-4 right-4 + safe-area`.
- **Body sizing:** `calc(100dvh - 88px)` mobile / `calc(100dvh - 100px)` ≥768px, single scroll container, `overflow-x: hidden` mandatory.
- **Default `--staff-base-size`:** 13px mobile, 14px ≥768px (overrides current `DEFAULT_SIZE = 14` / `MOBILE_DEFAULT_SIZE = 24` in `NotationRenderer.tsx`).
- **Spacing scale:** 4 / 8 / 16 / 24 / 32 / 48 / 64; icon tap targets `min-h-11 min-w-11`.
- **Typography:** strict 3-size (14 / 16 / 20) × 2-weight (400 / 600), Geist Sans only.
- **Color:** existing shadcn `neutral` + CSS vars; accent reserved for FAB / active view-mode / current-tune highlight only.
- **A+/A− moves into FAB sheet** (out of always-visible chrome).
- **Fullscreen mode removed** as a distinct mode — the default singing view IS the fullscreen.
- **Legacy /psalms/[id] tabbed page preserved** behind `/psalms/[id]/study` (or equivalent) — link from "About this psalm" → "Open full study view →".
- **Dark mode out of scope** (global deferral per STATE.md).
- **Swipe gestures, pinch-zoom, per-psalm view-mode memory** all explicitly deferred.

### Claude's Discretion

- Exact route shape for the preserved legacy page (`/psalms/[id]/study` vs route group vs query param). The UI-SPEC suggests `/study`; the planner should confirm.
- Whether the new chrome ships as a wrapper around existing `<PsalmTabs>` or replaces it at the route level. (Recommend: replace at the route level; render `<PsalmTabs>` content inside the FAB sheet's metadata section and from the `/study` route.)
- How to surface "Recommended" vs "Other" tunes in `TuneSwitcherSheet` — see Open Questions §1 (schema does not currently carry an `is_recommended` flag).
- ErrorBoundary placement and whether to use Next.js `error.tsx` per-route or a local boundary inside `NotationBody`.

### Deferred Ideas (OUT OF SCOPE)

Swipe-prev/next gestures · pinch-zoom · per-psalm view-mode localStorage · dark mode · removing the legacy 7-tab page entirely.

### Pattern 2: Container-derived staffwidth (ALREADY IMPLEMENTED in AbcPlayer.tsx:181-200, :282)

**What:** Measure `outerRef.current.clientWidth` synchronously in `useLayoutEffect` and via `ResizeObserver`; pass `staffwidth: staffWidth || 600` to `ABCJS.renderAbc`. `[VERIFIED: src/components/AbcPlayer.tsx]`

**What's missing for MOBILE-03:**

- No explicit `orientationchange` or `window.visualViewport.resize` listener. ResizeObserver fires for layout changes but iOS Safari has historically been unreliable when the visual viewport changes without a layout change (URL bar collapse, address-bar reveal). Add both with 150ms debounce per UI-SPEC §Interaction.
- `staffwidth - 16` (8px each side padding) to account for the `px-2` padding the UI-SPEC requires.

### Pattern 3: Sheet-based picker (existing convention)

`ChangeTuneDialog.tsx` already implements the same idea using shadcn `Dialog`. For 04.9.3, **port the same selection logic to `TuneSwitcherSheet`** using `Sheet side="bottom"`. Sections become:

### Anti-Patterns to Avoid

- **Re-implementing the staffwidth derivation in a new component.** The pattern already exists in `AbcPlayer.tsx`. New components should use `AbcPlayer` (or refactor it) — don't add a second copy of `renderAbc` + ResizeObserver elsewhere.
- **Putting view-mode in URL query.** `?tune=` is the only URL param this view needs. View mode is ephemeral; persisting it would conflict with the explicit deferral of per-psalm view-mode memory.
- **Hand-rolling the bottom sheet with motion.** shadcn's `Sheet side="bottom"` already provides focus trap, swipe-down close, backdrop, `aria-modal`, prefers-reduced-motion. `[VERIFIED: src/components/ui/sheet.tsx]`
- **Removing the legacy `<PsalmTabs>` entirely.** UI-SPEC requires it remain reachable via "Open full study view →". Move it to `/psalms/[id]/study` rather than delete.
- **Using `100vh` for body height.** `dvh` is locked in UI-SPEC; `vh` breaks on iOS Safari when the URL bar collapses/reveals.

## Common Pitfalls

### Pitfall 1: iOS Safari URL bar collapse breaks the layout
**What goes wrong:** `100vh` (or even early-`dvh` polyfills) recalculates as the URL bar slides away, causing layout jump. The notation may also render at the wrong height.
**Why it happens:** iOS Safari distinguishes "small viewport" / "large viewport" / "dynamic viewport". Only `dvh`/`svh`/`lvh` units reflect the dynamic one.
**How to avoid:** Use `100dvh` exclusively for body sizing (UI-SPEC has this locked). Test on iOS Safari via Playwright `--device "iPhone 15"` UAT.
**Warning signs:** Body height changes when scrolling reveals/hides the URL bar; FAB ends up under the home indicator.

### Pitfall 2: abcjs renders before width is measured → "wrong on first paint"
**What goes wrong:** `useEffect` measurement causes a flash of incorrectly sized notation.
**Why it happens:** `useEffect` runs after paint; abcjs has already drawn at fallback width 600 in the first frame.
**How to avoid:** `useLayoutEffect` for initial measurement (already in place at `AbcPlayer.tsx:185`). Keep this synchronous initial measurement. `[VERIFIED: src/components/AbcPlayer.tsx:185]`

### Pitfall 3: ResizeObserver fires once per render → infinite loop
**What goes wrong:** Renderer changes container layout → RO fires → setState → re-render → repeat.
**Why it happens:** If `setStaffWidth(w)` is called with the same value every observe pass, React still re-renders but React.memo / dep arrays may save us — but a width-rounded measure can cause oscillation between two values.
**How to avoid:** Existing code (line 195) sets only when `w > 0`. Add: only setState when width changes by ≥8px (UI-SPEC §3 NotationBody). This also debounces inconsequential reflows.

### Pitfall 4: `staffwidth` and `scale` interact unintuitively
**What goes wrong:** Raising `scale` (A+ via the FAB sheet) without re-measuring overflows because abcjs draws wider notes but staffwidth stays constant — except that's exactly when overflow happens.
**Why it happens:** abcjs `scale` multiplies note glyph sizes; `staffwidth` is the bounding box. abcjs *should* wrap to more rows as scale grows, **but only if the music line content allows wrapping** at the current staffwidth.
**How to avoid:** The hard clamp (`overflow-x: hidden` on outer wrapper) is the safety net. UI-SPEC accepts that at extreme zoom, notes may visually clip — but the page does NOT horizontally scroll. Document this tradeoff.

### Pitfall 5: Sheet stack collisions
**What goes wrong:** FAB sheet open → user taps "Open full study view →" link → navigation happens but sheet doesn't close cleanly → focus trap remains → keyboard nav broken on next page.
**Why it happens:** shadcn/Base UI Sheet keeps focus trap until unmount; route navigation in Next 15 can keep the previous tree mounted briefly.
**How to avoid:** Explicit `setOpen(false)` in the link's `onClick` before `router.push`. Or use `<SheetClose asChild>` wrapper.

### Pitfall 6: Tune switch URL re-renders the whole tree (loses notation scroll position)
**What goes wrong:** `router.replace(?tune=…)` re-runs RSC → page tree re-renders → `<NotationRenderer>` remounts → loses scroll, viewMode, baseSize.
**Why it happens:** Page-level RSC re-render replaces client subtree.
**How to avoid:** Either (a) lift viewMode + baseSize into `<SingingView>` (which IS the client boundary) and let only `abc`/`lyrics`/`tuneName` props change, OR (b) read `?tune=` inside `<SingingView>` via `useSearchParams` and pick the active tune from the prop list client-side. **Recommend (b)** — keeps the route purely static, no re-fetch needed since alt tunes already arrive as props.

### Pitfall 7: `is_recommended` does not exist in schema
**What goes wrong:** UI-SPEC §6 TuneSwitcherSheet wants "Recommended (same meter)" — ordered by `is_recommended` then alphabetical. The column doesn't exist.
**Why it happens:** Schema only has `psalmVersionTunes.isPrimary` (`src/db/schema.ts:210`). `[VERIFIED via grep]`
**How to avoid:** See Open Questions §1. Likely behavior: "Recommended" = all alt tunes returned by `fetchTunesByMeter()` for the active version's meter, minus the current one; "Other" = empty unless we widen the source. The planner must clarify.

## Code Examples

### Example 1: Mobile-default staff size detection

```tsx
// SingingView.tsx
function initialBaseSize(): number {
  if (typeof window === 'undefined') return 14
  // Mobile portrait <768px → 13; desktop/tablet → 14
  return window.innerWidth < 768 ? 13 : 14
}
```

### Example 2: Orientation + visualViewport resize listener

```tsx
// Add inside AbcPlayer.tsx near the existing ResizeObserver
useEffect(() => {
  if (typeof window === 'undefined') return
  let raf = 0
  const debounced = () => {
    cancelAnimationFrame(raf)
    raf = requestAnimationFrame(() => {
      const w = outerRef.current?.clientWidth ?? 0
      if (w > 0 && Math.abs(w - staffWidth) >= 8) setStaffWidth(w)
    })
  }
  window.addEventListener('orientationchange', debounced)
  window.visualViewport?.addEventListener('resize', debounced)
  return () => {
    cancelAnimationFrame(raf)
    window.removeEventListener('orientationchange', debounced)
    window.visualViewport?.removeEventListener('resize', debounced)
  }
}, [staffWidth])
```

// AbcPlayer.tsx line 394 — current:

## Open Questions (RESOLVED)

1. **TuneSwitcherSheet "Recommended" grouping**
   - **RESOLVED:** Adopt option (b) — "Recommended" = tunes editorially linked via `psalmVersionTunes` join; "Other" = meter-matched tunes not in that join. Embodied in Plan 03 (TuneSwitcherSheet section split) and Plan 05 (Task 1 `getEditoriallyLinkedTuneIdsForPsalm` query + `tuneSections` memo).
   - What we know: Schema (`src/db/schema.ts:210`) has `psalmVersionTunes.isPrimary` but no `is_recommended`. `fetchTunesByMeter()` returns all tunes matching meter, no priority.
   - What's unclear: How to split "Recommended" vs "Other" tunes for this psalm. UI-SPEC §6 implies an ordered list within a meter.
   - Recommendation: Either (a) treat all meter-matched alt tunes as one "Recommended" list and drop "Other"; (b) define "Recommended" = tunes already linked via `psalmVersionTunes` join (i.e. editorially attached) and "Other" = tunes-by-meter not in that join; (c) extend schema with `is_recommended` (defer to v2). **Planner: pick (b)** — uses existing data without schema change. UI-SPEC accepts the empty-state copy for §B.

2. **View-mode persistence across tune switches**
   - **RESOLVED:** `<SingingView>` owns `viewMode` + `baseSize` state and reads/writes `psalter-score-mode` + `psalter-staff-size` in localStorage (cross-psalm scope). Plan 02 makes `NotationRenderer` skip its own persistence when controlled (`isViewModeControlled` short-circuits the persistence effect). Plan 05 Task 2 implements the SingingView side.
   - What we know: `NotationRenderer` currently persists `viewMode` in `localStorage` (`STORAGE_MODE_KEY = 'psalter-score-mode'`).
   - What's unclear: When the view is lifted into `<SingingView>` and `NotationRenderer` becomes chromeless, who owns the persistence?
   - Recommendation: Move localStorage read/write into `<SingingView>` (same key — `psalter-score-mode`). Persistence is global (cross-psalm), matching current behavior. Per-psalm memory is explicitly deferred.

   - Recommendation: Add `src/app/psalms/[id]/study/page.tsx` as a thin RSC that performs the same data fetch + renders `<PsalmTabs>`. Reuse the existing `generateStaticParams` shape. `[ASSUMED — planner to confirm]`
