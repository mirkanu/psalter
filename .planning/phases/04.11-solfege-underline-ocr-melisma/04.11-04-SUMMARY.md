## Low-Confidence Threshold Rationale (finalised: 0.85)

The plan's spec called for "0.85" and Test 1 asserts at 0.5 < 0.85 → skip. The threshold is set conservatively because:

1. **Cost of false negative (skip a good tune):** zero regression — D-05 heuristic fallback continues to render that tune. The next Wave A iteration can re-OCR with a higher-context prompt or escalate to Sonnet (per RESEARCH §"Alternatives Considered").
2. **Cost of false positive (write a corrupt w-line):** non-zero — `verify-staff-alignment.js` may flag it but operator sing-test is the human gate. At 0.85, a missed underline propagating to production is a low-probability event.
3. **Empirical adjustment knob:** the constant `LOW_CONFIDENCE_THRESHOLD` is a single export. If Wave A shows the threshold is too strict (e.g. Haiku self-reports 0.80 for visually-clear underlines and we skip an otherwise-correct tune), it's a one-line tweak before Wave B.

## Verified Stanza-1 Syllable Schema Path (for Plan 05/06)

The plan-doc-assumed shape (`ls.cycles[0].stanzas[0].lines[0].syllables`) **does not exist** in this DB. Empirical shape from probe (Crimond, psalm_version_id=35):

```
schema.tunes
  → schema.psalmVersionTunes.tuneId (pvts; sort by psalm_version_id ASC; take [0])
  → schema.psalmVersions.lyricsStructured (Array<{index, lines: [{text, bibleVerseRef?}]}>)
  → [0].lines[0].text
  → syllabifyForAbc(text).split(/\s+/).filter(Boolean)
```

**Fallback:** when `lyricsStructured` is null, fall back to `lyricsImportedRaw`:
```
.split('\n')
.map(l => l.replace(/^\d+/, '').trim())
.find(l => l.length > 0)
→ syllabifyForAbc(...)
```

Probe confirmed Crimond CM first line → 8 syllables: `["The", "Lord's", "my", "she-", "pherd,", "I'll", "not", "want."]`.

**For Plan 05:** the resolver is already implemented in `ocr-melisma-batch.ts:resolveStanza1Syllables`. No re-derivation needed.

## DB Schema Details Discovered (for next plans)

1. **`lyrics_structured` is an Array (not an object with `cycles`).** Each element is `{ index: number, lines: [{ text: string, bibleVerseRef?: number }] }`. Lines do NOT contain pre-computed `syllables` arrays. All syllabification happens at read-time via `syllabifyForAbc` (src/lib/lyrics.ts).

2. **Multiple `psalm_version_tunes` rows per tune are common.** Crimond has 2 (Psalm 23 + Psalm 59); plan defaulted to `pvts[0]` which is the lowest psalm_version_id after our explicit sort. For Wave A this is deterministic. Plan 06's Wave B should similarly pick the lowest psalm_version_id pairing.

3. **4 candidate tunes have no psalm_version_tunes row in this DB:**
   Bangor, Dundee, Trentham, Old 44th, and Tallis Canon (Tallis is missing from `tunes` entirely). Wave B (when iterating the remaining ~138 tunes) will hit similar gaps — `processTune` already handles this via `status='no_syllables'` skip.

4. **Old 124th's `lyrics_imported_raw` is truncated** ("Now Israel" — only 2 words, 3 syllables). The full Psalm 124 text was not imported. This is a separate data-quality issue tracked in `.planning/phases/04.9.6-psalter-alignment-implementation/parse-failures.md` and out of scope for 04.11. The `samples.json` entry sets `minPopulated: 3` to accommodate.

5. **Stracathro is CM in the DB, not SM** as RESEARCH classified it. This may be a Phase 04.9 mis-classification (worth flagging in a follow-up cleanup phase but not blocking).

## Deviations from Plan

### [Rule 3 — Blocking Issue] Stanza-1 syllable schema shape

**Found during:** Task 1.5 probe.
**Issue:** Plan's probe script assumed `ls.cycles[0].stanzas[0].(lines[0]|metricalLines[0]).syllables` shape. The actual DB shape is `Array<{index, lines: [{text}]}>` with no pre-computed syllables.
**Fix:** Probe + resolver adapted to extract `.text` and apply `syllabifyForAbc`. Documented in stanza1-probe.json's `note` field and reused verbatim by Task 2's `resolveStanza1Syllables`.
**Why blocking:** Without this, Task 2's resolver would return null for every tune → entire Wave A no-op.
**Commit:** 5412df4

### [Rule 3 — Blocking Issue] OcrFn does not expose usage/model

**Found during:** Task 2 implementation.
**Issue:** Plan requires `logTokenUsage(slug, ocrResult.usage, ocrResult.model)` after each Vision call, but `ocrMelismaV3` (Plan 03 output) and underlying `callClaude` (Plan 03 reused from v2) do NOT expose the SDK's `response.usage` or `response.model`.
**Fix:** Made `usage` and `model` OPTIONAL on the `OcrFn` contract. Production logs nothing today; tests inject mocks that DO supply usage (Test 7 asserts the round-trip works). When Plan 03 is extended to surface usage (future follow-up), no change to ocr-melisma-batch needed.
**Files:** scripts/ocr-melisma-batch.ts (OcrFn type signature).
**Commit:** a9c152d
**Action for Plan 06:** Wave B cost projection from `wave-a-token-usage.json` will see ZERO rows for the Wave A apply (since usage isn't logged in production today). Plan 06 should either (a) re-derive cost from a one-tune ad-hoc Vision call after adding usage capture to v3, or (b) use Haiku's published per-MTok rates × estimated input size from JPG file bytes. Recommend (a).

### [Sample list adjustment — D-02 substitutions]
