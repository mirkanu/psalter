## Prompt Design Decisions

The `TRANSCRIPTION_PROMPT_V3` constant codifies four directives that the plan's binding research docs (`lyric-to-note-alignment.md` §3, `tonic-solfa-notation.md` "Other Symbols") require:

1. **PRESERVE every underline** — the underline beneath a note letter is the canonical melisma-continuation marker (`lyric-to-note-alignment.md` §3). The model is told to mark EVERY underlined note (not just the first of a span) with `"underlined": true`.

2. **Distinguish the underline from three visual lookalikes** (CLAUDE.md hard rule #1 + tonic-solfa "Other Symbols"):
   - **Dot subdivision** (`f.,r`) BETWEEN notes — rhythm subdivision, NOT melisma.
   - **Em-dash** (`—`) BETWEEN notes — sustained hold, NOT melisma.
   - **Subscript digit** (`d₁`) BELOW a letter — lower-octave indicator, NOT melisma.

   These are spelled out as separate bullets so the prompt's failure modes are isolated for the Wave A sing-test review.

3. **Per-token `conf` 0.0–1.0** — model self-reports confidence for the `(tok, underlined)` pair. Plan 04 will use this for low-confidence gating (skip-tune-if-any-token-below-threshold).

4. **JSON-only response** — `"Do not include any prose outside the JSON object."` Matches v2's `extractMelismaJson` (regex `/\{[\s\S]*\}/`) which is intolerant of leading/trailing prose anyway, but explicit instruction reduces parse failures.

The prompt deliberately uses the term **"underlined"** (visual descriptor) rather than **"passing"** (which has two unrelated meanings — CLAUDE.md hard rule #2). This avoids the harmonic/pedagogical conflation that has caused three prior failed melisma fixes (per memory `melisma-analysis-handoff`).

## MelismaTranscriptionResult Schema

```typescript
export interface MelismaTokenEntry {
  tok: string         // "m", "d'", "s_1", "te", ...
  dur: number         // 1=quarter, 2=half, 4=whole, 0.5=eighth
  underlined: boolean
  conf: number        // 0.0–1.0; defaults to 0 when missing
}

export interface MelismaTranscriptionResult {
  doh: string
  time: string
  soprano: MelismaTokenEntry[]
  alto?: MelismaTokenEntry[]
  tenor?: MelismaTokenEntry[]
  bass?: MelismaTokenEntry[]
  raw: string         // unmodified model response for audit
}
```

## Deviations from RESEARCH §Pattern 1 Sketch

1. **`mode` / `lah` fields omitted from MelismaTranscriptionResult.** Pattern 1 sketch did not specify minor-mode handling, and Plan 02's `buildEmbeddedWline` only consumes the per-voice arrays. The v2 module retains `mode` / `lah` for the heuristic fallback path (D-05); v3 callers needing key-mode info can read it from v2's `transcribeOnly` separately if/when that requirement surfaces in Plan 04. **Impact:** none for this plan's scope; flagged here so Plan 04 can revisit if minor-key tunes surface in Wave A.

2. **Two normalisation passes folded into one.** Pattern 1 sketch implied a two-step extract → normalise pipeline. Implementation collapses these into `extractMelismaJson`'s single `normaliseVoice` mapper for simplicity. Same observable behaviour; smaller surface area.

3. **`bass` / `alto` / `tenor` typed as optional in `MelismaTokenEntry[] | undefined`.** Pattern 1 implied all four voices always present. Real psalter pages occasionally have soprano-only segments (e.g. amen tags); optional typing avoids forcing the Plan 04 batch driver to insert empty arrays.
