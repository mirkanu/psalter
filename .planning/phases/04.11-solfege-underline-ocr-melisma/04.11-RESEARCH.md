## Summary

Phase 04.10 proved (negatively) that regenerating ABCs from MusicXML is the wrong direction: it threw out known-good pitches/rhythms to introduce a single missing dimension — melisma markers. Phase 04.10 also proved (positively) that the runtime path for canonical `w:` lines — `abc-embedded-lyrics.ts` + `abc-embedded-w-branch.ts` + the NotationRenderer additive branch — works correctly and is source-agnostic. **04.11 only needs to PRODUCE the `w:` lines.** All rendering plumbing exists.

The source of canonical melisma data is the original solfège JPG scans (the underline beneath a note IS the melisma marker — `lyric-to-note-alignment.md` §3). The current `ocr-solfege-v2.ts` prompt explicitly tells Claude Vision to *ignore* underlines (line 70 of that file). Rewriting the prompt to preserve them, then deriving `_` continuation tokens from preserved underline positions, is the entire technical core of this phase.

**Primary recommendation:** Build a **two-stage pipeline** that mirrors the existing v2 architecture: (1) Vision returns a structured JSON that includes per-token `underline` and `confidence` flags alongside the existing solfège text; (2) a deterministic TS function maps `(solfège tokens + underline flags + stanza-1 syllables)` → an ABC body with embedded `w:` lines containing `_` continuation tokens at exactly the slur-stop positions. Run Wave A (~12 tunes) for cost-bounded sing-test, then Wave B (~132 tunes) for population sweep.

### Pattern 1: Vision prompt — structured per-token underline JSON

**What:** Prompt the model to return JSON whose voice strings are accompanied by per-token underline + confidence flags, rather than embedding `_` suffixes into a single string.

**When to use:** All Wave A and Wave B OCR calls.

**Why structured (not string-suffix):** A string like `m f_ r_ d` cannot carry per-token confidence. We need confidence to gate D-05 fallback (low confidence → omit tune, heuristic continues). Structured JSON also makes downstream `build-embedded-wline.ts` unit-testable on fixtures.

**Recommended output shape** (sketch — finalise during Plan):
```json
{
  "doh": "F",
  "time": "3",
  "soprano": [
    { "tok": "c",   "dur": 2, "syll": "The",     "underlined": false, "conf": 0.98 },
    { "tok": "a",   "dur": 4, "syll": "Lord's",  "underlined": false, "conf": 0.97 },
    { "tok": "b",   "dur": 3, "syll": "my",      "underlined": false, "conf": 0.95 },
    { "tok": "g",   "dur": 1, "syll": null,      "underlined": true,  "conf": 0.93 },
    { "tok": "c'",  "dur": 2, "syll": "shep",    "underlined": false, "conf": 0.97 },
    { "tok": "b",   "dur": 3, "syll": "herd,",   "underlined": false, "conf": 0.96 },
    { "tok": "g",   "dur": 1, "syll": null,      "underlined": true,  "conf": 0.92 }
    /* ... */
  ],
  "alto": [ /* same shape */ ],
  /* ... */
}
```

**Source citation in prompt:** Include explicit instruction text derived from `lyric-to-note-alignment.md` §3 and `tonic-solfa-notation.md` "Other Symbols → Underline". Tell the model: "The underline beneath a note in solfège print is the canonical melisma-continuation marker — it indicates the note is sung as a continuation of the previous syllable's vowel. PRESERVE every underline. Do NOT confuse this with the dot subdivision `.` (rhythm) or the hold symbol `—` (sustained note)."

**Prompt anti-instruction to remove:** Current `ocr-solfege-v2.ts:70` says *"Underlined notes: passing notes — transcribe the letters, ignore the underline."* This sentence is the bug. The new prompt must contain the opposite directive.

### Pattern 2: Slur-walk algorithm — underline → `_` token

**What:** Walk the soprano token array left-to-right. For each token, if it has a syllable, emit the syllable into `w:`; if it is underlined (and previous token had a syllable or was itself underlined), emit `_`. This is the solfège-side restatement of `lyric-to-note-alignment.md` §6.

**Plain English:**
```
syllableIdx = 0
for token in soprano:
  if token.underlined:
    emit "_"
  else:
    emit syllables[syllableIdx]
    syllableIdx++
```

**Validation invariant** (must hold before DB write):
- `count(non-underlined tokens) === len(syllables)` for the stanza
- `count(syllables) === expected_for_meter(tune.meter)` (CM = 8+6+8+6 = 28; LM = 8×4 = 32; etc.)
- For each phrase, `countNoteHeads(phraseBody) === wTokenCount(phraseBody)`

If any invariant fails → log to per-tune review JSON, skip DB write, fall back to heuristic.

[CITED: `.planning/research/lyric-to-note-alignment.md` §6 algorithm]

### Pattern 4: PHRASE_BREAK preservation

The existing `abc_notation` already contains `% PHRASE_BREAK` markers (set by `scripts/annotate-phrase-breaks.ts`). 04.11 must **preserve** these — the new `w:` line is INTERPOLATED inside each existing phrase body, not by regenerating the music. Strategy:

1. Read existing `abc_notation` from DB.
2. `splitOnPhraseBreaks()` (from `src/lib/abc-phrases.ts`) → array of phrase bodies + the PHRASE_BREAK separators.
3. For each phrase body: compute the matching w-line slice from the OCR output (by note-head count).
4. Inject `w: ...` line at the end of each phrase body.
5. Rejoin with PHRASE_BREAK separators preserved verbatim.

**Critical invariant:** `countNoteHeads(phraseBody)` must equal `wTokenCount(injected_w_line)` for the phrase to render correctly (see Pitfall 4 in 04.10 patterns and `melisma-analysis-handoff` memory: dual-system drift = bug). With D-01 there is only ONE source of truth (the embedded `w:` line); PHRASE_BREAK becomes purely a visual stanza separator. **Verify this single-source-of-truth invariant explicitly in the validation step.**

[CITED: `src/lib/abc-phrases.ts` `splitOnPhraseBreaks` + `countNoteHeads`]

### Anti-Patterns to Avoid

- **Regenerating the entire ABC from solfège.** Phase 04.9's text-only OCR re-derived ABC from solfège and exposed octave-parser bugs (e.g. Glasgow dotted-comma — fixed in q06). The notes in `tunes.abc_notation` are now stable; 04.11 must touch only the `w:` line, not the music body. The notes were correct in 04.10's pre-pilot Crimond — the lesson stands.
- **Building any per-tune logic into NotationRenderer.** Renderer is generic — it consumes whatever `w:` line is in the ABC. Resist the urge to add "if tuneName === ... " branches.
- **Storing melisma data anywhere other than `abc_notation`.** D-01 explicitly forbids this. Any "intermediate" or "draft" column will re-introduce dual-system drift.
- **Skipping the per-tune validation invariant before DB write.** Even with Vision returning structured data, an off-by-one underline marker can produce a w-line of the wrong length. The `countNoteHeads === wTokenCount` check must run before every UPDATE.
- **Trusting `PHRASE_BREAK` positions blindly.** If Vision's underline detection moves a melisma across a PHRASE_BREAK boundary that was set by the dot-pair heuristic, the phrase note-counts will desync. Validation must flag this; the user can re-run `annotate-phrase-breaks.ts` post-hoc if surface bugs appear (DEFERRED per CONTEXT.md).

## Common Pitfalls

### Pitfall 1: Vision conflates underline with hold (`—`) or subscript (`_1`)

**What goes wrong:** Solfège notation has THREE distinct visual marks that all involve horizontal/vertical lines near a note: (a) underline beneath the note (melisma continuation), (b) em-dash `—` between notes (hold/sustain), (c) subscript `₁` below the letter (lower octave). Vision may merge or miscategorise them.
**Why it happens:** Faint print, low DPI on old scans, the marks overlap visually in some fonts.
**How to avoid:** Prompt must explicitly enumerate the distinction (cite `tonic-solfa-notation.md` "Other Symbols" verbatim into the prompt). Return per-token confidence. Below threshold → omit tune.
**Warning signs:** Wave A sing-test catches a wrong-vowel sustain or an octave shift; review JSON shows the offending token's confidence is < 0.85.

### Pitfall 2: Underline spans adjacent syllable, not adjacent note

**What goes wrong:** In some printed pages an underline visually extends under what looks like 2 notes but is really 1 note with a `.r` subdivision (the second token is a separate syllable in the next beat, not a melisma continuation).
**Why it happens:** Tight engraving + dot-pair rhythm subdivisions look like beamed pairs.
**How to avoid:** Per-token semantics. The model receives the prompt instruction: *"Underline marks apply per-NOTE-TOKEN, not per-visual-span. A note token is the letter (`d`, `r`, `m`, etc., with octave subscript/apostrophe), excluding the rhythm `.` separator."*
**Warning signs:** Validation invariant `countNoteHeads === wTokenCount` fails for the phrase; or the wrong syllable underflow/overflow appears in `verify-staff-alignment.js` trailing-empty count.

### Pitfall 3: Joined underlines under 3+ notes

**What goes wrong:** A melisma over 3 notes shows as a single long underline. Vision might split it into 2 short ones or merge it into a held-note interpretation.
**Why it happens:** Most CM tunes have 2-note melismas (the dot-pair pattern); 3+ note melismas are rare but exist (Old 100th phrase 4 has 24 notes for 8 syllables — `scottish-psalter-structure.md` §"Melismas").
**How to avoid:** Prompt explicitly mentions: *"An underline may span 2, 3, or more consecutive notes. Mark EVERY underlined note (not just the first) as `underlined: true`."*
**Warning signs:** Old 100th — particularly phrase 4 — fails Wave A sing-test. Already a known case in `staff-alignment-report.json` (psalm 100 fails with `noteCount: 24, notesWithLyric: 8, trailingEmpty: 14`).

### Pitfall 4: PHRASE_BREAK position desync after embedded `w:` line is added

**What goes wrong:** `% PHRASE_BREAK` markers in current ABCs were placed by `annotate-phrase-breaks.ts` using dot-pair-heuristic note counts. If the canonical underline data places a melisma differently than the heuristic assumed, a PHRASE_BREAK may fall mid-melisma — splitting a slur across phrases.
**Why it happens:** Two systems (PHRASE_BREAK from heuristic, `w:` from OCR) disagree on note grouping. This is the exact failure mode documented in `melisma-analysis-handoff` memory.
**How to avoid:** D-01 makes the embedded `w:` line the SINGLE source of truth for syllable→note mapping. With the new path, PHRASE_BREAK is purely visual (stanza-row separator) and the `w:` line carries melisma semantics. Validation invariant: each phrase body's note-head count equals its w-line's token count (including `_`s). If a phrase doesn't validate, skip the tune (heuristic fallback applies).
**Warning signs:** Validation fails for a tune; `verify-staff-alignment.js` reports trailing-empty notes on an embedded-w tune (should be zero — they're authored).

**Single-source-of-truth assertion (mandatory in plan):** Add a unit test that takes a Crimond-shaped fixture, runs the full pipeline, and asserts:
1. For each phrase: `countNoteHeads(body) === wTokenCount(body)`
2. There exists NO branch in `build-embedded-wline.ts` that consults PHRASE_BREAK position to decide melisma placement.
3. The output is byte-identical regardless of where PHRASE_BREAKs are positioned (move them around → output unchanged).

### Pitfall 5: Wave A sing-test reveals wrong-direction; Wave B fires anyway

**What goes wrong:** Without an explicit gate, a Wave B run could fire while Wave A failures are still under investigation, multiplying the rollback surface from 12 rows to 150.
**Why it happens:** Two scripts, two run commands — easy to invoke Wave B by habit.
**How to avoid:** Plan must require an explicit `--wave-a-passed` flag (or a manual git-tag check) on the Wave B script. The script reads the flag and refuses to run otherwise. Document in `rollback-recipe.md`.
**Warning signs:** User reports a sing-test failure in Wave A but `git log` already shows a Wave B commit.

### Pitfall 6: Verify-staff-alignment tolerance hides real failures

**What goes wrong:** `verify-staff-alignment.js` has `TOLERANCE=1` (env-overridable). A tune with 1 trailing-empty note passes; but in the new canonical-w path, ZERO trailing-empty notes is the correct outcome (every note has a syllable or a `_`).
**Why it happens:** Heuristic-era tolerance accommodated melisma compensation gaps.
**How to avoid:** For Wave A and Wave B, run `verify-staff-alignment.js` with `TOLERANCE=0`. Add this to the runbook in `rollback-recipe.md`.
**Warning signs:** All 150 pass with TOLERANCE=1 but multiple fail with TOLERANCE=0 → reveals tunes where Vision dropped an underline.

### Pitfall 7: Multi-stanza rendering — cycle > 0 falls back to heuristic

**What goes wrong:** 04.10's `renderEmbeddedWPhrase` returns `needsHeuristicFallback[i] = (i > 0)`. Cycle 0 uses authored `w:`; cycles 1+ use heuristic. If stanza 2 has different elision (`I'll` vs `I will`), heuristic may mis-syllabify and the stanza will look misaligned compared to stanza 1.
**Why it happens:** O-2 option A from 04.10 — only stanza 1 syllables are authored; later stanzas fall back.
**How to avoid:** Sing-test must include at least one multi-stanza traversal (Crimond Psalm 23 has 6 stanzas; Wave A should test stanza 2+ rendering at least once).
**Warning signs:** Stanza 1 sings perfectly; stanza 2 shows misalignment.
