<decisions>
## Implementation Decisions

### Storage / Output Format
- **D-01:** Melisma data is baked into each tune's `abc_notation` column as `_` continuation tokens inside the `w:` line. Single canonical string per tune. No new column, no merge-at-render-time layer.
  - **Why:** Matches the runtime path proved in 04.10. Avoids the two-system drift bugs documented in `melisma-analysis-handoff` memory (System 1 / System 2 disagreement on note-head counts caused every prior failed fix).
  - **Implication:** Rollback is a single-column UPDATE. Diffs are human-readable and code-reviewable.

### Verification Gate / Sampling
- **D-02:** Sing-test ~10–12 tunes total — for each meter family (CM, LM, SM, CMD, alt meters), pick **1 hardest** (most dot-pairs / awkward syllable counts / known historical failures) + **1 most-used** (Crimond, Martyrdom, etc.).
- **D-03:** Two-layer pass bar:
  1. **Human (sing-test):** every sampled tune sings correctly against the iOS Scottish Psalter reference — zero defects.
  2. **Machine:** `scripts/uat/verify-staff-alignment.js` reports 150/150 passing for the un-sampled population.
  - **Why:** Full 150-tune sing-test isn't feasible. Sampling covers worst case + most-impact; machine sweep catches population regressions.

### Migration Path / Rollout
- **D-04:** Two-wave rollout, with Vision-cost bounded by Wave A go/no-go:
  - **Wave A:** OCR ONLY the ~12 sampled tunes. Push to production. User sing-tests **on production** (this user's actual workflow). If any fail, root-cause and re-sample — do NOT proceed to Wave B.
  - **Wave B:** Once Wave A passes, OCR the remaining ~138 tunes in a single batch, run `verify-staff-alignment.js` (free) for the 150/150 gate, then a single production UPDATE with documented rollback recipe.
  - **Why (user constraint):** "if Claude Vision (costly) or anything else that's computing/time expensive is involved, it should only be executed on a dozen psalms/tunes at most. These should be pushed to production for me to sing-test there."
  - **Implication:** Plan must produce a rollback recipe BEFORE the Wave B UPDATE (snapshot of pre-phase `abc_notation` for all 150 rows).

### Heuristic Retirement
- **D-05:** Keep the heuristic path (`getPassingPositions`, dot-pair detection, `padWLineToNoteCount`, `abc-melisma.ts`) as fallback for un-OCR'd tunes. Do NOT delete in this phase.
  - **Why:** NotationRenderer's embedded-w-branch already auto-selects between embedded `w:` lines and the heuristic path. Tunes that fail OCR (missing/low-quality JPG, ambiguous underlines beyond Vision's confidence) stay heuristic transparently. No code-deletion needed; just don't write a `w:` line for failures.
  - **Implication:** "Tune failed OCR" = no DB write for that tune = heuristic continues to render it. Zero regression risk for tunes the OCR can't read cleanly.

### Cleanup of 04.10 Wrong-Direction Artifacts
- **D-06:** In this phase, also:
  - Delete `scripts/convert-crimond-musicxml.ts` and its test
  - Delete `.planning/research/abc-samples/crimond-verified.abc`
  - Replace the per-tune MusicXML migration recipe in `.planning/research/tune-digitisation-research.md` with the new underline-OCR recipe (the old one is "actively misleading" per 04.10-FINDINGS.md)
  - Keep `.planning/research/abc-samples/Crimond_deBoer.musicxml` as reference-only (not canonical)
  - **Why:** 04.10-FINDINGS.md flagged these as wrong-direction; 04.11 is the cleanup window.

### Claude's Discretion (user skipped this area)
- **OCR prompt design:** Vision prompt to be rewritten to (a) emit per-syllable melisma flags ("does this syllable extend an underline over the next note?"), (b) preserve existing solfège-text fidelity (dot subdivisions, octave subscripts, etc. — current parser already handles these correctly per `project_ocr_pipeline` memory).
- **Ambiguity handling:** if Vision is uncertain (faint print, joined-vs-separate underline under adjacent syllables, scan artifact), emit a per-syllable confidence flag. Below threshold → omit the tune from the batch (heuristic fallback applies). Above threshold but low → log to a per-phase review doc for the user to spot-check during Wave A.
- **Missing / low-quality JPGs:** tune is skipped, no DB write, heuristic fallback applies — no special handling required.
- **Tokenisation:** continue using the abc-embedded-lyrics helpers from 04.10; do not introduce a new representation.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets (do not rebuild)
- **abc-embedded-lyrics + abc-embedded-w-branch + NotationRenderer w-branch** — 04.10 already proved these render any ABC with embedded `w:` lines correctly. This phase only needs to PRODUCE such ABCs.
- **`ocr-solfege-v2.ts` retry/backoff logic** — handles 529 overloaded errors with 4-retry exponential backoff. Reuse for Wave A and Wave B batch jobs.
- **`solfege-parser.ts`** — already handles dot subdivisions, `_1` octave subscripts, flats, SATB multi-voice. Underline parsing is the new piece.
- **`verify-staff-alignment.js`** — the 150/150 machine gate is already wired up; no new tooling needed.

### Established Patterns
- **`% PHRASE_BREAK` placement in ABC** — set by `scripts/annotate-phrase-breaks.ts`. The two-system drift problem (System 1 PHRASE_BREAK position vs System 2 w-line builder) goes AWAY when D-01 ships: there's only one source of truth (the embedded w-line), and PHRASE_BREAK becomes purely a visual stanza-marker, not a melisma-gating mechanism.
- **PM2 deploy, not Docker for Next.js** — `npm run build && pm2 restart psalter`. Postgres runs as Docker. Wave A / Wave B production pushes follow this pattern.

### Integration Points
- **`tunes.abc_notation` column** — the single write surface. No schema changes.
- **DB rollback snapshot** — must be captured BEFORE Wave A (not Wave B) so any sing-test failure in either wave can roll back cleanly.
