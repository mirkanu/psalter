# Plan 15.2-03: Final verdict on POLISH-03

## Goal

Close Phase 15.2 with an accurate written record: what the scores actually are (median-of-5, not
single-run), what the three phases of optimisation bought, what the remaining ceiling is and why,
and a decision from the user about whether to keep going.

Marked `autonomous: false` because it ends in a genuine user decision with real cost on either
side. See Task 4.

## Background — the record currently needs correcting, not just updating

This is not a routine "mark the requirement done" plan. Three separate documents in
`.planning/` currently assert things the evidence contradicts:

1. **`REQUIREMENTS.md` line 67** attributes the `/` score drop to "a Turbopack chunk re-shuffle
   triggered by next.config.ts `qualities` array change."
2. **`ROADMAP.md` line 31** repeats it, and **line 32** scopes Phase 15.2 around "revert
   next.config.ts `qualities: [75,90]` to `[75]` (which alone recovered `/psalms` to 0.71...)".
3. **`15.2-VERIFICATION.md`** states the `qualities` revert "confirms `qualities` array addition
   was the regression trigger."

`.planning/phases/15.2-lighthouse-final-tbt-reduction/15.2-measurement-noise-evidence.md` disproves
this: the two Lighthouse JSONs behind the claim have **identical framework chunk hashes and a
28-byte total script payload difference** — incompatible with a re-chunk — while the 0.47 run
recorded a `benchmarkIndex` of 477.5 (2.2× slower CPU than the run it was compared against), a
376 ms server response time, and a 654 ms network RTT. And a zero-code-change control found a ±6
point spread, which is larger than most of the deltas these phases treated as signal.

Leaving those claims in place would mislead whoever picks this up next. Correcting them is the
main deliverable of this plan.

## Realistic ceiling

This plan changes no application code and moves no score. Its output is an accurate record.

Expected final state: **`/` ≈ 0.63–0.70, `/psalms` ≈ 0.63–0.70, `/psalms/23` ≈ 0.65–0.70**, each
±3, versus the 0.90 target. POLISH-03 stays open unless the user picks Option A and elects to
close it as consciously deferred.

**The user asked: "if we can significantly improve performance, let's do it."** The honest answer
this phase produces is that the largest single thing standing between this app and 0.90 was never
in the application code — it is React 19 + Next 16's client runtime on a mobile-throttled cold
load, plus a measurement instrument too noisy to tell progress from jitter. Phase 15.2 fixes the
instrument and takes the one remaining all-routes lever. What is left after that is a
server-component refactor, which is a real option with a real price, and that is the user's call
to make rather than Claude's.
