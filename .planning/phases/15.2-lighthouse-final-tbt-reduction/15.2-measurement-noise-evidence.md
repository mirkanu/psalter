The machine was thrashing, not the bundle.

## Direct disproof of the Turbopack re-chunk hypothesis

The claim was that `images.qualities: [75, 90]` triggered a Turbopack chunk re-shuffle that
exploded `Parse HTML & CSS` from 108 ms → 2972 ms.

From the two Lighthouse JSONs' own `network-requests` audits:

| | Phase 15 baseline (0.69) | Phase 15.1 (0.47) |
|---|---|---|
| Script bytes (20 requests) | 273,182 | 273,210 |
| Stylesheet bytes | 21,235 | 21,235 |
| Font bytes | 39,759 | 39,759 |
| Document resourceSize | 46,453 | 46,422 |
| Framework chunk name | `0r5n9xaeyh.pb.js` | `0r5n9xaeyh.pb.js` |

**The chunk hashes are identical and total script payload differs by 28 bytes.** A Turbopack
re-chunk would change chunk hashes and shift bytes between chunks. Neither happened. The
`qualities` array does not affect the JS graph at all — it only validates the `q=` query
parameter accepted by the `/_next/image` optimizer route.

`Parse HTML & CSS` measured 108 / 139 / 153 / 198 / 293 ms across all other runs and 2972 ms in
that single thrashing run. Under `simulate` throttling that bucket absorbs network-blocked time,
which is exactly what a 654 ms RTT produces.

**Conclusion: there was no regression to revert. `qualities: [75]` is fine to keep (it silences a
Next.js 16 warning and is required for any non-default `quality` prop), but it buys 0 points.**

## What is actually real and measurable

1. **`0r5n9xaeyh.pb.js` — 71,235 bytes transferred, 910–1134 ms scripting, 25,058 bytes unused.**
   This is the React 19 + Next.js 16 framework runtime. Present on every route. Real, and the
   single largest scripting contributor. Not splittable from application code — it *is* the
   framework. `next/dynamic` on app components cannot shrink it.
2. **`SiteHeader` is a `'use client'` component in the root layout, so it hydrates on every
   route.** It eagerly imports `GlobalSearch` (181 LoC + Dialog) and `FeedbackModal` (107 LoC +
   Dialog/Input/Label/Textarea/Checkbox), both of which render only behind `open` state, plus
   `authClient.useSession()` which fires a blocking `/api/auth/get-session` XHR on every page
   load for every anonymous visitor. **This is the one genuinely untouched all-routes lever.**
3. **LCP on `/` is 4.1–4.5 s simulated** (observed LCP is 2292 ms). LCP carries 25% of the mobile
   Performance score — a larger single lever than TBT's 30% at current values, and completely
   unaddressed so far.

## Hard constraint this places on Phase 15.2

**Any A/B comparison of fewer than 5 runs per route on this VPS is uninterpretable.** A ±6 point
swing is the noise floor. Single-run before/after comparisons — the methodology used in Phases 15,
15.1, and the 15.2 round-2 test — cannot detect anything smaller than a ~10 point change, and have
already produced two false conclusions (the PerformanceObserver "1.0/1.0/0.91" in Phase 15, and
the "`qualities` regression" in Phase 15.1/15.2).

Phase 15.2 must fix the measurement before trusting any optimisation verdict.
