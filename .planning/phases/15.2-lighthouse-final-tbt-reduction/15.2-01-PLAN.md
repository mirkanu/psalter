# Plan 15.2-01: Trustworthy Lighthouse harness + settle the `qualities` question

## Goal

After this plan, the repo has a committed benchmark script that runs Lighthouse **5 times per
route and reports the median plus the spread**, and we have a recorded median-of-5 baseline for
all three routes on the current code. Every subsequent plan in this phase measures against that
baseline with the same script.

This plan exists because **the measurement is currently broken**, and every optimisation verdict
in Phases 15 and 15.1 was drawn from single runs that cannot support the conclusions they were
used for.

## Background — read this before touching anything

`.planning/phases/15.2-lighthouse-final-tbt-reduction/15.2-measurement-noise-evidence.md` records a
control experiment run by the planner: **three Lighthouse runs on `/` with zero code change scored
0.61 / 0.64 / 0.64, with TBT ranging 611–1311 ms. Two runs on `/psalms` with zero code change
scored 0.60 and 0.66.**

The noise floor on this VPS is ±6 points. Every A/B result this phase inherits was a single run
per arm, so none of them are interpretable.

**The specific claim this plan retires:** Phase 15.1/15.2 concluded that adding
`images.qualities: [75, 90]` to `next.config.ts` triggered a Turbopack chunk re-shuffle that
exploded `Parse HTML & CSS` from 108 ms to 2972 ms on `/`, costing ~22 points. The evidence
disproves this:

- The two Lighthouse JSONs in question report **identical framework chunk hashes**
  (`0r5n9xaeyh.pb.js` in both) and total script payloads differing by **28 bytes**
  (273,182 vs 273,210). A re-chunk changes hashes and moves bytes. Neither happened.
- The 0.47 run recorded `benchmarkIndex: 477.5` (vs 1073 on the 0.69 run — a 2.2× slower CPU),
  `server-response-time: 376 ms` (vs 64 ms), and `network-rtt: 654 ms` (vs 38 ms). The machine
  was thrashing.
- `images.qualities` does not participate in the JS module graph. It is a validation allowlist
  for the `q=` parameter on the `/_next/image` optimizer route.

So there is **no regression to revert**. The brief for this phase asked for a "revert the
qualities change" plan as a cheap win; that win does not exist and this plan says so with
evidence rather than spending a commit pretending otherwise.

What we *do* need to settle is which `qualities`/`quality` combination the code should ship,
because the working tree currently has **uncommitted drift** that must be resolved either way.

The committed `HEAD` version of `SiteHeader.tsx` has `width={140} height={28} sizes="28px"` and
**no** `quality` prop. The working tree has the larger intrinsic size and `quality={100}`.

This matters: `quality={100}` with `qualities: [75]` is an **inconsistent pair**. Next.js 16
requires any `quality` prop value to be listed in `images.qualities`. The live server currently
serves `q=75` in its srcset (confirmed by `curl`), which means the `quality={100}` prop is being
silently ignored or clamped. Leaving this mismatch in place is a latent build-time error.

```js
#!/usr/bin/env node
// Phase 15.2: median-of-N Lighthouse harness.
//
// Single Lighthouse runs on this VPS have a ±6 point spread with zero code
// change (see .planning/phases/15.2-.../15.2-measurement-noise-evidence.md).
// Any A/B verdict drawn from one run per arm is noise. This script runs each
// route N times sequentially and reports the median plus the observed spread,
// so a reviewer can tell a real change from jitter.
//
// Usage: node scripts/lighthouse-bench.mjs [--runs 5] [--out path.json]

import { execFileSync } from 'node:child_process'
import { readFileSync, writeFileSync, mkdtempSync, rmSync } from 'node:fs'
import { tmpdir } from 'node:os'
import { join } from 'node:path'

const CHROME_PATH =
  process.env.CHROME_PATH ||
  '/home/claude/.cache/ms-playwright/chromium-1217/chrome-linux/chrome'

const ROUTES = [
  ['homepage', 'http://localhost:3005/'],
  ['psalms', 'http://localhost:3005/psalms'],
  ['psalm-detail', 'http://localhost:3005/psalms/23'],
]

const args = process.argv.slice(2)
const runs = Number(args[args.indexOf('--runs') + 1]) || 5
const outIdx = args.indexOf('--out')
const outPath = outIdx === -1 ? null : args[outIdx + 1]

const median = (xs) => {
  const s = [...xs].sort((a, b) => a - b)
  const m = Math.floor(s.length / 2)
  return s.length % 2 ? s[m] : (s[m - 1] + s[m]) / 2
}

const workDir = mkdtempSync(join(tmpdir(), 'lh-bench-'))
const results = {}

for (const [label, url] of ROUTES) {
  const samples = []
  for (let i = 0; i < runs; i++) {
    const jsonPath = join(workDir, `${label}-${i}.json`)
    execFileSync(
      'npx',
      [
        '--yes', 'lighthouse', url,
        '--output=json', `--output-path=${jsonPath}`,
        '--chrome-flags=--headless=new --no-sandbox --disable-dev-shm-usage --disable-gpu',
        '--only-categories=performance', '--quiet',
      ],
      { env: { ...process.env, CHROME_PATH }, stdio: ['ignore', 'ignore', 'ignore'] },
    )
    const d = JSON.parse(readFileSync(jsonPath, 'utf8'))
    const a = d.audits
    samples.push({
      perf: d.categories.performance.score,
      benchmarkIndex: d.environment?.benchmarkIndex ?? null,
      tbt: a['total-blocking-time'].numericValue,
      fcp: a['first-contentful-paint'].numericValue,
      lcp: a['largest-contentful-paint'].numericValue,
      cls: a['cumulative-layout-shift'].numericValue,
      si: a['speed-index'].numericValue,
    })
    rmSync(jsonPath, { force: true })
    console.log(
      `  ${label} run ${i + 1}/${runs}: perf ${samples[i].perf} ` +
        `(bench ${Math.round(samples[i].benchmarkIndex)}, TBT ${Math.round(samples[i].tbt)}ms)`,
    )
  }
  const perfs = samples.map((s) => s.perf)
  results[label] = {
    url,
    runs,
    perf: { median: median(perfs), min: Math.min(...perfs), max: Math.max(...perfs) },
    tbt_median: Math.round(median(samples.map((s) => s.tbt))),
    fcp_median: Math.round(median(samples.map((s) => s.fcp))),
    lcp_median: Math.round(median(samples.map((s) => s.lcp))),
    cls_median: median(samples.map((s) => s.cls)),
    benchmarkIndex_median: Math.round(median(samples.map((s) => s.benchmarkIndex))),
    samples,
  }
  const r = results[label]
  console.log(
    `${label}: median ${r.perf.median} (spread ${r.perf.min}-${r.perf.max}), ` +
      `TBT ${r.tbt_median}ms, LCP ${r.lcp_median}ms\n`,
  )
}

rmSync(workDir, { recursive: true, force: true })
const payload = { capturedAt: new Date().toISOString(), chromePath: CHROME_PATH, results }
if (outPath) {
  writeFileSync(outPath, JSON.stringify(payload, null, 2))
  console.log(`Wrote ${outPath}`)
}
```

Required constraints:
- Runs MUST be sequential. Do not add concurrency — two chromes will OOM this box.
- Each chrome is ephemeral (one `npx lighthouse` invocation, process exits, memory returns).
- Do NOT use the `playwright-daemon` here. The daemon holds a long-lived pre-warmed Chromium for
  Playwright scripting; Lighthouse needs its own clean profile per run with throttling applied.
  Ephemeral chrome via the Lighthouse CLI is the correct tool and is what Phase 15.1 proved works.
- Per-run JSONs are written to a temp dir and deleted; only the summary is kept. The three
  Phase 15.1 JSONs total 1.5 MB in git — do not repeat that.
- The script MUST print each run's score as it goes so a watching human sees the spread live.

## Realistic ceiling

**Expected score change from this plan: zero.** This plan buys no points and does not pretend to.

What it buys is the ability to tell whether the *next* plan bought any. Without a median-of-5
harness, a 5-point real improvement is indistinguishable from the ±6 point noise floor, and this
project has already shipped two false conclusions from single-run comparisons (Phase 15's
PerformanceObserver "1.0 / 1.0 / 0.91", and Phase 15.1's "`qualities` caused a 22-point
regression").

Post-plan expected medians, unchanged from today: **`/` ≈ 0.63, `/psalms` ≈ 0.63,
`/psalms/23` ≈ 0.65**, each ±3.

The brief for this phase asked for this plan to be "the cheap win — revert logo qualities, very
high confidence." That framing rested on the `qualities` regression being real. It is not — the
two Lighthouse JSONs show identical chunk hashes and a 28-byte payload difference, which is
incompatible with a re-chunk. The honest version of the cheap win is: there is nothing to revert,
here is the proof, and here is the instrument that would have caught it the first time.
