# Plan 15.2-02: Defer SiteHeader's always-on client weight

## Goal

`SiteHeader` is the one client component that hydrates on **every single route**. It currently
pulls two modal subtrees and fires an authentication XHR on first paint for every anonymous
visitor. After this plan, all three are deferred behind the interaction that actually needs them.

This is the only remaining all-routes lever that has never been touched. Phases 15 and 15.1
deferred psalm-detail and `/psalms` components; nothing has addressed the root layout.

## Background — why this target and not the framework chunk

The phase brief proposes splitting `0r5n9xaeyh.pb.js` (the 71 KB chunk with 910–1134 ms of
scripting, the single largest contributor on every route). **That is not achievable and this plan
does not attempt it.**

`0r5n9xaeyh.pb.js` is the React 19 + Next.js 16 framework runtime — the reconciler, the router,
and the RSC payload decoder. `next/dynamic` splits *application* modules out of a chunk; it cannot
split the framework out of itself, because the framework is what executes the dynamic import. The
`unused-javascript` audit attributes 25,058 unused bytes to it, but those are framework code paths
this app does not hit (Suspense edge cases, error boundaries), not app code that could be moved.
Removing them would require a custom React build. The brief's estimate of "another 5-15 points if
the framework chunk can be split" has no mechanism behind it, so this plan claims none of it.

What *is* real and attributable to application code, from `src/components/SiteHeader.tsx`:

| Line | Eager import | Cost |
|---|---|---|
| 10 | `GlobalSearch` | 181 LoC + `Dialog`/`DialogContent` + 4 lucide icons + `renderSnippet`. Renders only when `searchOpen` is true. |
| 11 | `FeedbackModal` | 107 LoC + `Dialog`/`Input`/`Label`/`Textarea`/`Checkbox` (5 shadcn primitives, several unused elsewhere). Renders only when `footerOpen === 'feedback'`. |
| 70 | `authClient.useSession()` | Fires `GET /api/auth/get-session` on first paint of every route, for every visitor including anonymous ones. Confirmed in the Lighthouse network trace. Its only purpose is deciding whether to show a "Log Out" link. |

The two inline `Dialog` blocks for About and Copyright (lines ~225–252) are gated behind
`footerOpen === 'about' | 'copyright'` in JSX, so they already do not render on first paint — but
their `Dialog` import is shared with the header's other uses, so extracting them buys nothing.
Leave them alone.

## Skepticism — what this is worth

**Expected: 3–7 points median on each route, and possibly zero.**

Grounding: `GlobalSearch` + `FeedbackModal` + their exclusive shadcn primitives are on the order
of 300 LoC of app code plus ~5 UI primitives. For scale, Phase 15.1 deferred ~1000 LoC across five
psalm-detail components (including the 498-LoC `PsalmListingGrid`) and the psalm-detail framework
scripting moved 3665 ms → 3030 ms, worth roughly +2 points on a single-run measurement that we now
know carries ±6 noise. So the honest read of the closest available precedent is that a deferral
this size lands somewhere between +0 and +7, and the median-of-5 harness from Plan 15.2-01 is what
will tell us which.

The session-fetch removal is the more interesting half: it deletes a **blocking network request
from the critical path of every route**, which affects FCP and LCP rather than only TBT. LCP is
25% of the mobile Performance score and currently sits at 4.1–4.5 s simulated on `/`. That is
where the headroom is, and it has never been touched.

**This plan will be judged by the median-of-5 delta, not by whether the code looks better.** If
the harness shows no movement outside the spread, Plan 15.2-03 records that as the honest result.

### Task 3: Defer the session fetch behind a mount gate

<read_first>
- `src/components/SiteHeader.tsx` lines 60–80 — the `useSession()` call, `showLogout`, and `handleLogout`.
- `src/components/SiteHeader.tsx` lines ~130–150 and ~175–195 — both render sites that read `showLogout` (desktop nav and mobile Sheet).
- `src/lib/auth-client.ts` — confirm `authClient` is the Better Auth client and `useSession` is its hook.
- `src/components/ChangelogComposer.tsx` line 25 — the other `useSession()` consumer. **Do not change it**; it is a page-level component, not in the root layout, so it does not affect every route.
</read_first>

<action>
`authClient.useSession()` fires `GET /api/auth/get-session` during hydration on every route. Its
sole output is `showLogout`, which controls a "Log Out" link shown next to the `/precent` nav
entry. Anonymous visitors — the overwhelming majority, and the ones Lighthouse measures — pay a
blocking request for a link they will never see.

Gate the hook behind an idle-deferred flag so the request leaves the critical path:

1. Add a state flag that starts `false` and flips after first paint:
   ```tsx
   // The session fetch exists only to decide whether to show the Log Out
   // link. SiteHeader is in the root layout, so an eager useSession() puts a
   // blocking /api/auth/get-session request on the critical path of every
   // route for every visitor, including anonymous ones. Deferring it to idle
   // keeps the link correct for logged-in precentors while taking the request
   // off first paint. requestIdleCallback is not available in Safari, hence
   // the setTimeout fallback.
   const [sessionEnabled, setSessionEnabled] = useState(false)
   useEffect(() => {
     const w = window as Window & { requestIdleCallback?: (cb: () => void) => number }
     if (typeof w.requestIdleCallback === 'function') {
       const id = w.requestIdleCallback(() => setSessionEnabled(true))
       return () => (window as Window & { cancelIdleCallback?: (h: number) => void })
         .cancelIdleCallback?.(id)
     }
     const t = setTimeout(() => setSessionEnabled(true), 1)
     return () => clearTimeout(t)
   }, [])
   ```
2. Keep the `useSession()` call itself unconditional — **hooks must not be called conditionally**.
   Gate only the *consumption*:
   ```tsx
   const { data: session, isPending: sessionPending } = authClient.useSession()
   const showLogout = sessionEnabled && !sessionPending && !!session
   ```

   **Check Better Auth's actual behaviour before settling on this shape.** If
   `authClient.useSession()` accepts an options argument supporting `enabled` / `disabled` (some
   Better Auth versions expose a `nanostores`-backed hook without one), prefer passing the gate
   into the hook so the request itself is deferred rather than just its consumption. If it does
   not, the gate above still removes `showLogout` from the first-paint render path but the fetch
   may still fire on mount — **in that case say so explicitly in the summary rather than claiming
   the request was deferred.** Verify empirically:
   ```bash
   # Should show the get-session request firing AFTER first paint, or not at all on first load
   node scripts/lighthouse-bench.mjs --runs 1 2>&1 | tail -5
   curl -s http://localhost:3005/ | grep -c "get-session"
   ```
   The authoritative check is the Lighthouse network trace: `get-session` should no longer appear
   as a render-blocking request in the critical path.
3. Do NOT change `handleLogout`, the nav-link markup, or the Sheet contents beyond what
   `showLogout` already controls. A logged-in precentor must still get the Log Out link — one
   frame later than before, which is fine for a link that sits behind a nav they are already
   looking at.
</action>

## Realistic ceiling

Post-plan expected medians:

| Route | Baseline median | Expected after | Confidence |
|---|---|---|---|
| `/` | ~0.63 | 0.63–0.70 | Low-moderate. Best case here: the homepage is the lightest route, so removing the session XHR and two modal subtrees is proportionally the biggest cut. |
| `/psalms` | ~0.63 | 0.63–0.70 | Low-moderate. Same header saving, but `PsalmListingGrid` still dominates this route's own bundle. |
| `/psalms/23` | ~0.65 | 0.65–0.70 | Low. `SingingView` and the abcjs notation path dwarf the header saving here. |

**None of these reach 0.90, and this plan should not be read as a path to 0.90.**

The reason is structural. Median TBT is 611–1311 ms on `/`, of which the framework runtime alone
accounts for 910–1134 ms of scripting. Mobile Lighthouse scores TBT ≥ 600 ms harshly, and the app
cannot get under that ceiling while shipping React 19 + Next 16 App Router with a client-component
root layout. Reaching 0.90 on mobile-simulated throttling would require converting `SiteHeader` to
a server component with tiny client islands for the theme toggle and search button — a real
option, but a larger refactor than this phase's remaining budget, and one that should be measured
before being committed to.

The LCP side has more headroom than TBT (4.1–4.5 s simulated on `/`, worth 25% of the score) but
is dominated by simulated network cost on a route whose document is only 11 KB transferred — most
of that LCP is waiting on the throttled script chain, which loops back to the same framework cost.

**Honest summary: this plan is worth attempting because the session-fetch removal is a genuine
critical-path win and the code is cleaner regardless, but the expected outcome is 0.63–0.70, not
0.90. If the median-of-5 shows no movement outside the spread, that is a real and reportable
result, and Plan 15.2-03 will say so.**
