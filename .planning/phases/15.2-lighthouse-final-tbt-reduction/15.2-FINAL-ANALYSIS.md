# Phase 15.2 — Final Lighthouse Analysis

## Executive summary (one paragraph)

Phase 15.2 set out to fix a 22-point regression on `/` that Phase 15.1 had blamed on `next.config.ts images.qualities` triggering a Turbopack chunk re-shuffle. Investigation **disproved that cause** (identical framework chunk hashes, 28-byte total payload delta, benchmarkIndex 477.5 vs 1073, RTT 654ms vs 38ms — the slow run was a thrashing VPS, not a bundle change). What Phase 15.2 actually delivered is a **trustworthy measurement harness** (`scripts/lighthouse-bench.mjs --runs 5`), the **only remaining all-routes lever** (SiteHeader's `GlobalSearch`/`FeedbackModal`/session-fetch deferral via `next/dynamic` and `requestIdleCallback`), and **this corrected record**.

Under that harness, the median-of-5 scores are **`/` 0.68, `/psalms` 0.69, `/psalms/23` 0.45** — each inside the baseline's min–max spread. **No improvement was measured**; the ceiling is set by the framework runtime (`0r5n9xaeyh.pb.js` = 71 KB, 910–1134 ms scripting, 25 KB unused bytes that `next/dynamic` cannot split — they are unhit framework paths, not app code). Reaching 0.90 mobile requires a server-component root-layout refactor: real work, real cost, and a user decision about whether to do it.

## 2. Verdict on the Phase 15.2 premise

The phase was scoped around three levers, in order of evidence:

1. **Investigate and revert the `qualities` array change.** Done — disproved (see §3). No code revert needed; `qualities: [75]` already matches the runtime default and silences the Next 16 warning. The `quality={100}` prop in `SiteHeader.tsx` (which was inert under `q=75` server output) was the latent inconsistency; Plan 15.2-01 fixed it.
2. **Take the one remaining all-routes lever** (`SiteHeader`'s `GlobalSearch`/`FeedbackModal`/`useSession` blocking weight). Done — Plan 15.2-02. Confirmed by build artefact (`GlobalSearch` and `FeedbackModal` no longer in `.next/server/app/page.js`), confirmed by tests (`SiteHeader.test.tsx` 4/4), and confirmed by TBT variance on `/psalms`. But the *score* didn't move because the network-pinned ceiling (framework runtime) wasn't touched.
3. **Reach 0.90 on all three routes.** **Not reachable** within Phase 15.2's scope. Remaining levers documented below (§5) for the user decision.

## 3. The corrected history (retraction of the `qualities` regression claim)

Three places in `.planning/` previously asserted that `next.config.ts images.qualities: [75, 90]` triggered a Turbopack chunk re-shuffle that exploded `/` `Parse HTML & CSS` from 108 → 2972 ms and dropped Performance from 0.69 → 0.47. Investigation in `15.2-measurement-noise-evidence.md` **disproves that claim on independent evidence**:

| Evidence (from the two Lighthouse JSONs' own `network-requests` audit) | Phase 15 baseline (0.69) | Phase 15.1 (0.47) |
|---|---|---|
| Script bytes (20 requests) | 273,182 | 273,210 |
| Stylesheet bytes | 21,235 | 21,235 |
| Font bytes | 39,759 | 39,759 |
| Document resourceSize | 46,453 | 46,422 |
| Framework chunk name | `0r5n9xaeyh.pb.js` | `0r5n9xaeyh.pb.js` |
| `environment.benchmarkIndex` (CPU speed probe) | 1073 | **477.5** (2.2× slower) |
| `server-response-time` | 64 ms | **376 ms** (5.9× baseline) |
| `network-rtt` | 38 ms | **654 ms** (17× baseline) |

**The chunk hashes are identical and the total script payload differs by 28 bytes.** A Turbopack re-chunk would change chunk hashes and shift bytes between chunks. Neither happened. Meanwhile, the slow run's `benchmarkIndex` was 2.2× slower, `SRT` was 5.9× higher, and `RTT` was 17× higher — the VPS was thrashing on that single run, full stop.

A zero-code-change control reproduced the same noise floor: 3 runs of `/` with identical code returned Performance 0.61 / 0.64 / 0.64 (spread 3 points) and TBT 1311 / 632 / 611 ms (2.1× variance); 2 runs of `/psalms` returned 0.60 / 0.66 (spread 6 points). **The "regression" was machine noise; the `qualities` array has no path into the JS module graph** (it validates the `q=` parameter on `/_next/image`, nothing else).

The previous Phase 15.1 analysis file (`15.1-lighthouse-analysis.txt`) labelled this TURBOPACK REGRESSION as a "ROOT-CAUSE unclear" hypothesis. It has now been investigated and discarded. The honest description of Phases 15 + 15.1 + 15.2 is:

| Phase | What actually shipped | Measured effect under trustworthy methodology |
|---|---|---|
| **15** | 5 dynamic-import wrappers (PsalmListingGridClient et al.), next/logo Image prop, Geist pruning | Median-of-5 baseline established *after* Phase 15: `/` 0.71, `/psalms` 0.67, `/psalms/23` 0.49. Single-run Phase 15 numbers (0.69 / 0.61 / 0.65) carry ±6 to ±14 noise and cannot be interpreted as a delta. |
| **15.1** | 5 more dynamic-import wrappers (PsalmPickerModalClient et al.), PsalmListingGrid hydration batching, logo q=100→90 | 0.47 / 0.60 / 0.67 single-run apples-to-apples. **The 0.47 was a thrashed VPS run**, not a Phase 15.1 regression. **No real motion was introduced.** |
| **15.2** | Trustworthy measurement harness + SiteHeader deferral + corrected record | Plan 02 medians 0.68 / 0.69 / 0.45, all inside baseline spread — **null result**. Genuine deliverable: a measurement instrument we can trust. |

## 4. Why 0.90 was not reached, mechanically

Three structural facts together fix a ceiling under any optimisation we can do without a server-component root-layout refactor:

1. **Framework runtime is unsplittable.** `0r5n9xaeyh.pb.js` = 71,235 bytes transferred, 910–1134 ms scripting on every route, 25,058 bytes of "unused" bytes that `next/dynamic` cannot remove — they are unhit framework paths (React 19 + Next 16 reconciler / router / RSC decoder), not application code. **This is the thing that executes dynamic imports; it cannot itself be split by `next/dynamic`.**
2. **Mobile Lighthouse scoring is steep on TBT ≥ 600 ms.** Observed TBT at the framework-runtime floor alone is 557–1850 ms on the routes we measure. **The mobile Performance scoring curve penalises this range harshly; even reaching 0.70 requires keeping first-paint blocking work strictly under the floor, not adding work to it.** Plan 02's deferred dialog code earned modest TBT variance but couldn't recover the framework floor.
3. **`/` LCP is 4.1–4.5 s simulated** against an 11 KB document — almost entirely throttled script chain. LCP carries 25% of the mobile Performance score, **larger than TBT at current values**, and is currently riding the same framework-runtime cost as seen through the LCP lens. No plan in Phase 15 or 15.2 addressed it.

**What this means:** the largest single thing standing between this app and 0.90 was never in the application code. It is React 19 + Next 16's client runtime on a mobile-throttled cold load, plus a measurement instrument that was too noisy to tell progress from jitter. Phase 15.2 fixes the instrument. What is left after that requires converting `SiteHeader` to a server component with tiny client islands — a real refactor with real regression risk to nav/theme/search/auth UI.

## 5. Three forward options (the user decision)

### Option A — stop here, accept the current scores

POLISH-03 marked consciously deferred with the ceiling documented. Rationale: this is a personal-use psalter for a single congregation, used overwhelmingly on **repeat visits with a warm cache** (mid-service precentor lookup is the canonical use case, and those are warm-cache by definition). Lighthouse's cold-cache mobile-simulated score on `localhost` is a poor proxy for what the precentor actually experiences mid-service. **Three phases of effort have bought little measurable movement**: from a Phase 15 single-run baseline of 0.69 / 0.61 / 0.65 (which itself carries ±6 to ±14 noise), the median-of-5 measurements after Phase 15.2 sit at 0.68 / 0.69 / 0.45 — statistically indistinguishable. The improvements that *were* made (`next/dynamic` wrappers, deferral, hydration batching, logo quality) are real and ship and cost nothing to keep; what they did *not* do is move the score on a noisy instrument.

Public-URL scores are 5–10 points lower than localhost (Cloudflare bot-challenge adds ~700–1200 ms `cdn-cgi` scripting per route — measured in Phase 15.1). That gap is closed independently by Option C.

### Option B — one more phase, scoped to the server-component root layout

Convert `SiteHeader` to a server component with small client islands (theme toggle, search trigger, mobile sheet). Removes the largest client subtree from every route. **Estimated +5–12 points**, moderate confidence — this is the single highest-value remaining change and the only one with a plausible path toward 0.90 on `/` and `/psalms`.

Cost and risks:
- Touches every page's chrome (layout.tsx, SiteHeader.tsx, About/Copyright dialogs, theme toggle, GlobalSearch trigger, FeedbackModal trigger).
- Real regression risk to existing UI: nav active state detection (currently client-side `usePathname()`), theme toggle (next-themes requires client), Better Auth session display, mobile hamburger sheet.
- The `useSession()` gate added in Plan 15.2-02 has to stay correct across the server/client boundary (the hook itself stays in a small client island).
- It will take the same wall-clock cost as Phase 15.2 (one full phase) and **must start by re-baselining with `scripts/lighthouse-bench.mjs --runs 5`** because the VPS state drifts between sessions.

### Option C — Cloudflare WAF rule (user action; complements A or B)

Exempt `/`, `/psalms`, `/psalms/[id]` from the Cloudflare bot-challenge JS. **Recovers 5–10 points on the public URL only** (no effect on `localhost` measurements).

This requires the user to make the change in the Cloudflare dashboard (Security → WAF → Custom Rules). It is outside Claude's authority. **It is a one-time change; the recovery holds as long as the rule exists.** Independent of whether Option A or Option B is chosen.

### Recommendation

If the user's instinct is "make it good enough that the public score passes 0.85 with cache warm," **Option C alone is the cheapest path to that bar** — five minutes in the dashboard, no code change, no regression risk. Option B is the right move only if the user specifically wants the `localhost` number to reach 0.90, and accepts the regression risk to nav/theme/search UI that goes with that.

## 6. Standing methodology note (binding for future performance claims)

**Any future performance claim on this project must come from `scripts/lighthouse-bench.mjs --runs 5` and must report the spread alongside any median.** Single-run before/after comparisons on this VPS have produced **three false conclusions** so far:

1. Phase 15's PerformanceObserver stand-in returned 1.0 / 1.0 / 0.91 (loopback localhost, no simulated throttling) and was treated as satisfying POLISH-03 — disproved by Phase 15.1's real Lighthouse run.
2. Phase 15.1's single-run 0.47 was attributed to `qualities` regression — disproved by chunk-hash + benchmarkIndex evidence (this analysis).
3. Plan 15.2-02's single-run perception of "moving the needle" on TBT would have read as a clear win under ±6 noise — actually inside the baseline spread.

A median without its spread is what got this project into three rounds of false conclusions. **Future performance work: do not trust any number that does not come out of `--runs 5`.**
