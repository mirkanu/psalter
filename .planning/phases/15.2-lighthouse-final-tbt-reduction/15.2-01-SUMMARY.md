# Phase 15.2 Plan 01: Trustworthy Lighthouse harness + settle the `qualities` question

## One-liner

Median-of-5 Lighthouse harness (`scripts/lighthouse-bench.mjs`) plus a self-consistent logo quality config; every subsequent Phase 15.2 plan measures against the recorded baseline.

## What changed

- **`scripts/lighthouse-bench.mjs` (new, 96 LoC):** Runs Lighthouse N times per route **sequentially** via `npx --yes lighthouse` with ephemeral chrome (`--headless=new --no-sandbox --disable-dev-shm-usage --disable-gpu`). Reports `perf.median` plus `perf.min` / `perf.max` spread, plus median TBT, FCP, LCP, CLS, and Lighthouse `benchmarkIndex` per route. Per-run JSONs go to a temp dir and are deleted; only the aggregate is kept. Defaults to 5 runs; `--runs N` and `--out path.json` flags supported. Sequential by design — two concurrent chromes would OOM the 3.7GB VPS.
- **`next.config.ts`:** Added `images.qualities: [75]` so Next 16's config validator stops warning. Matches the runtime default exactly. No other field touched (`cpus: 1` retained, `remotePatterns` retained).
- **`src/components/SiteHeader.tsx`:** Logo `<Image>` updated to `width={350} height={57}` with `sizes="(min-width: 768px) 350px, 175px"` (Phase 15 retina-sharpness fix from the planner's working tree). No `quality` prop — the previous `quality={100}` was inert under the server's `q=75` output.
- **`.planning/phases/15.2-.../15.2-baseline-median5.json` (new):** 5-sample median baseline for all three routes; lives in the worktree filesystem and is referenced from this SUMMARY (project's `.gitignore` excludes `.planning/phases/` operational artifacts by convention).

## Why the qualities "regression" was never real

The plan retires the Phase 15.1/15.2 conclusion that `images.qualities: [75, 90]` caused a Turbopack re-chunk that exploded `Parse HTML & CSS` from 108 ms to 2972 ms on `/`. Evidence (from `.planning/phases/15.2-.../15.2-measurement-noise-evidence.md`):

- The two Lighthouse JSONs in question report **identical** framework chunk hashes (`0r5n9xaeyh.pb.js` in both) and total script payloads differing by **28 bytes**. A re-chunk would change chunk hashes. Neither happened.
- The 0.47 outlier was captured on a run with `benchmarkIndex: 477.5` (vs 1073 on the 0.69 run — 2.2× slower CPU), `server-response-time: 376 ms` (vs 64 ms), and `network-rtt: 654 ms` (vs 38 ms). The machine was thrashing, not the bundle.
- `images.qualities` does not participate in the JS module graph. It validates the `q=` query parameter on `/_next/image`.

So there is no regression to revert. What the config *did* have was a latent invalid pair (`quality={100}` vs `qualities: [75]`) — that is what this plan corrected.
