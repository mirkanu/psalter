## Summary

Phase 04.9.4 is a **pure polish pass on existing code**. No new npm packages are introduced (UI-SPEC § Registry Safety). The entire feature set is implemented by restructuring or adding to the five existing singing-view components (`SingingView`, `PsalmTopBar`, `TuneSubBar`, `PsalmActionsFAB`, `AbcAudioControls`) plus three new client components (`GlassBottomBar`, `PlayMiniBar`, onboarding tour portal). The abcjs renderer and the Sheet primitive are left structurally unchanged.

The most complex piece is the **onboarding tour** — a custom React portal (~80 LOC per UI-SPEC) using a CSS box-shadow cutout spotlight. The design decision to hand-roll is already locked in the UI-SPEC; the implementation pattern is well understood from the spec and matches standard practice for Next.js App Router (portal to `document.body`, `localStorage` flag, SSR-safe hydration with `useState(false)` + `useEffect` mount check).

The **proportional zoom heuristic** extends the existing `window.addEventListener('resize', onResize)` in `NotationRenderer.tsx` (line 364) with a `referenceWidth` ref and a rescale formula. The formula and debounce thresholds are fully specified in UI-SPEC § Proportional Zoom Heuristic.

The **glass bottom bar** replaces both the 56×56 FAB (`PsalmActionsFAB`) and the 40px `TuneSubBar`. Tailwind 4 `backdrop-blur-md` and `bg-background/70` are already proven in the codebase (`SiteHeader`, `PsalmTopBar`, `TuneSubBar`). No browser-compat surprises.

**Primary recommendation:** Implement in two waves. Wave 1 restructures chrome (header + bottom bar + gear drawer, replacing FAB and sub-bar). Wave 2 adds the play mini-bar slide animation and the onboarding tour. The `loading.tsx` skeleton must be updated to match the new chrome layout.

### Pattern 3: PlayMiniBar — CSS translate slide animation

The UI-SPEC mandates Tailwind `transition-all` + class toggling (not Framer Motion) for the entry/exit. `[CITED: 04.9.4-UI-SPEC.md § PlayMiniBar Entry animation]`

// Source: UI-SPEC § Play Mini-Bar Entry / Exit
// The mini-bar is always rendered in the DOM after first play (avoids layout flash).

const [miniBarVisible, setMiniBarVisible] = useState(false)

  className={cn(

    'transition-all duration-200 ease-out',
    'pb-[env(safe-area-inset-bottom)]',

      ? 'translate-y-0 opacity-100'
      : 'translate-y-full opacity-0',

    'motion-reduce:translate-y-0 motion-reduce:!transition-opacity motion-reduce:duration-100',

  style={{ display: miniBarMounted ? undefined : 'none' }}

  ...

**Note on `display:none` after exit:** After the 150ms exit transition ends, use `onTransitionEnd` to set `display:none` — prevents focus trapping of hidden controls. `[CITED: 04.9.4-UI-SPEC.md § PlayMiniBar Exit animation]`

**Reduced motion:** `motion-reduce:` prefix in Tailwind 4 applies `@media (prefers-reduced-motion: reduce)`. Already used in codebase as `motion-reduce:transition-none`. For the mini-bar the pattern is opacity-only at 100ms. `[VERIFIED: globals.css, AbcPlayer.tsx pattern]`

### Pattern 4: Proportional Zoom Heuristic

The UI-SPEC defines a formula: `[CITED: 04.9.4-UI-SPEC.md § Proportional Zoom Heuristic]`

```
newStaffSize = clamp(baseSize × (newWidth / referenceWidth), 8, 40)
```

**Implementation location:** `SingingView.tsx` — because `baseSize` state already lives there (hoisted from NotationRenderer in Phase 04.9.3).

```tsx
// In SingingView — add alongside existing resize listener
const referenceWidthRef = useRef<number>(
  typeof window !== 'undefined' ? window.innerWidth : 375
)

// When user manually taps A+/A−, update referenceWidth
const handleBaseSizeChange = (newSize: number) => {
  referenceWidthRef.current = typeof window !== 'undefined' ? window.innerWidth : 375
  setBaseSize(newSize)
}

// ResizeObserver or resize event on viewport width change
// Use window.innerWidth (viewport, not container) — the heuristic is viewport-level
useEffect(() => {
  if (typeof window === 'undefined') return
  let timeoutId: ReturnType<typeof setTimeout>
  const onResize = () => {
    clearTimeout(timeoutId)
    timeoutId = setTimeout(() => {
      const newWidth = window.innerWidth
      const refWidth = referenceWidthRef.current
      if (Math.abs(newWidth - refWidth) < 8) return // <8px threshold
      const newSize = Math.max(8, Math.min(40, baseSize * (newWidth / refWidth)))
      referenceWidthRef.current = newWidth
      setBaseSize(Math.round(newSize))
    }, 150)
  }
  window.addEventListener('resize', onResize)
  window.addEventListener('orientationchange', onResize)
  return () => {
    clearTimeout(timeoutId)
    window.removeEventListener('resize', onResize)
    window.removeEventListener('orientationchange', onResize)
  }
}, [baseSize]) // baseSize in deps so closure captures current value
```

**Important:** The existing `window.addEventListener('resize', onResize)` in `NotationRenderer.tsx` (line 364) tracks `viewportW` for `staffWidthFactor`. That is separate from this heuristic — it runs in the renderer and drives sub-staff splits. The proportional zoom heuristic runs in `SingingView` and drives `baseSize`. They are independent. Do NOT remove the renderer's resize listener.

**Clamp bounds differ from NotationRenderer:** UI-SPEC specifies 8–40 for the zoom heuristic, while `NotationRenderer` uses `MIN_SIZE=4 / MAX_SIZE=120`. The heuristic clamp is narrower and intentional — it prevents runaway rescaling on extreme orientation flips. `[CITED: 04.9.4-UI-SPEC.md § Proportional Zoom Heuristic]`

**baseSize in deps causes stale-closure risk:** The effect captures `baseSize` from the closure. A stable pattern is to store `baseSize` in a ref alongside `referenceWidthRef` — that way the resize handler always reads the latest value without re-registering. Prefer ref pattern:

```tsx
const baseSizeRef = useRef(baseSize)
useEffect(() => { baseSizeRef.current = baseSize }, [baseSize])
// resize handler reads baseSizeRef.current
```

### Pattern 5: Onboarding Tour — custom React portal

The tour is a `'use client'` component that renders into `document.body` via `createPortal`. The spotlight cutout uses CSS `box-shadow: 0 0 0 9999px rgba(0,0,0,0.60)` on a positioned wrapper that is `z-[201]`, with the dark overlay at `z-[200]`. `[CITED: 04.9.4-UI-SPEC.md § Onboarding Tour]`

**SSR-safe hydration pattern:**

```tsx
// OnboardingTour.tsx
'use client'
import { useEffect, useState } from 'react'
import { createPortal } from 'react-dom'

const TOUR_KEY = 'psalter_tour_v1'

export function OnboardingTour() {
  const [mounted, setMounted] = useState(false)
  const [tourSeen, setTourSeen] = useState(true) // optimistic — assume seen to avoid flash
  const [step, setStep] = useState(0)

  useEffect(() => {
    // Only runs client-side — avoids SSR/hydration mismatch
    const seen = localStorage.getItem(TOUR_KEY) === 'done'
    setTourSeen(seen)
    setMounted(true)
  }, [])

  if (!mounted || tourSeen) return null

  const dismiss = () => {
    setTourSeen(true)
    try { localStorage.setItem(TOUR_KEY, 'done') } catch { /* ignore */ }
  }

  // ... step rendering
  return createPortal(
    <TourOverlay step={step} onNext={...} onSkip={dismiss} />,
    document.body
  )
}
```

**Key SSR-safety notes:**
- Initial `tourSeen = true` prevents any tour flash during hydration
- `mounted` gate ensures `localStorage` is only accessed client-side
- `createPortal` called only after `mounted` — `document.body` doesn't exist during SSR
- This mirrors the `SingingView` pattern for `viewMode`/`baseSize` (lines 95-106 of SingingView.tsx)
- `[VERIFIED: SingingView.tsx hydration pattern, lines 95-106]`

**Spotlight target measurement:**

```tsx
// Get bounding rect of tour target element
const el = document.querySelector('[data-tour-target="prev-next"]')
const rect = el?.getBoundingClientRect()
// Position highlight wrapper to match rect + 8px padding
```

Data attributes (`data-tour-target="..."`) should be added to the target elements in PsalmTopBar and GlassBottomBar. This avoids coupling the tour to CSS class names.

**Tour step targets (4 steps):**

| Step | `data-tour-target` | Added to |
|------|-------------------|----------|
| 1 | `prev-next` | `[←]` arrow in PsalmTopBar OR highlight the whole prev/next zone |
| 2 | `tune-name` | Tune name button in PsalmTopBar |
| 3 | `view-controls` | GlassBottomBar view radiogroup |
| 4 | `play-button` | Play button in GlassBottomBar |

**Keyboard handling:** `useEffect` adds `keydown` listener for `Escape` → `dismiss()`. Focus is locked inside the tip bubble (trap with a `tabIndex={-1}` wrapper + `useEffect` that calls `.focus()`). `[CITED: 04.9.4-UI-SPEC.md § Accessibility]`

### Anti-Patterns to Avoid

- **Persist `baseSize` update before `referenceWidth` update:** Always update `referenceWidthRef.current` atomically with the user's A+/A- change — if they diverge, the next resize will compute from stale reference. Do both in `handleBaseSizeChange`.
- **Tour portal before mount:** Never call `createPortal(…, document.body)` during SSR. The `!mounted` early return is mandatory.
- **`display:none` via React state alone on PlayMiniBar:** The transition must complete before `display:none` fires. Use `onTransitionEnd` callback to set a separate `hidden` state. If display is toggled immediately via React state, the CSS transition never plays.
- **New `useEffect` for resize without cleaning old one:** The existing `window.addEventListener('resize', onResize)` in `NotationRenderer.tsx` (line 365) remains — the proportional zoom is an additional listener in `SingingView`, not a replacement.
- **Hardcoding bottom offset in PlayMiniBar without CSS variable:** Bottom bar height is 56px on mobile, 60px on desktop. Use `bottom-14 md:bottom-15` Tailwind utilities (or `bottom-[56px] md:bottom-[60px]`) rather than a hardcoded `56`.

## Common Pitfalls

### Pitfall 1: Body height recalculation after sub-bar removal

**What goes wrong:** Removing `TuneSubBar` (40px) and adding a fixed bottom bar (56px) changes the body `calc(100dvh - ...)` formula. The current formula in `SingingView.tsx` (line 181) is `h-[calc(100dvh-147px)] md:h-[calc(100dvh-159px)]`, accounting for `SiteHeader(56) + PsalmTopBar(48) + TuneSubBar(40) + borders(3)`.

**New formula:** With sub-bar removed, body height is `calc(100dvh - 48px - 56px - env(safe-area-inset-top) - env(safe-area-inset-bottom))` on mobile (SiteHeader is 56px and is part of the site layout above `SingingView`). The glass bottom bar is `fixed`, so it does NOT participate in flow — body height accounts for it visually by reserving padding-bottom.

**Correct approach:** The body `<main>` gets `pb-14 md:pb-15` (matching bottom bar height) or `h-[calc(100dvh-104px)]` (48 topbar + 56 bottom-bar, no sub-bar). Exact value per UI-SPEC § Body Area table. `[CITED: 04.9.4-UI-SPEC.md § Body Area]`

**Also update `loading.tsx`:** The skeleton must reflect the new chrome: top-bar skeleton only (no sub-bar), bottom-bar skeleton as a fixed strip, no FAB skeleton. `[VERIFIED: src/app/psalms/[id]/loading.tsx]`

### Pitfall 2: z-index collision between tour overlay and existing stacking context

**What goes wrong:** `SiteHeader` is `z-50`. `PsalmTopBar` is `z-30`. `PsalmActionsFAB` was `z-40`. The tour overlay is `z-[200]` — above all of these. But if the tour's portal is attached to `document.body` and `SiteHeader` creates a stacking context, the overlay may not cover the header.

**Why it happens:** A `sticky` header with `backdrop-blur` does NOT create a new stacking context unless `transform`, `isolation`, or `will-change` is also set. Tailwind's `backdrop-blur` uses `filter` which DOES create a stacking context on some browsers.

**How to avoid:** Test tour overlay visibility over `SiteHeader` in Playwright at all 3 breakpoints. If the overlay clips, wrap the portal element with `isolation: isolate` or use `z-[9999]` on the overlay. The tour is a rare interaction; extreme z-index is acceptable. `[ASSUMED: stacking context behavior — verify in Playwright UAT]`

### Pitfall 3: PlayMiniBar transition doesn't play when `display:none` is toggled simultaneously

**What goes wrong:** If React toggles `display:none` in the same render as `opacity-0 translate-y-full`, the browser skips the transition (no transition from `none`).

**Why it happens:** CSS transitions only interpolate between two computed values. `display:none` removes the element from the computed style tree — nothing to transition from.

**How to avoid:** Two-phase visibility: (1) remove `display:none` first to trigger a paint, (2) on the next frame, apply `translate-y-0 opacity-100`. Use a small `requestAnimationFrame` delay after setting `miniBarMounted = true` before setting `miniBarVisible = true`. For exit, reverse: set `translate-y-full opacity-0` first, then on `transitionend` set `display:none`. `[VERIFIED: 04.9.4-UI-SPEC.md § PlayMiniBar Exit animation, same pattern]`

### Pitfall 4: Proportional zoom produces floats that cause abcjs jitter

**What goes wrong:** `baseSize * (newWidth / refWidth)` produces non-integer floats (e.g., 13.847). AbcPlayer re-renders on every `baseSize` change; abcjs re-lays out the SVG. Floating-point values can cause sub-pixel jitter across renders.

**How to avoid:** `Math.round()` the result before setting state. The UI-SPEC formula implies integer output; the clamp bounds (8, 40) are integers. `[ASSUMED: abcjs jitter from float baseSize — verify in UAT]`

### Pitfall 5: Tour spotlight misaligns on scroll or dynamic elements

**What goes wrong:** `getBoundingClientRect()` is relative to the viewport. If the tour target (e.g., GlassBottomBar Play button) is `fixed`, its rect is stable. But the `♩ Tune` name in PsalmTopBar is `sticky` — if the page is scrolled, `sticky` elements may report differently.

**How to avoid:** Call `scrollIntoView` before measuring rect (per UI-SPEC § Scroll handling). Add a 200ms delay after `scrollIntoView` before re-measuring (per UI-SPEC). All four tour targets in this phase are either `fixed` (GlassBottomBar) or `sticky top-14` (PsalmTopBar). Sticky elements at `top-14` will always be visible without scrolling. `[CITED: 04.9.4-UI-SPEC.md § Scroll handling]`

### Pitfall 6: SiteHeader height assumption in loading.tsx

**What goes wrong:** `loading.tsx` currently skeletons both the top-bar AND sub-bar. Deleting sub-bar without updating `loading.tsx` causes a layout shift when the real SingingView mounts (sub-bar skeleton disappears, glass bottom bar appears from nothing).

**How to avoid:** Update `loading.tsx` in the same plan wave that deletes `TuneSubBar`. The skeleton should show: top-bar (48px), glass bottom bar strip (fixed, 56px), body placeholder cards. `[VERIFIED: src/app/psalms/[id]/loading.tsx lines 14-20, 29-33]`
