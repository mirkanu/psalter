# Phase 04.9.8: Staff Display Word Alignment Fix - Research

**Researched:** 2026-05-28
**Domain:** ABC notation phrase splitting, syllable-to-note alignment, archaic word syllabification
**Confidence:** HIGH — all findings verified directly against the live codebase and database

---

## Summary

The staff view has a systematic word alignment bug: words are cut off at the right end of staff lines, and note heads appear with no lyrics underneath them. Three independent root causes have been verified against the live codebase and database:

**Root Cause 1 — bar-count split heuristic:** `splitMusicIntoSubLines` in `NotationRenderer.tsx` divides a phrase body into sub-staves by halving bar count. For a CM tune with 4 bars per phrase (2 per metrical line), the heuristic correctly splits at bar 2. But for tunes with unequal bar distributions (e.g., Crimond has 4 bars in phrase 0: 4 produce 11 note heads vs. the required 8-note CM line 1, then 8 note heads in bars 3-4 for the 6-note CM line 2), the split is always wrong. The only reliable split point is note-head count, not bar count.

**Root Cause 2 — trailing z2 rest as phantom bar:** Five CM tunes (Arnold, Crediton, New Britain, St. Andrew, St. Mary) end their last phrase with an unbarlined `z2` rest. `splitMusicIntoSubLines` tokenises on `|` only — a trailing `z2` with no closing bar becomes a 5th "measure" in a 4-measure phrase, causing `per = ceil(5/2) = 3` instead of `2`. For Crediton phrase 1 this pushes 3 music bars onto sub-staff 0 (15 note heads vs. 8 syllables) and leaves only 1 bar on sub-staff 1 (3 note heads vs. 6 syllables). Confirmed by simulation against live DB data.

**Root Cause 3 — archaic word under-syllabification:** 25 archaic `-eth` verb forms that occur in psalm lyrics are classified as 1 syllable by `nlp-syllables` but require 2 note positions when sung (e.g., "leadeth" → "lead-eth"). The complete list was extracted from the live DB: 23 distinct psalm versions use at least one affected word. Each wrong count shifts all following syllables left by 1, dropping the last syllable off the right edge.

**The architectural fix:** Rather than patching `splitMusicIntoSubLines`, the correct solution is to eliminate the need for it on the CM/LM/SM path by upgrading from 1 PHRASE_BREAK (2 phrases, each spanning 2 metrical lines) to 3 PHRASE_BREAKs (4 phrases, one per metrical line). When `phrasesForMeter("CM") = 4`, `mapCycleToPhraseSyllableLines` returns exactly 1 metrical line per phrase slot, and `linesPerPhrase = 1`, so `targetSubdivisions = max(phraseSubdivisions, 1) = phraseSubdivisions`. No sub-staff splitting is needed for lyrics alignment — the structural cause of the bug is eliminated.

**Primary recommendation:** Upgrade `phrasesForMeter` to return 4 for CM/LM/SM (and 8 for DCM/DLM/DSM); write a migration script that re-annotates all 134 tune ABCs using note-head counting to find the exact metrical-line boundary; fix the z2 trailing rest bug in `splitMusicIntoSubLines` as a defensive measure; add 25 archaic word overrides to `PSALM_SYLLABLE_OVERRIDES`.

### Pattern 1: Note-Head Counting for 8/6 Split

**What:** Parse ABC note tokens to count actual singing positions (note heads), excluding rests (`z`, `x`) and timing markers. Split phrase after exactly N note heads.

**When to use:** In `insertPhraseBreaks` (upgrade) and audit script. Pure function.

**Algorithm:**

```typescript
// Source: derived from ABC notation spec + codebase analysis [VERIFIED against Crimond, Crediton ABCs]
function countNoteHeads(abc: string): number {
  // ABC note tokens: optional accidentals (=^_), note letter (A-Ga-g), optional octave (', ,), duration
  // Rests: z (normal rest), x (invisible rest), Z (whole-bar rest)
  // Strip info fields (w:, V:, etc.)
  const musicOnly = abc.split('\n')
    .filter(l => !/^\s*[A-Za-z]:/.test(l))
    .join(' ')
  // Match note heads: optional accidentals + note letter (not z/x/Z)
  const notePattern = /[=^_]?[A-Ga-g]['`,]*\d*/g
  return (musicOnly.match(notePattern) ?? []).length
}
```

### Pattern 2: z2 Trailing Rest Fix

**What:** Strip trailing bare rests (not followed by a barline) before measure counting in `splitMusicIntoSubLines`.

**Why it happens:** Solfège images sometimes end a line with a half-rest (`z2`) but the OCR parser doesn't emit a closing `|` for the last "bar". This creates a 1-token "measure" that inflates bar count.

**Fix:** After tokenising on `|`, filter the `realMeasures` array to exclude entries that are pure rests with no barline (e.g., `z2`, `z4`, `x2`, `z` alone):

```typescript
// Source: NotationRenderer.tsx splitMusicIntoSubLines, lines 659-682 [VERIFIED]
const realMeasures = measures
  .filter(m => m && m !== '|')
  .filter(m => !/^\s*[zxZ]\d*\s*$/.test(m))  // exclude bare rest "bars"
```

**Note:** With the 4-PHRASE_BREAK approach, `splitMusicIntoSubLines` is called with `n=phraseSubdivisions` (not `n=linesPerPhrase`) because `linesPerPhrase=1` and `targetSubdivisions = max(phraseSubdivisions, 1)`. The z2 fix is still needed for chromeless/singing-view paths where `phraseSubdivisions=2`.

### Anti-Patterns to Avoid

- **Patching splitMusicIntoSubLines as primary fix:** The z2 fix is defensive only. The real fix is eliminating the bar-count heuristic's role in CM/LM/SM lyric alignment by upgrading PHRASE_BREAK count to 4.
- **Using bar count to find 8/6 split during migration:** Crimond phrase 0 has 4 bars but the 8-note split is at bar 2 (correct) only by coincidence. Crediton has unequal bar distributions. Always use note-head counting.
- **Running `annotate-phrase-breaks.ts --overwrite` without the note-head upgrade:** The current `insertPhraseBreaks` function uses equal-line-count splitting, which places PHRASE_BREAKs between music lines (a structural split) but cannot guarantee the 8/6 note-head boundary. The migration must use note-head counting.
- **Updating phrasesForMeter without running the migration:** If CM returns 4 phrases but the ABCs only have 1 PHRASE_BREAK, `splitOnPhraseBreaks` returns 2 phrases and the 3rd/4th phrase indices are empty — the renderer silently renders only 2 staff rows.

## Common Pitfalls

### Pitfall 1: Note-Head Regex Over-Matching

**What goes wrong:** A naive regex like `/[A-Ga-g]/g` matches letters inside chord brackets `[CEG]`, grace notes `{fg}`, text annotations `"text"`, and decoration strings like `!fermata!`.
**Why it happens:** ABC notation has many contexts where note-letter characters appear but are not note heads.
**How to avoid:** Strip chord brackets, grace note groups, text annotations, and decorations before counting. Alternatively, use ABC structure: a note head is a bare letter (optionally preceded by accidentals `=^_` and optionally followed by octave modifiers `'`,`) where the character is not `z`, `x`, or `Z`.
**Warning signs:** Note-head count is higher than expected for a CM tune; e.g., Crimond phrase 0 counted as 12 instead of 8+6=14.

### Pitfall 2: Double-Counting Ties

**What goes wrong:** A note `A4-A4` (tied note) counts as 2 note heads but consumes only 1 lyric syllable.
**Why it happens:** The second `A4` is the continuation of the same pitch; it is not a separate syllable.
**How to avoid:** After the tie character `-`, the next note is a continuation. Filter out continuation notes after `-`.
**Warning signs:** A CM tune has 16 "note heads" in phrase 0 but only 14 syllables are expected (8+6).

### Pitfall 3: Chords Counting Multiple Times

**What goes wrong:** `[CEG]` contains 3 letters but represents 1 note position (one syllable slot).
**Why it happens:** Chords are harmony; only the top note carries the lyric alignment.
**How to avoid:** Count each `[...]` group as 1 note head regardless of how many notes it contains.
**Warning signs:** Chord-heavy tunes produce counts larger than their syllable pattern predicts.

### Pitfall 4: phrasesForMeter Change Before DB Migration

**What goes wrong:** If `phrasesForMeter("CM")` returns 4 but ABCs still only have 1 PHRASE_BREAK, `splitOnPhraseBreaks` returns only 2 phrases. `wLinesForPhrase(2)` and `wLinesForPhrase(3)` receive empty phrase bodies. The renderer silently renders only 2 staff rows with the first 2 metrical lines' lyrics — but now each phrase slot only has 1 metrical line (since `mapCycleToPhraseSyllableLines` with `phrasesPerCycle=4` distributes 4 lines across 4 slots), so alignment is wrong in a new way.
**How to avoid:** The migration script must complete and be verified against the live DB **before** the `phrasesForMeter` change is deployed. Wrap as: Plan 2 includes both the DB migration AND the `phrasesForMeter` update in the same plan, run in order.
**Warning signs:** After deploying `phrasesForMeter=4` without DB migration: staff view shows only 2 rows for CM psalms instead of 4.

### Pitfall 5: LM "Already Works" Assumption

**What goes wrong:** LM (8.8.8.8) has equal-length lines, so the bar-count heuristic happens to split correctly for tunes with equal measures per line. It may appear that LM doesn't need re-annotation.
**Why it happens:** Bar-count = note-head-count for equal-line meters.
**How to avoid:** Still migrate LM to 4 PHRASE_BREAKs. Reasons: (1) consistency with CM/SM, (2) `phrasesForMeter("LM")` changing from 2 to 4 requires the ABCs to have 3 PHRASE_BREAKs or the renderer gets empty phrases 2+3, (3) some LM tunes may have anacrusis or unequal bars.

### Pitfall 6: Old 100th Pre-existing w: Lines

**What goes wrong:** Old 100th's `abc_notation` already contains `w:` lines interspersed with music lines (from an earlier manual annotation). Re-annotating without stripping these first places PHRASE_BREAKs in the wrong position (after a `w:` line rather than after a music line).
**How to avoid:** The migration script must strip pre-existing `w:` lines from ABC bodies before finding split points (or account for them in `isInfoFieldLine`). The `isInfoFieldLine` helper in `annotate-phrase-breaks.ts` already excludes `w:` lines from music-line identification — but the note-head counting loop must also skip `w:` lines.

#### splitMusicIntoSubLines (current — in NotationRenderer.tsx lines 659-682)

```typescript
// Source: src/components/notation/NotationRenderer.tsx [VERIFIED]
function splitMusicIntoSubLines(body: string, n: number): string[] {
  if (n <= 1) return [body]
  const segs = body.split(/(\|)/).filter((s) => s.length > 0)
  const measures: string[] = []
  let acc = ''
  for (const s of segs) {
    acc += s
    if (s === '|') {
      measures.push(acc.trim())
      acc = ''
    }
  }
  if (acc.trim()) measures.push(acc.trim())
  const realMeasures = measures.filter((m) => m && m !== '|')
  // BUG: z2 without trailing bar appears as 5th measure
  if (realMeasures.length < 2) return [body]
  const per = Math.max(1, Math.ceil(realMeasures.length / n))
  const lines: string[] = []
  for (let k = 0; k < realMeasures.length; k += per) {
    lines.push(realMeasures.slice(k, k + per).join(' '))
  }
  return lines
}
```
