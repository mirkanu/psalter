# Phase 04.9.8: Code Review Report

**Reviewed:** 2026-05-28
**Depth:** standard
**Files Reviewed:** 7
**Status:** issues_found

## Summary

The phase implements `% PHRASE_BREAK` annotation for ABC tunes, splits music into sub-staves, and adds syllable alignment. The logic is broadly sound — the core split algorithms are correct for the common cases, tie detection is directionally right, and the fallback paths are guarded. However, there are five bugs worth addressing:

- `splitMusicIntoSubLines` is duplicated between `NotationRenderer.tsx` and `split-music-into-sublines.ts`; the renderer uses its own inline copy rather than importing the extracted module, so unit-tested fixes to the module will not take effect in production.
- Path B of `insertPhraseBreaks` has a formula defect that silently skips annotation when the single music line has exactly `n-1` internal bars — the safe-guard `if (unique.length < n-1) return abc` fires due to collision, but only after the `internalBars.length >= n-1` precondition has already passed.
- `TOLERANCE` in the UAT script can silently become `NaN` from a bad env-var value, disabling all failure detection without any error.
- `stanzaMeter` is destructured but never read, and four lucide-react icons (`ZoomIn`, `ZoomOut`, `ChevronLeft`, `ChevronRight`) are imported but unused.
- `splitWLineIntoChunks` is declared inside the `useMemo` block but never called — dead code with a TODO comment marking it for removal.

### WR-02: Path B of `insertPhraseBreaks` silently fails to annotate when `internalBars.length === n-1`

**File:** `scripts/annotate-phrase-breaks.ts:224-234`

**Issue:** The splice-position formula is:
```typescript
const idx = Math.floor((internalBars.length * k) / n) - 1
const clamped = Math.max(0, Math.min(internalBars.length - 1, idx))
```
When `internalBars.length === n-1` (e.g. 3 internal bars for a 4-phrase tune), the `-1` offset causes `k=1` and `k=2` to both clamp to index `0`, producing duplicate splice positions. After deduplication, `unique.length < n-1` is true, so the function returns `abc` unchanged — no annotation is written. Yet the preceding guard `if (internalBars.length < n - 1) return abc` has already passed (length equals `n-1`, not less). The function promises to annotate when there are at least `n-1` internal bars, then silently refuses.

This affects single-line-body tunes with exactly one measure per phrase — a plausible structure for compact ABC source files.

**Fix:** Use a simpler formula that distributes `n-1` markers uniformly across `n-1` or more bars without the `-1` bias:

```typescript
// Replace the k-loop with:
for (let k = 1; k < n; k++) {
  // Place marker after bar at index floor(internalBars.length * k / n)
  // (no -1 offset — we want the bar AFTER which the k-th phrase ends)
  const idx = Math.min(
    internalBars.length - 1,
    Math.floor(internalBars.length * k / n)
  )
  splicePositions.push(internalBars[idx] + 1)
}
```

### WR-03: `TOLERANCE=invalid` in UAT script silently disables all failure detection

**File:** `scripts/uat/verify-staff-alignment.js:23`

**Issue:**
```javascript
const TOLERANCE = parseInt(process.env.TOLERANCE || '1', 10)
```
If `TOLERANCE` is set to a non-numeric string (e.g. `TOLERANCE=two`), `parseInt` returns `NaN`. Every comparison `s.trailingEmpty > NaN` evaluates to `false`, so `failures` is always empty and every psalm is reported as PASS. The UAT run would produce a fully-green report that is meaningless. There is no guard or error for this case.

**Fix:**
```javascript
const TOLERANCE_RAW = parseInt(process.env.TOLERANCE || '1', 10)
if (isNaN(TOLERANCE_RAW)) {
  console.error(`ERROR: TOLERANCE env var is not a valid integer: ${process.env.TOLERANCE}`)
  process.exit(1)
}
const TOLERANCE = TOLERANCE_RAW
```

### IN-03: `countNoteHeads` does not strip `%` comment lines before pattern matching

**File:** `scripts/annotate-phrase-breaks.ts:46-68`

**Issue:** `countNoteHeads` filters info-field lines (`w:`, `V:`, `K:`, etc.) via `isInfoFieldLine`, but `%` comment lines (e.g. `% in the key of G`) are not info fields and pass through the filter. If a `%` comment line also contains a `|` character, it would be included in `musicOnly` and any note-letter sequences in the comment text would be counted as note heads. The impact is low for the current dataset (the only `% ` comment in annotated tunes is `% PHRASE_BREAK` which has no `|`), but the function is exported and would silently over-count if reused with ABC that has inline comments.

**Fix:** Add a comment-line filter alongside the info-field filter:
```typescript
const musicOnly = abc
  .split('\n')
  .filter((l) => !isInfoFieldLine(l) && !/^\s*%/.test(l))
  .join(' ')
```
