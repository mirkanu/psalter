### Root Cause Analysis

The DB migration algorithm in `insertPhraseBreaks` accumulates note heads per **ABC text line** (the condition `line.includes('|')` on the full line) and inserts `% PHRASE_BREAK` after the whole text line when a threshold is crossed. This is text-line granularity.

For tunes like Crimond where the entire first half of the tune (CM lines 1 and 2, both 8-note and 6-note metrical lines) is encoded as a single ABC text line, the algorithm:
1. Counts all ~14 note heads in that line in one step
2. Crosses both the 8-head and 14-head thresholds on the same line
3. Emits two consecutive `% PHRASE_BREAK` lines immediately after that one text line

Result: phrases 0 and 2 contain 2 metrical lines each (combined 14-15 note heads), phrases 1 and 3 are empty. The renderer then assigns 15 notes to phrase 0 but only has 8 syllables worth of lyrics for one metrical line — leaving 7 trailing empty note heads.

The fix requires character-level tokenization: `insertPhraseBreaks` must walk the ABC notation token by token, count note heads inline, and emit `% PHRASE_BREAK` at the exact token boundary — potentially in the middle of what is a single ABC text line.

### Gaps Summary

The phase has one root cause generating all five failed truths: `insertPhraseBreaks` places `% PHRASE_BREAK` markers at ABC text-line boundaries rather than at exact note-head-count offsets within lines. The algorithm's insertion loop processes one ABC text line at a time and emits all PHRASE_BREAKs whose thresholds were crossed when exiting that line — so when multiple metrical lines (e.g., an 8-note CM line and a 6-note CM line) are stored as a single ABC text line, all pending breaks stack up at the end of that line, creating adjacent PHRASE_BREAKs and empty phrases.
