## Summary

This phase is a **single-tune end-to-end pilot** that proves the MusicXML-with-slurs ingestion pathway works against the canonical de Boer source for Crimond. Most of the infrastructure already exists — the de Boer Crimond.musicxml is publicly reachable, `xml2abc.py` v174 is installed at `scripts/xml2abc.py` and has already successfully converted four MusicXML files in a prior session, a `/dev/notation-compare` route demonstrates the dev-only preview pattern, the schema column (`tunes.abc_notation`) is correct, `% PHRASE_BREAK` is an existing marker convention with helpers in `src/lib/abc-phrases.ts`, and the `splitOnPhraseBreaks → wLinesForPhrase` rendering pipeline in `NotationRenderer.tsx` already strips any pre-existing `w:` lines from the phrase body (line 789).

The work consists of: (a) a one-off Node/Python conversion script that fetches `Crimond.musicxml`, runs xml2abc, extracts the soprano voice, applies the de Boer slur-walk algorithm to produce a `w:` line per phrase from a hard-coded Psalm 23 stanza-1 syllable list, inserts `% PHRASE_BREAK` markers at the four metrical-line boundaries, and writes the final ABC; (b) a single-branch change in `NotationRenderer.tsx` to skip `wLineForSyllables`/`buildWLineFromSolfa`/`syllabifyForAbc` when the phrase body already carries `w:` lines from the source — instead, preserve and emit them verbatim; (c) a dev-preview route (mirroring `/dev/notation-compare`) that loads the converted ABC string from a file or paste-box and renders it through the production `NotationRenderer`; (d) a single-row UPDATE on `tunes` (id=30, name='Crimond'); (e) a Playwright before/after screenshot of `/psalms/23` and `/psalms/24` to confirm only the target tune changed.

**Primary recommendation:** Treat this strictly as a pilot recipe — do not generalise the converter, do not refactor heuristic w-line code, do not touch the schema. The new code path is **parallel** to the heuristic path (solfège-OCR-driven `buildWLineFromSolfa` + `syllabifyForAbc` fallback) and is selected at render time by the presence of `w:` lines inside the phrase body. The heuristic path remains the default for every other tune.

### Pattern 1: Slur→Syllable Algorithm (per `.planning/research/lyric-to-note-alignment.md` §6)

**What:** Given a left-to-right note stream (with slur start/stop markers on each note) and a left-to-right syllable list, produce a `w:` token stream where each note gets either a syllable or an `_` (continuation).

**When to use:** Once, in `scripts/convert-crimond-musicxml.ts`, against the de Boer MusicXML and the hard-coded Psalm 23 stanza-1 syllable list.

**Pseudocode (canonical):**
```typescript
// Source: .planning/research/lyric-to-note-alignment.md §6 + de Boer src/lyrics.ts:92-101
//  - de Boer's implementation handles 2-note slurs ONLY (TODO comment in his source
//    re: triplets / 3-note slurs). Crimond uses only 2-note slurs per the worked
//    example in §8, so this limitation does not apply here. Document the
//    limitation in the script header.

function buildWTokens(notes: Note[], syllables: string[]): string[] {
  const tokens: string[] = []
  let si = 0
  let i = 0
  while (i < notes.length) {
    const syll = syllables[si]
    if (syll === undefined) {
      // safety: more notes than syllables — pad with _ to be safe;
      // the validator (countNoteHeads vs w-token-count) will flag if this happens
      tokens.push('_')
      i++
      continue
    }
    tokens.push(syll)
    if (notes[i].startsSlur) {
      // skip every note covered by the slur
      let j = i + 1
      while (j < notes.length && !notes[j-1].endsSlur) {
        tokens.push('_')
        j++
      }
      // j is now AT the note that ended the slur — advance one past it
      // for the 2-note slur case (Crimond) this equates to skipping 1 note
      i = j
    } else {
      i++
    }
    si++
  }
  return tokens
}
```

**Output for Crimond phrase 1 (per doc §8 worked example):**
```
w: The Lord's my _ shep herd, _ I'll not want;
```

### Pattern 2: NotationRenderer Branch Point — Embedded-`w:` Detection

**What:** Inside the `unifiedAbc` useMemo in `NotationRenderer.tsx` (current file: lines 661-857), the inner loop iterates `visiblePhraseIndices`. For each phrase, the code currently:
1. Strips any pre-existing `w:` lines from the phrase body (`cleanedBody`, line 789)
2. Calls `wLinesForPhrase(i)` → `mapCycleToPhraseSyllableLines` to produce raw stanza text
3. Calls `wLineForSyllables(text, i)` which delegates to `buildWLineFromSolfa` (if `solfegeOcrText` available) or `syllabifyForAbc`

**Insertion point:** Between steps 1 and 2, branch on `hasEmbeddedWLines(phraseBody)`:
- **If true (NEW path):** extract the original `w:` line(s) from the unstripped body. For the visible cycle that is stanza-1 (the only stanza we have lyrics for in the source ABC), emit the original `w:` line verbatim. For stanza 2+ on the same tune, fall back to the OLD path (heuristic) for that stanza.
- **If false (OLD path):** existing behaviour unchanged.

**Cite:** NotationRenderer.tsx lines 775-852 (the per-phrase loop in `unifiedAbc`).

**Critical detail:** The current code feeds music sub-lines (split on bar lines) through `padWLineToNoteCount`. The embedded-`w:` path must respect the same sub-staff split — i.e. when `splitMusicIntoSubLines(phraseBody, n)` produces 2 sub-staves for a phrase, the embedded w-line for that phrase must be re-split proportionally across the 2 sub-staves (or the embedded path must use `targetSubdivisions = 1` for embedded-lyric phrases). Recommend: for the embedded path, use a single sub-staff per phrase to keep the mapping 1:1 with the source-authored w-line, and rely on `responsive: 'resize'` to fit. Verify visually in dev-preview before locking.

## Common Pitfalls

### Pitfall 1: xml2abc emits chord notation `[FA]` and other multi-voice artefacts
**What goes wrong:** xml2abc may output bracketed chord notation, MIDI directives, or %%score headers that abcjs handles fine in 4-voice rendering but may interact weirdly with single-soprano rendering.
**Why it happens:** xml2abc is general-purpose and preserves source structure.
**How to avoid:** Use `extractMelodyVoice` (proven pattern in `scripts/extract-soprano-to-abc-notation.ts`). Strip `[...]` chord brackets and keep only the top note if any remain post-extraction.
**Warning signs:** abcjs renders multiple notes per beat; or note count doesn't match the source's soprano line.

### Pitfall 2: PHRASE_BREAK positions diverge between heuristic [8,14,22] and de Boer's printed line breaks
**What goes wrong:** Tune renders correctly note-for-note but staff-row line breaks don't match the iOS reference, putting "not want;" on the wrong row.
**Why it happens:** Doc §8 notes the current heuristic truncates the second melisma at the phrase-1 boundary (note 8 vs. note 10).
**How to avoid:** Inspect de Boer's MusicXML for `<system-break>` markers OR derive breaks from his measure groupings; document the chosen positions in the script header; verify in dev-preview before applying to DB. **Flagged as open question O-2 below.**
**Warning signs:** Visual diff shows row layout differing from the iOS reference even though all syllables are present.

### Pitfall 3: Embedded w-line gets re-syllabified
**What goes wrong:** The NEW path forgets to strip the w-line from the phrase body before passing to xml2abc-derived music; OR the renderer's `cleanedBody` step (line 789) strips the embedded w-line as it does today, leaving the OLD path's `syllabifyForAbc` to run on the stripped result.
**Why it happens:** Existing code at NotationRenderer.tsx:789 unconditionally drops w-lines. The new branch must consume the w-line BEFORE this strip happens.
**How to avoid:** In the new branch, extract w-lines from `phraseBody` (pre-cleanedBody) and bypass `wLineForSyllables` entirely.
**Warning signs:** Lyrics under the notes match what `syllabifyForAbc` would have produced, not what the de Boer source authored.

### Pitfall 4: NotationRenderer sub-staff splitting breaks the source w-line alignment
**What goes wrong:** `splitMusicIntoSubLines` slices the music body at bar lines into 2+ sub-staves for chromeless/mobile views. The embedded w-line was authored against the WHOLE phrase, not each sub-staff. Result: lyrics on the first sub-staff only; second sub-staff has notes but no lyrics.
**Why it happens:** The proportional `splitWLineIntoChunks` path (NotationRenderer.tsx:728) assumes a single w-line to split; it works for `syllabifyForAbc` output but the embedded w-line carries `_` continuations that don't split on whitespace cleanly.
**How to avoid:** For the embedded path, force `targetSubdivisions = 1` (no sub-staff split), or implement a note-aware splitter that re-aligns w-tokens to sub-staves by counting note heads per sub-staff. Recommend force-1 for the pilot — simpler — and verify visually that the line still fits the viewport at 375px.
**Warning signs:** Mobile staff view shows lyrics under the first half of a phrase only.

### Pitfall 5: `LENGTH(abc_notation)` regression in DB sanity checks
**What goes wrong:** The current Crimond abc_notation is 183 chars (no w-lines). The new value will be substantially longer (~300-500 chars with embedded w-lines). Any test that asserts string length will fail.
**Why it happens:** Defensive length assertions.
**How to avoid:** Search the codebase for `abc_notation.length` / `LENGTH(abc_notation)` assertions before applying. (Quick `grep` suggests none — but verify.)
**Warning signs:** A test fails post-DB-update that wasn't expected to.

### Pitfall 6: Multi-stanza behaviour confused
**What goes wrong:** Psalm 23 has 6 stanzas. The embedded w-line is for stanza 1 only. The NotationRenderer currently renders up to 3 stanzas per page (`CYCLES_PER_PAGE = 3`); stanzas 2 and 3 will also need w-lines.
**Why it happens:** The pilot scope is "one tune", but a tune is rendered with multiple stanzas.
**How to avoid:** In the NEW branch, when rendering stanza index > 0, fall back to the OLD path (`wLineForSyllables`) for that stanza. This means stanza 1 uses the verified de Boer alignment; stanzas 2-6 use the existing heuristic. Acceptable for the pilot since the user's sing-test is presumably stanza 1.
**Warning signs:** Stanzas 2+ render with mis-aligned syllables on Psalm 23.

### Pitfall 7: Test framework / Vitest pulls in browser-only modules
**What goes wrong:** Importing `NotationRenderer` (which is `'use client'` and uses abcjs) into a Vitest unit test triggers a JSDOM module-resolution error.
**Why it happens:** abcjs touches DOM directly.
**How to avoid:** Unit-test only the pure pieces — the slur-walk algorithm, the `hasEmbeddedWLines` helper, the conversion script's intermediate outputs. Render verification stays in Playwright.
**Warning signs:** `Cannot find module 'abcjs'` or `document is not defined` in Vitest.

### Detect embedded `w:` lines in a phrase body
```typescript
// src/lib/abc-embedded-lyrics.ts (NEW)
// Pure module — no DOM, no abcjs. Safe for SSR and unit tests.

/**
 * True iff the given phrase body (a string from splitOnPhraseBreaks().phrases[i])
 * contains at least one `w:` line. Used by NotationRenderer to opt into the
 * verified-MusicXML rendering path for Crimond (Phase 04.10) — when present,
 * the heuristic w-line construction (buildWLineFromSolfa / syllabifyForAbc) is
 * skipped and the source-authored lyrics are rendered verbatim.
 */
export function hasEmbeddedWLines(phraseBody: string): boolean {
  return /^\s*w:/m.test(phraseBody)
}

/**
 * Returns the `w:` line(s) in order from a phrase body. Strips the `w: ` prefix.
 * Each returned string is the raw lyric payload as authored in the source ABC.
 */
export function extractEmbeddedWLines(phraseBody: string): string[] {
  return phraseBody
    .split('\n')
    .map((l) => l.trim())
    .filter((l) => /^w:/.test(l))
    .map((l) => l.replace(/^w:\s*/, ''))
}
```

### Conversion script skeleton

```typescript
// scripts/convert-crimond-musicxml.ts (NEW)
import 'dotenv/config'
import { readFileSync, writeFileSync } from 'node:fs'
import { execSync } from 'node:child_process'
import { drizzle } from 'drizzle-orm/postgres-js'
import postgres from 'postgres'
import { eq } from 'drizzle-orm'
import * as schema from '../src/db/schema'
import { extractMelodyVoice } from '../src/lib/abc-voice-extract'
import { insertPhraseBreaks, getSplitPointsForMeter } from './annotate-phrase-breaks'
import { splitOnPhraseBreaks, countNoteHeads } from '../src/lib/abc-phrases'

const SOURCE = '.planning/research/abc-samples/Crimond.musicxml'

// Psalm 23 stanza 1 syllable list per .planning/research/lyric-to-note-alignment.md §8
const PSALM_23_STANZA_1: string[] = [
  'The', "Lord's", 'my', 'shep-', '-herd,', "I'll", 'not', 'want;',
  'he', 'makes', 'me', 'down', 'to', 'lie',
  'in', 'pas-', '-tures', 'green,', 'he', 'lead-', '-eth', 'me',
  'the', 'qui-', '-et', 'wa-', '-ters', 'by.',
] // 28 syllables = 8+6+8+6 = CM

async function main() {
  // 1. Run xml2abc
  const satb = execSync(`python3 scripts/xml2abc.py ${SOURCE} -o /tmp/crimond.abc && cat /tmp/crimond.abc`)
    .toString('utf-8')

  // 2. Extract soprano
  const soprano = extractMelodyVoice(satb) // existing helper

  // 3. Parse the MusicXML directly to get slur map (~30 LOC walker over <note><slur>)
  const slurMap = parseSlursFromMusicXml(readFileSync(SOURCE, 'utf-8'))

  // 4. Walk soprano notes + slurMap + PSALM_23_STANZA_1 → wTokens (per §6 algorithm)
  const wTokens = buildWTokens(slurMap, PSALM_23_STANZA_1)

  // 5. Insert PHRASE_BREAK markers (CM → 4 phrases)
  const phrased = insertPhraseBreaks(soprano, 4, getSplitPointsForMeter('CM', 4))

  // 6. Weave wTokens into the body, one w: line per phrase
  const final = weaveWLinesIntoPhrases(phrased, wTokens)

  // 7. Validate
  const split = splitOnPhraseBreaks(final)
  for (let i = 0; i < split.phrases.length; i++) {
    const heads = countNoteHeads(split.phrases[i])
    const wTokenCount = countWTokens(split.phrases[i]) // helper
    if (heads !== wTokenCount) {
      throw new Error(`phrase ${i}: ${heads} notes vs ${wTokenCount} w-tokens`)
    }
  }

  // 8. Write fixture and optionally apply
  writeFileSync('.planning/research/abc-samples/crimond-verified.abc', final)
  console.log(final)
  if (process.argv.includes('--apply')) {
    const sql = postgres(process.env.DATABASE_URL!)
    const db = drizzle(sql, { schema })
    await db.update(schema.tunes).set({ abcNotation: final }).where(eq(schema.tunes.name, 'Crimond'))
    await sql.end()
    console.log('Applied to tunes.name=Crimond (id=30)')
  }
}
main().catch(e => { console.error(e); process.exit(1) })
```
