  <context>
    Psalm 23 has 6 metrical stanzas. The de Boer Crimond.musicxml has no lyrics —
    we hard-coded stanza-1 syllables into the conversion script (Plan 02). The
    resulting `crimond-verified.abc` has w-lines for the first stanza only.

    The renderer paginates stanzas (CYCLES_PER_PAGE = 3). When the user navigates
    to stanza 2 of Psalm 23, the question is what to render.

    User outcome differences:
    - Option A: Stanza 1 uses verified de Boer alignment; stanzas 2-6 fall back to
      the existing heuristic (buildWLineFromSolfa / syllabifyForAbc). User sees
      verified alignment on the FIRST stanza only — stanzas 2-6 look the way the
      production page looks today.
    - Option B: Hard-fail / hide stanzas 2-6 until per-stanza w-lines exist.
      User sees only stanza 1 and cannot page forward.
    - Option C: Re-use stanza-1 w-tokens for stanzas 2-6 (substitute the stanza's
      own syllable text on each note position the same way as stanza 1's alignment).
      Requires the renderer to know "this is a verified-aligned tune" and to mechanically
      re-align stanza-N text against stanza-1's token shape.
  </context>
  <options>
    <option id="option-a">
      <name>Stanza 1 verified, stanzas 2-6 heuristic fallback</name>
      <pros>Pilot scope is honoured — "verify one tune end-to-end". User sing-test predicate (per ROADMAP) is most naturally about stanza 1 / the first page. Lowest implementation complexity in NotationRenderer.</pros>
      <cons>Stanzas 2-6 of Psalm 23 may have visible mis-alignment compared to stanza 1 (the very mis-alignment this pilot is meant to fix). Must be documented as a known pilot limitation.</cons>
    </option>
    <option id="option-b">
      <name>Hide stanzas 2-6 entirely for Crimond</name>
      <pros>No mis-alignment visible. Forces the issue back to data — future phases must add per-stanza w-lines.</pros>
      <cons>Worse UX than the status quo for Psalm 23 (which today shows all 6 stanzas). Breaks the pagination contract. Likely rejected by user.</cons>
    </option>
    <option id="option-c">
      <name>Mechanically re-align stanzas 2-6 against stanza-1 token shape</name>
      <pros>Best UX — all 6 stanzas render with verified alignment.</pros>
      <cons>Requires a per-stanza syllable re-walker that respects the `_` continuation positions from stanza 1. Substantial new code in the renderer. Out of scope for a pilot. Defer to a follow-up phase.</cons>
    </option>
  </options>
  <resume-signal>Select: option-a, option-b, or option-c</resume-signal>
