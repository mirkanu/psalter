# Phase 04.10 — Pilot Conclusion: Failed Usefully

Plan 05's sing-test gate exposed not just two defects in the rendered output but a deeper framing error in the entire phase scope. Phase 04.10 is **not** marked complete in the success sense. It is **concluded** as a pilot whose negative result clears the way for Phase 04.11.

## The framing error

Phase 04.10 was scoped as **"Verified MusicXML Pilot (Crimond/Ps23)"** — the assumption being that authoritative ABC must be regenerated from MusicXML to be trustworthy. That assumption is wrong on two counts:

1. **The notes were already correct.** Crimond's pre-phase ABC had correct pitches, durations, and bar structure. The *only* thing missing was melisma data (the `_` continuation tokens in `w:` lines that mark held-note text-setting). Regenerating the whole ABC from MusicXML threw out known-good data and introduced regressions (note 3 vs note 4 duration drift; "down to" syllable cascade — see Defects below).

2. **MusicXML doesn't scale to all ~150 tunes.** Even if the converter had been perfect, the per-tune migration recipe added to `tune-digitisation-research.md` requires hunting MusicXML per tune. Most tunes don't have one. The melisma data already lives in the project — in the **original solfège JPG scans** — and the OCR pipeline currently throws the underlines away (per `CLAUDE.md` hard rule #3: "the current solfège OCR pipeline lost underline data... All current `*-melisma*` code is heuristic compensation, not canonical detection. Plan accordingly").

Phase 04.10 didn't plan accordingly. It went around the problem instead of fixing it at the source.

## Defects observed (kept here for posterity — not the actionable items)

Both defects co-located at the same point in the score, supporting "single root cause in the converter":

**Defect 1 — Syllable alignment breaks at "down to" (end of stanza 1, line 2).** First ~14 notes perfect, then all syllables wrong from "down" onward. Cascades from Defect 2.

**Defect 2 — Note 3 renders slightly longer than note 4 (should be identical).** MusicXML `<duration>` / `<divisions>` math drifted in the converter. Original ABC had them equal.

Neither needs fixing in 04.10. Both disappear when the DB is rolled back to the original ABC.

## Why this pilot was still valuable

- Proved the embedded-w-line runtime path works (NotationRenderer + w-branch decision module are correct).
- Forced the framing question to surface: "where does melisma data come from?" — answered definitively: **solfège underlines, re-OCR'd**.
- Established the test infrastructure (Playwright UAT scripts, baseline sha256, regression negative-control) that 04.11 will reuse per-tune.
- The sing-test gate worked exactly as designed — caught the defects automation couldn't.

Phase 04.11 scope (subject to the discuss-phase): **"Solfège underline OCR → universal melisma extraction"**.

Topics for the discuss-phase to nail down:

- Claude Vision OCR prompt that **preserves** underlines (the current prompt deliberately discards them — needs rewriting)
- How to handle ambiguous underlines (faint print, scan artifacts, joined-vs-separate underlines under adjacent syllables)
- What to do with tunes whose source JPG is missing or low-quality
- Output format: emit `_` continuation tokens into each tune's `abc_notation` directly, or store melisma data as a separate column and merge at render time?
- Verification gate per tune family (CM/LM/SM/CMD): not feasible to sing-test all 150 tunes individually — needs a sampling strategy
- Migration path: rewrite all 150 `tunes.abc_notation` rows in one batch with a documented rollback, or progressive per-meter rollout?
