# Plan 15.1-02: PsalmListingGrid hydration-cost reduction

## Goal

After this plan, the `src/components/PsalmListingGrid.tsx` component performs a single batched `localStorage` read (instead of 5 separate ones) and defers the search-input autofocus + `useMediaQuery` listener until after the hydration effect completes. After commit + rebuild, the **bootup-time scripting cost** of the chunk that holds PsalmListingGrid drops measurably in the next Lighthouse re-run, AND the **CLS** on `/psalms` drops from 0.095 to ≤ 0.05.

**Concrete must-have truth (verifiable post-execution):**
- `grep -c "useLocalStorage" src/components/PsalmListingGrid.tsx` returns `0` (the 5 `useLocalStorage(...)` calls are all replaced by a single batched `useEffect`).
- `npm test -- src/components/PsalmListingGrid.test.tsx` exits 0 (regression — the component still behaves identically with the new hydration code).
- `npm run build && grep -c "PsalmListingGrid\|m.PsalmListingGrid" .next/server/app/psalms/page.js` returns `≥ 1` (the chunk still exists, just lighter).

## Background — what we are fixing

The Phase 15 Lighthouse JSON (`15-lighthouse-psalms.json`) shows the chunk that holds PsalmListingGrid (filename hash `0uqgm3y7qfyr6.js`, 137 KB transferSize, 37900 bytes over the wire) contributing **2518ms of scripting time** and **78% of the chunk's total CPU time spent on script evaluation**. The chunk loads on `/psalms` and (transitively via PsalmPickerModal — fixed in Plan 15.1-01) on psalm-detail. The current `PsalmListingGrid.tsx` source:

- Calls `useLocalStorage` 5 times (lines 86-90), each of which fires its own `useEffect` on mount and reads a separate localStorage key.
- Calls `useMediaQuery('(max-width: 639px)')` separately (line 105), which sets up a `matchMedia` listener on mount.
- Fires `useEffect(() => { setSelectedIndex(0) }, [trimmedQuery, meterFilter])` (line 116) — runs on every render where trimmedQuery or meterFilter changes (including the very first render where trimmedQuery starts as `''`).
- Has a desktop-only autofocus `useEffect` (lines 107-111) that runs synchronously on mount and calls `.focus()` on the search input.

Each of those hooks adds work to the first-paint-to-LCP window. The 5 localStorage reads in particular are 5 separate `JSON.parse` round-trips. The fix is to batch the reads into a single `useEffect` (one parse, one re-render after hydration), and to gate the search-focus + useMediaQuery listeners on a `hydrated` flag.

CLS 0.095 on `/psalms` is the second-largest contributor to the perf score. The current Suspense fallback for `PsalmListingGridClient` is the `PsalmsLoading` skeleton (72 boxes). When the lazy chunk loads, the real 150-box grid mounts and shifts the page down by ~12px if the skeleton's row heights don't perfectly match the real grid's row heights. The fix is to ensure the real grid renders at its final dimensions on its FIRST paint (no post-mount re-render that changes box dimensions). The most common cause of post-mount box-dimension change is the `isNarrowViewport` flag flipping from `false` (SSR default) to `true` (after matchMedia fires) — which swaps the long search placeholder for a short one. The `placeholder` swap doesn't change the box, but the `hasAdvancedFilter` check at line 175 (also a useEffect) auto-opens the advanced filter panel on mount, which DOES change layout.

function updatePersisted<K extends keyof typeof persisted>(
  key: K,
  value: (typeof persisted)[K],

}
