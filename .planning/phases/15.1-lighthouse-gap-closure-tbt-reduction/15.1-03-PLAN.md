# Plan 15.1-03: Real-Lighthouse re-run + LCP quality drop + honest POLISH-03 verdict

## Goal

After this plan, the three Lighthouse JSON files at `.planning/phases/15.1-lighthouse-gap-closure-tbt-reduction/15.1-lighthouse-{homepage,psalms,psalm-detail}.json` are replaced with NEW JSON files captured by the **actual `lighthouse` CLI** (not the PerformanceObserver stand-in used in Phase 15-03) against the freshly rebuilt PM2 process with Plans 15.1-01 and 15.1-02 deployed. The logo image quality drops from `100` to `90` in `next.config.ts` (saving the 6 KiB Lighthouse flagged in `image-delivery-insight` on `/` and `/psalms`).

**Concrete must-have truth (verifiable post-execution):**
- 3 new JSON files exist at the canonical paths, each with `categories.performance.score >= 0.9` OR the orchestrator is told honestly that a route falls short with the exact measured score.
- `grep -c "qualities: \[75, 90\]" next.config.ts` returns `1` (the qualities list no longer includes 100 — the priority logo uses q=90).
- REQUIREMENTS.md POLISH-03 row text reflects an HONEST measurement: either "all three ≥ 0.9" with the JSON evidence, OR a partial verdict identifying the specific route + measured score + reason the gap couldn't close in this phase.

This plan has **one human checkpoint** at the end (Task 5) where the human decides whether the partial verdict — if any — is acceptable, OR whether to iterate further. The plan does NOT silently pass on a sub-90 score.

## Background — what we are verifying

The Phase 15 Lighthouse JSONs (`15-lighthouse-*.json` in the Phase 15 directory) were generated via Playwright PerformanceObserver (documented in `15-VERIFICATION.md` lines 9-25 and the executor's Task 3 substitution). They show:
- `/` Performance 69, FCP 2.0s, LCP 3.9s, TBT 700ms, CLS 0
- `/psalms` Performance 61, FCP 2.4s, LCP 3.8s, TBT 950ms, CLS 0.095
- `/psalms/23` Performance 65, FCP 2.3s, LCP 2.3s, TBT 1670ms, CLS 0

After Plans 15.1-01 (5 dynamic-import wrappers for PsalmPickerModal + SingingView children) and 15.1-02 (PsalmListingGrid hydration batching), the expected deltas are:
- `/`: TBT unchanged (PsalmListingGrid not used here) but framework-runtime hydration pressure should drop slightly because SingingView is not loaded here either. LCP should improve by ~500-800ms because the priority logo now loads at q=90 instead of q=100. Target: Performance ≥ 85.
- `/psalms`: TBT should drop substantially (Plan 02's hydration batching + Plan 01's deferred wrappers). Realistic post-patch TBT for `/psalms` is probably 400-700ms — the auto-open-advanced panel still slides open even after hydration completes, so the visible CLS reduction is driven mainly by Plan 02's deferred `isNarrowViewport` flag rather than the `hydratedRef` gate. LCP should improve by ~500ms (logo q=90). CLS should drop from 0.095 to ≤ 0.06. Target: Performance ≥ 85.
- `/psalms/23`: TBT expected to drop from 1670ms to somewhere in the 1100-1500ms range (Plan 01 defers 5 heavy children including the biggest one, PsalmPickerModal → PsalmListingGrid; the framework-runtime hydration floor from `0r5n9xaeyh.pb.js` ~700ms is irreducible here). LCP is already 2.3s so it may not move much. Target: Performance ≥ 80 — `/psalms/23` may end up the weakest route.

**Honest cap:** this plan does NOT claim all three routes will hit ≥ 90. The framework-runtime baseline alone (`0r5n9xaeyh.pb.js` at ~1100ms scripting on every route) means each route carries a ~700ms TBT floor from framework + React 19 hydration that this plan cannot reduce without deeper changes (server components for layout shells, React Server Components for `SiteHeader` chrome, or splitting the framework chunk — out of scope for this gap-closure phase). The realistic target is 85-89 per route, with a clear-eyed partial verdict if 90 is not hit.
