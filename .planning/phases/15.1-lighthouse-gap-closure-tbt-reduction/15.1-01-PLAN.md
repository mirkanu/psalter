# Plan 15.1-01: Dynamic-import wrappers for PsalmPickerModal + SingingView heavy children

## Goal

After this plan, the eager imports `PsalmPickerModal`, `PsalmTopBar`, `OnboardingTour`, `TuneSwitcherSheet`, and `GearPopover` inside `src/components/singing/SingingView.tsx` are replaced with thin `'use client'` `next/dynamic({ ssr: false })` wrappers. Each wrapper adds a Suspense fallback so no CLS is introduced. After commit + rebuild, the **psalm-detail bootup-time** breakdown shows the `0uqgm3y7qfyr6.js` scripting-time dropping from the current 102ms (psalm-detail chunk) and the unattributable long-task at startTime=1105ms dropping by an equivalent amount, because the PsalmListingGrid code path (eagerly pulled by PsalmPickerModal) no longer ships in the psalm-detail initial bundle.

**Concrete must-have truth (verifiable post-execution):**
- `grep -c "import { PsalmPickerModal } from '@/components/PsalmPickerModal'" src/components/singing/SingingView.tsx` returns `0` (the eager import is gone — replaced by `PsalmPickerModalClient`).
- `grep -c "import { TuneSwitcherSheet } from './TuneSwitcherSheet'" src/components/singing/SingingView.tsx` returns `0` (replaced by `TuneSwitcherSheetClient`).
- `npm run build && grep -c "dynamic" .next/server/app/psalms/\[id\]/page.js` returns `≥ 5` (the new dynamic-import boundaries emit Next's `__next_require__` lazy markers in the server bundle for the psalm-detail page).

## Background — what we are fixing

The Phase 15 Lighthouse JSON (`15-lighthouse-psalm-detail.json`) shows TBT 1670ms on `/psalms/23` and bootup-time contribution from chunk `0uqgm3y7qfyr6.js` of 102ms scripting + 30ms unattributable (the psalm-detail page's own chunk). The bigger problem on `/psalms/23` is the framework runtime's 888ms / 577ms / 165ms long-tasks from `0r5n9xaeyh.pb.js` — these are framework runtime + SingingView's eager child-component hydration. Plan 15-01 deferred only `PlayMiniBar`; **the other 5 eager imports inside SingingView still ship in the psalm-detail initial bundle**.

Specifically:
- `PsalmPickerModal` (line 12 of `src/components/singing/SingingView.tsx`) eagerly imports `PsalmListingGrid` (498 LoC, 5 useLocalStorage hooks, 5 lucide icons, the `Dialog` shadcn UI). Even though the modal only opens on user tap (it sits at `open={psalmSelectorOpen}`), its full code path is in the initial bundle. **This is the single biggest psalm-detail win.**
- `TuneSwitcherSheet` pulls `TieredTuneRowList` and the Sheet UI.
- `GearPopover` pulls 6+ lucide icons, the Popover UI, and `useRouter`.
- `OnboardingTour` is a one-time tour shown after several seconds.
- `PsalmTopBar` (top chrome) — useful but the only client component pulling `useEffect`+`useLayoutEffect`+`useTransition` for keyboard nav. **Lower priority but still deferrable.**

```tsx
'use client'

import dynamic from 'next/dynamic'
import { Suspense } from 'react'
import type { ComponentProps } from 'react'
import type { PsalmPickerModal } from './PsalmPickerModal'

const LazyPsalmPickerModal = dynamic(
  () => import('./PsalmPickerModal').then((m) => m.PsalmPickerModal),
  { ssr: false },
)

export type PsalmPickerModalProps = ComponentProps<typeof PsalmPickerModal>

/**
 * Dynamic-import wrapper for PsalmPickerModal. Deferrs the modal's full
 * dependency tree (PsalmListingGrid + useLocalStorage hydration + lucide
 * icons + Dialog UI) off the initial psalm-detail bundle. Modal renders
 * nothing visible on mount (`open={false}` until user taps picker), so
 * the Suspense fallback is a hidden sentinel — guarantees no CLS when
 * the modal is finally opened.
 */
export function PsalmPickerModalClient(props: PsalmPickerModalProps) {
  return (
    <Suspense fallback={null}>
      <LazyPsalmPickerModal {...props} />
    </Suspense>
  )
}
```
