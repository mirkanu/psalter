# Phase 04.9.15 Plan 04: Inline Staff Explicit-Approval Gating Summary

Gated inline (non-split) Staff notation behind an EXPLICIT `tuneMelismaDecisions.status === 'approved'` check for the active tune, rebuilding the `melismaStatus` data-layer plumbing that quick-task 260712-lcg had deleted (that removal targeted inline Solfège, which stays permanently disabled for a different reason — abcjs has no tonic sol-fa support). Non-approved tunes now show a disabled, tooltip-labeled Inline button in the Gear popover, and any navigation path that would otherwise land the user in inline Staff on a non-approved tune instead falls back to Split-Leaf with a one-time locked toast.

## What Was Built

**`src/lib/inline-staff-gating.ts`** — pure module (no React/DB/next imports), three functions:
- `resolveStaffInlineApproved(status)` — `true` only for the literal string `'approved'`; `null`, `'not_approved'`, `undefined`, and any other string all resolve to `false`.
- `computeInlineLayoutDisabled({ isStaff, staffInlineApproved, solfegeInlineAvailable })` — Staff branch checks `staffInlineApproved`; non-Staff (Solfège) branch is byte-for-byte the pre-existing `!solfegeInlineAvailable` check.
- `shouldFallbackToSplit({ viewMode, staffInlineApproved })` — `true` only when `viewMode === 'staff'` (not `'staff-split'`) and the tune is not approved.

**`src/lib/inline-staff-gating.test.ts`** — 13 vitest cases covering every documented `<behavior>` case from the plan (approval resolution for all four input classes, both branches of the layout-disabled computation, and all four fallback scenarios including the "already split — no toast" and "solfège view — not gated by this check" negatives).

**`src/db/queries/tunes.ts`**:
- Added `MelismaStatus` type and `fetchTuneMelismaStatus(tuneId)` — single-tune latest-non-null-status lookup (mirrors the existing `/api/dev/melisma-decision` route's query shape).
- Added `melismaStatus: MelismaStatus | null` to the `AlternateTune` interface.
- `fetchTunesByMeter` now batch-fetches the latest non-null status for every returned tune ID in a single `inArray` query, builds a `Map<tuneId, status>`, and attaches `melismaStatus` to each returned `AlternateTune`.

**`src/components/singing/GearPopover.tsx`**:
- New required prop `staffInlineApproved: boolean`.
- `inlineLayoutDisabled` now computed via `computeInlineLayoutDisabled({ isStaff, staffInlineApproved, solfegeInlineAvailable })` instead of the old `!isStaff && !solfegeInlineAvailable`.
- Inline button `title` is now conditional: `"Inline Staff notation isn't approved for this tune yet"` when `isStaff`, else the pre-existing `"Inline Solfège coming soon"`.
- `handleLayoutChange` gained a defensive early-return guard for `layout === 'inline' && isStaff && !staffInlineApproved` (belt-and-suspenders alongside the `disabled` attribute).

**`src/components/singing/SingingView.tsx`**:
- Derives `staffInlineApproved = resolveStaffInlineApproved(activeTune?.melismaStatus ?? null)` from the active tune.
- Passes `staffInlineApproved` to `<GearPopover>`.
- New fallback effect: when the user (via navigation, tune switch, or a stale localStorage restore) ends up with `viewMode === 'staff'` on a non-approved tune, calls `setViewMode('staff-split')` and fires the locked toast (default sonner styling — no `richColors`/variant). Guarded by `lastFallbackTuneIdRef` (keyed to the active tune's id) so the toast fires exactly once per transition into this state, not on every render while the state persists.

**`src/app/psalms/[id]/page.tsx`** — the inline-built `primaryTune` IIFE is now `async` and calls `fetchTuneMelismaStatus(primaryTuneRow.id)`, attaching the real status. `alternateTunes` already carry `melismaStatus` via `fetchTunesByMeter`'s spread (no change needed there).

**`src/app/precent/[id]/sing/[pos]/page.tsx`** — `buildTuneOption` now returns `melismaStatus: (tune.melismaStatus ?? null)`. A `primaryTuneNeedsMelismaStatus` flag (see Deviations) is set only when `primaryTune` was built via `buildTuneOption(primaryTuneRow)` (both the `item.tuneId` fallback branch and the no-`item.tuneId` branch), and in that case the real status is fetched afterward via `fetchTuneMelismaStatus` and merged in. The `assignedInAlternates` path is left untouched since it already carries the batch-fetched real status.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Plan's suggested primaryTune melismaStatus backfill check would never fire**
- **Found during:** Task 3, wiring `precent/[id]/sing/[pos]/page.tsx`
- **Issue:** The plan specified: (a) `buildTuneOption` should default `melismaStatus: (tune.melismaStatus ?? null)`, and (b) a follow-up check `if (primaryTune && primaryTune.melismaStatus === undefined)` should then backfill the real status via `fetchTuneMelismaStatus`. Since (a) always coerces the field to `null` (never leaves it `undefined`), the `=== undefined` guard in (b) can never be true — the real status would never actually be fetched for any primary tune built via `buildTuneOption`, silently defaulting every such tune to `melismaStatus: null` (i.e. permanently gated off) regardless of its true approval status.
- **Fix:** Replaced the `undefined`-check with an explicit `primaryTuneNeedsMelismaStatus` boolean, set to `true` only at the two `buildTuneOption(primaryTuneRow)` call sites (the `item.tuneId` fallback branch and the no-`item.tuneId` branch). The `assignedInAlternates` path (which already carries the correct batch-fetched status from `fetchTunesByMeter`) is left alone, avoiding a redundant DB round-trip.
- **Files modified:** `src/app/precent/[id]/sing/[pos]/page.tsx`
- **Commit:** d09df44

Otherwise, plan executed as written.
