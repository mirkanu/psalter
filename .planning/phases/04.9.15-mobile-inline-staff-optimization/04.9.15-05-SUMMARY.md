## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] First fix attempt (staffWidthFactor neutralization) had no material effect — corrected via root-cause re-diagnosis**
- **Found during:** Task 2, post-rebuild verification
- **Issue:** The plan's hypothesis (and RESEARCH.md's Assumption A2) was that chromeless inline Staff's narrowed `staffWidthFactor` (0.55/0.85) was causing abcjs's non-last-line auto-stretch to short-circuit against too-small a target. Neutralizing the factor to 1 (mirroring the 260712-kov split-leaf fix) was implemented, but live measurement (before/after diagnostic runs, then direct SVG `getBBox()` inspection via a throwaway Playwright script) showed virtually zero change in fill ratio (0.807→0.821). Root cause was actually that every wrapped row's *natural* minimum content width already exceeded any staffwidth target the formula could reasonably produce, so abcjs's compression bottomed out at each row's own floor regardless of the target's value — narrower-content rows simply have a smaller natural floor.
- **Fix:** Reverted the staffWidthFactor neutralization; added abcjs's native `expandToWidest: true` render option instead (gated to the same `staffWidthFactor < 1` signal). This causes abcjs to rerun layout for every row using whichever row's natural content is widest as the shared target, converging all non-last rows to matching widths.
- **Files modified:** `src/components/AbcPlayer.tsx`
- **Verification:** Live diagnostic + direct SVG `getBBox()` inspection before/after on a throwaway dev server (port 3013), then re-confirmed identically on the rebuilt production deployment. Psalm-78 rows went from 303/303/336/336px (spread of 33px) to 337/340/340/340px (spread of 3px).
- **Commit:** `058e629` (supersedes `834c45f`)

**2. [Rule 3 - Blocking] Production build was being killed mid-build on this VPS**
- **Found during:** Attempting the required production rebuild to verify Tasks 1-2 on the live deployment
- **Issue:** `next build` (both Turbopack and webpack) consistently received `SIGTERM` on a build worker partway through compilation. Root cause: this VPS has only 3.7GB RAM with ~2.4GB baseline usage across other services (multiple concurrent Claude Code sessions, other PM2 apps), and swap was already ~100% utilized before the build even started.
- **Fix:** (a) Added `experimental.cpus: 1` to `next.config.ts` to limit build worker concurrency; (b) created and `swapon`'d a temporary 4GB swapfile (`/swapfile-tmp-build`) to give the build breathing room. Neither alone was sufficient; combined, the build completed reliably (~2 min) three times in a row.
- **Files modified:** `next.config.ts`
- **Verification:** Three consecutive successful full production builds (1529 static pages each) after the fix, vs. five consecutive failures before it.
- **Commit:** `7bffebe`
- **Note for user:** `/swapfile-tmp-build` is active (`swapon`) but **not** persisted to `/etc/fstab` — it will disappear on next reboot. Given the chronic memory pressure this session surfaced (swap was already near-full at baseline, independent of this build), consider making this swap permanent or reviewing what's consuming baseline memory (multiple concurrent Claude Code sessions were observed running during this session, which CLAUDE.md's memory hygiene section already advises against).

## Issues Encountered

- The plan's stated acceptance criterion of "worst fill ratio ≥ 0.97" is not reached (current worst-case: 0.898-0.914). Investigation traced the remaining ~9% gap to two **intrinsic, structural** constraints, not a remaining instance of the reported bug: (1) `AbcPlayer`'s own outer `px-2` cosmetic padding (16px of the 375px mobile viewport ≈ 4.3%), and (2) abcjs's own internal SVG viewBox left/right margins that scale down proportionally with everything else (≈5.5%). Both are present on every row equally now (confirmed: all 4 rows render within 1-3px of each other), so the *originally reported* problem — rows 1/2 looking visibly shorter/uneven than rows 0/3 — is fixed. The residual uniform margin is a consistent, symmetric-looking gap rather than the "wasted whitespace" unevenness originally reported. This is flagged explicitly for human visual judgment at the Task 3 checkpoint rather than unilaterally decided by further code changes (removing `AbcPlayer`'s cosmetic padding would be a broader, un-scoped visual change affecting all view modes, not just inline Staff).
