# Phase 04.9.15 Plan 05: Inline-Staff Clef/Key/Time-Signature Shrink + Row-Stretch Fix Summary

**All rows (including row 1) now shrink the clef, key-signature, AND time-signature to 60% as a single tightly-packed group — glyphs AND the gaps between them both compress together — via a post-render SVG transform pass that stays correctly anchored to the staff and reflows the full freed space into the notation; non-last inline-Staff rows are equalized in width via abcjs's native `expandToWidest` option. Verified live on the rebuilt production deployment across four rounds of human feedback.**

### Auto-fixed Issues

**1. [Rule 1 - Bug] First fix attempt (staffWidthFactor neutralization) had no material effect — corrected via root-cause re-diagnosis**
- **Found during:** Task 2, post-rebuild verification
- **Issue:** The plan's hypothesis (and RESEARCH.md's Assumption A2) was that chromeless inline Staff's narrowed `staffWidthFactor` (0.55/0.85) was causing abcjs's non-last-line auto-stretch to short-circuit against too-small a target. Neutralizing the factor to 1 was implemented, but live measurement showed virtually zero change in fill ratio (0.807→0.821). Root cause was actually that every wrapped row's *natural* minimum content width already exceeded any staffwidth target the formula could reasonably produce.
- **Fix:** Reverted the staffWidthFactor neutralization; added abcjs's native `expandToWidest: true` render option instead.
- **Files modified:** `src/components/AbcPlayer.tsx`
- **Verification:** Live diagnostic + direct SVG `getBBox()` inspection. Psalm-78 rows went from 303/303/336/336px (spread 33px) to 337/340/340/340px (spread 3px).
- **Commit:** `058e629` (supersedes `834c45f`)

**3. [Rule 1 - Bug] CSS-only clef/key shrink was vertically misaligned and did not reclaim space — human caught on visual review**
- **Found during:** Task 3 checkpoint, first human review round
- **Issue:** Three problems reported: (a) row 1 wasn't shrinking (per original plan intent, later explicitly overridden); (b) the shrunk clef/key-signature glyphs were not vertically aligned to the staff lines; (c) the horizontal space freed by shrinking was not being used by the notation/lyrics, leaving a visible gap.
- **Root cause:** A static `transform: scale(0.6); transform-origin: left center;` CSS rule has two compounding flaws: percentage-based `transform-origin` on an SVG child element defaults to resolving against the entire multi-row SVG's viewBox (hundreds of units tall) rather than the individual element's own ~30-60-unit bounding box — confirmed live: without an explicit `transform-box: fill-box`, the clef rendered ~60px away from the staff. Even accounting for that, "center" (50%) does not correspond to the staff's actual vertical center for every glyph — the key-signature's own bbox center sat ~24% of its height above the true staff center for one real tune/key. And fundamentally, a CSS transform never changes abcjs's own layout math, so it can only ever shrink the glyph in place, never reclaim the space for other content.
- **Fix:** Replaced the CSS rule with a post-render DOM pass (`applyClefKeySignatureShrink` in `AbcPlayer.tsx`) that, per row: (1) measures the actual staff `getBBox()` to find its true vertical center; (2) for each clef/key-signature element, computes a transform-origin Y-percentage relative to THAT element's own bbox that lands exactly on the staff center, with `transform-box: fill-box` set explicitly so the percentage resolves correctly; (3) computes the horizontal space freed by the scale (which pivots from the left edge) and translates every other element in the row (notes, bars, time signature, lyrics — not the 5 staff lines) left by that amount. Applied uniformly to all rows, not just wrapped rows, per the human's explicit override.
- **Files modified:** `src/app/globals.css` (rule removed), `src/components/AbcPlayer.tsx` (new pass added)
- **Verification:** Live `getBoundingClientRect()` measurement confirmed correct alignment (clef 119.65–143.4 vs. staff 121.02–143.02) and correct space reclaim (first note starts 7-19px after the key-signature's new right edge, vs. what would have been a much larger unclaimed gap at the original clef/key width). Screenshots confirmed visually on both a throwaway dev server and the rebuilt production deployment.
- **Commit:** `dfe9c70`

**4. [User-directed scope growth] Extended shrink+reflow to the time-signature glyph, per follow-up request**

**5. [Rule 1 - Bug] Glyphs shrank but the gaps between them didn't — human caught on Psalm 31 re-review**
- **Found during:** Task 3 checkpoint, third human review round (after the time-signature size was approved)
- **Issue:** User reported the glyph *size* was now correct, but (a) they weren't packed tightly enough to the left, and (b) the space freed by shrinking wasn't visibly going to the notation.
- **Investigation:** Per the user's explicit instruction not to assume, measured the actual gaps live via `getBoundingClientRect()` on `/psalms/31`: an 11.8px gap between clef and key-signature, and a 17.3px gap between key-signature and time-signature — neither had shrunk at all, despite the glyphs themselves being visibly smaller.
- **Root cause:** The previous implementation scaled each glyph INDEPENDENTLY, each pivoting from its own left edge. This only shrinks each glyph's own footprint; the whitespace BETWEEN glyphs (originally sized for full-size glyphs) is a separate, untouched distance between two independently-transformed elements — nothing was closing it. The freed-space calculation compounded this: it only took the rightmost glyph's own shrink amount (via a `max()` over each element's post-shrink right edge), so shrinking the clef and key-signature contributed NOTHING to the total freed width used to shift the notation — only the time-signature's own ~5-unit shrink counted, undercounting the true available space by roughly 7x.
- **Fix:** Rewrote `applyLeadingGlyphShrink` to wrap all leading glyphs found in a row (whichever of clef/key-signature/time-signature exist) in one new `<g>` element, and apply a SINGLE `scale(0.6)` transform to that GROUP — pivoting from the group's own combined bounding-box left edge and the staff's vertical center (same `transform-box: fill-box` technique, applied to the combined bbox instead of each element's own). Because the inter-glyph gaps are just empty space within that combined bounding box, scaling the whole group compresses gaps and glyphs by the identical factor. The freed-width calculation now uses `groupWidth * (1 - scale)` — the group's full original width — correctly capturing every glyph's contribution instead of only the last one's.
- **Files modified:** `src/components/AbcPlayer.tsx`
- **Verification:** Live `getBoundingClientRect()` measurement on the rebuilt production deployment: clef-to-keysig gap 11.8px → ~4px, keysig-to-timesig gap 17.3px → ~4px (both mathematically consistent with the 0.6 scale factor when checked in local SVG units: e.g. clef-to-keysig gap went from 9.97 to 5.98 local units, a ratio of exactly 0.6). First note shifted from x=86.68 to x=65.66 (~21px further left). Vertical alignment unaffected (time-signature center still matches staff center exactly). No regression on psalm-23/78 (identical fill ratios) or unit tests.
- **Commit:** `1c8bdfe`

## Issues Encountered

Investigation traced the remaining ~9-10% gap to two **intrinsic, structural** constraints, not a remaining instance of the reported bug: (1) `AbcPlayer`'s own outer `px-2` cosmetic padding (16px of the 375px mobile viewport ≈ 4.3%), and (2) abcjs's own internal SVG viewBox left/right margins that scale down proportionally with everything else (≈5.5%). Both are present on every row equally (confirmed: all 4 rows render within 1-3px of each other), so the *originally reported* problem — rows 1/2 looking visibly shorter/uneven than rows 0/3 — is fixed. Flagged for human visual judgment rather than unilaterally changed further (removing `AbcPlayer`'s cosmetic padding would be a broader, un-scoped visual change affecting all view modes).
