# Phase 04.9.15: Mobile Inline Staff Optimization - Research

**Researched:** 2026-07-16
**Domain:** abcjs SVG internals (clef/key glyph scaling, row justification), React state decoupling (font-size vs. notation scale), Drizzle/Next.js data-layer gating
**Confidence:** MEDIUM-HIGH (grounded directly in installed `abcjs@6.6.3` source and the live codebase; one UI-SPEC implementation anchor is contradicted by source inspection — see Pitfall 1)

## Summary

This phase is a codebase-grounded delta, not a new feature. All 5 scope items map to code that already exists and was inspected directly: `NotationRenderer.tsx` (1467 lines, the render/scale/layout engine), `AbcPlayer.tsx` (the abcjs mount + render-effect component), `GlassBottomBar.tsx` (the A+/A− control), `GearPopover.tsx` (the existing solfège-inline gating pattern to replicate for Staff), `StanzaList.tsx` (the `.verse-number` reference implementation), and `src/db/schema.ts` + `src/db/queries/tunes.ts` (the `tuneMelismaDecisions` approval table and the `AlternateTune`/`TuneOption` query that currently does NOT surface it).

**Most important correction to the UI-SPEC:** its implementation anchor for item (a) — `.abcjs-staff-wrapper:not(:first-of-type) .abcjs-top-line` — is factually wrong. Direct inspection of `node_modules/abcjs/dist/abcjs-basic.js` shows `abcjs-top-line` is the class of the **topmost of the 5 staff ruling lines** (`src/write/draw/staff.js`), not a clef/key-signature group. The real clef/key classes are `abcjs-staff-extra abcjs-clef` and `abcjs-staff-extra abcjs-key-signature` (from `createClef`/`createKeySignature` in `src/write/creation/`, run through abcjs's `Classes.prototype.generate` which auto-prefixes every token with `abcjs-` and appends a per-line class `abcjs-lN`). The planner must correct the CSS selector accordingly (see Code Examples).

**Item (b)** is a real coupling bug to fix: `GlassBottomBar.tsx`'s A−/A+ buttons currently hardcode `Math.max(8, baseSize-1)` / `Math.min(40, baseSize+1)` (step 1, ceiling 40 — NOT the UI-SPEC's step-2/soft-40/hard-120 contract) and call `onBaseSizeChange`, which is `SingingView`'s `handleBaseSizeChange` → `setBaseSize` → passed straight into `NotationRenderer`'s controlled `baseSize` prop. Inside `NotationRenderer`, `scale = isSplitForScale ? SPLIT_LEAF_NOTATION_SCALE : baseSize / 14` (line 496) — so for `viewMode === 'staff'` (inline, non-split), `baseSize` currently drives BOTH the lyric CSS var (`--staff-base-size`) AND the abcjs render `scale`. This is the exact coupling the phase must break by introducing `INLINE_STAFF_NOTATION_SCALE`, mirroring the `SPLIT_LEAF_NOTATION_SCALE = 1` pattern already shipped in 04.9.14-01.

**Item (c)** is a genuine gap, not a wiring bug: `mapCycleToPhraseSyllableLines` (in `stanza-cycles.ts`) builds inline-Staff `w:` syllable text from `l.text` only — it silently drops `Line.bibleVerseRef` entirely. `StanzaList.tsx`'s `<sup className="verse-number">` pattern cannot be reused verbatim inside a `w:` ABC line, because abcjs renders `w:` text as SVG `<text>` nodes it generates itself, not React DOM — there is no JSX injection point inside an abcjs-rendered lyric line. This is flagged as an open question requiring a design decision before planning (see Open Questions §1).

**Item (d)**: abcjs's own justification math (`calcHorizontalSpacing` in `abcjs-basic.js`) stretches every non-last system to fill `targetWidth` by default — `stretchlast` only special-cases the LAST line. This means the reported "wasted whitespace on rows 1 and 2" is unlikely to be a missing global format flag; it is more likely caused by this codebase's own `effectiveStaffWidth` computation (`AbcPlayer.tsx`'s `targetStaffwidth = (containerWidth * staffWidthFactor) / effectiveScale`) producing a `staffwidth` value abcjs treats as already "near target width" for short/melisma-light phrases, short-circuiting the stretch. This needs live-render (Playwright) verification before finalizing a fix, since the pure-source read is inconclusive on the actual per-tune numbers.

**Item (e)** requires new data-layer plumbing: `tuneMelismaDecisions.status` exists in the DB and is readable via `/api/dev/melisma-decision` (Cloudflare-Access-gated dev route), but the production `AlternateTune`/`TuneOption` type (`src/db/queries/tunes.ts`) and its single fetch function `fetchTunesByMeter` do NOT currently select or join this status at all — the 260712-lcg quick task explicitly removed the melismaStatus fetch from the public page. `GearPopover.tsx`'s existing `inlineLayoutDisabled = !isStaff && !solfegeInlineAvailable` computation is the exact pattern to extend per the UI-SPEC's `isStaff ? !staffInlineApproved : !solfegeInlineAvailable` branch.

**Primary recommendation:** Treat this phase as 5 independent, narrowly-scoped edits across `NotationRenderer.tsx`, `AbcPlayer.tsx`, `GlassBottomBar.tsx`, `GearPopover.tsx`, `stanza-cycles.ts`/`lyrics-structured.ts`, and `src/db/queries/tunes.ts` + both page.tsx call sites. Item (a)'s CSS selector must be re-verified against a live-rendered SVG before implementation (do not trust the UI-SPEC's anchor). Item (c) needs a design decision resolved during planning, not execution (a `w:` line cannot carry a `<sup>`).

### Pattern 1: Controlled-scale decoupling (already shipped once — replicate, don't invent)

**What:** A fixed-value scale constant that bypasses the user-adjustable `baseSize`, used only for the abcjs `scale`, while `baseSize` continues to drive `--staff-base-size` unconditionally.
**When to use:** Any view mode where notation size and lyric size must vary independently.
**Example (existing split-leaf precedent, `NotationRenderer.tsx:488-496`):**
```typescript
// Source: src/components/notation/NotationRenderer.tsx (existing code, lines 488-496)
const isSplitForScale = isSplitMode(viewMode)
const SPLIT_LEAF_NOTATION_SCALE = 1
const scale = isSplitForScale ? SPLIT_LEAF_NOTATION_SCALE : baseSize / 14
```
The phase 04.9.15 fix should extend this ternary to a 3-way branch (split / inline-staff / other):
```typescript
const SPLIT_LEAF_NOTATION_SCALE = 1
const INLINE_STAFF_NOTATION_SCALE = /* fixed viewport-heuristic value — see SingingView's
  existing referenceWidthRef/clamp(baseSize*newWidth/refWidth,8,40) logic, which the UI-SPEC
  says should continue driving inline Staff's notation scale independently of the new
  lyric-only A+/A- range */
const scale = isSplitForScale
  ? SPLIT_LEAF_NOTATION_SCALE
  : viewMode === 'staff'
  ? INLINE_STAFF_NOTATION_SCALE
  : baseSize / 14
```
Note: `SingingView.tsx` ALREADY computes a proportional-zoom value independent of manual A+/A− (`referenceWidthRef` heuristic, lines 178-217) but currently feeds it back into the SAME `baseSize` state that also drives lyrics. The planner must decide whether `INLINE_STAFF_NOTATION_SCALE` becomes a second piece of state in `SingingView` (parallel to `baseSize`) or a derived value computed inside `NotationRenderer` from `viewportW` (which `NotationRenderer` already tracks internally, lines 502-510). The latter avoids new prop plumbing.

### Anti-Patterns to Avoid

- **SVG post-processing to strip/replace clef glyphs:** UI-SPEC explicitly rejects this (fragile, not abcjs-native) — confirmed correct given `abcjs-basic.js`'s clef path is generated fresh on every render via `createClef`, so any DOM mutation would be wiped on the next re-render (which happens on every `baseSize`/`abc`/`staffWidth` change per the `useEffect` deps at `AbcPlayer.tsx:452`).
- **Reusing `<sup className="verse-number">` literally inside a `w:` string:** Not possible — `w:` lines are plain ABC text tokens, rendered by abcjs into SVG `<text>` elements with no React involvement. Do not let the planner schedule a task that "just adds `<sup>` to the w: line" — it will not render as JSX. See Open Questions §1.
- **Trusting UI-SPEC's `.abcjs-top-line` selector verbatim:** Confirmed wrong by source inspection (it's a staff ruling-line class from `staff.js`, unrelated to clef/key). Use the corrected selector in Code Examples §1.

## Common Pitfalls

### Pitfall 1: UI-SPEC's clef/key CSS selector targets the wrong element
**What goes wrong:** Implementing `.abcjs-staff-wrapper:not(:first-of-type) .abcjs-top-line { transform: scale(0.6) }` literally, per the UI-SPEC's stated anchor, will shrink the topmost of the 5 horizontal staff ruling lines on every wrapped row — NOT the clef and key signature. Visually this would produce a broken-looking staff (one line short, four full-length) with the clef/key still full size.
**Why it happens:** The UI-SPEC's author reasoned from abcjs's emitted class list (`abcjs-top-line` sounds plausible for "the block at the top of a line") without cross-checking the actual drawing code that assigns it.
**How to avoid:** Use the corrected selector from Code Examples §1, and — per the UI-SPEC's own caveat ("executor must render a real multi-row tune and inspect the actual DOM/class structure before finalizing the selector") — verify with a live Playwright DOM inspection of a rendered multi-row inline Staff tune (e.g. Crimond, CM, 4+ wrapped rows) before committing to the final selector, since `abcjs-clef`/`abcjs-key-signature` classes are grouped inside a parent `staff-extra` wrapper whose exact SVG group nesting (and whether `abcjs-l{N}` per-line classes land on the same `<g>` or a sibling) was not confirmed by static source reading alone.
**Warning signs:** Visual regression showing a shortened/offset staff line on wrapped rows instead of a shrunk clef block.

### Pitfall 2: The row-stretch bug may not be a missing format option
**What goes wrong:** Adding `format: { stretch: 1 }` or similar blindly (there is no such abcjs option — only `stretchlast` exists) will have no effect, or the planner may spend a task hunting for a nonexistent global "stretch all rows" flag.
**Why it happens:** `calcHorizontalSpacing` (abcjs-basic.js:26701) shows non-last lines are ALREADY stretched to `targetWidth` by default whenever `Math.abs(targetWidth - lineWidth) >= 2` — there is no opt-in needed for non-last rows. `stretchlast` exists ONLY because the LAST line is deliberately NOT auto-stretched by default (to avoid an unnaturally sparse trailing row).
**How to avoid:** The real bug is more likely in this codebase's own `effectiveStaffWidth`/`targetStaffwidth` computation (`AbcPlayer.tsx:406-426`, which divides `containerWidth * staffWidthFactor` by `effectiveScale` and feeds the result as `staffwidth` to abcjs) producing a target width that's already close to each phrase's natural content width for short/melisma-heavy phrases, so `Math.abs(targetWidth - lineWidth) < 2` short-circuits the stretch. Confirm via Playwright: render a known-affected tune, read `getBoundingClientRect().width` on `.abcjs-staff-wrapper` elements per line vs. the container, and diff against `effectiveStaffWidth`'s computed value logged via `console.log` (there's already a `debug` param plumbed through `setXSpacing`/`calcHorizontalSpacing` in abcjs's own source that could be temporarily enabled for diagnosis, mirroring the pattern in `tests/diagnostics/split-leaf-staff-diff.mjs` referenced repeatedly in STATE.md).
**Warning signs:** Fix appears to do nothing when tested, or only affects the last row.

### Pitfall 3: AbcPlayer's `scale` prop is NOT abcjs's `scale` option
**What goes wrong:** Assuming `<AbcPlayer scale={someValue}>` maps directly to abcjs's internal rendering scale (i.e., assuming setting `INLINE_STAFF_NOTATION_SCALE = 1` will produce visually identical output to today's `baseSize/14`).
**Why it happens:** `AbcPlayer.tsx` deliberately keeps abcjs's own `scale: 1` fixed (line 439: "Keep abcjs `scale` at 1; visual size is driven by staffwidth above") and instead folds the `scale` prop into `targetStaffwidth = (containerWidth * staffWidthFactor) / effectiveScale` (line 425) — a SMALLER `effectiveScale` produces a WIDER `staffwidth`, which produces FEWER wraps and thus a visually SMALLER-looking result relative to viewport (see the extensive comment block at lines 408-424 explaining this inverse relationship). This is a non-obvious, load-bearing implementation detail (MOBILE-03 hotfix per the comment).
**How to avoid:** `INLINE_STAFF_NOTATION_SCALE` must be chosen empirically to match the CURRENT visual size users see today (before decoupling), not assumed to be `1`. Since `SingingView`'s existing proportional-zoom heuristic already clamps to `[8, 40]` before this phase, and `baseSize / 14` was the pre-existing scale formula, a safe starting value is `viewportW`-driven using the SAME clamp logic SingingView already runs (`clamp(baseSize × newWidth/refWidth, 8, 40) / 14`) — i.e., keep computing the scale the same way as today, just from a value that ISN'T the lyric-only `baseSize` the user now controls via A+/A−.
**Warning signs:** Inline Staff visibly jumps in size (bigger or smaller) immediately after this phase ships, even though A+/A− wasn't touched.

## Open Questions

1. **Verse numbers in `w:` lines (item c) cannot use `<sup className="verse-number">` — what should they look like instead?**
   - What we know: `StanzaList.tsx`'s pattern renders a React `<sup>` element, which only works because `StanzaList` is plain React DOM. Inline Staff's lyric text is instead emitted as ABC `w:` syntax (a plain-text string), which abcjs itself renders into SVG `<text>` nodes at render time — there is no React injection point inside that text. `lyrics-structured.ts`'s `serialiseLyrics` shows the ONLY existing precedent for verse numbers inside plain text: gluing the digit directly to the first character with no separator (e.g. `"1Before"`, per the digit-preserving fix in commit 148d44e). `mapCycleToPhraseSyllableLines` currently drops `bibleVerseRef` entirely for the structured-lyrics path feeding inline Staff.
   - What's unclear: Whether "matching how they display in lyrics-only/split-leaf" (UI-SPEC's wording) means (a) visually identical superscript styling — technically impossible inside a `w:` line without post-render SVG manipulation (wrapping the abcjs-emitted verse-number glyphs in a scaled `<tspan>`, which IS possible via targeted SVG text-node post-processing, unlike the clef case which was rejected for fragility) — or (b) functionally equivalent (a visible verse-number marker at the right position, in whatever style abcjs's `w:` renderer supports, e.g. a plain digit prefix glued to the syllable per the existing legacy-blob convention).
   - Recommendation: This needs a decision, not more research — likely via `/gsd-discuss-phase` or explicit user confirmation before planning locks a task list. Two viable paths: (1) glue the digit as plain text before the first syllable (simple, matches existing legacy-blob precedent, but no superscript styling — visually inconsistent with lyrics-only/split-leaf), or (2) post-render DOM query for abcjs's emitted lyric `<text>` elements at verse-boundary note positions and wrap/rescale that specific glyph via targeted SVG manipulation (matches visual style, but is exactly the kind of "SVG post-processing" the UI-SPEC rejected for item (a) as fragile — the same fragility argument likely applies here). The planner should surface this tradeoff explicitly rather than picking silently.
