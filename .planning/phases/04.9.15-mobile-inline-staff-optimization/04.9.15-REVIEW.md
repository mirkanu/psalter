# Phase 04.9.15: Code Review Report

**Reviewed:** 2026-07-19
**Depth:** standard
**Files Reviewed:** 17 (16 unique source files listed; `tests/diagnostics/inline-staff-clef-stretch-diff.mjs` reviewed as a diagnostic utility, not held to app-code standards)
**Status:** issues_found

## Summary

The mobile inline-staff optimization work (staff/key/clef shrink-and-reflow, height-fit scaling, split-leaf compaction, notation-scale decoupling, precenting-tune assignment) is largely sound and clearly documents its own reasoning trail across multiple checkpoint rounds. Two BLOCKER-level defects were found: a silent "ignore the precentor's chosen tune" bug in the precenting sing page, and an audio-playback control loss when toggling "Show original" mid-playback in `AbcPlayer`. The remaining findings are WARNING-level maintainability/robustness issues, several of which are exactly the kind of "leftover complexity from superseded approaches" the task called out: a write-only ref, a functionally-dead state variable kept alive with a no-op JSX hack, and a placeholder-name filter with a dead (case-mismatched) array entry duplicated across two functions.

## Critical Issues

### CR-01: Precenting sing page silently substitutes the wrong tune when precentor's assigned tune is outside the psalm's default meter

**File:** `src/app/precent/[id]/sing/[pos]/page.tsx:79-93`
**Issue:** When `item.tuneId` is set but the assigned tune is not found in `alternateTunes` (i.e. it isn't in the psalm's default meter), the code comment claims it will "fetch it from the DB via set item tune relation," but no such fetch happens. The `else` branch instead falls back to `primaryTuneRow` — the psalm's *default* tune — completely discarding the precentor's actual tune assignment with no error, warning, or fallback UI indicating the mismatch:

```ts
if (item.tuneId) {
  const assignedInAlternates = alternateTunes.find((t) => t.id === item.tuneId)
  if (assignedInAlternates) {
    primaryTune = assignedInAlternates
  } else {
    // Tune is outside the psalm's default meter — fetch it from the DB via set item tune relation
    // Fallback: still use the psalm's default tune
    primaryTune = primaryTuneRow ? buildTuneOption(primaryTuneRow) : null   // <-- never fetches item.tuneId
    primaryTuneNeedsMelismaStatus = !!primaryTune
  }
}
```
A live-service precentor who deliberately assigned a cross-meter tune to a set item will see a *different* tune rendered during the actual service, with no indication anything went wrong.
**Fix:** Actually fetch the assigned tune by id when it isn't in `alternateTunes`, e.g.:
```ts
} else {
  const assignedTuneRow = await db.query.tunes.findFirst({ where: eq(tunes.id, item.tuneId) })
  primaryTune = assignedTuneRow ? buildTuneOption(assignedTuneRow) : (primaryTuneRow ? buildTuneOption(primaryTuneRow) : null)
  primaryTuneNeedsMelismaStatus = !!primaryTune
}
```
(and import `tunes` from `@/db/schema` alongside the existing `precentingSets, setItems` import). At minimum, surface a warning if the fetch also fails to find the tune.

### CR-02: Toggling "Show original" mid-playback leaves audio uncontrollably playing

**File:** `src/components/AbcPlayer.tsx:513-628, 793-863, 877`
**Issue:** `showOriginal=true` swaps the entire notation subtree (including `containerRef`'s mount point) for a JPG `<img>` via a ternary at line 793 — this is a normal conditional render within the same component instance, so the unmount-cleanup effect (lines 678-690, which stops the synth) does **not** run. Meanwhile:
- The Play/Pause button is `disabled={showOriginal}` (line 877), so the user has no way to pause playback once "Show original" is active.
- The render effect (lines 513-628) that would call `stopAudio()` bails out immediately when `containerRef.current` is null (`if (!el) return`, line 515-516) — which it is, since the container isn't rendered while `showOriginal` is true.
- Even the `synthInputsChanged` check (lines 519-524) that decides whether to call `stopAudio()` does **not** include `showOriginal` in its comparison, so even when `el` is later non-null again the toggle itself never triggers a stop.

Net effect: if a user starts playback, then taps "Show original," the abcjs synth keeps running in the background with no visible player and no way to stop it short of navigating away or letting it finish.
**Fix:** Stop playback explicitly when `showOriginal` transitions to `true`, e.g. add:
```ts
useEffect(() => {
  if (showOriginal) stopAudio()
}, [showOriginal, stopAudio])
```

## Warnings

### WR-01: `applyLeadingGlyphShrink` cosmetic DOM pass can fail the entire render

**File:** `src/components/AbcPlayer.tsx:598-627`
**Issue:** The post-render clef/key/time-signature shrink pass (`applyLeadingGlyphShrink`, called at line 621) runs inside the *same* `try { ... } catch (e) { ...; setAudioError('Could not render notation.'); visualObjRef.current = null }` block that wraps the core `abcjs.renderAbc` call. `applyLeadingGlyphShrink` calls `getBBox()` repeatedly on freshly-inserted SVG elements — a call that can throw in some browser/DOM edge cases (e.g. an element not yet laid out, zero-area geometry). If that cosmetic pass throws, the catch handler incorrectly reports "Could not render notation" and nulls out `visualObjRef`, disabling Play — even though the actual musical notation rendered successfully and only the glyph-shrink cosmetic step failed.
**Fix:** Wrap the cosmetic pass in its own try/catch that logs and no-ops on failure, so a shrink-pass bug degrades gracefully (full-size clef/key glyphs) instead of taking down the whole player:
```ts
if (staffWidthFactor < 1) {
  try { applyLeadingGlyphShrink(el) } catch (e) { console.error('leading-glyph shrink failed:', e) }
}
```

### WR-02: Dead/write-only state and refs left over from prior iterations

**File:** `src/components/AbcPlayer.tsx:353, 369, 503, 715, 975-976`
**Issue:** Two pieces of state exist purely as write targets with no functional read:
- `needsSynthReinitRef` (line 369) is set to `true`/`false` (lines 503, 715) but its `.current` value is never read anywhere in the file.
- `audioReady` (line 353) is set via `setAudioReady(true/false)` but the only place its *value* is consulted is a deliberately inert expression at line 975-976: `{audioReady && false && <span />}`, explicitly commented as existing only "to suppress TS warning about audioReady."

Both are leftover complexity from an earlier version of the loading/synth-reinit UX that never got wired up (or was later stripped out) — exactly the kind of superseded-approach residue worth cleaning up.
**Fix:** Either remove `needsSynthReinitRef` and `audioReady` entirely, or finish wiring them (e.g. show a loading indicator while `audioReady` is false and synth is priming).

### WR-03: `mapCycleToPhraseSyllableLines` can silently drop trailing lyric lines

**File:** `src/lib/stanza-cycles.ts:103-120`
**Issue:** `linesPerPhrase = Math.max(1, Math.floor(flatLines.length / phrasesPerCycle))`, then each phrase slot only consumes `slice(start, start + linesPerPhrase)`. When `flatLines.length` is *not* an exact multiple of `phrasesPerCycle` (e.g. 6 lines across 4 phrases: `linesPerPhrase = floor(6/4) = 1`, so only the first 4 of 6 lines are ever assigned to a slot), the remaining lines are silently discarded — not deferred to a later page, not logged, just gone. This differs from the documented "under-fill" behavior (D-04, trailing `[]` slots for too few lines) — this is data loss for *too many* lines relative to an uneven division. The existing test suite only exercises exact-multiple cases (4 lines/2 phrases, 8 lines/4 phrases, 5 lines/5 phrases, 2 lines/4 phrases) and never exercises a non-exact-multiple case with excess lines, so this gap is untested.
**Fix:** Either round up (`Math.ceil`) and pack any deficit into the last phrase, or explicitly detect and log/warn on remainder lines so malformed-stanza data doesn't silently vanish from the rendered psalm.

### WR-04: `wLinesForPhrase` phrase-shape-override padding loop can silently no-op

**File:** `src/components/notation/NotationRenderer.tsx:644-656`
**Issue:** `lastLine` is captured once, before the `while` loop, from `lastStanza.lines[lastStanza.lines.length - 1]`. If the *last stanza in the cycle* happens to have zero lines (while other stanzas in the same cycle have lines, so `flatLineCount > 0` still passes the outer guard), `lastLine` is `undefined`, the `while` condition (`... && lastLine`) is false immediately, and no padding occurs even though the cycle is short of `effectivePhraseCount`. This is a narrow edge case but has no error path — the phrase-shape-override feature (e.g. Abbeyville's `[8,6,8,6,6]`) silently fails to repeat the last line for that cycle.
**Fix:** Fall back to searching backward through `padded` for the last non-empty stanza's last line, rather than assuming it's always the final stanza in the cycle.

### WR-05: Duplicated `PLACEHOLDER_PREFIXES` with a case-sensitivity dead entry

**File:** `src/db/queries/tunes.ts:25, 165-166`
**Issue:** Two separate declarations of essentially the same filter list, shadowing across scopes:
```ts
const PLACEHOLDER_PREFIXES = ['use ', 'do NOT ', 'do not ']       // module scope, line 25
...
const PLACEHOLDER_PREFIXES = ['use ', 'do not ', 'do NOT ']       // local to fetchTunesByMeter, line 165 — shadows the outer const
```
Both are checked via `t.name.toLowerCase().startsWith(p)` — but `p` itself is never lowercased. Since the entry `'do NOT '` contains uppercase letters, `t.name.toLowerCase().startsWith('do NOT ')` can **never** be true (a fully-lowercased string cannot start with a mixed-case prefix). This entry is dead code; it happens to be functionally masked because the redundant all-lowercase `'do not '` entry in the same array already catches the same names case-insensitively. Net effect: harmless today, but confusing, duplicated (DRY violation), and shadows an existing module-level binding with the same name.
**Fix:** Hoist a single shared `PLACEHOLDER_PREFIXES` constant, lowercase it once, and drop the dead `'do NOT '` entry (or lowercase the comparison prefix too):
```ts
const PLACEHOLDER_PREFIXES = ['use ', 'do not '] // all lowercase; name is already lowercased before comparison
```

### WR-06: `'psalter-score-mode'` localStorage key duplicated as a hardcoded literal in three places

**File:** `src/components/singing/GearPopover.tsx:130`, `src/components/singing/SingingView.tsx:20`, `src/components/notation/NotationRenderer.tsx:163`
**Issue:** `SingingView.tsx` and `NotationRenderer.tsx` each independently declare `const STORAGE_MODE_KEY = 'psalter-score-mode'`, and `GearPopover.tsx` uses the raw literal `'psalter-score-mode'` directly (line 130) rather than importing a shared constant. Three independent sources of truth for the same storage key create drift risk — a future rename in one file silently breaks the other two's read/write consistency.
**Fix:** Export `STORAGE_MODE_KEY` (and the analogous `STORAGE_SIZE_KEY`) from a single shared module (e.g. `src/lib/singing-storage-keys.ts`) and import it everywhere it's used.

### WR-07: `GlassBottomBar`'s hardcoded A− floor (8) diverges from `NotationRenderer`'s exported `MIN_SIZE` (4)

**File:** `src/components/singing/GlassBottomBar.tsx:71-72`, `src/components/notation/NotationRenderer.tsx:153`
**Issue:** `GlassBottomBar` imports `MAX_SIZE` and `SIZE_STEP` from `NotationRenderer` but not `MIN_SIZE`, and instead hardcodes a literal floor of `8`:
```ts
onClick={() => onBaseSizeChange(Math.max(8, baseSize - SIZE_STEP))}
disabled={baseSize <= 8}
```
while `NotationRenderer` exports (and its own non-chromeless `sizeGroup` uses) `MIN_SIZE = 4`. Since `GlassBottomBar` is the *only* size control exposed in the chromeless singing view (`NotationRenderer`'s own `controlBar` is hidden when `chromeless`), mobile singing-view users can never zoom below 13→8 while desktop/tune-page users can zoom to 4. This may be intentional (mobile floor higher for legibility) but is undocumented and not derived from a shared constant — any future change to `MIN_SIZE` won't propagate here.
**Fix:** Either import `MIN_SIZE` and use it directly, or introduce a documented `MOBILE_MIN_SIZE` constant exported from `notation-scale.ts` alongside `SPLIT_LEAF_NOTATION_SCALE`/`INLINE_STAFF_NOTATION_SCALE`.

### WR-08: `generateStaticParams` swallows all errors, including genuine failures

**File:** `src/app/psalms/[id]/page.tsx:22-47`
**Issue:**
```ts
export async function generateStaticParams() {
  try {
    const rows = await db.select(...)...
    ...
    return Array.from(slugs).map((slug) => ({ id: slug }))
  } catch { return [] }
}
```
A bare `catch { return [] }` swallows *any* error — a genuine DB connectivity problem, a schema mismatch, an unexpected query bug — and silently produces zero static params. Given `CLAUDE.md`'s "Static rendering... no runtime DB queries on the read path" rule, this means a build-time DB outage (or a real bug in this function) doesn't fail the build; it silently ships a production build with **no static psalm pages at all**, with nothing in the build log to distinguish that from "the psalm table happens to be empty."
**Fix:** At minimum log the caught error before returning `[]` (`console.error('generateStaticParams failed:', e)`) so a broken build is diagnosable instead of silently degraded.

### WR-09: `showLyrics` gating uses the legacy raw blob while lyric rendering uses the canonical structured source

**File:** `src/components/singing/SingingView.tsx:142`, `src/components/notation/NotationRenderer.tsx:266-281`
**Issue:** `SingingView` derives `showLyrics = !!lyrics` from the raw `lyricsImportedRaw` blob string passed down from the page component. `NotationRenderer`'s `stanzas` derivation, however, prefers the canonical `lyricsStructured` field when populated (`if (lyricsStructured && lyricsStructured.length > 0) return lyricsStructured`) and only falls back to parsing the raw blob when `lyricsStructured` is empty. If a psalm-version ever has a populated `lyricsStructured` but an empty `lyricsImportedRaw` (e.g. a data-entry/migration edge case), `NotationRenderer` would have real stanzas to render while `SingingView` believes there are none — hiding the "Lyrics only" toggle, `w:` line generation, and the entire lyrics-gated UI even though content exists.
**Fix:** Derive `showLyrics` from whichever source is authoritative for the given row (e.g. `!!lyrics || (lyricsStructured?.length ?? 0) > 0`), or pass a single pre-computed `hasLyrics` boolean down from the server component where both fields are already available.

### WR-10: `computeNotationScale`'s inline-Staff fallback duplicates its own exported constant as a magic number

**File:** `src/lib/notation-scale.ts:9, 26`
**Issue:** The module exports `INLINE_STAFF_NOTATION_SCALE = 13 / 14` specifically to document "the pre-A+/A- mobile default," yet the function's actual fallback branch re-derives the same value from raw magic numbers instead of referencing the exported constant:
```ts
export const INLINE_STAFF_NOTATION_SCALE = 13 / 14
...
if (opts.chromeless && opts.viewMode === 'staff') {
  return (opts.notationBaseSize ?? 13) / 14   // magic 13 / magic 14, not INLINE_STAFF_NOTATION_SCALE
}
```
This works today only because `13` and `14` happen to match the constant by coincidence of not having been refactored together. A future change to `INLINE_STAFF_NOTATION_SCALE`'s definition would silently desync from this fallback.
**Fix:** `return opts.notationBaseSize !== undefined ? opts.notationBaseSize / 14 : INLINE_STAFF_NOTATION_SCALE` (or otherwise derive the fallback from the exported constant directly).
