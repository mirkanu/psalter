# Phase 04.9.15.1 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Phase Nature

This phase is (1) a silent bug fix — no new UI surface — and (2) an additive interaction
layer on top of the existing, already-shipped singing-view chrome (`GlassBottomBar`,
`OnboardingTour`, `NotationRenderer`). It does **not** introduce a new page, new
color usage, or a new typographic role. Nearly every visual decision is therefore
**inherited verbatim** from the existing components it extends, not newly invented.
Where CONTEXT.md explicitly left something to "Claude's Discretion," this document
makes the prescriptive call so the executor has zero ambiguity — see inline notes.

## Component Spec: Page-Dot Indicator (new, MOBILE-10)

Resolves CONTEXT.md's "Claude's Discretion" item on exact styling. Sketch 007 Variant C is the visual reference; below are the concrete, buildable values.

**Render condition (exact, per CONTEXT.md — do not broaden or narrow):**
- `phoneLandscapeChromeHide === true` (existing flag from `SingingView.tsx`) AND `totalStanzas > 1`.
- Everywhere else (bar visible), the existing `GlassBottomBar` stanza indicator is the ONLY stanza display — the dot indicator must not render alongside it.

**Visual (≤8 stanza-sets — the common case):**
- Container: pill, `fixed` positioned (not absolute-in-flow — must survive the notation region's own internal scroll/measurement), `bottom-[calc(env(safe-area-inset-bottom)+8px)] right-3 z-30`.
- Container style: `flex items-center gap-1.5 rounded-full border border-border bg-background/85 backdrop-blur-sm px-2 py-1` (mirrors `GlassBottomBar`'s existing `bg-background/70 backdrop-blur-md border-border/50` glass treatment, slightly more opaque since it floats over notation content rather than a dedicated bar).
- Dot (inactive): `h-1.5 w-1.5 rounded-full bg-muted-foreground/40`.
- Dot (active): `h-1.5 w-1.5 rounded-full bg-foreground`, with a subtle pulse: `scale(1 → 1.35)`, 1.8s ease-in-out infinite — gate the animation behind `motion-reduce:animate-none` (existing project convention, see `GlassBottomBar`/`main` region `motion-reduce:transition-none` usage).
- z-index: 30 — above notation content, below the tour overlay (`z-[200]`/`z-[201]`/`z-[202]`) and below any modal/sheet, so the tour can still spotlight it and sheets still cover it.

**Overflow rule (>8 stanza-sets — resolves an open question the sketch didn't address, since it only showed 3 illustrative dots):**
- When `totalStanzas > 8`, do NOT render 9+ individual dots (illegible at 6px + 6px gap on a phone-width screen). Instead render the same pill container with the text fallback `"{current} / {total}"` (`text-xs text-muted-foreground tabular-nums`, no dots) — reusing `GlassBottomBar`'s exact stanza-copy convention, just without the "Stanza " word prefix (space-constrained floating pill vs. full-width bar).
- This threshold (8) is a design-contract default, not empirically tuned — flag to the human reviewer if a real psalm exceeds it during UAT and the pill looks cramped before that count.

**Interaction:** dots are indicator-only, not tappable (no direct-jump-to-page interaction was requested in CONTEXT.md — swipe and the (hidden, in this state) bar buttons are the only navigation methods). Do not add tap targets to individual dots.

## Component Spec: Swipe Gesture (new, MOBILE-10)

Resolves CONTEXT.md's "Claude's Discretion" item on touch implementation. No existing swipe/touch-gesture precedent exists elsewhere in this codebase (confirmed via search) — this is a genuinely new interaction pattern, hand-rolled (no gesture library currently in `package.json`; do not add one for this alone).

**Applies:** Universal — any device, any orientation, whenever `totalStanzas > 1`. Touch-only (desktop mouse/no-touch devices keep the existing `GlassBottomBar` prev/next buttons only, unchanged, no swipe listener attached).

**Recommended default thresholds** (prescriptive default; CONTEXT.md leaves exact numbers to implementation, but the executor needs concrete starting values, not a blank):
- Attach `onTouchStart`/`onTouchMove`/`onTouchEnd` to the notation viewport container (the same element already carrying `data-notation-viewarea` / `data-notation-slot`, per view mode).
- Direction lock: compare `|dx|` vs `|dy|` after the first ~10px of movement; only treat as a horizontal swipe if `|dx| > |dy| * 1.5` (avoids hijacking any residual vertical scroll, e.g. non-fitting tall content in portrait before the MOBILE-09 fit fix fully applies, or split-leaf's independent lyrics scroll region).
- Commit threshold: `|dx| >= 50px` at touch-end to trigger prev/next; below that, treat as a tap/no-op (matches typical swipe-carousel UX, avoids accidental triggers from small drags).
- `swipeLeft` → next stanza-set (same action as `GlassBottomBar`'s existing `onStanzaNext` / `ChevronRight`); `swipeRight` → previous (same as `onStanzaPrev` / `ChevronLeft`). Reuse the SAME handler functions already passed into `GlassBottomBar` from `SingingView.tsx` (`handleStanzaPrev`/`handleStanzaNext`) — do not create a parallel pagination path (explicit CONTEXT.md constraint).
- At boundary (already at first/last stanza-set), swipe attempting to go further is a no-op — no bounce/rubber-band animation required (out of scope; keep it simple, matches the existing prev/next buttons' `disabled` no-op behavior).
- Must not conflict with the existing scroll-hide touch/scroll listeners in `SingingView.tsx` (the capture-phase `scroll` listener) — the swipe listener is a separate `touchstart/move/end` set, not a `scroll` listener, so there is no event-type collision, but verify during implementation that `touchmove` doesn't get `preventDefault()`'d in a way that breaks the existing vertical scroll-hide detection in portrait/split-leaf modes where vertical scroll must still work.

## Onboarding Tour Extension (new step, MOBILE-10)

**Locked visual direction:** Sketch 007, Variant C (★ Selected) — `.planning/sketches/007-swipe-tutorial-tour/index.html`. Must match `OnboardingTour.tsx`'s existing visual language exactly (SVG-mask spotlight, 30%-alpha backdrop, `bg-background`/`border-border`/`rounded-lg`/`shadow-lg` bubble, "Step N of M" counter, Skip tour / Next→ / Done buttons) — this is NOT a new visual system, it is one more entry in the existing `Step[]` array.

**Mechanics:**
- New step object: `{ target: 'scroll-area', copy: 'Swipe left or right to move between stanza groups — the dots show where you are.' }` — reuses the `scroll-area` target (the `<main data-tour-target="scroll-area">` element already exists in `SingingView.tsx`; spotlighting it highlights the whole notation region, matching the sketch's "spotlight the notation area itself, not a button" direction). Do not invent a new `data-tour-target` value unless `scroll-area`'s existing rect proves visually wrong at implementation time (e.g. because it targets the outer `<main>` rather than the inner viewarea) — try the existing target first.
- Gate this step into a new conditional array following the exact `SCROLL_HIDE_STEPS` precedent (conditionally appended, not unconditionally in `STEPS`). Condition: `totalStanzas > 1` for the current tune (i.e. more than one stanza-set exists) — the tour component will need this value threaded in as a new prop (mirrors how `viewMode` is already threaded in for the `isSplitLeafMobile` gate).
- Per Variant C: within the spotlighted area, show (a) an animated hand-swipe visual sliding left-right with a dotted trail (see sketch's `.hand-swipe`/`.swipe-trail` CSS for the animation keyframes/timing — 1.8s ease-in-out infinite, opacity fade in/out at the ends) and (b) a live preview of the page-dot indicator itself (pulsing), positioned bottom-right of the spotlight — i.e. show the REAL dot-indicator component (or a visual clone matching it exactly) during this step, not a separate mockup graphic.
- This step's hand/dot visuals must respect `prefers-reduced-motion` (project convention) — fall back to a static (non-animated) hand glyph and non-pulsing dots when reduced motion is requested; the bubble copy stays the same either way.
- Restartable via the existing Gear menu "Restart tour" entry (`handleRestartTour` in `SingingView.tsx`) — no new restart mechanism needed, it already clears both tour localStorage keys and increments `tourKey`.

## Landscape Fit Fix (MOBILE-09 — no new UI surface)

This is a silent calculation fix, not a new component. Design-contract implication: **zero new visual elements**. The existing `compactSplitMobile`/`staffWidthFactor` gate in `NotationRenderer.tsx` (currently `chromeless && viewportW < 768`) must be extended to also trigger when `isPhoneDevice() && isLandscapeOrientation` (reusing `src/lib/device.ts` + the `isLandscapeOrientation` pattern already computed in `SingingView.tsx`), covering both Android and iOS phones in landscape regardless of the resulting `viewportW` (which can read 768–926px in landscape and currently escapes the mobile-compact branch). No new copy, color, spacing, or component is introduced by this fix — it purely widens an existing boolean gate.
