# Phase 04.9.15.1: Inline Staff Landscape Fit + Swipe Stanza Navigation - Context

**Gathered:** 2026-07-26
**Status:** Ready for planning
**Source:** `/gsd-explore` session (2026-07-23/24) — see `.planning/notes/inline-staff-landscape-scaling.md` and `.planning/sketches/007-swipe-tutorial-tour/`

<domain>
## Phase Boundary

Two related but distinct pieces of work, both scoped to the inline Staff view:

1. **Bug fix:** the existing "fit one stanza-set on screen without scrolling"
   system (already working in portrait phone and on desktop) breaks on
   landscape phones because its gate only checks viewport width, not
   orientation/height.
2. **Universal enhancement:** swipe left/right navigation between
   stanza-sets, available on any device/orientation with more than one
   stanza-set, plus a conditional page-dot indicator and a one-time tutorial.

</domain>

<decisions>
## Implementation Decisions

### Landscape fit-to-screen bug (MOBILE-09)
- Root cause confirmed via live Playwright measurement against
  psalter.gsdlabs.dev: Psalm 1's inline Staff rendered a 566px-tall SVG into
  a 412px-tall landscape viewport (915×412, Android UA) — forced scroll.
- The existing "mobile compact fit" system (`compactSplitMobile` +
  `staffWidthFactor` in `src/components/notation/NotationRenderer.tsx`) is
  gated by `chromeless && viewportW < 768` — this correctly catches narrow
  portrait phones but misses landscape phones (wide, 768-926px, but just as
  height-constrained, 390-430px).
- Fix must extend this gate to also trigger on landscape phones — reuse this
  session's existing phone/orientation detection (`isPhoneDevice()` in
  `src/lib/device.ts`, the `isLandscapeOrientation`/`phoneLandscapeChromeHide`
  pattern already built in `SingingView.tsx`) rather than inventing a new
  width-only check or a separate ad-hoc gate.
- Scope: Android AND iOS landscape (not iOS-only) — confirmed explicitly in
  exploration ("Android too, tho I won't be able to test").
- Inline Staff is **already paginated** into stanza-sets (fits one set — up
  to 3 stanzas — on screen without scrolling, in portrait/desktop today).
  This is a fix to the existing per-set fit calculation, NOT a request to
  invent pagination from scratch. Do not conflate with split-leaf's separate
  `CYCLES_PER_PAGE` pagination (`cyclePage`/`totalStanzaPages` in
  `NotationRenderer.tsx`) — that's a related but distinct system.

### Swipe stanza navigation (MOBILE-10)
- Swipe left/right between stanza-sets is **universal**: any device,
  any orientation, whenever there's more than one stanza-set. Additive
  alongside the existing bottom-bar stanza display — NOT a replacement.
  Desktop (no touch) keeps its existing buttons only; no swipe there.
- The existing bottom-bar stanza display/nav stays exactly as-is everywhere
  the bottom chrome bar is visible (portrait phone, tablet, desktop,
  landscape-with-bar-visible).
- It is **only** replaced by a subtle page-dot indicator (carousel-style) in
  the specific case where the bottom bar is auto-hidden via this session's
  `phoneLandscapeChromeHide` mechanism — i.e. phone + landscape + not blocked
  by the iOS rotate-prompt. Concretely: Android phone in landscape (always,
  browser tab or installed), or iOS phone in landscape ONLY when
  home-screen-installed (browser-tab iOS landscape is still blocked by the
  earlier rotate-prompt feature, so this case never arises there).
- Do NOT gate the dot-indicator-vs-bar-buttons swap on "iOS home-app only" —
  it's the broader `phoneLandscapeChromeHide` condition, confirmed explicitly
  during exploration when the user initially assumed it was iOS-only and was
  corrected.

### Tutorial (part of MOBILE-10)
- One-time, first-encounter explainer for the swipe gesture.
- **Locked design decision (from `/gsd-sketch` 007, winner Variant C):**
  extend the existing `OnboardingTour.tsx` spotlight system as one more step
  — same visual language (SVG-mask spotlight, 30%-alpha backdrop, tip bubble
  with `bg-background`/`border-border`/`rounded-lg`/`shadow-lg`, "Step N of M"
  counter, Skip tour / Next→ / Done buttons) — NOT a standalone hero overlay.
  Repeatable via the existing Gear menu "Restart tour" entry, matching how
  the rest of the tour already works.
  - The new step spotlights the notation area itself (not a button) and
    shows an animated hand icon sliding left-right with a dotted trail,
    PLUS a live preview of the new page-dot indicator (pulsing) in the
    corner of the spotlight — teaching both "how to move" and "what tells
    you where you are" in one step.
  - Gate this new step into `STEPS`/a conditional array the same way
    `SCROLL_HIDE_STEPS` is already conditionally appended today (existing
    precedent in `OnboardingTour.tsx`) — condition: more than one
    stanza-set exists for the current tune.
  - See `.planning/sketches/007-swipe-tutorial-tour/index.html` (Variant C
    tab) and its `README.md` for the exact visual reference — build should
    match this sketch's feel (restrained, not playful/kinetic beyond the
    existing tour's tone).

### Claude's Discretion
- Exact swipe gesture implementation detail (touch event thresholds,
  library vs. hand-rolled touch handlers) — not discussed, use best judgment
  consistent with existing touch/scroll handling patterns already in
  `SingingView.tsx` (e.g. the existing scroll-hide touch/scroll listener
  patterns).
- Exact dot-indicator visual styling (size, color, placement) — sketch 007
  Variant C shows a reasonable default (small pulsing dots, bottom-right of
  notation area) but is not pixel-locked.
- How many "sets" a psalm can have and how that interacts with existing
  `currentStanza`/`totalStanzas`/`stanzaPage` state already in
  `SingingView.tsx` — use existing state/derivation, do not introduce a
  parallel pagination concept.

</decisions>
