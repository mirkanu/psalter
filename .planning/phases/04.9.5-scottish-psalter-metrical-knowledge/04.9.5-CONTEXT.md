<decisions>
## Implementation Decisions

### Worked examples
- **D-01:** Doc includes **several worked examples inline**, woven into the relevant sections (not banished to an appendix). Examples must cover:
  - A standard CM psalm + tune (e.g. Psalm 23 + CRIMOND) aligned syllable-by-syllable
  - A DCM tune sung against two CM stanzas (showing the 2-stanza pairing)
  - At least one alternate-meter case (drawn from actual Airtable data)
  - The amen-skip case (final 2 notes ignored when aligning lyrics)
  - An anacrusis (pickup-note) case
  - A mid-line / mid-stanza Bible-verse-split case (illustrating why stanza ≠ verse)
- Examples should be concrete enough that the implementation phase can lift them as test cases.

### Meter taxonomy scope
- **D-02:** Cover the **Scottish Psalter metrical tradition comprehensively** (CM, LM, SM, CMD/LMD/SMD, named alternate meters, etc.), AND **explicitly mark which subset appears in this app's Airtable data**.
- The "present in data" subset is non-negotiable to cover correctly; the broader tradition material is context that protects against future surprises and grounds the taxonomy properly.
- The data-driven subset must be enumerated by **actually querying the Airtable data**, not assumed.

### Research sources & priority
- **D-03:** All four sources are **primary and important**, no single source dominates:
  1. User's conversational briefing (the spine — user's knowledge as a CPRC precentor / domain expert)
  2. The Airtable data itself (to find what's actually in scope, validate claims, surface edge cases)
  3. 1650 Scottish Psalter prefaces & historic sources (authoritative tradition)
  4. Modern hymnology references / Free Church / CPRC publications (practitioner-focused, easier-to-cite)
- The researcher should triangulate across all four where possible. Disagreements between sources should be noted explicitly in the doc, not silently resolved.

### Citation depth
- **D-04:** **Cite every non-trivial claim** with its source (1650 preface §N, named hymnology reference, specific Airtable record, etc.).
- The doc must be defensible and auditable — a future precentor or contributor should be able to verify any rule by following its citation.
- Trivial claims (definitions of common terms, universally-known facts) can pass without inline citation, but a "Sources" appendix lists everything consulted.

### Claude's Discretion
The following were not raised by the user and Claude will default sensibly:

- **Doc shape:** Single monolithic doc at `.planning/research/scottish-psalter-structure.md` (sibling to `tonic-solfa-notation.md`). NOT split across multiple files. Section ordering: meter taxonomy → tune anatomy → stanza-vs-verse model → syllabification principles → line-break principles → worked examples (inline within above sections) → sources appendix.
- **Briefing workflow:** Mirror the solfège-doc process exactly:
  1. User briefs Claude conversationally on what he already knows.
  2. Claude reflects back + identifies known unknowns → agreed list of research questions.
  3. Claude does the research pass (all four sources triangulated).
  4. User + Claude converge on the doc through review/revision cycles.
- **Plan count:** Likely 2 plans — (1) Briefing capture + research-questions agreement + research pass producing a working draft; (2) Review/revision cycles to converge on final doc. To be confirmed by planner.
- **No UI work, no code, no tests in the conventional sense.** "Verification" for this phase = user sign-off that the doc is correct and complete enough to plan the implementation phase against.

<specifics>
## Specific Ideas

From the prior `/gsd-explore` session, the user named these concrete things the doc must illuminate:

1. **CM = 8.6.8.6 syllables per line** — confirm and document syllable counts, rhyme pattern.
2. **DCM = 8.6.8.6.8.6.8.6** — a DCM tune is paired with two CM stanzas, and currently rendered wrongly in lyrics alignment and visual line breaks.
3. **Most tunes have a final 2-note "amen"** — we want to skip this when aligning lyrics.
4. **Lyrics are stored as a single multi-line text per psalm with embedded verse numbers** — verse numbers are Bible-verse divisions, not stanza boundaries. A stanza can contain 1–3 verses; a verse can split across lines or even stanzas.
5. **Alternate meters already exist in the DB** — meter matching (tune meter ↔ versification meter) already works correctly; what doesn't work is the lyric alignment and line breaks for these alternate meters.
6. **Future** (NOT this phase — captured as the `user-stanza-selection` seed): users will be able to pick which stanzas to sing; the stanza-vs-verse complexity makes this UI tricky.

These specifics should anchor the doc's worked examples (D-01) and the data-driven taxonomy subset (D-02).
