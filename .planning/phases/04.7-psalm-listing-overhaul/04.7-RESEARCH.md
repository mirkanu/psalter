# Phase 4.7: Psalm Listing Overhaul - Research

**Researched:** 2026-05-09
**Domain:** Next.js 16 client component, in-memory search, dense grid UI
**Confidence:** HIGH

---

## Summary

Phase 4.7 replaces the existing `/psalms` listing page with a dense numbered-box grid and instant client-side search. The current implementation (`PsalmGrid` + `PsalmCard`) already establishes the server-fetches → client-component pattern used throughout this codebase: an RSC page fetches data and passes it as props to a `'use client'` component. This phase extends that pattern with a new, more capable client component (`PsalmListingGrid`) that owns search state, Advanced panel state, and filter logic entirely in memory.

All 150 psalms fit comfortably in a single RSC query. The existing query in `page.tsx` already fetches `id`, `firstLine`, and `meter` from `psalmVersions` — the only addition needed is a truncated KJV excerpt from `psalms.kjvText` for text search. The KJV full text averages 2,892 characters per psalm; a 120-character truncated excerpt in the payload is all that is required for the client-side text search. Total estimated payload: ~30KB JSON — well within feasible bounds for a prop-passed client component.

The `[data-snippet] b` rule in `globals.css` already exists at `font-weight: 600`; the UI-SPEC requires updating it to `700`. The shadcn `Checkbox` component is not yet installed. These are the only infrastructure changes needed before implementing the new components.

**Primary recommendation:** Implement a single `PsalmListingGrid` client component receiving all 150 psalms as props (RSC fetch), with `PsalmNumberBox` as a pure presentational child. Do not use the server-side FTS route (`fetchSearchResults`) — all filtering is in-memory JavaScript.

### Pattern 2: Client-side search with bold match highlighting

**What:** Filter an array in-memory, locate the query string in each result, wrap with `<strong>` or `<span className="font-bold">`, truncate at 80 chars.

**When to use:** Small dataset (<500 items), instant response required, no server round-trip.

**Implementation approach:**
```typescript
// Detect mode
const isNumeric = /^\d+$/.test(query.trim())

// Number mode: sort by distance, all shown
if (isNumeric) {
  const target = parseInt(query)
  return [...psalms].sort((a, b) => Math.abs(a.id - target) - Math.abs(b.id - target))
}

// Text mode: match first line and KJV excerpt, inject snippet
const lower = query.toLowerCase()
return psalms
  .filter(p => 
    p.firstLine?.toLowerCase().includes(lower) || 
    p.kjvExcerpt?.toLowerCase().includes(lower)
  )
  .map(p => ({ ...p, snippet: buildSnippet(p, lower) }))
  .sort(byRelevance)
```

### Anti-Patterns to Avoid

- **Using `fetchSearchResults` (FTS route) for the listing page search:** That function executes a DB query on every keystroke. The UI-SPEC requires client-side in-memory search. [VERIFIED: UI-SPEC interaction contract]
- **Putting search state in the RSC page:** State must live in the client component — RSC cannot hold React state.
- **Rendering `PsalmNumberBox` as a server component:** It handles `active:scale-[0.97]` and conditional rendering based on client state — it must be a child of a `'use client'` component.
- **Fetching full `kjv_text`:** Avg 2,892 chars per psalm × 150 = ~430KB. Instead truncate to 120 chars per psalm in the DB query using `LEFT(kjv_text, 120)` or a `SUBSTRING` — reduces payload to ~18KB for that field.

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Checkbox UI | Custom checkbox div | `shadcn Checkbox` | Accessibility (keyboard, ARIA), consistent checked animation, Radix primitive |

| Bold match highlighting | Regex replace on raw HTML | Manual `indexOf` + string slice + `<strong>` wrap | Safe — no innerHTML involved; avoids XSS |

**Key insight:** The bold match injection uses string splitting (not innerHTML), avoiding the sanitisation complexity that exists in the FTS `search.ts` module (which processes `ts_headline` HTML output from PostgreSQL).

## Common Pitfalls

### Pitfall 1: Meter data inconsistency — `psalmVersions.meter` vs `tunes.meter`

**What goes wrong:** The current `page.tsx` uses `psalmVersions.meter` for the listing. 14 psalms have multiple versions (psalm 119 has 22!). The dedup keeps only the first version row.

**Why it happens:** `psalmVersions` has a `meter` field and `tunes` also has a `meter` field. They should agree but the data path is `psalmVersion → psalmVersionTunes → tune`. The current join is the simpler path (directly from `psalmVersions.meter`).

**How to avoid:** Continue using `psalmVersions.meter` (same as existing implementation). The dedup already handles multi-version psalms. Do not add a join to `tunes` for meter — unnecessary complexity. [VERIFIED: schema.ts, page.tsx]

**Warning signs:** If meter filter shows wrong meter for a psalm, investigate whether the "first version" dedup selects the primary version. Could add `isPrimary` ordering to the join if needed.

### Pitfall 2: `xl:grid-cols-15` requires Tailwind arbitrary value or safelist

**What goes wrong:** Tailwind 4 generates utilities on-demand, but `grid-cols-15` is not a standard Tailwind utility. The class may be purged or simply not generated.

**Why it happens:** Tailwind includes `grid-cols-1` through `grid-cols-12` by default. 15 columns is non-standard.

**How to avoid:** Use `grid-cols-[15]` (arbitrary value) or define it in the Tailwind config. In Tailwind 4, use `@theme` to extend. Alternatively use `grid-template-columns` inline style or a CSS class. [VERIFIED: UI-SPEC specifies `xl:grid-cols-15` — implementation detail requires verification]

**Warning signs:** If the grid shows 12 columns at xl, the class wasn't generated.

### Pitfall 3: `autoFocus` on search input causing scroll jump

**What goes wrong:** `autoFocus` scrolls the browser viewport to the focused element on page load, which can push page content down on mobile.

**Why it happens:** Native browser `autofocus` behaviour.

**How to avoid:** Use `useEffect` to call `inputRef.current?.focus()` after mount with a short delay, or accept the behaviour (UX-SPEC requires `autoFocus`). On mobile the keyboard appearing may cause layout shift regardless. [ASSUMED — standard Next.js/React gotcha]

### Pitfall 4: KJV excerpt search — partial word matches producing noise

**What goes wrong:** Searching "God" matches "good", "goods" etc. because `includes()` is substring-based.

**Why it happens:** Client-side `String.includes()` is not word-boundary-aware.

**How to avoid:** For the MVP, substring search is acceptable per UI-SPEC (no word-boundary requirement stated). If noise is problematic, add a word-boundary check: `new RegExp(`\\b${escapeRegex(query)}\\b`, 'i').test(text)`. [ASSUMED — improvement from UI-SPEC review; UI-SPEC does not specify exact algorithm]

### Pitfall 5: `[data-snippet] b` styling applies to search page too

**What goes wrong:** Updating `font-weight` to 700 in globals.css affects the Phase 3 search results page which also uses `data-snippet`.

**Why it happens:** `[data-snippet] b` is a global selector.

**How to avoid:** This change is intentional (search results also benefit from bolder matches). Verify the search page `/search` still looks correct after the change. [VERIFIED: globals.css line 133-134]

### Bold match snippet builder (pure TypeScript)
```typescript
function buildSnippet(text: string, query: string, maxLen = 80): string {
  const lower = text.toLowerCase()
  const idx = lower.indexOf(query.toLowerCase())
  if (idx === -1) return ''
  // Window around match
  const start = Math.max(0, idx - 20)
  const end = Math.min(text.length, start + maxLen)
  let excerpt = text.slice(start, end)
  if (start > 0) excerpt = '…' + excerpt
  if (end < text.length) excerpt = excerpt + '…'
  // Bold the match
  const re = new RegExp(`(${query.replace(/[.*+?^${}()|[\]\\]/g, '\\$&')})`, 'gi')
  return excerpt.replace(re, '<BOLD>$1</BOLD>') // use JSX <strong> in render
}
// In JSX: render with dangerouslySetInnerHTML or split on <BOLD> and map to <strong>
```
