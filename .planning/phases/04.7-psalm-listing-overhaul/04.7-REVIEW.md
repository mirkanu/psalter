## Critical Issues

### CR-01: Keyword search silently drops results when `kjvExcerpt` matches but `firstLine` does not contain the query

**File:** `src/components/PsalmListingGrid.tsx:80-85`

**Issue:** The relevance scoring block reads:

```ts
const fl = p.firstLine?.toLowerCase() ?? ''
const relevance = fl.split(/\s+/).includes(lowerQuery) ? 0
  : fl.includes(lowerQuery) ? 1
  : 2
```

Then `.filter((p) => p.snippet !== null)` is applied. A psalm whose `firstLine` does not contain the query word at all (relevance = 2) but whose `kjvExcerpt` does match will have a non-null `snippet` (the `kjvSnippet` path). That psalm is correctly kept by the filter. **However**, if `firstLine` is `null`, `fl` is `''`, `fl.includes(lowerQuery)` is `false` for any non-empty query, and relevance is `2`. This is fine.

The actual bug is more subtle: the filter condition is `p.snippet !== null`, where `snippet = firstLineSnippet ?? kjvSnippet`. `buildSnippet` returns `null` when `idx === -1`. For a psalm whose `kjvExcerpt` matches the query but whose `firstLine` also contains the query, `firstLineSnippet` is non-null, so `snippet` is the first-line snippet — the KJV excerpt hit is silently discarded even though it might have been the better match. This is a UX correctness issue but not data loss.

The actual **blocker** is the case where `kjvExcerpt` is `null` (the `LEFT(kjv_text, 120)` raw SQL returns `null` when `kjv_text` is `null`) **and** `firstLine` is `null`. `buildSnippet(null, ...)` returns `null`, so `snippet = null ?? null = null`. The psalm is filtered out even though the psalm exists — the user sees fewer than 150 results with no indication of why. This is a silent data loss from the user's perspective when a psalm has no text in either column.

More importantly: when a psalm has `kjvExcerpt` matching but `firstLine` **does not** match, `relevance` is `2`, which is correct, but the psalm card correctly appears. The real issue is the **numeric sort path does not apply the meter filter**. On line 68-71:

```ts
if (isNumeric) {
  const target = parseInt(trimmedQuery, 10)
  return [...meterFiltered]
    .sort(...)
}
```

`meterFiltered` is used here — this path is correct. However, the `buildSnippet` relevance path operates on `meterFiltered` (line 74) but the relevance guard `fl.split(/\s+/).includes(lowerQuery)` uses a **word-boundary word split**. If `lowerQuery` is a multi-word phrase like `"the lord"`, `lowerQuery` will never match a single entry in `fl.split(/\s+/)`, so relevance is always `1` or `2` — the word-boundary fast path (relevance 0) is dead for any multi-word query. This is not a crash but is a logic defect that incorrectly deprioritises exact first-line matches when the query contains spaces.

**Fix:** Guard the word-boundary check against multi-word queries:

```ts
const relevance =
  (!lowerQuery.includes(' ') && fl.split(/\s+/).includes(lowerQuery)) ? 0
  : fl.includes(lowerQuery) ? 1
  : 2
```

For the null-psalm silent omission issue, consider keeping psalms with no text rather than hiding them (or accept the behaviour and document it).

## Warnings

### WR-01: Invalid Tailwind `grid-cols` class — `xl:grid-cols-[15]` will not compile

**File:** `src/components/PsalmListingGrid.tsx:102`

**Issue:** The grid column class string contains `xl:grid-cols-[15]`. Tailwind's arbitrary value syntax for grid columns requires CSS-valid syntax: `grid-cols-[repeat(15,minmax(0,1fr))]` or simply `xl:grid-cols-15` if using the Tailwind 4 extended scale. The class `xl:grid-cols-[15]` is not valid CSS for a `grid-template-columns` property — `15` alone is not a CSS length, count, or track list. This class will be silently ignored, so at the `xl` breakpoint the grid falls back to whatever the previous breakpoint defines (`lg:grid-cols-12`). On very wide screens, the intended 15-column layout never renders.

**Fix:** Use a valid arbitrary value:
```ts
"grid-cols-6 sm:grid-cols-8 md:grid-cols-10 lg:grid-cols-12 xl:grid-cols-[repeat(15,minmax(0,1fr))]"
```
Or define a custom Tailwind theme key.

### WR-02: `showMeter` state is tracked but never influences `hasExpanded` / grid column layout

**File:** `src/components/PsalmListingGrid.tsx:40,99`

**Issue:** `showMeter` controls whether the meter badge renders inside each card (line 59 in `PsalmNumberBox.tsx`). However, `hasExpanded` on line 99 is calculated as:

```ts
const hasExpanded = showFirstLine || (trimmedQuery.length > 0 && !isNumeric)
```

`showMeter` is not included. When only `showMeter` is checked (and `showFirstLine` is false with no active query), the card layout uses the compact `aspect-square h-12 md:h-14` class (line 41 in `PsalmNumberBox.tsx`). The meter label then renders inside an `aspect-square` box with `flex flex-col items-center justify-center`, forcing overflow or awkward wrapping on narrow boxes, since meter strings like `"CMD"`, `"66.66.88"` can be 8+ characters. The card does not expand to accommodate the extra line. This is a layout/rendering bug.

**Fix:** Include `showMeter` in the `hasExpanded` calculation:
```ts
const hasExpanded = showFirstLine || showMeter || (trimmedQuery.length > 0 && !isNumeric)
```
And pass `hasExpanded` or a relevant prop into `PsalmNumberBox` so it applies the expanded box sizing when meter is shown.

### WR-03: ReDoS risk in `renderSnippet` regex construction from user-controlled input

**File:** `src/components/PsalmNumberBox.tsx:5`

**Issue:**

```ts
const escaped = query.replace(/[.*+?^${}()|[\]\\]/g, '\\$&')
const parts = snippet.split(new RegExp(`(${escaped})`, 'gi'))
```

The input is escaped with a standard regex metacharacter escape, which is correct. However the regex is reconstructed with a capturing group and the `gi` flags. The escaping **does not** protect against catastrophic backtracking with an adversarial input that slips through — e.g. a query consisting of many escaped literal spaces or repeated characters that create ambiguous alternation paths in certain regex engines. In a client-side context this runs in the browser's JS engine, which is largely immune to catastrophic backtracking for simple patterns, and the query comes from the user's own input rather than a third party. The risk is low but non-zero for edge inputs.

More practically: if `query` is an empty string (line 4 short-circuits this), but if `escaped` is empty after escaping a string that contains only special characters (e.g. the user types `"["`), `escaped` becomes `"\\["`, which is a valid regex for a literal `[`. This is fine. The real issue is that the `parts.map()` comparison on line 10 uses `part.toLowerCase() === query.toLowerCase()` — this will **miss highlighting** when the snippet contains the match across a case boundary that was not exactly one of the split parts. For example, if `query` is `"The"` and the snippet is `"the LORD"`, the split produces `["", "the", " LORD"]`, and `"the".toLowerCase() === "The".toLowerCase()` is `true` — so this works. No actual bug here, but the escaping utility should be extracted as a named function for testability.

The genuine concern is: the `parts` array will contain empty strings at split boundaries (standard `String.prototype.split` behaviour with a capturing group). These are rendered as empty `<span key={i}></span>` elements — harmless but wasteful. No correctness bug.

**Actual finding:** If `query` contains only regex special characters that after escaping produce a zero-length match pattern (impossible given the escaping), or if `query` is a single repeated character like `"aaaa"`, the regex `/(aaaa)/gi` can produce many zero-length or overlapping match artefacts in some edge inputs. This is a **low-severity** ReDoS risk in a client-only context but should be noted.

**Fix:** Filter empty parts before rendering:
```ts
const parts = snippet.split(new RegExp(`(${escaped})`, 'gi')).filter(Boolean)
```
This avoids empty `<span>` nodes and reduces risk from degenerate patterns.

### WR-04: Missing `loading.tsx` for the `/psalms` route

**File:** `src/app/psalms/page.tsx` (absence of `src/app/psalms/loading.tsx`)

**Issue:** The project's `CLAUDE.md` and global conventions mandate that every Next.js route folder MUST have a `loading.tsx` that renders a skeleton/shimmer placeholder. The `PsalmsPage` performs a database query (`await db.select(...)`) that will block rendering until PostgreSQL returns. Without a `loading.tsx`, the user sees nothing (or the nearest parent's layout) while the query executes. For a 150-row query with a JOIN this is typically fast, but on cold DB connections or high load it can take hundreds of milliseconds.

**Fix:** Create `src/app/psalms/loading.tsx` with a skeleton grid:

```tsx
import { Skeleton } from "@/components/ui/skeleton"

export default function PsalmsLoading() {
  return (
    <div className="max-w-7xl mx-auto px-4 sm:px-6 lg:px-8 py-6 md:py-8">
      <div className="mb-6 mt-4">
        <Skeleton className="h-10 w-32 mb-3" />
        <Skeleton className="h-5 w-64" />
      </div>
      <Skeleton className="h-10 w-full mb-4" />
      <div className="grid grid-cols-6 sm:grid-cols-8 md:grid-cols-10 lg:grid-cols-12 gap-2">
        {Array.from({ length: 48 }).map((_, i) => (
          <Skeleton key={i} className="aspect-square rounded-lg" />
        ))}
      </div>
    </div>
  )
}
```

### IN-01: `leftJoin` instead of `innerJoin` silently includes psalms with no version row

**File:** `src/app/psalms/page.tsx:20`

**Issue:** The query uses `leftJoin(psalmVersions, ...)`. For any psalm that has no corresponding row in `psalm_versions`, `firstLine` and `meter` will be `null` in the result. The deduplication logic on lines 25-30 will still emit one row per such psalm (with null fields). This is probably the intended behaviour for display purposes (show all 150 even if some have no versification data), but it is worth making this intent explicit with a comment, because switching to `innerJoin` would silently hide psalms.

**Fix:** Add a comment:
```ts
// leftJoin so psalms without versification data still appear in the listing
.leftJoin(psalmVersions, eq(psalmVersions.psalmId, psalms.id))
```

### IN-02: `transition-all` and `transition-transform` applied simultaneously on the same element

**File:** `src/components/PsalmNumberBox.tsx:38-39`

**Issue:**

```ts
"hover:border-primary transition-all duration-200",
"active:scale-[0.97] transition-transform",
```

Both `transition-all` and `transition-transform` are in the class list. When both are present, `transition-all` takes precedence (it overrides `transition-transform` since it comes first in the generated CSS, depending on Tailwind's ordering). The `active:scale` transform will animate because `transition-all` covers `transform`. There is no actual visual bug, but `transition-all` animates every animatable property (including layout-affecting ones like `width`, `height`, and `border-width`) which is heavier than needed and can cause jank on border-width transitions.

**Fix:** Replace the two separate transition classes with one explicit list:
```ts
"transition-[border-color,transform] duration-200",
```

### IN-03: `aria-current` on a `<Link>` set to `"true"` (string) instead of a valid ARIA token

**File:** `src/components/PsalmNumberBox.tsx:52`

**Issue:**

```tsx
aria-current={isHighlighted ? "true" : undefined}
```

The `aria-current` attribute accepts the tokens `page`, `step`, `location`, `date`, `time`, or `true`/`false` (boolean). Passing the string `"true"` is technically valid per ARIA spec (treated as a truthy aria-current state), but the semantically correct value for a highlighted search result that is not a navigation landmark would be omitting `aria-current` entirely and instead using `aria-selected` or a visually distinct class. Using `"true"` is an unusual choice and screen readers may announce it inconsistently.

**Fix:** Either use `aria-current="location"` (for the best search-result semantic) or remove it in favour of `aria-selected`:
```tsx
aria-selected={isHighlighted ? true : undefined}
```
