# Phase 05.1: Auth Gate - Context

**Gathered:** 2026-06-18
**Status:** Ready for planning

<domain>
## Phase Boundary

Add Better Auth login to the CPRC Psalter site with two roles (admin, precentor). Gate `/dev/*` routes to admin only and `/precent/*` routes to any authenticated user. Filter the `/precent` set list to the logged-in user's own sets. Give admin a dropdown to switch into another precentor's view with full create/edit/delete rights. Provide a `/dev/accounts` page for creating new accounts and a one-time seed script for bootstrapping the admin account.

**Out of scope:** Self-registration, password reset flow, OAuth/social login, the Visitor role (deferred), email verification, public route changes.

</domain>

<decisions>
## Implementation Decisions

### Route Protection
- **D-01:** `/dev/*` is admin-only — any non-admin (or unauthenticated) user hitting these routes is redirected to `/login`.
- **D-02:** `/precent/*` requires any authenticated session — precentors and admins both have access.
- **D-03:** All other routes (public psalm/tune pages, search, explore) remain unauthenticated — no change.

### Login Page & Session
- **D-04:** Login lives at `/login` as a dedicated page that renders a modal/card overlay. No site nav shown around the form.
- **D-05:** Unauthenticated users hitting a protected route are redirected to `/login?callbackUrl=<original>`. After successful login they are returned to the original URL.
- **D-06:** Session duration is **30 days** (Better Auth `expiresIn` / cookie max-age). No "remember me" toggle needed — always 30 days.
- **D-07:** No self-registration link on the login page. Admin-created accounts only.

### Roles
- **D-08:** Two roles for this phase: `admin` and `precentor`. The `role` field is stored on the Better Auth `user` table.
- **D-09:** Only one admin account will ever exist (the owner). The seed script creates it.
- **D-10:** The `visitor` role is **deferred** to a future phase — the role system must be designed extensibly to accommodate a third role later without a schema change.

### Account Creation
- **D-11:** New precentor accounts are created via an admin page at `/dev/accounts` (already admin-gated). The page lists existing accounts and has a "New account" form: name, email, temporary password, role selector (admin/precentor).
- **D-12:** The initial admin account is seeded via a one-time CLI script (`node scripts/seed-admin.ts`) that reads `PSALTER_ADMIN_EMAIL` and `PSALTER_ADMIN_PASSWORD` from the shared `.env.production`. Script is idempotent — safe to run more than once.
- **D-13:** No password change UI in this phase. Precentors use whatever password the admin sets for them.

### Admin Toggle on /precent
- **D-14:** Admin sees a "Viewing as [name]" dropdown in the `/precent` page header. Default is their own account. Selecting a name shows that precentor's sets.
- **D-15:** When admin is viewing-as another precentor, they have **full rights** — can create, edit, and delete sets on behalf of that precentor. New sets created while viewing-as are owned by the selected precentor (not admin).
- **D-16:** The viewing-as state is **not** persisted across sessions or page navigations — it resets to the logged-in user on each visit to `/precent`.

### DB Schema Changes
- **D-17:** Add a `user_id` foreign key column to `precenting_sets` referencing the Better Auth `user` table (text PK, not integer). Column is NOT NULL after migration.
- **D-18:** Remove the `precentor_name` text column from `precenting_sets` entirely. Display name is derived at query time via JOIN to the `user` table.
- **D-19:** Migrate all existing rows (currently `precentor_name = 'Manuel'`) to the admin account's user ID in the same drizzle migration.
- **D-20:** `set_items` table is unchanged.

### Precentor Filter Logic
- **D-21:** `/precent` page server component reads `session.user.id` and queries `WHERE precenting_sets.user_id = $1`. If admin is viewing-as, the server action or client state passes the target user's ID instead.
- **D-22:** All precenting set API routes (`/api/precent/*`) validate that the authenticated user either owns the set (`set.userId === session.user.id`) or is admin. Return 403 otherwise.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `src/components/ui/` (shadcn) — all form components (Input, Button, Label, Card, Dialog) available for the login modal and /dev/accounts form
- `src/components/precent/PrecentingSetList.tsx` — receives serialized sets; will need a `viewingAsUserId` prop to handle admin viewing-as state
- `src/components/precent/CreateSetForm.tsx` — set creation form; will need to pass target `userId` when admin is viewing-as

### Established Patterns
- Next.js middleware (`middleware.ts`) does not exist yet — create it for route protection. Pattern: check Better Auth session cookie, redirect to `/login?callbackUrl=<pathname>` if missing or insufficient role.
- Server components already do DB queries directly (e.g. `precent/page.tsx`). Auth check pattern: call Better Auth's `auth.api.getSession({ headers: request.headers })` in server components and API routes.
- `export const dynamic = 'force-dynamic'` is already set on `/precent/page.tsx` — session-aware pages must keep this.

### Integration Points
- Better Auth will create its own tables (`user`, `session`, `account`, `verification`) via its schema migration. These must be pushed to `psalter-db` before any auth code runs.
- `precentingSets.userId` FK references Better Auth's `user.id` (text UUID, not integer). Drizzle schema must use `text('user_id').notNull().references(() => users.id)` — Better Auth's `user` table must be added to the Drizzle schema or referenced via a raw FK.
- The `PSALTER_ADMIN_EMAIL` and `PSALTER_ADMIN_PASSWORD` env vars go into `/home/services/.env.production` following the project-scoped naming convention.

</code_context>

<specifics>
## Specific Ideas

- Login page at `/login` renders the modal/card directly (no ambient page content). Similar to a "gate" page — user lands there, fills in form, gets sent to their destination.
- The "Viewing as" dropdown on `/precent` should only be visible to admin. A precentor visiting the page never sees it.
- `/dev/accounts` page design: simple table of existing users (name, email, role, created date) + a "New account" button that opens a Dialog form (shadcn Dialog already available). No inline editing needed in this phase.

</specifics>

<deferred>
## Deferred Ideas

- **Visitor role** — A third role (`visitor`) will be added in a future phase. The role system should use a text enum (not boolean flags) so adding `visitor` requires only a new valid value, not a schema change. Note for planner: don't hardcode a 2-role check anywhere — check `role === 'admin'` or `role === 'precentor'` explicitly, don't infer role from absence.
- **Password reset / "forgot password"** — Not in scope for this phase. Precentors contact admin to reset.
- **Email verification on account creation** — Not needed; admin creates accounts directly.
- **"Remember me" toggle** — Session is always 30 days; no per-login choice needed.

</deferred>
