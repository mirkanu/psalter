## User Constraints (from CONTEXT.md)

### Locked Decisions

**Route Protection**
- D-01: `/dev/*` is admin-only — any non-admin (or unauthenticated) user hitting these routes is redirected to `/login`.
- D-02: `/precent/*` requires any authenticated session — precentors and admins both have access.
- D-03: All other routes (public psalm/tune pages, search, explore) remain unauthenticated — no change.

**Login Page & Session**
- D-04: Login lives at `/login` as a dedicated page that renders a modal/card overlay. No site nav shown around the form.
- D-05: Unauthenticated users hitting a protected route are redirected to `/login?callbackUrl=<original>`. After successful login they are returned to the original URL.
- D-06: Session duration is 30 days (`expiresIn` = 60 * 60 * 24 * 30). No "remember me" toggle — always 30 days.
- D-07: No self-registration link on the login page. Admin-created accounts only.

**Roles**
- D-08: Two roles: `admin` and `precentor`. Stored on the Better Auth `user` table.
- D-09: Only one admin account will ever exist. The seed script creates it.
- D-10: `visitor` role deferred; role system must be designed extensibly (check `role === 'admin'` / `role === 'precentor'` explicitly — never infer from absence).

**Account Creation**
- D-11: New precentor accounts created via `/dev/accounts` page (admin-only). Lists accounts + "New account" form: name, email, temp password, role selector.
- D-12: Initial admin account seeded via `node scripts/seed-admin.ts` reading `PSALTER_ADMIN_EMAIL` and `PSALTER_ADMIN_PASSWORD` from `/home/services/.env.production`. Script is idempotent.
- D-13: No password change UI in this phase.

**Admin Toggle on /precent**
- D-14: Admin sees a "Viewing as [name]" dropdown in the `/precent` page header. Default is their own account.
- D-15: Admin viewing-as another precentor has full create/edit/delete rights. New sets created viewing-as are owned by the selected precentor.
- D-16: Viewing-as state is NOT persisted across sessions or page navigations — resets to logged-in user on each `/precent` visit.

**DB Schema Changes**
- D-17: Add `user_id` text FK column to `precenting_sets` referencing Better Auth `user` table. NOT NULL after migration.
- D-18: Remove `precentor_name` text column from `precenting_sets` entirely. Display name derived at query time via JOIN.
- D-19: Migrate all existing rows (currently `precentor_name = 'Manuel'`) to admin account's user ID in the same drizzle migration.
- D-20: `set_items` table is unchanged.

**Precentor Filter Logic**
- D-21: `/precent` page reads `session.user.id` and queries `WHERE precenting_sets.user_id = $1`. Admin viewing-as passes target user's ID instead.
- D-22: All `/api/precent/*` routes validate authenticated user either owns the set or is admin. Return 403 otherwise.

## Summary

Phase 05.1 adds Better Auth 1.6.x to an existing Next.js 16 + Drizzle ORM project. The primary work is: (1) install and configure Better Auth with the `admin` plugin and email+password strategy, (2) create a Next.js middleware that gates `/dev/*` to admins and `/precent/*` to any authenticated user, (3) migrate the `precenting_sets` table to replace `precentor_name` text with a `user_id` FK referencing Better Auth's `user` table, and (4) add the `/login` page and `/dev/accounts` admin UI.

The critical integration point is the Drizzle adapter, which is bundled inside `better-auth` itself at `better-auth/adapters/drizzle` — no separate package is needed. Better Auth will create its own `user`, `session`, `account`, and `verification` tables; these must be added to the Drizzle schema and pushed to `psalter-db` before any auth code runs. The `user.id` is a text UUID — the FK on `precenting_sets.user_id` must be typed `text`, not integer.

**Primary recommendation:** Install `better-auth@1.6.19`, configure with the bundled Drizzle adapter + `admin` plugin, generate auth schema via `npx auth@latest generate`, run `drizzle-kit push`, then build middleware + UI. Do not use `@better-auth/drizzle-adapter` as a separate npm package — it is already included in the main package.

### Pattern 3: Middleware (Node.js runtime required)

```typescript
// middleware.ts (project root)
// Source: https://github.com/better-auth/better-auth/blob/main/docs/content/docs/integrations/next.mdx
import { NextRequest, NextResponse } from "next/server"
import { getSessionCookie } from "better-auth/cookies"
import { auth } from "@/lib/auth"

export async function middleware(request: NextRequest) {
  const { pathname } = request.nextUrl

  // Fast cookie check for /precent/* — any authenticated session
  if (pathname.startsWith("/precent")) {
    const sessionCookie = getSessionCookie(request)
    if (!sessionCookie) {
      const callbackUrl = encodeURIComponent(pathname)
      return NextResponse.redirect(new URL(`/login?callbackUrl=${callbackUrl}`, request.url))
    }
    return NextResponse.next()
  }

  // Full session check for /dev/* — admin role required
  if (pathname.startsWith("/dev")) {
    const session = await auth.api.getSession({ headers: request.headers })
    if (!session) {
      const callbackUrl = encodeURIComponent(pathname)
      return NextResponse.redirect(new URL(`/login?callbackUrl=${callbackUrl}`, request.url))
    }
    if (session.user.role !== "admin") {
      return NextResponse.redirect(new URL("/login", request.url))
    }
    return NextResponse.next()
  }

  return NextResponse.next()
}

export const config = {
  runtime: "nodejs",  // Required for auth.api.getSession DB calls
  matcher: ["/dev/:path*", "/precent/:path*"],
}
```

**Note:** `getSessionCookie` is a fast cookie-presence check (no DB call). For `/precent/*` this is sufficient — full session validity is enforced by the server component. For `/dev/*` we need the full role check, so `auth.api.getSession` (DB call) is used. [CITED: https://www.better-auth.com/docs/integrations/next]

### Anti-Patterns to Avoid

- **Importing `auth` in client components:** `src/lib/auth.ts` uses `betterAuth()` which imports server-only code. Only import it in server components, API routes, middleware, and scripts. Client code uses `auth-client.ts`.
- **Using Edge runtime in middleware:** `auth.api.getSession` requires a DB connection — Edge runtime cannot open TCP sockets to PostgreSQL. Always set `runtime: "nodejs"` in middleware config when calling `auth.api.*`. [CITED: Context7 — middleware docs]
- **Using `getSessionCookie` as the sole security check for admin routes:** It only checks cookie presence, not validity or role. Admin routes must call `auth.api.getSession` to get the full session with role data.
- **Hardcoding `BETTER_AUTH_SECRET`:** Must be in env file only. Generate with `openssl rand -hex 32`.
- **Forgetting `export const dynamic = 'force-dynamic'` on session-aware RSC pages:** Better Auth session reads must not be cached. Already set on `/precent/page.tsx` — maintain this on all auth-aware pages.
- **Drizzle `schema` mapping mismatch:** Better Auth's Drizzle adapter expects table name `user` (singular). Since our schema uses camelCase exports (`users` vs `user`), pass `schema: { ...schema }` and verify Better Auth can find the `user` table name. If the generated schema exports a table named differently, use the mapping pattern: `schema: { ...schema, user: schema.users }`.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Password hashing | Custom bcrypt code | Better Auth internal | Timing-safe comparison, salt rounds, upgrade path |
| Session token generation | Custom UUID + DB insert | Better Auth sessions | CSRF protection, cookie security flags, rotation |
| User creation endpoint | Custom POST handler | `auth.api.createUser` (admin plugin) | Role assignment, password hashing, idempotency |
| Session cookie parsing | Manual cookie header parsing | `getSessionCookie(request)` from `better-auth/cookies` | Handles cookie name, encoding, multiple cookies |
| Role checking middleware | Custom JWT decode | `auth.api.getSession()` | Validates against DB, handles revocation |

**Key insight:** Better Auth's `admin` plugin provides `createUser`, `listUsers`, `setRole`, `banUser` as first-class server API methods. There is no need to write custom account management CRUD — call `auth.api.*` from server actions or API routes.

## Common Pitfalls

### Pitfall 1: Better Auth Tables Not in Drizzle Schema

**What goes wrong:** `drizzle-kit push` or queries fail with "relation does not exist" because Better Auth creates its own tables (`user`, `session`, `account`, `verification`) that are not in `src/db/schema.ts`.

**Why it happens:** The Drizzle adapter reads from DB tables that must exist; the adapter itself does not run DDL migrations.

**How to avoid:** Run `npx auth@latest generate` after configuring `src/lib/auth.ts` to emit a Drizzle schema fragment, then either:
1. Append the generated types to `src/db/schema.ts` manually, or
2. Keep them in a separate `src/db/auth-schema.ts` and re-export from `src/db/index.ts`

Then run `drizzle-kit push` (which the project already uses instead of migrate).

**Warning signs:** TypeScript errors on `schema.user`, runtime errors on first auth call.

### Pitfall 2: `precenting_sets.user_id` FK Cannot Be NOT NULL Before Data Migration

**What goes wrong:** Adding `user_id NOT NULL` in the same migration that removes `precentor_name` fails if existing rows have no `user_id` value yet.

**Why it happens:** SQL constraint violation — existing rows don't have a `user_id` until the admin account is seeded.

**How to avoid:** The migration must be ordered:
1. Add `user_id` column as NULLABLE first
2. Seed the admin account (get the user ID)
3. UPDATE all existing rows to set `user_id = <admin-id>`
4. ALTER COLUMN to set NOT NULL

With `drizzle-kit push` (no migration files), this three-step process requires a script that runs between schema states, or a raw SQL migration file.

**Alternative approach (D-19):** Use a Drizzle migration file (not push) for this specific schema change so the UPDATE step can be embedded. Run `drizzle-kit generate` to produce the file, then edit it to add the UPDATE statement between column add and NOT NULL constraint.

### Pitfall 3: `BETTER_AUTH_SECRET` Not Set

**What goes wrong:** Better Auth throws at startup or produces invalid session tokens.

**Why it happens:** The secret is required for signing session tokens; missing it causes the library to use an insecure fallback or throw.

**How to avoid:** Generate with `openssl rand -hex 32` and store as `BETTER_AUTH_SECRET` in `/home/services/.env.production`. Reference via `process.env.BETTER_AUTH_SECRET!` in `src/lib/auth.ts`.

### Pitfall 4: Admin Plugin Client Not Included in Auth Client

**What goes wrong:** `authClient.admin.createUser()` call from `/dev/accounts` page throws "admin is not a function".

**Why it happens:** The admin plugin's client-side methods require `adminClient()` to be added to `createAuthClient({ plugins: [...] })`.

**How to avoid:** Add `adminClient()` from `better-auth/client/plugins` to the auth client config. The server config and client config must both include matching plugin declarations.

### Pitfall 5: Middleware Caches Session Calls in Edge Runtime

**What goes wrong:** `auth.api.getSession` silently fails or times out in middleware.

**Why it happens:** Vercel/Next.js defaults to Edge runtime for middleware; postgres.js cannot open TCP connections in Edge.

**How to avoid:** Always export `export const config = { runtime: "nodejs" }` in `middleware.ts`. [CITED: Context7 — Next.js middleware docs for better-auth 1.6.x]

### Pitfall 6: `callbackUrl` Redirect Open Redirect Risk

**What goes wrong:** An attacker crafts `?callbackUrl=https://evil.com` and the login page redirects there.

**Why it happens:** Naive `router.push(callbackUrl)` without origin validation.

**How to avoid:** In the login form `onSuccess` handler, validate that `callbackUrl` starts with `/` (relative path) before redirecting. Reject or ignore any absolute URL.

### API Route Ownership Check Pattern

```typescript
// src/app/api/precent/[id]/route.ts — D-22 ownership guard
import { auth } from "@/lib/auth"
import { headers } from "next/headers"

export async function PATCH(req: Request, { params }: ...) {
  const session = await auth.api.getSession({ headers: await headers() })
  if (!session) return NextResponse.json({ error: "Unauthorized" }, { status: 401 })

  const set = await db.query.precentingSets.findFirst({ where: eq(precentingSets.id, setId) })
  if (!set) return NextResponse.json({ error: "Not found" }, { status: 404 })

  const isOwner = set.userId === session.user.id
  const isAdmin = session.user.role === "admin"

  if (!isOwner && !isAdmin) {
    return NextResponse.json({ error: "Forbidden" }, { status: 403 })
  }
  // ... proceed with update
}
```

### Seed Admin Script Pattern

```typescript
// scripts/seed-admin.ts — D-12
import "dotenv/config"
import { auth } from "@/lib/auth"

async function seedAdmin() {
  const email = process.env.PSALTER_ADMIN_EMAIL
  const password = process.env.PSALTER_ADMIN_PASSWORD
  if (!email || !password) throw new Error("PSALTER_ADMIN_EMAIL and PSALTER_ADMIN_PASSWORD must be set")

  // Idempotent: check if admin already exists
  const existing = await auth.api.listUsers({ body: { filter: [{ field: "email", operator: "eq", value: email }] } })
  if (existing?.users?.length) {
    console.log("Admin already exists, skipping.")
    return
  }

  await auth.api.createUser({
    body: { email, password, name: "Admin", role: "admin" }
  })
  console.log("Admin account created:", email)
}

seedAdmin().catch(console.error)
```

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | yes | Better Auth email+password with `disableSignUp: true` |
| V3 Session Management | yes | Better Auth sessions (DB-backed, 30-day, cookie `httpOnly` + `SameSite`) |
| V4 Access Control | yes | Middleware role check (`role === 'admin'`); ownership guard in API routes |
| V5 Input Validation | yes | Better Auth validates email/password format; API routes validate body shapes |
| V6 Cryptography | yes | Better Auth handles password hashing internally (never hand-roll) |

### Known Threat Patterns for Better Auth + Next.js

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Open redirect via `callbackUrl` | Spoofing | Validate `callbackUrl` starts with `/` before redirect in login form |
| Session fixation | Elevation of privilege | Better Auth rotates session token on login (built-in) |
| CSRF on state-mutating API routes | Tampering | Better Auth sets `SameSite=Lax` cookie; Next.js API routes with JSON body are CSRF-resistant by default |
| Horizontal privilege escalation (precentor accessing another's sets) | Elevation of privilege | D-22 ownership guard in every PATCH/DELETE API route |
| Admin role bypass | Elevation of privilege | Role stored in DB-backed session, not in JWT; middleware calls `auth.api.getSession` for `/dev/*` (DB validated) |
| Brute-force login | Denial of service | Better Auth has built-in rate limiting on auth endpoints [ASSUMED — verify in BA docs] |

## Open Questions

1. **Better Auth schema table naming convention**
   - What we know: Better Auth's Drizzle adapter expects a `user` table (singular). Our schema may or may not conflict with existing table names.
   - What's unclear: The generated schema fragment may use a different export name (e.g., `users`, `betterAuthUsers`). Wave 0 must run `npx auth@latest generate` and inspect the output before writing any schema integration code.
   - Recommendation: Wave 0 plan includes `npx auth@latest generate --adapter drizzle --dialect postgresql` as the first task; inspect output before writing `auth.ts`.

2. **precentingSets migration: `drizzle-kit push` vs migration file**
   - What we know: `drizzle-kit push` is the project standard. But D-19 requires a multi-step migration (add nullable column → UPDATE existing rows → set NOT NULL) that `push` cannot express atomically.
   - What's unclear: Can the data migration (UPDATE) happen in the seed script before the NOT NULL constraint is applied, given push is not transactional?
   - Recommendation: Use `drizzle-kit generate` to produce a migration file for this specific table change, then manually edit the SQL to embed the UPDATE statement. Run via `drizzle-kit migrate` for this one change only. Alternatively, add the column as nullable, run seed, then a separate push to set NOT NULL — two-step push is safe.
