# Phase 05.1: Code Review Report

**Reviewed:** 2026-06-19
**Depth:** standard
**Files Reviewed:** 27
**Status:** issues_found

## Summary

This phase implements Better Auth-backed authentication, precentor ownership guards, and an admin account management UI. The core ownership model (`canAccessSet`, `loadSetWithAccess`) is sound and well-tested. The middleware redirect logic is correct. However, two blockers were found: a DB query is unconditionally executed in `src/app/precent/[id]/page.tsx` before the session is verified, meaning unauthenticated requests perform wasteful DB work (and in edge timing scenarios could see timing side-channels), and the `PATCH /api/precent/[id]/items/[itemId]` route will throw an unhandled 500 if the client sends a body with no recognised fields. Several warnings relate to missing error handling in client-side async functions that leave UI in a permanently stuck state on network failure, and a missing psalmId range guard in the `POST /items` route.

## Critical Issues

### CR-01: DB query executes before auth check on set detail page

**File:** `src/app/precent/[id]/page.tsx:24-41`
**Issue:** The `precentingSets` record is fetched from the database at line 24 before `auth.api.getSession` is called at line 40. Every request to `/precent/[id]` — including requests from completely unauthenticated users — executes a DB query with a join. The middleware only checks for cookie presence, not validity, so an attacker with a malformed or expired session cookie passes the middleware and hits this page. The session is then checked at line 40, but by then the DB has already done the work. While the actual set data is never sent to the client (the code redirects or calls `notFound()`), this is an unnecessary resource expenditure and the correct pattern is to authenticate before querying.

**Fix:**
```ts
// Move the session check BEFORE the DB query:
const session = await auth.api.getSession({ headers: await headers() })
if (!session) redirect('/login')

const set = await db.query.precentingSets.findFirst({
  where: eq(precentingSets.id, setId),
  // ... with clause unchanged
})
if (!set) notFound()
if (set.userId !== session.user.id && session.user.role !== 'admin') notFound()
```

### CR-02: PATCH `/api/precent/[id]/items/[itemId]` will throw a 500 on empty body

**File:** `src/app/api/precent/[id]/items/[itemId]/route.ts:32-53`
**Issue:** `updateSet` is initialised as `{}` and populated only if `'tuneId'`, `'verseRange'`, or `'psalmId'` appear in the request body. If the client sends `{}` (or any body with none of those keys), `updateSet` remains `{}` and drizzle-orm 0.45.2 throws `"No values to set"` at line 49's `.set(updateSet)` call. This unhandled exception propagates as an HTTP 500. The same guard is absent in `src/app/api/precent/[id]/route.ts` PATCH handler but that one always sets `updatedAt: new Date()`, so it is safe.

**Fix:**
```ts
// After the body parsing block and before the DB call, add:
if (Object.keys(updateSet).length === 0) {
  return NextResponse.json({ error: 'no fields to update' }, { status: 400 })
}
```

## Warnings

### WR-01: `handleSaveNote`, `handleSaveMeta`, and `handleDeleteSet` leave `saving`/`deleting` state permanently `true` on fetch error

**File:** `src/components/precent/SetDetail.tsx:172-204`
**Issue:** All three async handlers (`handleSaveNote`, `handleSaveMeta`, `handleDeleteSet`) set a loading boolean to `true` and `await fetch(...)` without a `try/catch`. If the `fetch` rejects (e.g., network error, server restart), the promise rejects, the component is not unmounted, and the saving/deleting state stays `true` forever. For `handleSaveNote` and `handleSaveMeta` this renders the Save button permanently disabled. For `handleDeleteSet` the Delete button becomes unclickable, and `router.push('/precent')` is never called.

**Fix:** Wrap each handler in a `try/catch` and reset the loading flag in a `finally` block:
```ts
async function handleSaveNote() {
  setSaving(true)
  try {
    await fetch(`/api/precent/${set.id}`, {
      method: 'PATCH',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ note: editNote.trim() || null }),
    })
    setEditing(false)
    router.refresh()
  } catch {
    // surface error to user
  } finally {
    setSaving(false)
  }
}
```
Apply the same pattern to `handleSaveMeta` (`savingMeta`) and `handleDeleteSet` (`deleting`).

### WR-02: `POST /api/precent/[id]/items` does not validate psalmId range

**File:** `src/app/api/precent/[id]/items/route.ts:31-36`
**Issue:** The POST handler only checks `typeof body.psalmId !== 'number'`. It does not verify the value is a valid psalm (integer in range 1–150). A psalmId of `0`, `-5`, `99999`, or `3.14` passes this guard and reaches the DB `INSERT`, which will fail at the PostgreSQL foreign-key constraint on `psalms.id`, surfacing as an unhandled 500 instead of a 400. The PATCH handler for the same resource correctly validates `1 ≤ psalmId ≤ 150` at line 43 — the POST should match.

**Fix:**
```ts
if (
  typeof body.psalmId !== 'number' ||
  !Number.isInteger(body.psalmId) ||
  body.psalmId < 1 ||
  body.psalmId > 150
) {
  return NextResponse.json({ error: 'psalmId must be an integer 1–150' }, { status: 400 })
}
```

### WR-03: Admin-supplied `userId` in `POST /api/precent` is not validated against existing users

**File:** `src/app/api/precent/route.ts:54-66`
**Issue:** When an admin posts with `{ userId: "some-id" }`, the handler trusts the string and inserts it as `precentingSets.userId`. If the supplied ID does not exist in the `user` table, the INSERT fails at the FK constraint and the error propagates as a 500 instead of a 400. This is only reachable by admins, which limits the impact, but it will produce confusing opaque errors.

**Fix:**
```ts
if (typeof body.userId === 'string' && session.user.role === 'admin') {
  const targetUser = await db.query.users.findFirst({ where: eq(users.id, body.userId) })
  if (!targetUser) {
    return NextResponse.json({ error: 'target user not found' }, { status: 400 })
  }
  ownerId = body.userId
}
```

### WR-04: `AccountsClient` coerces `'precentor'` role to `'user' | 'admin'` type at the API call boundary

**File:** `src/app/dev/accounts/AccountsClient.tsx:83`
**Issue:** The role selector allows `'precentor'` and `'admin'` values (lines 151–153), but the `authClient.admin.createUser` call casts `role` as `'user' | 'admin'`, which is a TypeScript lie. The Better Auth admin plugin's TypeScript types do not list `'precentor'` as a valid role, so at compile time the application silences a type error instead of fixing it. At runtime the `'precentor'` string is sent to Better Auth, which — because the project uses a drizzle adapter with a custom `role` column — happens to work. However, this is fragile: a Better Auth upgrade that adds server-side role validation would silently start rejecting precentor account creation with a misleading error.

**Fix:** Either declare `role` as `string` in the call (acceptable with a comment), or use Better Auth's `setRole` API after creation:
```ts
const { error: createError } = await authClient.admin.createUser({
  name: name.trim(),
  email: email.trim(),
  password,
  role: role,  // Better Auth drizzle adapter accepts any string role
})
```
Or add `'precentor'` to the type via module augmentation so the cast is honest.

### WR-05: `seed-admin.ts` — `auth.api.createUser` return value is not checked for errors

**File:** `scripts/seed-admin.ts:24-27`
**Issue:** `auth.api.createUser` is called without capturing or inspecting the return value. If Better Auth returns an error (e.g., duplicate email race condition after the idempotency check, or a misconfigured secret), the script silently succeeds with `process.exit(0)` instead of surfacing the failure.

**Fix:**
```ts
const result = await auth.api.createUser({
  body: { email, password, name: 'Admin', role: 'admin' },
})
if (result?.error) {
  throw new Error(`createUser failed: ${JSON.stringify(result.error)}`)
}
console.log('Admin account created:', email)
```

### WR-06: Batch psalm add in `CreateSetForm` is not atomic — partial success is silent

**File:** `src/components/precent/CreateSetForm.tsx:86-93`
**Issue:** When the user pastes multiple psalms, the form creates the set and then adds each item in a sequential `for` loop with individual `fetch` calls. If any item fetch fails (network blip, server error), the loop continues silently — some items are added and others are dropped, with no error displayed to the user (the outer `catch` only fires if the entire `try` block throws, not individual awaited fetches that return non-200). The user is navigated to the new set and may not notice missing psalms.

**Fix:** Check `res.ok` for each item fetch inside the loop and collect failures, then display an error after navigation if any items failed:
```ts
const failures: number[] = []
for (const entry of validEntries) {
  if (!entry.psalm) continue
  const itemRes = await fetch(`/api/precent/${id}/items`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ psalmId: entry.psalm.id, verseRange: entry.verseRange }),
  })
  if (!itemRes.ok) failures.push(entry.psalm.id)
}
// surface failures before navigating
```

### IN-03: `date` field in `POST /api/precent` and `PATCH /api/precent/[id]` accepts any non-empty string — no ISO format validation

**File:** `src/app/api/precent/route.ts:35-36`, `src/app/api/precent/[id]/route.ts:39-43`
**Issue:** The validation only checks `typeof body.date !== 'string' || body.date.trim() === ''`. Values like `"not-a-date"` or `"2026-13-45"` pass validation and reach the DB insert. PostgreSQL will reject them at the `date` column type and the error surfaces as a 500.

**Fix:** Add a simple ISO date format check:
```ts
const isoDateRegex = /^\d{4}-\d{2}-\d{2}$/
if (!isoDateRegex.test(body.date.trim()) || isNaN(Date.parse(body.date.trim()))) {
  return NextResponse.json({ error: 'date must be a valid YYYY-MM-DD date' }, { status: 400 })
}
```
