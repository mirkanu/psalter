### On WR-01 (deferred) — should it block phase completion?

**Recommendation: does NOT block phase completion; track as a known data-quality gap.**

Reasoning:
- WR-01 is a **correctness risk under a specific data condition** (a tune where `abcSatb`'s phrase-break markers don't line up 1:1 with `abcNotation`'s), not a missing or broken feature. The phase's three goals (split-leaf layout, inline solfège rendering + approval gate, PlayMiniBar position) all function correctly independent of whether this edge case exists for any given tune.
- The skip reason in `04.9.14-REVIEW-FIX.md` is well-reasoned: both proposed fixes (authoring-time verification process, or a second per-source `melismaPositions` column) are data-model/process changes requiring a migration and melisma-editor UI changes — correctly out of scope for a "code fix" pass, and correctly not resolved by a superficial code patch that could mask real data errors instead of fixing them.
- This is consistent with the project's own binding rule in `.planning/research/lyric-to-note-alignment.md` and `CLAUDE.md`: melisma/alignment issues are treated as data-model decisions requiring deliberate human judgment, not something to silently patch in code.
- **Action item for the phase owner:** track WR-01 as a backlog item — either (a) add a data-authoring-time check in the melisma editor UI that warns when `abcSatb` and `abcNotation` phrase counts diverge for a tune with `melismaPositions` set, or (b) audit existing approved tunes' phrase-count parity between the two ABC sources. Until then, inline Solfège views for tunes with divergent phrase counts *may* silently misplace melisma underlines — a real but bounded risk affecting an unknown, likely small subset of tunes.
