# Phase 04.9.14: Code Review Report

**Reviewed:** 2026-07-12T10:15:11Z
**Depth:** standard
**Files Reviewed:** 9
**Status:** issues_found

## Summary

The three sequential plans (split-leaf layout, inline solfège + approval gate, PlayMiniBar repositioning) each work in isolation, but their combination in `SingingView.tsx` and `NotationRenderer.tsx` introduces several real cross-feature defects. Two are outright crash/regression risks (a tour crash on resize, and a feature that most tunes will never be able to reach in the UI); one is a state-reset bug where scroll-hidden chrome can get stuck permanently invisible after a tune switch; and one is an architectural mismatch where a public-facing approval gate depends on a dev-tools API route that is documented as being gated by Cloudflare Access. None of these were caught by the plan's own UAT specs, which only test the isolated, freshly-loaded state of each feature and never simulate a tune switch or a mid-tour resize.

## Critical Issues

### CR-01: OnboardingTour crashes if the step list shrinks while mid-tour

**File:** `src/components/singing/OnboardingTour.tsx:88-101, 126-144, 158, 214`
**Issue:** `steps` is `useMemo`'d from `isSplitLeafMobile` (`isMobile && viewMode is *-split`), and `isMobile` is recomputed on every `window resize` (lines 88-93). If a user is mid-tour in split-leaf mode on a narrow viewport (`steps.length === 7`, including `SCROLL_HIDE_STEPS`) and resizes/rotates the window across the 768px breakpoint (a normal action — DevTools resize, tablet rotation, browser window drag), `isSplitLeafMobile` flips to `false` and `steps` shrinks back to `STEPS` (`length === 4`) on the next render. If `step` is currently `>= 4` (i.e. the user has already advanced into the `SCROLL_HIDE_STEPS`), the measurement effect calls `measure(steps[step].target)` (line 129) with `steps[step] === undefined`, throwing `TypeError: Cannot read properties of undefined (reading 'target')` inside a `useEffect`. The render path (`steps[step].copy` at line 214, `steps.length - 1` at line 158) has the same exposure once `mounted && !tourSeen` render happens with the stale `step`.
**Fix:** Clamp `step` whenever `steps` shrinks, e.g.:
```tsx
useEffect(() => {
  setStep((s) => Math.min(s, steps.length - 1))
}, [steps.length])
```
or defensively guard the read: `const currentStep = steps[Math.min(step, steps.length - 1)]` and use `currentStep` everywhere instead of `steps[step]`.

### CR-02: Public solfège approval gate depends on a Cloudflare-Access-gated dev API

**File:** `src/components/singing/SingingView.tsx:179-190`; `src/app/api/dev/melisma-decision/route.ts:1-14`
**Issue:** `SingingView` (rendered on the public `/psalms/[slug]` page for anonymous visitors) fetches `/api/dev/melisma-decision?tuneId=...` to drive `melismaStatus` → `isTuneApproved`, which gates the entire inline Solfège feature (Plan 04.9.14-02, "Approval Gate Decision" — locked). The route's own docstring states it is "Gated by Cloudflare Access on `/dev/*` (psalter-dev-tools app)." If that Access policy applies to this path (as the comment claims), every anonymous request from the public psalm page will be redirected to the Access login flow instead of returning JSON; `r.json()` will then reject (or resolve garbage), the `.catch` sets `melismaStatus` to `null`, and `isTuneApproved` is permanently `false` for every real visitor — silently disabling inline Solfège site-wide, the opposite of the feature's intent. Even if Access happens not to cover this specific path today, wiring a permanent public-facing feature to an endpoint that lives under the `/api/dev/` dev-tooling namespace (and is explicitly documented as access-gated) is an architecture mistake that will resurface the moment access rules are tightened or reorganized.
**Fix:** Either (a) confirm and document that `/api/dev/*` API routes are excluded from the Cloudflare Access policy that protects `/dev/*` pages, and add an integration test that hits this route unauthenticated; or (b) move the read path to a stable, non-dev-prefixed route (e.g. `/api/melisma-status`) that is intentionally public, keeping the write path (`POST`) under `/api/dev/` behind Access.

### CR-03: Scroll-hidden chrome (top bar, bottom bar, PlayMiniBar) can get stuck hidden after a tune switch

**File:** `src/components/singing/SingingView.tsx:381-414`
**Issue:** The scroll-hide effect's dependency array is `[abc]` only. `topBarHidden`, `bottomBarHidden`, and `miniBarAutoHidden` are plain `useState` values that are never reset when the effect re-runs. Switching tunes via `TuneSwitcherSheet` changes `activeTune` and therefore `abc`, causing this effect to detach and reattach its scroll listener — but the three "hidden" booleans persist unchanged. If the user had scrolled past the 40px/100px thresholds on the previous tune (hiding the top bar, bottom bar, and PlayMiniBar), switching to a new tune leaves all three permanently hidden even though the new tune's notation renders from the top of a fresh scroll container. Because the container is now already at (or near) `scrollTop = 0`, there may be no further scroll-up delta available to trigger the reveal logic (`scrollingDown = scrollTop > lastScrollTop`), leaving the user with no navigation chrome and no PlayMiniBar until they scroll down and back up again — a state most users won't discover.
**Fix:** Reset the three hidden flags whenever the effect (re)attaches:
```tsx
useEffect(() => {
  if (!abc) return
  setTopBarHidden(false)
  setBottomBarHidden(false)
  setMiniBarAutoHidden(false)
  // ...attach listener as before
}, [abc])
```

### CR-04: GearPopover's single `solfegeAvailable` boolean blocks split-leaf Solfège (JPG) for unapproved tunes, contradicting NotationRenderer's documented gating

**File:** `src/components/singing/SingingView.tsx:540`; `src/components/singing/GearPopover.tsx:57-67, 163-193`; `src/components/notation/NotationRenderer.tsx:141-149, 1141-1173`
**Issue:** `NotationRenderer` explicitly documents (and implements) that the melisma approval gate applies **only** to inline Solfège (`viewMode === 'solfege'`); split-leaf Solfège (`solfege-split`, JPG-based) is "unaffected by melisma approval status" per the locked CONTEXT decision (lines 141-149, 1173+). However, `SingingView` passes the same `isTuneApproved` value as `solfegeAvailable` to `GearPopover` (line 540), and `GearPopover` uses that single boolean to `disabled`-gate the entire "Solfège" notation-type button (lines 163-193) — the one control that drives *both* `solfege` and `solfege-split` via `handleNotationChange`/`handleLayoutChange`. Since most tunes have no melisma-decision row yet (`melismaStatus` defaults to `null` → not approved), this disables the Solfège button for the large majority of tunes, meaning users can no longer reach `solfege-split` (the legacy JPG fallback view) through the UI at all for those tunes — a functional regression versus the pre-existing behavior, and a direct contradiction of the "split-leaf solfège is unaffected" decision that this same plan documents.
**Fix:** Split the availability signal in two — e.g. `solfegeInlineAvailable` (gated by `isTuneApproved`) and `solfegeSplitAvailable` (ungated, based on JPG/`solfegePages` presence) — and have `GearPopover` only disable the Solfège button when the *currently selected layout* requires the gated variant, or disable inline selection specifically rather than the shared notation-type button.

## Warnings

### WR-01: Shared `melismaPositions` applied across two ABC sources with potentially different phrase counts

**File:** `src/components/notation/NotationRenderer.tsx:750-756, 1040-1051`
**Issue:** `buildUnifiedAbc` is called once with `abc` (staff view) and once with `solfegeAbc || abc` (inline solfège view, sourced from `abcSatb` when available — see `SingingView.tsx:352-359`). Each call independently derives its own phrase split (`splitOnPhraseBreaks(sourceAbc)`), but both calls apply the *same* `melismaPositions` prop, indexed by phrase number, to build `w:` lines. The code's own comment acknowledges "the two sources may have different phrase counts (e.g. SATB carries markers the monophonic column lacks)" while simultaneously asserting "everything else ... is identical regardless of source". If `abcSatb`'s `% PHRASE_BREAK` markers don't line up 1:1 with `abcNotation`'s, `melismaPositions[i]` (authored/approved against one source's phrase `i`) will be applied to a different phrase in the other source, producing silently wrong melisma (`_`) placement in the inline Solfège view — a correctness violation of the project's binding lyric-to-note alignment rules (see `.planning/research/lyric-to-note-alignment.md`).
**Fix:** Verify at data-authoring time (melisma editor) that phrase counts/order match between `abcNotation` and `abcSatb` for every tune with `melismaPositions` set, or compute/store per-source melisma positions instead of a single shared array.

### WR-02: Dead props passed to `GlassBottomBar` that are documented as unused

**File:** `src/components/singing/SingingView.tsx:512-513, 523`; `src/components/singing/GlassBottomBar.tsx:9-10, 24, 41-53`
**Issue:** `GlassBottomBar`'s own doc comments say `viewMode`, `onViewModeChange`, and `showLyricsOption` are "Retained for prop compatibility ... view selection now lives in GearPopover" / "no longer rendered here" — and indeed they are not destructured in the component signature (lines 41-53). Yet `SingingView` still passes all three at the call site. This is dead wiring across two files: harmless today, but it invites a future maintainer to assume `GlassBottomBar` reads `viewMode` (it doesn't), or to "fix" a bug by editing the wrong component.
**Fix:** Remove the three props from both the `Props` interface and the call site, or if kept intentionally for a documented reason, add a one-line note at the call site cross-referencing why they're still passed.

### WR-03: SoundCloud iframe combines `allow-scripts` and `allow-same-origin` in its sandbox attribute

**File:** `src/components/singing/PlayMiniBar.tsx:202-210`
**Issue:** `sandbox="allow-scripts allow-same-origin"` is a well-known anti-pattern: together, these two tokens let the framed document script its way out of the sandbox (e.g. via `iframe.sandbox = ''` self-mutation or by navigating the parent), effectively defeating the purpose of the sandbox attribute. The `src` is built from `soundcloudUrl`, a DB-controlled field (populated during tune ingestion/admin edits) rather than raw user input, so exploitability today is low, but the combination should be avoided as a matter of defense in depth, especially since this DB field is precentor/admin-editable.
**Fix:** Drop `allow-same-origin` unless SoundCloud's embed genuinely requires same-origin storage access (it does not, per SoundCloud's own embed docs), or drop `allow-scripts` if playback controls don't need script execution in-frame.

### WR-04: Ad hoc type assertions bypass `TuneOption`'s declared type in three places

**File:** `src/components/singing/SingingView.tsx:352-359, 460, 465`
**Issue:** `(activeTune as { abcSatb?: string | null }).abcSatb`, `(activeTune as { phraseShapeOverride?: number[] | null } | undefined)?.phraseShapeOverride`, and `(activeTune as { melismaPositions?: number[][] | null } | undefined)?.melismaPositions` each re-declare a fragment of `TuneOption`'s shape inline instead of adding the fields to the shared `TuneOption` type (imported from `./types`). This bypasses the type checker's ability to catch a rename or type change in the underlying query and duplicates the field's type in three separate call sites.
**Fix:** Add `abcSatb`, `phraseShapeOverride`, and `melismaPositions` to the `TuneOption` interface in `types.ts` and drop the inline casts.

### IN-03: Inconsistent/confusing conditional expression in test helper

**File:** `tests/e2e/split-leaf.spec.ts:174`
**Issue:** `const sizeAfter = verseText.count && (await verseText.count()) ? ... : null` — `verseText.count` (the unbound method reference, not a call) is always truthy, so the `verseText.count &&` clause is a no-op; the line is functionally equivalent to (and should just read) `(await verseText.count()) ? ... : null`, matching the cleaner pattern used two lines above for `sizeBefore`.
**Fix:** `const sizeAfter = (await verseText.count()) ? await verseText.evaluate(...) : null`.
