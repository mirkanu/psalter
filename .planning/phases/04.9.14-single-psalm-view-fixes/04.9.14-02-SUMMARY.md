# Phase 04.9.14 Plan 02: Inline View — Solfege ABC Rendering + Approval Gate Summary

Implemented live abcjs rendering for the inline Solfège view (previously JPG-only), gated behind the melisma editor's approval status, by extracting the Staff view's ABC-composition pipeline into a reusable `buildUnifiedAbc` factory and threading a new `solfegeAbc`/`isTuneApproved` prop pair from `SingingView` through `NotationRenderer` and `GearPopover`.

## What Was Built

### Task 1 — Enable abcjs rendering for solfège in inline view
`NotationRenderer.tsx`'s `unifiedAbc` `useMemo` (the ~250-line pipeline that composes phrase bodies + melisma-aware `w:` lines from `abc`) was extracted into a `buildUnifiedAbc(sourceAbc: string)` factory function. Two `useMemo` calls now invoke it — one for the existing Staff view (`unifiedAbc = buildUnifiedAbc(abc)`) and a new one for inline Solfège (`unifiedSolfegeAbc = buildUnifiedAbc(solfegeAbc || abc)`). Each call computes its own local `split`/`visiblePhraseIndices` since the two ABC sources can carry a different phrase count (e.g. the SATB column carries `% PHRASE_BREAK` markers the monophonic column may lack). The inline solfège branch (`viewMode === 'solfege'`) now renders an `<AbcPlayer abc={unifiedSolfegeAbc} .../>` with the same props as Staff view (scale, staffWidthFactor, renderLyricsBelow, etc.), falling back to the pre-existing JPG + thumbnail branch when no solfège ABC is available (`solfegeAbc` empty AND `abc` empty). Split-leaf solfège (`viewMode === 'solfege-split'`) is untouched — still JPG-only.

### Task 2 — Wire solfège ABC through SingingView
`SingingView.tsx` derives `solfegeAbc = sopranoOnly(pickAbcWithMarkers(activeTune.abcSatb, activeTune.abcNotation)) ?? ''` via `useMemo`, imported from `@/lib/utils`, and passes it to `NotationRendererClient` as the new `solfegeAbc` prop. `NotationRendererProps` gained `solfegeAbc?: string` (default `''`) and `isTuneApproved?: boolean` (default `true`, so non-gated callers like `/tunes/[id]` and `/study` see no behavior change).

### Task 3 — Approval gate for inline solfège view
Added `isTuneApproved = melismaStatus === 'approved'` in `SingingView.tsx` and passed it through to `NotationRendererClient`. In `NotationRenderer.tsx`, a new branch precedes the ABC-rendering branch: `viewMode === 'solfege' && !isTuneApproved` renders an inline message ("This tune's notation hasn't been approved yet. Please check the melisma editor.") instead of any notation. This guard applies ONLY to inline solfège — Staff view and split-leaf solfège are never gated, matching CONTEXT's locked "Approval Gate Decision."

### Task 4 — GearPopover approval logic
`GearPopover.tsx`'s `handleNotationChange` toast copy was updated to reference melisma-editor approval explicitly ("This tune's melisma positions haven't been approved. Approve in the melisma editor to enable solfège view."), and a `title` tooltip ("Notation not yet approved — use melisma editor to approve") was added to the disabled Solfège radio button. `SingingView.tsx` now passes `staffAvailable={!!(activeTune?.abcNotation || activeTune?.abcSatb)}` (no longer factoring in `melismaStatus`) and `solfegeAvailable={isTuneApproved}` — both computed from the same `isTuneApproved` value the render guard uses, so the gear popover's disabled state and the actual rendered content never disagree.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 — Bug] `melismaStatus` fetch read the wrong response field**
- **Found during:** Task 3
- **Issue:** `SingingView.tsx`'s melisma-status effect read `data.status`, but `/api/dev/melisma-decision`'s `GET` handler returns `{ currentStatus, history }` — there is no `status` field on the response body. This left `melismaStatus` permanently `null` in production, which would have silently made the entire approval gate this plan implements inert (all tunes would appear "not approved" forever, or — depending on the prior gating logic's polarity — the opposite).
- **Fix:** Changed to `setMelismaStatus(data.currentStatus ?? null)`.
- **Files modified:** `src/components/singing/SingingView.tsx`
- **Commit:** `be39ca0`

**2. [Rule 1 — Bug] `staffAvailable` contradicted the locked "Staff always available" decision**
- **Found during:** Task 3/4
- **Issue:** The pre-existing `staffAvailable` prop passed to `GearPopover` was `!!(activeTune?.abcNotation || activeTune?.abcSatb) && melismaStatus !== 'not_approved'` — i.e. Staff view was ALSO gated behind melisma approval, directly contradicting CONTEXT's locked "Approval Gate Decision" ("Staff view remains available regardless of approval status") and this plan's Task 3 acceptance criterion #4.
- **Fix:** Removed the `melismaStatus` clause; `staffAvailable` now reflects only ABC data presence.
- **Files modified:** `src/components/singing/SingingView.tsx`
- **Commit:** `be39ca0`

**3. [Rule 2 — Missing functionality, minor] Dead code left over from the `unifiedAbc` refactor**
- **Found during:** Task 1 (post-refactor lint pass)
- **Issue:** Extracting `buildUnifiedAbc` left the top-level `split`, `T`, `effectivePhraseTotal`, and `visiblePhraseIndices` variables entirely unused (each caller now computes its own local equivalents).
- **Fix:** Removed all four; verified via `git stash`/eslint-diff that no other code depended on them.
- **Files modified:** `src/components/notation/NotationRenderer.tsx`
- **Commit:** `4c72922`

No architectural (Rule 4) deviations — no checkpoint was needed.
