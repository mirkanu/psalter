<domain>
## Phase Boundary

A surgical regression fix. Phase 4.9.6 rewrote `mapCycleToPhraseSyllableLines` to consume `Stanza[]` and map metrical lines onto staff phrases, but treated `phrasesPerCycle` as an upper bound on metrical-line count. CM/LM/SM stanzas have 4 metrical lines and only T=2 staff phrases, so **lines 2 and 3 silently disappear** from the staff view. DCM stanzas lose lines 4–7 of each cycle.

**Strictly in scope:**
- Fix `mapCycleToPhraseSyllableLines` (one function in `src/lib/stanza-cycles.ts`) to group `linesPerStanza / phrasesPerCycle` metrical lines into each phrase slot.
- Strengthen the Plan 07 regression tests so they actually fail under the broken implementation (i.e. assert all 4 CM metrical lines appear in the output for Psalm 23 stanza 0).
- Re-run Playwright UAT against the live psalter.gsdlabs.dev once deployed.

**Strictly out of scope:**
- Any data-model changes (`lyrics_structured` shape stays unchanged).
- Lyrics-only view (already correct — StanzaList consumes Stanza[] directly).
- Mid-stanza superscript handling (already correct).
- Tune-quality phrase-count curation backlog (still deferred).

</domain>

<decisions>
## Implementation Decisions

### Root cause (verified by live inspection)

- **D-01:** The bug lives entirely in `src/lib/stanza-cycles.ts:67-91` (function `mapCycleToPhraseSyllableLines`). The loop bound `Math.min(flatLines.length, phrasesPerCycle)` causes silent line-dropping when `flatLines.length > phrasesPerCycle`. Confirmed by reading the source and matching against live staff-view output for Psalm 23 (Crimond CM), Psalm 100 (Old 100th LM), Psalm 1 (St. Peter CM).

### The fix

- **D-02:** Replace the broken loop with line-grouping:
  ```ts
  const linesPerPhrase = Math.max(1, Math.floor(flatLines.length / phrasesPerCycle))
  for (let p = 0; p < phrasesPerCycle; p++) {
    const start = p * linesPerPhrase
    const slice = flatLines.slice(start, start + linesPerPhrase)
    if (slice.length === 0) continue
    const text = slice
      .map((l) => l.syllables?.length ? l.syllables.join(' ') : syllabifyForAbc(l.text))
      .join(' ')
    result[p] = [text]
  }
  ```
  This restores the pre-4.9.6 semantics of `splitStanzaIntoPhrasePortions` (which packed 2 metrical lines into each staff phrase for CM 8.6.8.6) without re-introducing the meter-string heuristic that 4.9.6 deliberately replaced.

- **D-03:** **Return shape stays `string[][]` (B1 contract preserved).** Each phrase slot still gets a single-element array `[joinedSyllableText]`. The renderer's `grid[i] ?? ['']` consumer at NotationRenderer.tsx:447-454 keeps working unchanged.

- **D-04:** **Under-fill behaviour (D-12 from Phase 4.9.6 carries forward):** when a cycle has fewer lines than expected (odd stanza count against DCM, partial last cycle), unfilled phrase slots stay as the initial `['']` sentinel — blank lyric portion, never repeat content.

- **D-05:** **Over-fill behaviour (new):** if a stanza has MORE metrical lines than expected by meter (e.g. parser error, or alternate meter like 10.10.10.10.10 with 5 lines and T=5), `linesPerPhrase = floor(5/5) = 1` per phrase — one line per phrase slot, correctly. If parsing produced an unexpected line count, fall through with what we have.

### Test strengthening

- **D-06:** **Augment `tests/psalm-23-crimond-regression.test.ts`** with the assertion that would have caught this bug:
  ```ts
  it('all 4 CM metrical lines appear in mapCycleToPhraseSyllableLines output', () => {
    const grid = mapCycleToPhraseSyllableLines([r.stanzas[0]], 2)
    const concatenated = grid.map((slot) => slot[0]).join(' ')
    // Every metrical line's leading word must appear in the output.
    expect(concatenated).toMatch(/Lord's my she/)        // line 0
    expect(concatenated).toMatch(/He makes me/)          // line 1
    expect(concatenated).toMatch(/In pas-?tures green/)  // line 2 — was dropped pre-fix
    expect(concatenated).toMatch(/the qui-?et waters by/) // line 3 — was dropped pre-fix
  })
  ```

- **D-07:** **Add a DCM test** (analogous): for a `double_length=true` tune with a 2-stanza cycle, assert all 8 metrical lines (4 per stanza × 2 stanzas) appear in the output.

- **D-08:** **Add an LM test** for Psalm 100 + Old 100th to lock in the LM 8.8.8.8 case (4 lines, T=2, 2 lines per phrase).

### UAT

- **D-09:** **Playwright UAT** loads the live site after deploy and asserts (per psalm):
  - Staff view contains the substring of the *last* metrical line of each visible stanza (the line that's currently being dropped). Concrete: for Psalm 23, the rendered text under the staff must include `"waters by"`.
  - Psalm 100 staff view must include `"rejoice"` (line 3 of stanza 0).
  - DCM example (pick one from `tunes WHERE double_length=true`): must include the last metrical line of the second stanza in the cycle.

<code_context>
## Existing Code Insights

### Why the bug went undetected in Plan 07

The Plan 07 test at `tests/psalm-23-crimond-regression.test.ts:46-58` asserted:
```ts
const grid = mapCycleToPhraseSyllableLines([r.stanzas[0]], 2)
expect(grid).toHaveLength(2)
grid.forEach((slot) => {
  expect(Array.isArray(slot)).toBe(true)
  expect(slot.length).toBe(1)
  expect(typeof slot[0]).toBe('string')
})
expect(grid[0][0].length).toBeGreaterThan(0)
expect(grid[1][0].length).toBeGreaterThan(0)
```

It checked the **shape** of the grid (length 2, each cell a single-string array, non-empty) but never asserted that all 4 metrical lines of the stanza appeared somewhere in the output. A grid containing only lines 0 and 1 satisfies all of these assertions — and that's exactly what the broken implementation produces.

### Why the Playwright UAT screenshot looked OK

The UAT screenshot showed `<sup>` verse-numbers and stacked stanza rows under each system. At a glance, the lyrics looked correct — but only because stanza 0 line 0 ("The Lord's my shepherd...") was visible and the tspan-stacking made it look like a normal staff overlay. The dropped lines ("In pastures green / the quiet waters by") were never under the second staff system; the staff just ended early.

### Why lyrics-only view is unaffected

`NotationRenderer.tsx:735-740` passes `stanzas` directly to `<StanzaList>`:
```ts
const lyricsBelow = showLyrics && stanzas.length > 0 ? (
  <div className="mt-4 max-h-[60vh] overflow-y-auto">
    <StanzaList stanzas={stanzas} />
  </div>
) : null
```

`StanzaList` iterates `stanza.lines` directly with no phrase-count cap. The bug is exclusive to the staff-overlay pathway.
