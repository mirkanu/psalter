## Summary

This phase implements melisma-aware `w:` line generation for the Scottish Psalter staff view. The core algorithm (`buildWLineFromSolfa` + `getPassingPositions`) is structurally sound and the test coverage is appropriate. The main new wiring in `NotationRenderer` (the `solfegeVoices` memo + `wLineForSyllables` helper) is correctly guarded with null checks.

The critical issue is a semantically incorrect fallback token (`*`) emitted into the abcjs `w:` field when syllable tokens run short — abcjs interprets `*` as a special alignment token, not a visible asterisk, causing invisible lyric misalignment rather than a safe no-op. Four warnings cover: a `force-dynamic` / `generateStaticParams` conflict that silently defeats the static build, a misleading comment about sort tie-breaking direction, a type assertion that bypasses the type system for `abcSatb` on the primary tune, and a dead `TODO` comment marking a function that remains called. Three info items flag dead code.

## Critical Issues

### CR-01: Incorrect abcjs fallback token `*` causes silent lyric misalignment

**File:** `src/lib/abc-melisma.ts:184`
**Issue:** When the syllable token list runs shorter than the note count (i.e. `sylIdx` exceeds `sylTokens.length`), the code emits `'*'` as the per-note token. In abcjs, `*` is a reserved `w:` field token meaning "advance alignment by one note without printing anything" — it is not a literal asterisk. The intended behaviour (safe placeholder) is instead a stealth syllable-skip that misaligns every subsequent syllable to the wrong note. The mismatch warning in Step 5 fires _before_ building tokens, but Step 6 can still hit this path when `adjustedPassings` produces more non-passing slots than `sylTokens.length` (e.g. when `syllabicCount` converges to `sylTokens.length` after heuristic but the adjustedPassings array iteration creates additional gaps due to the `getDurationEvents` slice misaligning with `allPassings.slice`).

The correct safe fallback is `'_'` (hold continuation, semantically: "this note continues the previous syllable"), which abcjs renders silently and does not perturb alignment.

**Fix:**
```typescript
// abc-melisma.ts line 184 — replace '*' with '_'
tokens.push(sylTokens[sylIdx] ?? '_')
```

## Warnings

### WR-01: `force-dynamic` and `generateStaticParams` coexist — static params are silently ignored

**File:** `src/app/psalms/[id]/page.tsx:1,22`
**Issue:** The file exports both `export const dynamic = 'force-dynamic'` (line 1) and `export async function generateStaticParams()` (line 22). Next.js documents that `force-dynamic` opts the route out of static generation entirely — it renders every request at runtime. `generateStaticParams` is therefore called but its return value is discarded; no HTML is pre-rendered at build time. This is a silent correctness divergence from the stated architecture intent in CLAUDE.md ("Public psalm and tune pages use `generateStaticParams` — no runtime DB queries on the read path"). The `fetchPsalmListRows()` and `getPsalmNeighbors()` calls inside the page component fire on every request, which is explicitly what the static approach was meant to avoid.

If the intent is dynamic (e.g. because `lyricsStructured` is not yet fully migrated), the `generateStaticParams` export should be removed to make the intent explicit. If the intent is static, `force-dynamic` must be removed.

**Fix:** Choose one of:
```typescript
// Option A — truly dynamic (remove generateStaticParams)
export const dynamic = 'force-dynamic'
// delete the generateStaticParams function

// Option B — static (remove force-dynamic, keep generateStaticParams)
// delete: export const dynamic = 'force-dynamic'
export async function generateStaticParams() { ... }
```

### WR-02: Misleading comment — sort tie-breaking favours earlier, not later, indices

**File:** `src/lib/abc-melisma.ts:159`
**Issue:** The comment reads "later indices preferred for ties". JavaScript's `Array.prototype.sort` has been stable (preserves original insertion order for equal elements) in V8 since Node 12 and in all modern browsers. The `candidates` array is built by iterating event indices in ascending order, so for two events with equal duration, the lower-index event appears first in `candidates` and is converted to passing first. The comment is therefore backwards. This matters because the heuristic converts notes to passing greedily from the front — the choice of which note at a tie is incorrectly documented, which could mislead future maintenance of the tie-breaking strategy.

**Fix:**
```typescript
// abc-melisma.ts line 159 — correct the comment
// Convert shortest notes to passing, earlier indices preferred for ties (stable sort)
```

### WR-03: Type assertion casts bypass type safety for `abcSatb` on primary tune in `page.tsx`

**File:** `src/app/psalms/[id]/page.tsx:124,130`
**Issue:** The primary tune is shaped from `rawTune` (typed as the Drizzle query result for `psalmVersionTunes[n].tune`). The fields `abcSatb` and `solfegeOcrText` are accessed via `(primaryTuneRow as { abcSatb?: string | null }).abcSatb` — a runtime cast that bypasses the type checker. If the DB schema ever drops or renames these columns (both are already present in the schema at the time of review), the cast silently returns `undefined` instead of a compile-time error. The same fields are available without a cast via `fetchTuneDetail` which fetches the full tune. Either the query feeding `fetchPsalmDetail` should explicitly include these columns, or the cast should be replaced with an optional-chain against a properly-typed object.

**Fix:**
```typescript
// Extend the psalmVersionTunes.tune sub-query in fetchPsalmDetail to include
// abcSatb and solfegeOcrText, then access them directly:
abcSatb: primaryTuneRow.abcSatb ?? null,
solfegeOcrText: primaryTuneRow.solfegeOcrText ?? null,
```

### IN-03: `generateStaticParams` silently returns `[]` on DB error — hides build failures

**File:** `src/app/psalms/[id]/page.tsx:46`
**Issue:** The `generateStaticParams` function wraps the entire DB query + slug computation in `try { ... } catch { return [] }`. If the database is unreachable at build time (network partition, missing `DATABASE_URL`, cold container), the build silently produces zero static params rather than failing. Next.js will then generate no static pages, and every request will fall through to the runtime handler with no indication that anything went wrong. A better pattern is to let the error propagate (Next.js will abort the build with a clear message) or at minimum log the error before returning.

**Fix:**
```typescript
} catch (err) {
  console.error('[generateStaticParams] DB query failed:', err)
  return []  // or: throw err  (to hard-fail the build)
}
```
