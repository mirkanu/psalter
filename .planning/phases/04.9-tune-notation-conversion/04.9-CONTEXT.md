<decisions>
## Implementation Decisions

### Approach
- **D-01:** One-shot pipeline — single Claude vision call per tune, image → ABC string directly. No separate OCR + deterministic parser step.
- **D-02:** Model tier: `claude-haiku-4-5` as primary (fast, cheap for clean printed text). Auto-escalate to `claude-sonnet-4-6` if the haiku output fails abcjs validation.
- **D-03:** Script stores intermediate OCR output as JSON (one entry per tune) before DB update — enables debugging and partial reruns without re-calling the API.

### Key Convention
- **D-04:** Use the actual printed key from each image header (DOH=C → K:C, DOH=G → K:G, etc.). Do NOT transpose to G major. The 5 hand-crafted ABCs will be inconsistent in key with generated ones; that's acceptable for now and can be re-keyed in a future editorial pass.

### Image-to-Tune Mapping
- **D-05:** Derive slug from DB tune name at runtime: lowercase + replace non-alphanumeric with hyphen + collapse repeated hyphens (e.g. `"Artaxerxes (EPC tune)"` → `"artaxerxes-epc-tune"`). Look for `{slug}-solfege-0.jpg` in `public/tunes/`.
- **D-06:** Log any tunes where no matching file is found (unmatched list in output JSON). Do not error; continue processing.
- **D-07:** For tunes with multiple solfège pages (e.g. `aurelia-solfege-0.jpg` + `aurelia-solfege-1.jpg`): send ALL pages to the LLM in a single call (multi-image message) and ask it to identify page order and produce the complete ABC. The LLM can determine ordering from visual cues (page numbers, "continued" headers, musical continuity).

### Failure Handling
- **D-08:** If the LLM output (after haiku → sonnet escalation) still fails abcjs validation: do NOT update that tune's `abc_notation`. The tune keeps its current state (NULL or existing hand-crafted value). Log to failures JSON.
- **D-09:** Acceptance bar: **95%+ of the 172 tunes must have valid ABC notation** in DB after the script runs. A final Playwright spot-check of 10+ tunes verifies rendering correctness (per TUNE-09 success criteria).
- **D-10:** Script is retained in `scripts/` (per roadmap SC-5). Not deleted after run.

### Script Design
- **D-11:** Two scripts as per roadmap plan structure:
  - `scripts/ocr-solfege.ts` — iterates all solfège files, calls Claude vision, stores raw output + generated ABC per tune to `scripts/output/solfege-ocr.json`
  - `scripts/apply-abc-notation.ts` — reads `solfege-ocr.json`, validates each ABC string with abcjs (server-side render check), bulk-updates `tunes.abc_notation` for passing tunes

### Claude's Discretion
- Exact slugification function implementation (edge cases for parentheses, apostrophes, punctuation)
- abcjs server-side validation approach (headless render vs regexp check for structural validity)
- Prompt wording for multi-image "which page is first?" instruction
- Rate limiting / concurrency for 168 API calls (sequential with small delay, or batched)

</decisions>

<specifics>
## Specific Ideas

- Spike prompt structure (from `/tmp/solfege-spike.js`) proved effective — adapt it as the production OCR prompt:
  - Identify tune name + meter from header
  - Read DOH key
  - Extract soprano (top) voice line only
  - Output complete ABC string with X/T/C/M/L/Q/K headers
- The `se` chromatic in tonic sol-fa = sharpened soh = `^G` in ABC (when DOH=C) — the LLM handled this correctly in the spike
- Tonic sol-fa rhythm convention: `d :m` = d on beat 1, m on beat 2 (each a crotchet in C time); `d :-` = d held for 2 beats; `d :—` with following `—` = whole note — the LLM slightly underestimated held note durations; production prompt should clarify this

</specifics>
