# Phase 04.12: Code Review Report

**Reviewed:** 2026-06-14
**Depth:** standard
**Files Reviewed:** 15
**Status:** issues_found

## Summary

Reviewed the full Explore Page Rebuild implementation: migration script, query layer, page components, sub-components, and tests. The implementation is structurally sound but contains four blockers: a data migration bug that silently drops entries for Airtable records linked to multiple topics, a URL null-safety crash in the Heidelberg Catechism renderer, a slug-routing mismatch that produces broken links for messianic topics whose names collide with other Nave's topics, and inconsistent psalm counts between the badge and the detail page caused by querying two different junction tables. Several secondary issues affect display correctness and test reliability.

## Critical Issues

### CR-01: Migration silently discards all but the last topic for multi-topic Nave's entries

**File:** `scripts/migrate-explore-04-12.ts:106-129`

**Issue:** `migrateNavesTopicEntries` iterates over `linkedTopicIds` and for each topic calls an `INSERT ... ON CONFLICT (airtable_id) DO UPDATE` that sets only `sub_topic` and `quotation` — it does **not** update `navesTopicId`. This means: if an Airtable record's "Main Topic" field links to two topics, the first iteration inserts a row with `navesTopicId = topic1`. The second iteration hits the unique constraint on `airtable_id`, updates `sub_topic`/`quotation` (no-op), and returns the existing row's `id` (topic1's entry). Verse links from the second iteration are attached to topic1's entry, not topic2. The entry is never associated with topic2 at all. Any content that belongs under topic2 is silently misfiled.

**Fix:** To correctly associate one Airtable record with multiple topics, generate a composite key instead of using `airtable_id` alone. One approach: insert a separate row per `(airtable_id, navesTopicId)` pair, using a compound unique constraint as the conflict target.

```sql
-- Schema addition
ALTER TABLE naves_topic_entries ADD CONSTRAINT uq_entry_topic UNIQUE (airtable_id, naves_topic_id);
```

```typescript
// Migration: change conflict target
await db
  .insert(schema.navesTopicEntries)
  .values({ airtableId: r.id, navesTopicId, subTopic, quotation })
  .onConflictDoUpdate({
    target: [schema.navesTopicEntries.airtableId, schema.navesTopicEntries.navesTopicId],
    set: { subTopic: sql`excluded.sub_topic`, quotation: sql`excluded.quotation` },
  })
  .returning({ id: schema.navesTopicEntries.id })
```

### CR-02: Heidelberg Catechism crashes at render if `url` is NULL in the database

**File:** `src/components/HeidelbergCatechism.tsx:54`

**Issue:** The schema defines `creedal_references.url` as `text('url')` with no `.notNull()`, so it can be `NULL`. The `fetchHeidelbergCatechism` query casts the result as `Array<{ url: string }>` (non-nullable), hiding the null. At render time, line 54 calls `row.url.startsWith('http')` unconditionally. If any row has `url = NULL`, this throws a `TypeError: Cannot read properties of null (reading 'startsWith')` and crashes the Explore page Server Component.

**Fix:**
```tsx
// HeidelbergCatechism.tsx line 54
href={row.url
  ? (row.url.startsWith('http') ? row.url : `https://${row.url}`)
  : '#'}
```

Also update the type in `CatechismRow`:
```typescript
interface CatechismRow {
  question_number: number
  url: string | null   // matches schema nullable
  verses: Array<{ psalmId: number; verseNumber: number | null }>
}
```

### CR-03: `MessianicByTopic` generates unambiguous slugs that may not match the actual disambiguated route

**File:** `src/components/MessianicByTopic.tsx:29`

**Issue:** `MessianicByTopic` builds its `href` with a local `slugify(t.name)` call (no disambiguation). The `/explore/naves/[slug]` route is resolved by `buildNavesSlugMap`, which appends `-${id}` when two Nave's topics produce the same base slug. If any of the 12 messianic topics shares a slug with another Nave's topic, the link generated by `MessianicByTopic` will not match a real route and will 404.

The parent `explore/page.tsx` already builds a correct `navesSlugMap` (line 95) and uses it for `NavesExpand` — but does not pass those slugs into `MessianicByTopic`. Instead, `messianicByTopic` comes from a separate query (`fetchMessianicByTopic`) whose results are passed without disambiguation.

**Fix:** Pass pre-computed slugs from the explore page into `MessianicByTopic`, sourcing them from `navesSlugMap` keyed on topic id. This requires `fetchMessianicByTopic` results to be cross-referenced against `navesSlugMap`:

```tsx
// In explore/page.tsx
const messianicWithSlugs = messianicByTopic
  .filter((t): t is typeof t & { name: string } => t.name !== null)
  .map((t) => ({ ...t, slug: navesSlugMap.get(t.id) ?? slugify(t.name) }))

// Pass to component
<MessianicByTopic topics={messianicWithSlugs} />
```

Update `MessianicByTopic` to accept a `slug` field and use it instead of computing its own.

### CR-04: `fetchNavesTopicsWithCounts` and `fetchNavesSubTopics` query different junction tables, producing inconsistent psalm counts

**File:** `src/db/queries/explore.ts:62-71` and `src/db/queries/explore.ts:227-248`

**Issue:** `fetchNavesTopicsWithCounts` counts distinct psalms via `verse_naves_topics` (the old junction table). `fetchNavesSubTopics` — used on the `/explore/naves/[slug]` detail page — joins via `verse_naves_topic_entries` (the new table populated by the 04.12 migration). These are populated from different Airtable sources and will contain different rows. A Nave's topic badge may read "12 psalms" on the Explore grid while the detail page lists only 3 psalm links (or vice versa), undermining user trust and indicating at least one table has stale data.

**Fix:** Decide which junction table is authoritative and use it consistently for both the count badge and the detail page. If `verse_naves_topic_entries` is the new canonical source, rewrite `fetchNavesTopicsWithCounts` to count through it:

```sql
SELECT nt.id, nt.name,
       COUNT(DISTINCT v.psalm_id)::integer AS psalm_count
FROM naves_topics nt
JOIN naves_topic_entries nte ON nte.naves_topic_id = nt.id
JOIN verse_naves_topic_entries vnte ON vnte.entry_id = nte.id
JOIN verses v ON v.id = vnte.verse_id
GROUP BY nt.id, nt.name
ORDER BY psalm_count DESC
```

## Warnings

### WR-01: `AuthorsTable` sort direction contradicts the "earliest date" label

**File:** `src/components/AuthorsTable.tsx:44-48`

**Issue:** The table header reads "Sorted from earliest date" with a `ChevronUp` (ascending) icon, and the sort comparator is `a.dateBC - b.dateBC` (ascending numeric). For BC dates, a larger number means further in the past: BC 1406 is earlier than BC 500. Ascending numeric order places BC 500 before BC 1406, which is most-recent-first, not earliest-first. Psalm 90 (Moses, ~1406 BC) should appear first but appears near the end.

**Fix:** Reverse the comparator:
```typescript
return b.dateBC - a.dateBC  // larger BC number = earlier in history = sort first
```

### WR-02: `fetchHeidelbergCatechism` groups by `(question_number, url)` — same question with two URL variants produces duplicate collapsible rows with a duplicate React key

**File:** `src/db/queries/explore.ts:203-222`, `src/components/HeidelbergCatechism.tsx:45`

**Issue:** The SQL groups by both `cr.question_number` and `cr.url`. If a question number appears with two different `url` values in the database (possible given there's no unique constraint on `(creed, question_number)`), the result set contains two rows for the same question number. `HeidelbergCatechism.tsx` uses `key={row.question_number}`, producing a duplicate React key warning and rendering the question twice with no visual distinction.

**Fix:** Group only by `question_number`, taking a consistent URL with `MIN(cr.url)` or `MAX(cr.url)`:
```sql
SELECT cr.question_number,
       MIN(cr.url) AS url,
       json_agg(...) AS verses
FROM creedal_references cr
JOIN verses v ON v.id = cr.verse_id
WHERE cr.creed = 'Heidelberg'
GROUP BY cr.question_number
ORDER BY cr.question_number
```

### WR-03: Migration drops `creedal_references` records that link to more than one verse

**File:** `scripts/migrate-explore-04-12.ts:147`

**Issue:** `migrateCreedalReferences` takes only `linkedVerses[0]` — the first linked verse — and stores it as the sole `verse_id`. The schema has a single `verse_id` column on `creedal_references` (not a junction table), so multiple verse links for one creedal reference cannot be stored. If the Airtable "Creedal References" table links a question to multiple verses, all but the first are silently discarded.

This is a schema limitation compounded by silent data loss in migration. If the Airtable data genuinely has multi-verse creedal references, the Heidelberg Catechism display will be incomplete.

**Fix (schema):** Convert `creedal_references` to a `verse_creedal_references` junction table, or accept the limitation explicitly and log a warning when `linkedVerses.length > 1`:
```typescript
if (linkedVerses.length > 1) {
  console.warn(`  [warn] creedal ref ${r.id} has ${linkedVerses.length} verses; only first stored`)
}
```

### WR-04: E2E test mobile column-hiding assertion always passes via false-positive path

**File:** `tests/e2e/explore-rebuild.spec.ts:222-234`

**Issue:** The test asserts that the "Date B.C." column is hidden at 375px viewport width, with the comment "They use hidden sm:table-cell". However, `AuthorsTable.tsx` does not apply any responsive hiding classes (`hidden`, `sm:table-cell`, etc.) to its columns — all four columns are always rendered. The test has a fallback branch (line 232-234) that fires when the element is "not in DOM at all" and treats that as a pass. In practice, the header is in the DOM at 375px and `isVisible()` returns `true`, so the test fails the `!isVisible` check and falls through to the else-branch which passes. The test is not detecting the intended behaviour.

**Fix:** Either add responsive hiding to `AuthorsTable.tsx`:
```tsx
<th className="w-24 px-3 py-2 font-semibold hidden sm:table-cell">Date B.C.</th>
<td className="w-24 px-3 py-2 text-muted-foreground hidden sm:table-cell">...</td>
```
Or remove the misleading test assertion. The current code tests neither path correctly.

### WR-05: `naves/[slug]/page.tsx` calls `fetchNavesTopicsWithCounts` three times per build/request without benefit

**File:** `src/app/explore/naves/[slug]/page.tsx:42, 50, 62`

**Issue:** `generateStaticParams`, `generateMetadata`, and the page component each call `fetchNavesTopicsWithCounts()`. React `cache()` deduplicates within a single request, so `generateMetadata` and the page body share one DB hit. However, `generateStaticParams` runs at build time as a separate invocation and hits the DB once more. More importantly, the slug-resolution logic (`buildNavesSlugMap`) is duplicated across all three call sites within the same file with identical implementations. If the slug resolution logic ever diverges from `page.tsx`'s `buildDisambiguatedSlugMap`, the detail page will resolve slugs differently from the list page.

**Fix:** Extract `slugify` and `buildNavesSlugMap` into a shared utility (e.g., `src/lib/naves-slugs.ts`) imported by both `explore/page.tsx` and `explore/naves/[slug]/page.tsx`.

### IN-03: Migration has no `client.end()` in the error path

**File:** `scripts/migrate-explore-04-12.ts:201-204`

**Issue:** The `.catch` handler calls `process.exit(1)` without calling `client.end()`. For a one-shot script, the OS reclaims the connection, so this is not harmful in practice. However, Postgres may hold the connection slot open briefly and emit a log warning about abrupt disconnection.

**Fix:**
```typescript
main().catch(async (e) => {
  console.error(e)
  await client.end()
  process.exit(1)
})
```
