## Summary

Phase 04.12 rebuilds `/explore` from a 4-section flat page into a 6-section single-scrollable layout matching psalter.cprc.co.uk. The work is two distinct tracks that must execute in strict order: (1) schema migrations + Airtable data fetches, then (2) UI rebuilds against the newly available data.

The critical research finding is a **schema design conflict** in the ROADMAP spec: the roadmap says "add `sub_topic` and `quotation` to `verse_naves_topics`", but live Airtable data shows 677 cases where the same `(verse_id, naves_topic_id)` pair appears under multiple different sub_topics. The existing composite primary key `(verse_id, naves_topic_id)` cannot hold a per-row `sub_topic` field without allowing duplicate primary keys. The correct implementation requires a new intermediate table `naves_topic_entries` rather than adding columns directly to `verse_naves_topics`. [VERIFIED: Airtable API query of all 1906 tblggtBfVTmTUeyNs records]

Sections 1 and 2 ("When you're feeling..." and "By Theme") are pure UI rearrangements — all data is already in the `topics` table, no migration needed. Sections 3-6 all require schema changes and Airtable data migration before UI work is possible.

**Primary recommendation:** Execute Wave 0 (schema + migrations) as a true blocking wave before any UI work. Plan Wave 0 tasks in DB-dependency order: `psalms` fields → `naves_topics` fields → new `naves_topic_entries` table → new `creedal_references` table → Airtable data migration.

## Schema Changes Required

### Verified field values from Airtable

**`psalms.date_bc` and `psalms.occasion`** [VERIFIED: Airtable API, tblZyQFfNUFnmkNyG]
- `"B.C."` field: integer (e.g., 1015, 1044, 515, 588). Not all psalms have a value.
- `"Probably Occasion on which Psalm was Composed"` field: text (e.g., "Inserted toward the end of David's life (1Ch 28:21)"). Not all psalms have a value.
- Author values found: David, Unknown, Asaph — confirms existing `psalms.author` column matches.

**`naves_topics.messianic`** [VERIFIED: Airtable API, tblWBfuxleN74E3tM — full 488-record scan]
- Field name: `Messianic?`
- 12 records have this field set (not null).
- All 12 have value `"Messianic"` — NOT the three-value enum described in the roadmap.
- Roadmap states three values: "Primarily Messianic", "Not Messianic but glimpses (Highlights)", "Not Messianic; parallel situations (Parallels)". **These values are NOT in the `naves_topics` table.** The three-value classification is in `messianic_psalms.classification` (already migrated).
- **Action:** Add `messianic text` column to `naves_topics`. Migrate with value `"Messianic"` for the 12 matching records.

**`naves_topic_entries` (new table — replaces roadmap's verse_naves_topics column plan)** [VERIFIED: Airtable API, full 1906-record analysis]

The Airtable "Topics - Verses (Nave's)" table (tblggtBfVTmTUeyNs) has 1906 records. Each record has:
- `Sub-Topic` (text) — e.g., "Romans 4:7, \"Blessed are they whose iniquities...\""
- `Quotation` (text) — KJV verse text(s) with verse references
- `Main Topic` (linked record array → naves_topics)
- `References` (linked record array → verses)

**Critical finding:** 677 of 6005 `(verse_id, naves_topic_id)` pairs have MULTIPLE different sub_topics. The current composite PK `(verse_id, naves_topic_id)` on `verse_naves_topics` cannot accommodate a `sub_topic` column without breaking uniqueness. [VERIFIED: Python analysis of all 1906 Airtable records]

**Correct schema design** (deviates from roadmap wording, but implements roadmap intent):

```sql
-- New table: one row per Airtable record in tblggtBfVTmTUeyNs
CREATE TABLE naves_topic_entries (
  id         SERIAL PRIMARY KEY,
  airtable_id TEXT NOT NULL UNIQUE,
  naves_topic_id INTEGER NOT NULL REFERENCES naves_topics(id),
  sub_topic  TEXT,
  quotation  TEXT
);

-- New junction: verse ↔ entry (replaces or supplements verse_naves_topics for sub-topic queries)
CREATE TABLE verse_naves_topic_entries (
  verse_id   INTEGER NOT NULL REFERENCES verses(id),
  entry_id   INTEGER NOT NULL REFERENCES naves_topic_entries(id),
  PRIMARY KEY (verse_id, entry_id)
);
```

The existing `verse_naves_topics` table (verse_id, naves_topic_id) is **kept intact** — it powers the current explore page queries and must not be broken. New queries for sub-topic display use the new tables.

**`creedal_references` (new table)** [VERIFIED: Airtable API, tblMJW2An5w3CB0ws — all 97 records]
- 97 records total, no pagination needed.
- Fields: `Creed` (always "Heidelberg"), `Creedal Reference` (question number as string, e.g., "26"), `URL` (relative path like "relight.app/resource/Heidelberg.26"), `Verses` (linked record array → verses)
- Each row links ONE verse to ONE question number.
- URL is per-question (all rows for Q26 have the same URL).
- 35 distinct question numbers.
- URL needs `https://` prefix prepended at display time.

```sql
CREATE TABLE creedal_references (
  id              SERIAL PRIMARY KEY,
  airtable_id     TEXT NOT NULL UNIQUE,
  verse_id        INTEGER REFERENCES verses(id),
  creed           TEXT,              -- "Heidelberg"
  question_number INTEGER,           -- parsed from "26" → 26
  url             TEXT               -- store as-is, prepend https:// at render
);
```

### Pattern 1: Additive schema migration with drizzle-kit push

This project uses `drizzle-kit push` (no migration files). The safe procedure is: update schema.ts → run `npm run db:push` → run migration script. The push command is non-destructive for additive changes (new columns, new tables).

```typescript
// schema.ts — adding columns to existing table
export const psalms = pgTable('psalms', {
  // ... existing columns unchanged ...
  dateBC: integer('date_bc'),          // NEW — Airtable "B.C." field
  occasion: text('occasion'),           // NEW — Airtable "Probably Occasion..."
})
```

### Pattern 2: Airtable migration script extension

The existing `scripts/migrate-airtable.ts` pattern uses `fetchAll(tableName)` to paginate all records, then upserts. New fields on existing tables use `onConflictDoUpdate`:

```typescript
// Pattern for updating existing rows with new fields
await db.insert(schema.psalms)
  .values({ id: psalmNumber, airtableId, dateBC, occasion, /* other fields */ })
  .onConflictDoUpdate({
    target: schema.psalms.airtableId,
    set: { dateBC: sql`excluded.date_bc`, occasion: sql`excluded.occasion` },
  })
```

New tables use `.onConflictDoNothing()` (same as existing migration patterns).

## Common Pitfalls

### Pitfall 1: Assuming verse_naves_topics can hold sub_topic directly
**What goes wrong:** Adding a `sub_topic text` column to `verse_naves_topics` and re-running the migration produces 677 rows where the PK `(verse_id, naves_topic_id)` is ambiguous (same pair, multiple sub_topics).
**Why it happens:** The ROADMAP spec says "add sub_topic and quotation to verse_naves_topics" but this was written without checking for duplicate (verse, topic) pairs.
**How to avoid:** Use the new `naves_topic_entries` + `verse_naves_topic_entries` table structure described above.
**Warning signs:** Migration script logs fewer than 6005 rows for verse_naves_topic_entries due to `onConflictDoNothing`.

### Pitfall 2: Collapsible requires `'use client'` — breaks server component tree
**What goes wrong:** QuotedInNT.tsx or HeidelbergCatechism.tsx are intended as server components but import shadcn Collapsible which is `'use client'`. This causes a build error.
**Why it happens:** shadcn Collapsible uses React state internally.
**How to avoid:** Make the components `'use client'` (they receive data props, not async queries) and call DB queries in the parent page.tsx server component, passing data down as props.
**Warning signs:** Build error: "You're importing a component that needs useState. It only works in a Client Component."

### Pitfall 3: Messianic classification values mismatch
**What goes wrong:** Code checks `naves_topics.messianic` against the three roadmap values ("Primarily Messianic", etc.) but the actual Airtable values are just "Messianic".
**Why it happens:** Roadmap described messianic_psalms.classification values by mistake, not naves_topics values.
**How to avoid:** Store whatever Airtable returns. Display it as-is with a simple null check. For Section 3b, all 12 matching naves_topics rows display together (they're all "Messianic").
**Warning signs:** MessianicByTopic component shows 0 items because the filter string doesn't match.

### Pitfall 4: Creedal URL missing https:// prefix
**What goes wrong:** External links render as bare `relight.app/...` (treated as relative path by browser) and navigate to the current domain instead of relight.app.
**Why it happens:** Airtable stores URLs without protocol prefix.
**How to avoid:** At render time: `href={url.startsWith('http') ? url : 'https://' + url}`.
**Warning signs:** Clicking a Heidelberg link navigates to `psalter.gsdlabs.dev/relight.app/...`.

### Pitfall 5: IntersectionObserver active section flicker
**What goes wrong:** `<ExploreAnchorNav>` flickers between sections while scrolling, especially when sections are short.
**Why it happens:** Multiple section thresholds firing simultaneously.
**How to avoid:** Use a single root margin that detects when a section header enters the top viewport band (e.g., `rootMargin: '-10% 0px -85% 0px'`). Track the "last entered" section, not just "is intersecting".
**Warning signs:** Anchor nav active indicator jumps between items rapidly while scrolling.

## Code Examples

### New query: fetchQuotedInNT

```typescript
// src/db/queries/explore.ts
// Returns 68 sub-entries under "Quotations and Allusions" topic
// Join: naves_topic_entries → naves_topics (filter name = 'Quotations and Allusions')
//       → verse_naves_topic_entries → verses (for psalm links)
export const fetchQuotedInNT = cache(async function fetchQuotedInNT() {
  const rows = await db.execute(sql`
    SELECT
      nte.id,
      nte.sub_topic,
      nte.quotation,
      json_agg(json_build_object('verseId', vnte.verse_id, 'psalmId', v.psalm_id, 'verseNumber', v.verse_number)
        ORDER BY v.psalm_id, v.verse_number) AS verses
    FROM naves_topic_entries nte
    JOIN naves_topics nt ON nt.id = nte.naves_topic_id
    JOIN verse_naves_topic_entries vnte ON vnte.entry_id = nte.id
    JOIN verses v ON v.id = vnte.verse_id
    WHERE nt.name = 'Quotations and Allusions'
    GROUP BY nte.id, nte.sub_topic, nte.quotation
    ORDER BY nte.sub_topic
  `)
  return rows as unknown as Array<{
    id: number
    sub_topic: string | null
    quotation: string | null
    verses: Array<{ verseId: number; psalmId: number; verseNumber: number | null }>
  }>
})
```

### Migration script pattern for naves_topic_entries

```typescript
// scripts/migrate-airtable.ts addition
async function migrateNavesTopicEntries(navesTopicIdMap: Map<string, number>, verseIdMap: Map<string, number>) {
  const records = await fetchAll("Topics - Verses (Nave's)")
  let entryCount = 0, linkCount = 0
  for (const r of records) {
    const linkedTopicIds = (r.get('Main Topic') as string[] | null) ?? []
    const linkedVerseIds = (r.get('References') as string[] | null) ?? []
    const subTopic = r.get('Sub-Topic') as string | null
    const quotation = r.get('Quotation') as string | null

    for (const airtableTopicId of linkedTopicIds) {
      const navesTopicId = navesTopicIdMap.get(airtableTopicId)
      if (!navesTopicId) continue
      
      const [entry] = await db.insert(schema.navesTopicEntries)
        .values({ airtableId: r.getId(), navesTopicId, subTopic, quotation })
        .onConflictDoUpdate({
          target: schema.navesTopicEntries.airtableId,
          set: { subTopic: sql`excluded.sub_topic`, quotation: sql`excluded.quotation` },
        })
        .returning({ id: schema.navesTopicEntries.id })
      entryCount++

      for (const airtableVerseId of linkedVerseIds) {
        const verseId = verseIdMap.get(airtableVerseId)
        if (!verseId) continue
        await db.insert(schema.verseNavesTopicEntries)
          .values({ verseId, entryId: entry.id })
          .onConflictDoNothing()
        linkCount++
      }
    }
  }
  console.log(`  Naves topic entries: ${entryCount}, verse links: ${linkCount}`)
}
```
