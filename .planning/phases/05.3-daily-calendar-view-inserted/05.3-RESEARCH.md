## Summary

Phase 05.3 replaces the flat 365-row `/daily` list with two new UI elements: a server-rendered today hero card pinned at the top of the page, and a client-rendered monthly calendar grid with month navigation below it. The phase also includes a prerequisite data migration that adds `starting_verse` and `ending_verse` columns to `daily_readings` and backfills them from Airtable.

The implementation touches exactly four areas: (1) the Drizzle schema (`src/db/schema.ts` — two new integer columns), (2) a standalone Airtable backfill script, (3) the DB query layer (`src/db/queries/daily.ts` — select the new columns), and (4) the route (`src/app/daily/page.tsx` — rewrite) plus a new calendar client component. The existing `DailyPlanClient.tsx` is deleted; the existing `TodayCard.tsx` is replaced (or significantly revised) with a spec-compliant version. A `loading.tsx` must also be added to the `/daily` route (currently absent; required by PERF-01).

The calendar grid is a custom 7-column CSS grid, NOT the installed shadcn `Calendar` component (which is a date-picker and doesn't support per-cell psalm content). All shadcn components needed (`Card`, `Button`, `Skeleton`, `Separator`) are already installed.

**Primary recommendation:** Execute in three sequential waves — (1) schema + migration, (2) query update + today card rewrite, (3) calendar client component + loading skeleton.

### Pattern 2: Standalone Backfill Script (Airtable → PostgreSQL)

**What:** A standalone `npx tsx` script that fetches "365 Days" records from Airtable and updates the two new columns.
**When to use:** Any Airtable→DB backfill for fields omitted from the original migration.

```typescript
// scripts/backfill-daily-verse-ranges.ts
import 'dotenv/config'
import Airtable from 'airtable'
import { drizzle } from 'drizzle-orm/postgres-js'
import postgres from 'postgres'
import { eq } from 'drizzle-orm'
import * as schema from '../src/db/schema'

const BASE_ID = 'appY3dB1EHtex0fUJ'
const base = new Airtable({ apiKey: process.env.AIRTABLE_PAT }).base(BASE_ID)
const client = postgres(process.env.DATABASE_URL!)
const db = drizzle({ client, schema })

const records = await base('365 Days').select({ pageSize: 100 }).all()
let updated = 0
for (const r of records) {
  const startingVerse = typeof r.get('Starting Verse') === 'number' ? r.get('Starting Verse') as number : null
  const endingVerse = typeof r.get('Ending Verse') === 'number' ? r.get('Ending Verse') as number : null
  if (startingVerse === null && endingVerse === null) continue
  await db.update(schema.dailyReadings)
    .set({ startingVerse, endingVerse })
    .where(eq(schema.dailyReadings.airtableId, r.id))
  updated++
}
console.log(`Updated ${updated}/${records.length} records`)
await client.end()
```

**Run:** `npx tsx scripts/backfill-daily-verse-ranges.ts`

### Pattern 4: Psalm Reference Formatting

**What:** Pure utility function for consistent psalm reference display.
**Where:** Inline in component or extracted to `src/lib/daily.ts`.

```typescript
// Format psalm reference: "50:1-8" (cell) or "Psalm 50:1-8" (today card)
function formatPsalmRef(
  psalmId: number,
  startingVerse: number | null,
  endingVerse: number | null,
  prefix = false
): string {
  const base = prefix ? `Psalm ${psalmId}` : String(psalmId)
  if (startingVerse !== null && endingVerse !== null) {
    return `${base}:${startingVerse}-${endingVerse}`
  }
  return base
}
```

### Pattern 5: Calendar Grid Cell Computation

**What:** Pure function that builds the array of cells for a given month, including leading/trailing empty cells for Mon-first alignment.
**When to use:** Called inside the client component on each month change.

```typescript
// Key algorithm: Monday-first week alignment
function getCalendarCells(year: number, month: number /* 0-11 */) {
  const firstDay = new Date(year, month, 1)
  // getDay(): 0=Sun, 1=Mon, ..., 6=Sat
  // For Mon-first: Mon=0, Tue=1, ..., Sun=6
  const leadingEmpties = (firstDay.getDay() + 6) % 7
  const daysInMonth = new Date(year, month + 1, 0).getDate()
  return { leadingEmpties, daysInMonth }
}
```

The conversion `(getDay() + 6) % 7` maps Sunday (0) → 6, Monday (1) → 0, giving a Monday-first offset. [ASSUMED: Monday-first is specified by UI-SPEC "Mon Tue Wed Thu Fri Sat Sun"; formula is standard JS]

### Pattern 6: Day-Number-to-Reading Lookup

**What:** Map calendar date to `daily_readings` row by day-of-year calculation.
**Critical:** The `daily_readings.dayNumber` is 1–365 (day of year), not a calendar date. The reading for June 20 is day 171 of the year — the calendar must convert each calendar date to a day-of-year to find its reading.

```typescript
// Map a calendar date cell to its day-of-year (reuse getDayOfYear logic)
function calendarDateToDayOfYear(year: number, month: number, day: number): number {
  const startOfYear = Date.UTC(year, 0, 1)
  const targetDay = Date.UTC(year, month, day)
  const dayOfYear = Math.floor((targetDay - startOfYear) / (1000 * 60 * 60 * 24)) + 1
  return ((dayOfYear - 1) % 365) + 1  // Wraps day 366 on leap year, consistent with getDayOfYear()
}
```

Pre-build a lookup map `dayOfYear → reading` from the 365 readings array, then use it per cell. [VERIFIED: getDayOfYear logic in src/lib/daily.ts lines 6-12]

### Anti-Patterns to Avoid

- **Using `react-day-picker` / shadcn Calendar for the grid:** The installed `Calendar` component is a date-picker. Forcing psalm data into its cells requires deep `DayContent` override and fighting its CSS. Use a plain CSS grid instead.
- **Additional DB calls on month navigation:** All 365 readings must be passed as a prop at page load. The client component filters them in-memory. Never call the DB from within the client calendar component.
- **Calling `getDayOfYear()` in a server component without wrapping:** `getDayOfYear()` uses `new Date()` — safe in Node/RSC context since it doesn't use browser-only APIs. But do NOT call it during static generation; `force-dynamic` prevents that.
- **Relying on `readingDate` column for day-of-year mapping:** The schema has `readingDate date` but it is `null` for all rows (confirmed in migration: line 388 `readingDate: null`). Always use `dayNumber` for day-of-year mapping.
- **Showing "50:null-undefined" if migration is incomplete:** Guard: `if (startingVerse !== null && endingVerse !== null)` — show full ref; else show psalm number only.
- **Deleting TodayCard.tsx before confirming it is unused:** Check imports across the entire codebase before deletion.

## Common Pitfalls

### Pitfall 1: dayNumber vs Calendar Date Mismatch

**What goes wrong:** Developer uses calendar day number (1–28/30/31) instead of day-of-year (1–365) to look up readings, resulting in wrong psalm displayed for most months.
**Why it happens:** The `daily_readings.dayNumber` is day-of-year, not day-of-month. June 20 is day 171, not day 20.
**How to avoid:** Build a `Map<number, DailyReadingWithPsalm>` keyed on `dayNumber` (day-of-year) and look up via `calendarDateToDayOfYear(year, month, calendarDay)`.
**Warning signs:** Psalm 20 always showing on day 20 of every month.

### Pitfall 2: Monday-First Week Start

**What goes wrong:** Using `getDay()` directly (0=Sun) produces Sunday-first calendars, misaligning day cells in the 7-column grid.
**Why it happens:** JS `Date.getDay()` returns 0 for Sunday; UK/European convention is Monday-first.
**How to avoid:** Apply `(getDay() + 6) % 7` for leading empty cell count.
**Warning signs:** Calendar starts on Sunday, July 1 (Wednesday) appears in column 3 not column 2.

### Pitfall 3: hydration Mismatch in TodayCard

**What goes wrong:** RSC renders today card with a specific day; client hydration disagrees if the component re-computes today on the client.
**Why it happens:** The current `TodayCard.tsx` uses `useState(null)` and `useEffect` to avoid this — it deliberately renders a skeleton on first render. The new today card is a pure RSC rendered with `force-dynamic`, so the server always has the correct date. No client state is needed on the today card itself.
**How to avoid:** Keep today card as a server component. Do not add any `useEffect` or `useState` to it. Only the calendar grid is a client component, and it receives `todayDay` as a prop from the server.
**Warning signs:** Console hydration warning; today card flickers on load.

### Pitfall 4: Backfill Script Field Name Assumptions

**What goes wrong:** Airtable field names differ from what the script assumes, causing silent `null` writes for all 365 rows.
**Why it happens:** The original migration script (line 386 comment: "Actual field names verified via Airtable Meta API before migration — research-phase assumptions were incorrect for 6 fields across 4 tables") shows this has happened before.
**How to avoid:** Log a sample record's keys before the backfill loop to verify `Starting Verse` and `Ending Verse` are the actual field names. Add: `if (records.length > 0) console.log('Fields:', Object.keys(records[0].fields))`.
**Warning signs:** `Updated 0/365 records` — all were skipped as `null`.

### Pitfall 5: Missing `loading.tsx` for /daily

**What goes wrong:** Navigating to `/daily` shows a blank white screen while `force-dynamic` fetches data server-side.
**Why it happens:** No `loading.tsx` currently exists in `src/app/daily/`. PERF-01 deferred loading states to Phase 6 for remaining routes, but the UI-SPEC explicitly calls for skeleton loading states in this phase.
**How to avoid:** Create `src/app/daily/loading.tsx` as part of this phase. Use the three Skeleton blocks specified in the UI-SPEC.
**Warning signs:** White flash on navigation to /daily; Lighthouse CLS score degraded.

### Pitfall 6: drizzle-kit push vs generate/migrate

**What goes wrong:** Running `db:generate` + `db:migrate` when only `db:push` is needed (or vice versa), creating migration files that conflict.
**Why it happens:** Project uses `db:push` for schema changes (no migration files tracked), not the generate/migrate workflow.
**How to avoid:** Run `npm run db:push` — this is the established project pattern. [VERIFIED: package.json scripts, drizzle.config.ts `out: './drizzle/migrations'` — migrations dir exists but push is the stated workflow]
