# Phase 05.3: Code Review Report

**Reviewed:** 2026-06-21T00:00:00Z
**Depth:** standard
**Files Reviewed:** 10
**Status:** issues_found

## Summary

This phase adds a `/daily` page with a monthly calendar view showing the 365-day reading plan, a "today" hero card, verse-range columns in the schema, and a backfill script. The implementation is generally clean, but three blockers were found: the calendar cannot navigate to the next year (year is frozen in state), the `prevMonth` helper silently drops the year decrement making January navigation wrong, and the backfill script holds an open DB connection even when records are skipped by the `continue` guard (minor resource leak that can be a problem during CI). There are also four warnings around the `force-dynamic` placement, year-boundary edge cases in the leap-year wrap, missing null-guard on `psalmId` in the aria-label, and the absence of an upper-bound constraint on `dayNumber` in the schema.

## Critical Issues

### CR-01: Calendar year is permanently frozen — navigation past December or before January is impossible

**File:** `src/components/DailyCalendarClient.tsx:42`

`displayedYear` is captured once with `useState(() => now.getFullYear())` and has no setter. `prevMonth` and `nextMonth` both receive and return a `year` value, but `handlePrevMonth` and `handleNextMonth` ignore the returned `year` entirely — only `month` is destructured.

```ts
// line 44-46
const handlePrevMonth = () => {
  const { month } = prevMonth(displayedMonth, displayedYear)  // year discarded
  setDisplayedMonth(month)
}
```

Navigating backwards from January sets `displayedMonth` to 11 but `displayedYear` stays at 2026 forever. Every cell in "December 2026" maps to the same day-of-year values as "December 2025" because the year passed to `calendarDateToDayOfYear` never changes. The calendar silently shows the wrong readings for any month in a different year, and it is impossible for the user to reach prior years even if future phases need history.

**Fix:**

```ts
const [displayedYear, setDisplayedYear] = useState(() => now.getFullYear())

const handlePrevMonth = () => {
  const { month, year } = prevMonth(displayedMonth, displayedYear)
  setDisplayedMonth(month)
  setDisplayedYear(year)
}

const handleNextMonth = () => {
  const { month, year } = nextMonth(displayedMonth, displayedYear)
  setDisplayedMonth(month)
  setDisplayedYear(year)
}
```

### CR-02: `prevMonth` drops year on December→January wrap — January always returns year unchanged

**File:** `src/components/DailyCalendarClient.tsx:15-17`

```ts
function prevMonth(m: number, y: number) {
  return m === 0 ? { month: 11, year: y } : { month: m - 1, year: y }
}
```

When `m === 0` (January), the function returns `{ month: 11, year: y }` — the year is **not decremented**. It should return `year: y - 1`. This is already blocked from manifesting by CR-01 (year is frozen), but once CR-01 is fixed this bug becomes independently load-bearing.

**Fix:**

```ts
function prevMonth(m: number, y: number) {
  return m === 0 ? { month: 11, year: y - 1 } : { month: m - 1, year: y }
}
```

### CR-03: Backfill script leaves DB connection open when all records are skipped

**File:** `scripts/backfill-daily-verse-ranges.ts:41-48`

The `continue` guard skips records where both verse fields are null. If **all 365 records** have null verse data (e.g. first run before Airtable is populated, or a field-name mismatch), the loop exits without calling `client.end()` because that call is only at line 49 after the loop. The `catch` handler does call `client.end()`, but a silent "all skipped" scenario is not an error — it exits via the normal path and hangs with an open connection.

This is likely not a production risk if Airtable is always populated, but on CI or a dry-run the process will not exit cleanly.

**Fix:** Move `client.end()` to a `finally` block:

```ts
async function main() {
  try {
    const records = await base('365 Days').select({ pageSize: 100 }).all()
    // ... loop ...
    console.log(`Updated ${updated}/${records.length} records`)
  } finally {
    await client.end()
  }
}

main().catch((err) => {
  console.error('Backfill failed:', err)
  process.exit(1)
})
```

## Warnings

### WR-01: `export const dynamic = 'force-dynamic'` declared before imports — non-standard placement

**File:** `src/app/daily/page.tsx:1`

The `export const dynamic` segment variable is placed on line 1, before the `import` statements. While Next.js processes it correctly, placing it before imports violates module ordering conventions (imports must come first per ES module spec; segment config must be an `export const` in the module body, which technically starts after imports). Linters set to enforce import ordering will flag this. It also makes the intent less visible — route segment configs are conventionally placed after imports as a block.

**Fix:** Move to after all imports:

```ts
import type { Metadata } from "next"
import { fetchAllDailyReadings } from "@/db/queries/daily"
// ... other imports

export const dynamic = 'force-dynamic'
export const metadata: Metadata = { ... }
```

### WR-02: Leap-year day 366 wraps to day 1 — the reading for Dec 31 in leap years is silently swapped

**File:** `src/lib/daily.ts:11`

```ts
return ((dayOfYear - 1) % 365) + 1
```

In a leap year (2024, 2028…), Dec 31 is day 366. The modulo maps it to day 1. The user who opens `/daily` on 31 December 2028 sees the day-1 psalm (January 1) rather than the day-365 psalm. This is a behavioural correctness issue, not just a boundary curiosity — it affects one real calendar date per leap year.

The test at `tests/daily-calendar.test.ts:29-31` asserts this wrap-to-1 behaviour as correct, but it is a product decision that should be made explicitly. If the intent is to repeat January 1 on Dec 31 of leap years, the comment should say so and the test description should reflect the intent rather than just documenting the mechanic. If the intent is always show day 365 on Dec 31, the fix is:

```ts
return Math.min(dayOfYear, 365)
```

**Fix:** Clarify the intent in comments and align the test name. If the clamp behaviour is preferred, use `Math.min` instead of the modulo.

### WR-03: `psalmRef` used in aria-label before it is guaranteed non-empty

**File:** `src/components/DailyCalendarClient.tsx:130`

```tsx
aria-label={`Day ${dayOfYear}, ${monthLabel} ${day}: Psalm ${psalmRef}`}
```

`psalmRef` is computed as `formatPsalmRef(psalmId, ...)` only when `psalmId` is truthy (line 115-117). The `<Link>` is only rendered when `psalmId` is truthy (line 125), so `psalmRef` will never be empty inside this branch. However the label says "Psalm 50:1-8" but `psalmRef` already contains the psalm number — the aria-label becomes "Psalm Psalm 50:1-8" when `prefix=false` is passed and the caller manually prepends "Psalm " in the template string.

Trace: `formatPsalmRef(psalmId, ..., false)` returns `"50:1-8"` (no "Psalm" prefix). The aria-label template adds `"Psalm "` manually, yielding `"Psalm 50:1-8"` — that is correct. But if the call signature were changed to `prefix=true` the label would read `"Psalm Psalm 50:1-8"`. The current state is not broken, but it is fragile. The label construction should not depend on knowing what `prefix` mode was passed.

**Fix:** Remove the hardcoded "Psalm " from the aria-label template and pass `prefix=true` to `formatPsalmRef` for the accessibility label:

```tsx
const psalmRefAccessible = psalmId
  ? formatPsalmRef(psalmId, reading!.startingVerse, reading!.endingVerse, true)
  : ""

aria-label={`Day ${dayOfYear}, ${monthLabel} ${day}: ${psalmRefAccessible}`}
```

### WR-04: No DB-level constraint on `dayNumber` range — values outside 1-365 can be inserted silently

**File:** `src/db/schema.ts:107`

```ts
dayNumber: integer('day_number').notNull(),    // 1-365
```

The comment documents the 1-365 invariant but there is no `CHECK` constraint enforcing it. A mis-run backfill script or a future Airtable record with `dayNumber: 0` or `dayNumber: 400` will silently land in the table and cause `fetchDailyReading` to return unexpected results, or cause `getDayOfYear()` to miss a match.

**Fix:** Add a Drizzle check constraint:

```ts
import { check } from 'drizzle-orm/pg-core'

export const dailyReadings = pgTable('daily_readings', {
  // ...
  dayNumber: integer('day_number').notNull(),
}, (t) => [
  check('day_number_range', sql`${t.dayNumber} >= 1 AND ${t.dayNumber} <= 365`),
])
```

## Info

### IN-01: `byDay` Map rebuilt on every render inside the component body

**File:** `src/components/DailyCalendarClient.tsx:37-39`

```ts
const byDay = new Map<number, DailyReadingWithPsalm>(
  readings.map((r) => [r.dayNumber, r])
)
```

This Map is rebuilt every time the component re-renders (e.g. on month navigation). Since `readings` is a stable prop, this should be memoized with `useMemo`. With 365 entries the cost is negligible in practice, but it is contrary to the idiom for derived data in React and will trigger lint rules in most configs.

**Fix:**

```ts
const byDay = useMemo(
  () => new Map(readings.map((r) => [r.dayNumber, r])),
  [readings]
)
```

### IN-02: `formatPsalmRef` silently returns just the psalm number when `startingVerse` is set but `endingVerse` is null

**File:** `src/lib/daily.ts:26-29`

```ts
if (startingVerse !== null && endingVerse !== null) {
  return `${base}:${startingVerse}-${endingVerse}`
}
return base
```

The test at `tests/daily-calendar.test.ts:13-16` asserts that a non-null `startingVerse` with a null `endingVerse` returns just the psalm number (`"Psalm 50"`). This is intentional by design, but the case `startingVerse=1, endingVerse=null` silently drops the starting verse rather than displaying `"50:1"`. If Airtable data ever has a starting verse with no ending verse (partial ranges), the display gives no indication that a partial range exists.

This is a documented product decision but worth flagging: the test name says "omits range" which is correct behaviour per spec — the concern is whether "silently same as no range" is the right user experience.

**Fix (if desired):** Optionally show single-verse refs: `return startingVerse !== null ? \`${base}:${startingVerse}\` : base`

### IN-03: `DailyTodayCard` uses `new Date()` for the date label — will mismatch server-computed `todayDay` on timezone boundaries

**File:** `src/components/DailyTodayCard.tsx:22-27`

```tsx
const dateLabel = new Date().toLocaleDateString("en-GB", {
  weekday: "long",
  ...
})
```

`todayDay` is computed on the server via `getDayOfYear(new Date())` (UTC). The client `new Date()` in the card uses local browser time. A user in a UTC+X timezone shortly after midnight UTC will see a date label that says "Saturday" but `todayDay` is already pointing to Sunday's psalm. This is a cosmetic inconsistency, not a data error, since `todayDay` drives the data and the date label is display-only.

**Fix:** Pass the date label down from the server alongside `todayReading`, or accept the minor inconsistency and document it.
