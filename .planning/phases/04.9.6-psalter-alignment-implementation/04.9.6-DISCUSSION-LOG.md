## Area 1: Data model location

### Q1 — Where should the structured Stanza→Line→Syllable+verseRef model live?

Options:
- New DB tables, populated once
- Derived JSON column on psalm_versions

**User selected:** Derived JSON column on psalm_versions.
→ Locked as D-01.

### Q2 — How should `lyrics_structured` stay in sync with the source `lyrics` blob?

Options:
- Re-parse on every Airtable sync
- Parse once, then `lyrics_structured` is canonical
- Both columns editable, last-write-wins is human

**User answered (freeform):** "Airtable will soon be deleted (we are migrating away from it) so nothing should depend on Airtable. But we should keep a permanent untouched record of the lyrics as imported from Airtable."
→ Locked as D-02 (lyrics_imported_raw immutable snapshot; lyrics_structured canonical editable).

### Q3 — Persisted granularity of `lyrics_structured`?

Options:
- Stanza → Line (+ verseRef), syllables computed at render

- Hybrid: syllables[] only when overridden, else computed

**User selected:** Hybrid.
→ Locked as D-03.

## Area 2: Parser strictness

### Q1 — On an unparseable lyric blob, what should happen?

Options:
- Fail loudly — migration aborts
- Quarantine: parse what we can, flag failures into a report
- Best-effort silently — degrade to single-stanza

**User selected:** Quarantine.
→ Locked as D-04.

### Q2 — What's the round-trip test bar (success criterion #2)?

Options:
- Strict (every parsed psalm, modulo whitespace)
- Semantic (same content, formatting may differ)
- Curated set strict + parse-cleanly on the rest

**User asked for explanation** of round-trip testing.
Claude explained: parse(blob) → serialise → compare against original; "modulo whitespace" means whitespace differences allowed but no content drift.

### Q2 (re-asked) — Which round-trip bar?

**User selected:** Strict (every parsed psalm, modulo whitespace).
→ Locked as D-05.

## Area 3: Mid-stanza verse-boundary UI

### Q1 — How should a mid-stanza Bible-verse boundary appear?

Options:
- Inline superscript verse number
- Small marker in left gutter
- Colour/underline first syllable + hover
- Both inline superscript AND gutter

**User selected:** Inline superscript verse number.
Plus a critical parser fact (freeform):
> "every single numerical digit in the lyrics is a verse number; the rare times the lyrics themselves contain numbers these are written out (eg 'four'); note also that AFAIK in the current lyrics the lyrics themselves immediately follow the verse number without a space (eg '1The Lord's…')"

→ Locked as D-07 (UI). Parser invariants captured in D-06 and the `<specifics>` section.

## Area 4: Alternate-meter line-break source

### Q1 — Where do canonical staff line breaks come from?

Options:
- Derived from meter alone
- Derived from the ABC source's bar structure
- Per-psalm override via printed-psalter index

**User answered (freeform expansion of option 1):**
> "We should derive from meter alone. However, we will not always render '2-per-system'. In fact the default render is to follow the current raw lyrics, eg 4 lines for CM per stanza. The only time we adjust line breaks is when placing lyrics inline with musical notation: in that case we follow the line break in the notation. Eg for CM the default notation line break is each 8 6 pair is a single line."

→ Locked as D-08 (meter determines metrical line count), D-09 (default lyrics-only = 1 per metrical line), D-10 (staff-overlay follows ABC notation phrase boundaries).
