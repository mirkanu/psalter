# Phase 04.9.6: Psalter Alignment Implementation — Research

**Researched:** 2026-05-18
**Domain:** Lyrics data-model redesign + parser + staff-alignment algorithm
**Confidence:** HIGH (corpus directly sampled; all code touch-points read)

## Summary

This phase rewrites the staff-alignment pipeline by moving from a flat
`lyrics` text blob to a structured `Stanza → Line (+ bibleVerseRef)` JSON
form persisted as `lyrics_structured jsonb` on `psalm_versions`, then drives
DCM behaviour off `tunes.double_length` (already migrated in 260517-u35)
instead of meter-string equality. A one-shot parser migrates all 184
psalm-versions; failures fall into a quarantine bucket that keeps using the
legacy renderer. The renderer migration is per-psalm-version, gated on
`lyrics_structured IS NOT NULL`.

**Primary recommendation:** Treat the parser as the highest-risk component
and the load-bearing artefact of the phase. D-06's invariants are correct
for ~90% of CM psalms but **break in five named ways** for the remaining
~10% and for every non-CM psalm — see "Parser design" §"Invariants verified
against corpus". The planner must sequence the parser plan to surface and
hand-resolve these edge cases via the quarantine bucket; nothing else
unblocks the rest of the phase until the parser produces deterministic
output the round-trip test accepts.

The DCM detection rewrite is a small, atomic, low-risk change once the
data-model is in place — three call sites pass `tune.meter` today
(`NotationRenderer.tsx:193`, `singing/SingingView.tsx:333`, plus the
component prop on the consumers `PsalmTabs.tsx`, `tunes/[id]/page.tsx`,
`psalms/[id]/page.tsx`); switching to `tune.doubleLength` is mechanical.

### Pattern 1: Pure parser/serialiser pair

**What:** Two pure functions in `src/lib/lyrics-parser.ts` with no DB
dependencies, easily unit-testable.

**Signature:**
```typescript
// src/lib/lyrics-parser.ts
export interface Line {
  text: string                  // metrical line as printed, NO leading verse number
  bibleVerseRef?: number        // present iff a new Bible verse starts at this line
  syllables?: string[]          // optional manual override (D-03 hybrid)
}
export interface Stanza {
  index: number                 // 0-based
  lines: Line[]
}
export interface ParseResult {
  ok: boolean
  stanzas?: Stanza[]
  reason?: string               // populated when ok=false; quarantine reason
}
export function parseLyrics(raw: string, meter: string | null): ParseResult
export function serialiseLyrics(stanzas: Stanza[]): string
```

**Why pure:** Round-trip test runs in pure-vitest with zero DB cost. Parser
can be re-run against a fixture file without touching the running database.

### Pattern 2: Per-row gating in the renderer

**What:** `NotationRenderer` receives both `lyrics_structured` (or null) and
the legacy `lyrics` string. When `lyrics_structured` is non-null the new
alignment pipeline runs; otherwise the legacy path runs.

**Why:** Phase ships incrementally. A psalm landing in quarantine still
renders today's output; nothing breaks.

```typescript
// In NotationRenderer.tsx
const useStructured = lyricsStructured != null
const cycles = useMemo(() => {
  if (useStructured) {
    return groupStructuredStanzasIntoCycles(lyricsStructured, tune.doubleLength)
  }
  // Legacy path (unchanged)
  return groupStanzasIntoCycles(stanzas, tuneMeter, stanzaMeter)
}, [...])
```

### Anti-Patterns to Avoid

- **Branching on `meter === 'CMD'` or any meter-string substring for DCM.**
  D-11 mandates the boolean. `meter` is for *line counts per stanza*, not
  for tune-pass cardinality.
- **Persisting syllables.** D-03 locks compute-at-render; persistence
  doubles payload size and creates two sources of truth for syllabification.
- **Using `\n\s*\n` to derive metrical stanzas** for alternate meters. The
  corpus audit (see "Parser design") proves this is unreliable.
- **Synthesising amen notes.** D-13: ABC corpus has zero amen patterns; the
  renderer must not add tail notes under any circumstance.

## Data Model

### JSON shape (D-03 — load-bearing)

```typescript
interface Line {
  text: string                    // verbatim metrical line, NO leading verse digits
  bibleVerseRef?: number          // present iff this line begins a new Bible verse
  syllables?: string[]            // optional hand-override of auto-syllabifier
}

interface Stanza {
  index: number                   // 0-based stanza ordinal
  lines: Line[]                   // length == metrical-line count for the stanza's meter
}

type LyricsStructured = Stanza[]  // top-level shape stored in jsonb
```

**Worked example — Psalm 23 stanza 1 (CM, 4 lines):**
```json
{
  "index": 0,
  "lines": [
    { "text": "The Lord's my shepherd, I'll not want.", "bibleVerseRef": 1 },
    { "text": "He makes me down to lie",                "bibleVerseRef": 2 },
    { "text": "In pastures green: he leadeth me" },
    { "text": "the quiet waters by." }
  ]
}
```

`bibleVerseRef` is omitted (NOT `null`) on lines that continue the
previous verse. Serialiser uses `bibleVerseRef` presence to decide whether
to emit a leading digit run.

### Edge cases the data model MUST represent

1. **Continuation stanza (no leading verse number):** Multiple consecutive
   stanzas where the same Bible verse continues. The first line of a
   continuation stanza has NO `bibleVerseRef`. Found in ~50 of 184 corpus
   blobs (see Parser §invariants).
2. **Mid-stanza verse split:** Two `bibleVerseRef` values within one
   stanza, on different lines. Canonical case: Psalm 23 stanza 1 (verses
   1 and 2).
3. **Refrain repetition:** Ps 136 (Second Version) has the same refrain
   stanza repeated 16 times verbatim with NO verse number on the refrain.
   Each refrain instance is its own `Stanza` with all `bibleVerseRef`
   omitted. No special structural marker — refrain semantics live in the
   text itself.
4. **Colophon line:** Ps 72 ends with `#The prayers of David the son of
   Jesse are ended.` — a single-line printed-psalter note that is NOT a
   metrical line. The parser must either represent this as a metadata
   field on the Stanza (e.g. `note: string`), or quarantine the psalm.
   **Recommendation:** quarantine — only one corpus row, not worth a
   schema field. Planner picks.
5. **Trailing whitespace / multiple blank lines:** D-05 mandates
   round-trip "modulo whitespace." The serialiser MUST emit canonical
   form (single blank line between stanzas, no trailing whitespace) and
   the round-trip test MUST normalise both sides before comparison.

## Parser Design

### Algorithm

```
parseLyrics(raw, meter):
  1. Split raw on /\n\s*\n/ → blob-groups
  2. For each blob-group:
     a. Trim and split on /\n/ → raw lines
     b. Extract leading-digit run from FIRST line via /^(\d+)/; that
        digit run is the verse number for line 0 (if present).
     c. For each subsequent line, check for leading-digit run AT START
        of line OR mid-line digit followed by letter (\b\d+(?=[A-Za-z])).
        Mid-line digits ARE verse boundaries (corpus has ~10 such cases).
     d. Build Line[] for this blob-group.
  3. Group blob-groups into Stanzas per the meter's line-count:
       linesPerStanza = METRICAL_LINES[meter]   // CM=4, DCM=8, LM=4, SM=4, '66 66 88'=6, '10 10 10 10 10'=5
     Flatten all lines across all blob-groups (preserving order) then
     re-chunk into stanzas of linesPerStanza.
     - If the total non-blank line count is not a multiple of
       linesPerStanza → quarantine with reason "line count not a
       multiple of meter's lines-per-stanza".
  4. Return { ok: true, stanzas } or { ok: false, reason }.

serialiseLyrics(stanzas):
  1. For each stanza:
       For each line:
         If line.bibleVerseRef && line is the start of a stanza,
            emit "${ref}${line.text}\n"
         Else if line.bibleVerseRef, emit "${ref}${line.text}\n"
            (no leading whitespace, glued — D-06 invariant 2)
         Else emit "${line.text}\n"
  2. Join stanzas with "\n\n" (one blank line).
  3. Trim trailing whitespace.
```

**Critical decision the planner must make:** Step 3 (re-chunk by meter) is
a re-interpretation of the source blob's blank-line groupings. For CM
this is a no-op (1 blob-group = 1 metrical stanza). For alternate meters
this MUST happen. The audit below proves the blob's blank-line groups are
4-line chunks regardless of meter, NOT metrical stanzas, so step 3 is
load-bearing for alternate-meter correctness.

### Invariants verified against corpus (HIGH confidence — direct DB query)

For each of D-06's invariants, the result of querying the live
`psalter-db` snapshot (184 rows):

| # | D-06 invariant | Holds for | Breaks for |
|---|---|---|---|
| 1 | "Every numeric digit is a Bible verse number." | All 184 rows | None — `regexp_matches(lyrics, '\d')` is always preceded by `\b` or start-of-stanza. Two-digit verses (`10`, `11`...) are fine — they read as one digit run. |
| 2 | "Verse number is glued directly to next character with no space." | ~95% of cases | **Breaks for ~10 cases**: e.g. Ps 145(2nd) id=76: `"Thy wondrous works I will record.\n6 By men..."` — space between `6` and `By`. Parser must accept `\d+\s*` not just `\d+`. |
| 3 | "Stanzas delimited by blank lines (`lyrics.split(/\n\s*\n/)`)." | All 170 CM rows EXCEPT continuation stanzas | **Breaks structurally for all 14 non-CM rows.** Source blob always groups in 4-line blocks regardless of meter. For `10 10 10 10 10` (5 metrical lines/stanza), `66 66 88` (6 lines), `66 66 D` (8 lines), `87 87` (2 lines) — the blob's blank lines split mid-stanza. **Re-chunking by meter (Step 3 above) is mandatory.** Verified by SQL: `select meter, max(blob_groups_4line_chunks) where nonblank_lines / 4 = blob_groups`. |
| 4 | "One newline = one metrical line." | All 184 rows | None — every newline corresponds to a metrical line break in the printed psalter. |
| 5 | "A stanza may contain 1–N verses; a verse may span 1–N stanzas." | All 184 rows | None — model accommodates both. ~50 stanzas have no leading verse number (continuation stanzas). |

### Failure cases the parser must handle (corpus-confirmed)

| ID | Pattern | Example | Recommended handling |
|---|---|---|---|
| F-1 | Continuation stanza (first line of a blob-group has no leading digit) | Ps 90 id=5: `"Ere ever thou hadst form'd the earth..."` after blank line | **Accept**: line has no `bibleVerseRef`; rely on prior stanza's last `bibleVerseRef` for "current verse" inference. NOT a quarantine. |
| F-2 | Mid-line verse number with space | Ps 145(2nd) id=76: `"\n6 By men the might shall..."` | **Accept**: extract digit run, strip whitespace, attach `bibleVerseRef` to the line. |
| F-3 | Mid-LINE verse number (after first word of a line) | Ps 11 id=100: `"His eyes do see, his eye-lids try\n5men's sons..."` and Ps 22 id=31: `"When they me saw they from me fled.\n12Ev'n so I am forgot,"` | **Accept**: this is the canonical D-06 case — digit at line-start is the verse boundary. The line "5men's sons. The just he proves:" carries `bibleVerseRef: 5` and `text: "men's sons. The just he proves:"` (digit stripped). |
| F-4 | Refrain repetition with no verse numbers | Ps 167 (Ps 136 2nd): 16x `"For certainly / His mercies dure..."` | **Accept**: each refrain becomes a Stanza with all lines `bibleVerseRef`-omitted. Round-trip test passes (serialiser emits identical refrain text). |
| F-5 | Colophon / non-metrical trailing line | Ps 72 id=66: `#The prayers of David the son of Jesse are ended.` | **Quarantine** — only one row affected; not worth special-casing in the data model. Planner may opt to add a `note` field on the final Stanza if cheap. |
| F-6 | Line count not a multiple of metrical lines-per-stanza | Possible in declared-`66 66 88` Ps 136 id=181 (declared meter may be wrong vs actual 4-line refrain structure) | **Quarantine** with diagnostic showing expected vs actual. Hand-fix in follow-up loop. |
| F-7 | Declared meter mismatch (e.g. Ps 167's `66 66 88` declared meter but content is 4-line blocks) | Ps 167 id=167 | **Quarantine**. Re-classify the meter as a separate data-quality pass (out of scope — see `project_alignment_phase_prerequisites.md`). |

### Round-trip serialisation rules (D-05)

The round-trip bar is `normalise(serialise(parse(lyrics))) ===
normalise(lyrics)` where `normalise`:

1. Trims leading and trailing whitespace.
2. Collapses any run of `\n\s*\n+` (multiple blank lines) to a single
   `\n\n`.
3. Right-trims every line (`replace(/[ \t]+$/gm, '')`).
4. Does NOT alter inline whitespace within a line.

**Whitespace tolerance is asymmetric:** the parser accepts `"\d+\s*"`
between verse number and word (F-2); the serialiser ALWAYS emits the
strict D-06 form `"${digit}${word}"` with no space. The round-trip test
normalises the original blob by stripping `\d+(\s+)([A-Za-z])` →
`\d+\2` before comparing. Document this asymmetry in the parser file
header so future maintainers don't "fix" it.

### Failure handling

```
parseLyrics returns { ok: false, reason } on:
  - Line count not a multiple of metrical lines-per-stanza (F-6)
  - Declared meter not in METRICAL_LINES table (unknown meter)
  - Lines containing non-letter, non-punctuation, non-digit prefix
    characters (e.g. '#' colophon) (F-5)
  - Round-trip mismatch detected by the script itself before write
```

The migration script writes `{ ok: false, reason }` rows to
`parse-failures.md` keyed by `psalm_version.id` and `psalter_number`:

```markdown
## Parse failure: psalm-version id=66 (Psalm 72)
**Reason:** Trailing colophon line `#The prayers of David the son of
Jesse are ended.` cannot be represented in current data model.
**Action:** Hand-fix in follow-up loop.
```

### Line-folding for staff overlay (D-10)

The staff-overlay path folds metrical `Line[]` into per-phrase `w:`
contributions:

```typescript
// Pseudo:
const phraseCount = splitOnPhraseBreaks(abc).phrases.length  // = T
const stanzasPerCycle = tune.doubleLength ? 2 : 1
const linesPerPhrase = (stanzasPerCycle * stanza.lines.length) / phraseCount
//   CM × CM: (1 × 4) / 2 = 2 lines per phrase  → "8+6" syllables wrapped onto 1 system
//   DCM × CM: (2 × 4) / 4 = 2 lines per phrase  → same wrapping, 4 phrases
//   10.10.10.10.10 × Old 124th: (1 × 5) / 5 = 1 line per phrase  → 1 line per system
```

For each phrase index `i ∈ [0, T)`:
- Pull the `i*linesPerPhrase` through `(i+1)*linesPerPhrase` lines from
  the current cycle (across all stanzas in the cycle).
- Concatenate their `.text` values into one `w:` payload.
- Inject inline `<sup>` for `bibleVerseRef` at the parallel React overlay
  layer (NOT inside the `w:` string — see UI-SPEC §"Implementation note
  for abcjs `w:` field").

### Alternate-meter alignment (D-14)

For `10 10 10 10 10` against Old 124th: 5 phrases × 1 line per phrase.
For `66 66 88` against (any matching tune): 6 lines wrapped into the tune's
phrase count (the tune's `% PHRASE_BREAK` markers determine the actual
phrase count, NOT the lyric meter).

**The structured form makes this direct:** no meter-heuristic needed; just
iterate `stanza.lines[]` and map proportionally onto
`splitOnPhraseBreaks(abc).phrases`. If the ratio doesn't divide cleanly
(e.g. 5 lines × 4 phrases), defer to a "lines per phrase" array that
front-loads the remainder. Document this fallback in the algorithm spec.

## Common Pitfalls

### Pitfall 1: Treating `\n\s*\n` splits as metrical stanzas

**What goes wrong:** Alternate-meter psalms (Ps 124 2nd, Ps 148 2nd,
Ps 136 1st/2nd, Ps 143 2nd) mis-align because the blob's blank-line
groups are 4-line chunks regardless of the declared meter.

**Why it happens:** It's a reasonable heuristic for CM (which dominates
the corpus) and the existing `extractVerse1()` and `NotationRenderer`
code already use this split. Easy to assume it generalises.

**How to avoid:** The parser MUST re-chunk lines by meter (Step 3 of the
parse algorithm). Test this explicitly with Ps 124 2nd (id=138) as a
fixture.

**Warning signs:** Round-trip test fails on rows where the declared meter's
lines-per-stanza ≠ 4.

### Pitfall 2: Verse number prefix has whitespace tolerance

**What goes wrong:** Regex `^(\d+)([A-Za-z])` misses cases like `"6 By
men"` (space between digit and letter — found in id=76, id=20, id=44,
others).

**Why it happens:** D-06 invariant 2 says "no space" — but the corpus has
exceptions.

**How to avoid:** Use `^(\d+)\s*` (zero-or-more whitespace) for parsing
input; the serialiser emits the strict `\d+[A-Za-z]` form. Asymmetric
tolerance is documented in the parser file header.

**Warning signs:** Parse failures on alternate-meter psalms with multi-
digit verse numbers (10+).

### Pitfall 3: Refrain stanzas without verse numbers

**What goes wrong:** Strict "every stanza starts with a digit" parser
quarantines Ps 136 1st (16 refrain stanzas with no verse numbers).

**Why it happens:** D-06 invariant 1 is about *digits in the text*, not
*every stanza starts with one*. Continuation stanzas (F-1) and refrains
(F-4) legitimately have no leading verse number.

**How to avoid:** Treat absence of leading digit as "this stanza
continues the previous Bible verse" not "parse error". Refrain detection
isn't necessary — just accept the absence.

**Warning signs:** Quarantine count > 5.

### Pitfall 4: Renaming `lyrics` column without auditing all readers

**What goes wrong:** The Drizzle column rename compiles, but a code path
that does `row['lyrics']` (string subscript) or a SQL fragment slips
through. Search-snippet rendering breaks silently in production.

**Why it happens:** Drizzle's typed API catches `.lyrics` property access
but not stringly-typed access.

**How to avoid:** `grep -rn '\blyrics\b' src/` audit before merge; review
every match. The audit done in this research found only typed accesses
— but re-verify at PR time.

**Warning signs:** TypeScript clean, runtime null in search snippets.

### Pitfall 5: abcjs `w:` field cannot carry HTML

**What goes wrong:** Trying to inject `<sup>1</sup>` inside the `w:`
string. abcjs renders it as literal text or strips the markup.

**Why it happens:** abcjs's `w:` parser is plain-text only — designed for
hyphenated syllables, not arbitrary HTML.

**How to avoid:** Render verse-number superscripts as a parallel React
overlay positioned beneath the abcjs SVG. UI-SPEC §"Implementation note"
explicitly mandates this. The planner must spec the overlay DOM
structure (likely a `position: relative` container around the abcjs SVG
with absolutely-positioned `<span>` overlays per phrase line — though a
simpler approach is to use abcjs's `clickListener` per-element callback
to retrieve syllable positions at render time and absolutely-position
the `<sup>` elements after the fact).

**Warning signs:** Verse superscripts appear in staff view as plain `1`
or are missing entirely.

### Pitfall 6: Re-running the one-shot migration

**What goes wrong:** Developer re-runs `parse-lyrics.ts` after editing
`lyrics_structured` by hand. Edits are overwritten.

**Why it happens:** D-02 says `lyrics_imported_raw` is immutable post-
parse, and `lyrics_structured` is the canonical editable form going
forward. The migration script reads the IMMUTABLE source and writes the
EDITABLE target — so re-running clobbers edits.

**How to avoid:** Script must check whether `lyrics_structured` is non-
null and skip those rows by default. Add `--force` flag for explicit
re-runs.

**Warning signs:** A hand-corrected psalm-version regresses to original
parse output after a re-migration.

## Code Examples

### Example 1: Parser core (unit-test friendly)

```typescript
// src/lib/lyrics-parser.ts
import type { Line, Stanza, ParseResult } from './lyrics-types'

const METRICAL_LINES: Record<string, number> = {
  'CM': 4,
  'LM': 4,
  'SM': 4,
  // Note: 'CMD' / 'DCM' is not a stanza-level concept — see D-08.
  // DCM tunes pair two CM stanzas at the cycle level, not the stanza level.
  '66 66 88': 6,
  '66 66 D': 8,
  '87 87': 2,
  '10 10 10 10 10': 5,
  '76 76 D': 8,
}

function metricalLinesForMeter(meter: string | null): number | null {
  if (!meter) return null
  // Match phrasesForMeter normalisation: first whitespace-delimited token
  const firstToken = meter.trim().split(/\s+/)[0].toUpperCase()
  if (METRICAL_LINES[firstToken] != null) return METRICAL_LINES[firstToken]
  if (METRICAL_LINES[meter.trim()] != null) return METRICAL_LINES[meter.trim()]
  return null
}

export function parseLyrics(raw: string, meter: string | null): ParseResult {
  const linesPerStanza = metricalLinesForMeter(meter)
  if (!linesPerStanza) {
    return { ok: false, reason: `Unknown meter: ${meter}` }
  }

  // Step 1: split on blank lines; collect ALL non-blank lines preserving order
  const allLines = raw
    .split(/\n+/)
    .map((l) => l.trim())
    .filter(Boolean)

  // Step 2: detect colophon / non-metrical prefixes
  if (allLines.some((l) => /^[#*(]/.test(l))) {
    return {
      ok: false,
      reason: 'Non-metrical prefix character (#, *, ( ) detected — quarantine for hand-fix.',
    }
  }

  // Step 3: parse each line — extract optional leading-digit run
  const parsed: Line[] = allLines.map((rawLine) => {
    const m = rawLine.match(/^(\d+)\s*(.*)$/)
    if (m) {
      return { text: m[2], bibleVerseRef: Number(m[1]) }
    }
    return { text: rawLine }
  })

  // Step 4: re-chunk into stanzas of `linesPerStanza`
  if (parsed.length % linesPerStanza !== 0) {
    return {
      ok: false,
      reason: `Line count ${parsed.length} not a multiple of ${linesPerStanza} (meter ${meter}).`,
    }
  }

  const stanzas: Stanza[] = []
  for (let i = 0; i < parsed.length; i += linesPerStanza) {
    stanzas.push({
      index: stanzas.length,
      lines: parsed.slice(i, i + linesPerStanza),
    })
  }

  return { ok: true, stanzas }
}

export function serialiseLyrics(stanzas: Stanza[]): string {
  return stanzas
    .map((stanza) =>
      stanza.lines
        .map((line) =>
          line.bibleVerseRef != null
            ? `${line.bibleVerseRef}${line.text}`
            : line.text,
        )
        .join('\n'),
    )
    .join('\n\n')
}
```

## Open Questions

> **Status (revision 2):** All four Open Questions are RESOLVED. Recommendations are now binding planner decisions and have been wired into Plans 01-07. See per-question RESOLVED markers below.

1. **Q: Should the column be `lyrics_structured` or a different name?** (RESOLVED)
   - What we know: D-01 says jsonb, name illustrative.
   - **RESOLVED:** Column name is `lyrics_structured` (TS: `lyricsStructured`). Plan 01 Task 2 makes this canonical. No further action.

2. **Q: Where does the inline `<sup>` overlay live in the staff DOM?** (RESOLVED)
   - What we know: UI-SPEC §"Implementation note" forbids it inside `w:`; mandates parallel display layer.
   - **RESOLVED — option (a):** Inline `<sup>` lives inside `StanzaList` (Plan 06), which is rendered in all three view modes — lyrics-only, solfège, and staff (via AbcPlayer.renderLyricsBelow). To keep Plan 07's UAT assertion (≥ 2 `sup.verse-number`) robust regardless of AbcPlayer internal state, the UAT explicitly navigates to the lyrics-only tab before counting. No positioned-overlay work (no abcjs SVG bounding-box computation) is in scope for this phase.

3. **Q: What happens to `splitOnPhraseBreaks` count when the tune has more `% PHRASE_BREAK` markers than the meter's nominal phrase count? Specifically: do all `double_length=true` tunes have exactly 4 phrase breaks?** (RESOLVED)
   - What we know: §4.9.2 backfilled phrase markers into 75 tunes; CMD was annotated with 4 markers per STATE.md 04.9.2-02.
   - **RESOLVED — option (b):** The design assumption is that every `double_length=true` tune has exactly **4** phrase breaks (`splitOnPhraseBreaks(abc).phrases.length === 4`). Plan 07 Task 2 adds `tests/tune-quality-phrase-count.test.ts` which queries the live `tunes` table for all `doubleLength=true` rows, runs `splitOnPhraseBreaks(abc)`, and asserts `phrases.length === 4`. Offenders are SURFACED into the test failure output (and appended to `parse-failures.md` under a new `## Tune-quality issues` section by the executor on failure). The test's pass bar is hard-zero offenders.

4. **Q: How is the legacy `groupStanzasIntoCycles` kept correct for quarantined psalms?** (RESOLVED)
   - What we know: Quarantined psalms use the legacy path; today's legacy path is broken for DCM.
   - **RESOLVED:** Plan 04 unifies the contract — there is NO "legacy" `groupStanzasIntoCycles` after Plan 04. The function takes `(stanzas: Stanza[], doubleLength: boolean)` and is called from BOTH the structured-lyrics path AND the quarantine-fallback path in NotationRenderer.tsx (Plan 05 Step B parses the legacy blob into transient `Stanza[]` so the call site is uniform). The `doubleLength` boolean is plumbed from `tune.double_length` regardless of whether the psalm-version is quarantined.
