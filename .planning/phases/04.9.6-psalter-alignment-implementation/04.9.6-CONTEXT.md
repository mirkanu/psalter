# Phase 4.9.6: Psalter Alignment Implementation — Context

**Gathered:** 2026-05-18
**Status:** Ready for planning

<domain>
## Phase Boundary

Redesign the lyrics representation from a flat text blob into a structured `Stanza → Line (+ bibleVerseRef) → Syllable[]` form, parse every existing Airtable lyric blob into that form, and rewrite the staff alignment + line-break algorithm to drive off `tunes.double_length` (not `meter='CMD'`) so that:

- DCM tunes correctly sing two consecutive CM stanzas per tune-pass (fixes the live mis-render)
- Alternate-meter psalms align syllable-to-note correctly
- Mid-stanza Bible-verse boundaries surface visually inside the lyric flow without disrupting the metrical line structure
- Amens are not synthesised by the renderer (they are absent from the digitised ABC by convention)
- Psalm 23 + Crimond canonical case has zero regression

**Strictly in scope:** the data model, the one-shot parser for the Airtable-imported blob, the alignment+line-break algorithm, the mid-stanza-verse-boundary UI surface, and the renderer migration.

**Strictly out of scope:** user stanza-selection UI (own seed: `psalter-alignment-implementation` → triggers `user-stanza-selection`), 4-part SATB rendering, meter-mismatch warning UI, ingestion of the printed-psalter's tune-pairing recommendations.
</domain>

<decisions>
## Implementation Decisions

### Data model location & lifecycle

- **D-01:** Persist the structured form as a new `lyrics_structured` `jsonb` column on `psalm_versions`. NOT a new join table; NOT a build-time derivation.
- **D-02:** **Airtable is being decommissioned.** Nothing in this phase may depend on Airtable being live. The current `lyrics` text column is renamed/treated as an **immutable imported snapshot** (e.g. `lyrics_imported_raw` — planner picks the exact column name) and is never written again after the one-shot parse. `lyrics_structured` becomes the canonical editable form from this phase forward.
- **D-03:** Persisted JSON shape: `Stanza → Line` with `bibleVerseRef` on the Line. **Syllables are NOT persisted by default** — they are computed at render time via the existing `syllabifyForAbc` library. Hybrid override: an optional `syllables: string[]` field on a Line that, when present, overrides the auto-syllabifier for that line (used for hand-correction of awkward cases). This keeps the payload small, keeps one global syllabification rule, and still allows per-line manual fixes when needed.

### Parser

- **D-04:** **Quarantine-on-failure.** The one-shot migration parses every `lyrics` blob it can; failures do not abort the migration. Each failure is written to a `parse-failures.md` report keyed by psalm-version id with the line and reason. Psalms in the quarantine bucket keep using the legacy `lyrics` blob through the renderer (feature-flag-per-psalm) until fixed in a follow-up loop. The new alignment renderer only takes effect when `lyrics_structured` is populated for that psalm-version.
- **D-05:** **Strict round-trip bar.** For every parsed psalm-version, `serialise(parse(lyrics)) === lyrics` modulo whitespace. This is enforced by an automated test that runs against the full 184-version corpus during the migration. Any version that cannot meet this bar lands in the quarantine bucket (D-04). This satisfies success criterion #2.
- **D-06:** **Parser invariants from the user briefing (load-bearing):**
  1. Every single numeric digit in a current `lyrics` blob is a Bible verse number. Lyric numbers themselves are always spelled out (`four`, never `4`).
  2. A verse number is glued directly to the next character with **no space** between (`1The Lord's my shepherd...`).
  3. Stanzas are delimited in the blob by blank lines (preserve current behaviour: `lyrics.split(/\n\s*\n/)`).
  4. A line is a metrical line as it appears in the source text (one newline = one line).
  5. A single Bible verse may start mid-line / mid-stanza; a stanza may contain 1–N Bible verses; a Bible verse may span 1–N stanzas (per §3 of `scottish-psalter-structure.md`). The parser MUST preserve these relationships.

### Mid-stanza verse-boundary UI

- **D-07:** **Inline superscript verse number before the first syllable of the new verse**, in both the staff-overlay lyric line and the lyrics-only view. (e.g. `… ⁴He maketh me down to lie …`.) Non-disruptive, traditional psalter convention, mobile-safe. No gutter, no hover-only.

### Line breaks

- **D-08:** **Meter alone determines the natural metrical-line count per stanza** (CM=4, DCM=8, LM=4, SM=4, `10.10.10.10.10`=5, etc.). This is the structured form's `Line[]` count per stanza.
- **D-09:** **Default lyrics-only render: one metrical line per visible line** (CM = 4 visible lines per stanza).
- **D-10:** **Staff-overlay render: lyric line breaks follow the ABC notation's phrase boundaries**, NOT the metrical-line breaks. For CM the notation default groups each `8+6` syllable pair onto one staff system → two metrical lines collapse onto one staff line. The current `splitOnPhraseBreaks(abc)` already exposes this; the new algorithm uses it.

### Alignment algorithm

- **D-11:** **DCM detection is driven by `tunes.double_length === true`**, not `meter === 'CMD'` and not string-comparison on meter labels. This is the load-bearing fix for the live mis-render. `groupStanzasIntoCycles` (or its successor) takes the `double_length` boolean and the stanza count directly.
- **D-12:** **Stanza-cycle model carries forward** (D-19 / D-20 from prior phase context): one tune-pass renders 1 stanza for normal tunes, 2 stanzas for `double_length=true` tunes. Under-fill behaviour for the last cycle (e.g. odd stanza count against a DCM tune) remains: blank lyric portions for the missing tail, never repeat content.
- **D-13:** **Amens are not present in the digitised ABC and the renderer must not synthesise them** (success criterion #7; doc §2). No code path adds two trailing notes; no lyric-skip-final-2-notes heuristic is needed because the notes aren't there.
- **D-14:** **Alternate-meter alignment** works by syllable-count matching between the metrical line (per D-08) and the corresponding ABC notation phrase. The structured form's explicit lines make this a direct mapping, replacing the current meter-heuristic in `splitStanzaIntoPhrasePortions`.

### Renderer migration

- **D-15:** The new alignment pathway lights up **per-psalm-version** — gated on `lyrics_structured` being non-null AND not in the quarantine bucket. Psalms still using `lyrics_imported_raw` continue through the current renderer until they're fixed. This lets the phase ship incrementally without a corpus-wide cutover.
- **D-16:** Regression canary: **Psalm 23 + Crimond** (per success criterion #6 and doc §4). Automated test renders this pairing and asserts the expected syllable→note grid.

### Claude's Discretion

The following were not raised by the user and Claude will default sensibly:

- **Column name `lyrics_structured`** is illustrative — planner may choose `lyrics_json`, `structured_lyrics`, etc.
- **Renaming `lyrics` → `lyrics_imported_raw`** is a Drizzle migration; planner sequences it after the structured-column backfill is verified.
- **Parse-failures report file path:** likely `.planning/phases/04.9.6-psalter-alignment-implementation/parse-failures.md` (or `.planning/data/`), planner picks.
- **Test corpus location** for the round-trip test: a snapshot of the 184 lyric blobs captured at migration time, committed under `.planning/data/` or `tests/fixtures/`. Planner decides.
- **No new abcjs work expected** — the structured form still drives the ABC `w:` field at render time; abcjs's syllable-to-note alignment is unchanged.

</decisions>

<specifics>
## Specific User Inputs (load-bearing)

1. **Airtable is going away.** The structured form must stand on its own; the original blob is preserved only as an immutable historical record, not as a sync source.
2. **Every numeric digit in the lyric blob is a Bible verse number; lyric numbers are spelled out.** This is the parser's foundational regex assumption.
3. **Verse numbers are glued directly to the following character with no whitespace** (`1The Lord's…`). The parser splits on the digit-letter boundary.
4. **Default lyrics-only render = one metrical line per visible line** (CM = 4 lines per stanza). Staff-overlay render folds metrical lines according to the ABC's notation phrase breaks (CM default = `8+6` per system).
5. **Inline superscript verse number** is the chosen mid-stanza-verse-boundary surface — matches the printed psalter convention, no gutter, no hover.
6. **`tunes.double_length` is the DCM signal**, not the meter string.

</specifics>
