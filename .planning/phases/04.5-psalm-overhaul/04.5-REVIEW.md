# Code Review — Phase 04.5 (Psalm Overhaul)

## Summary

Reviewed 10 files covering the psalm detail page, notation player, tab UI, skeleton loading states, and the DB query layer. The skeleton and loading files are clean. The query layer is structurally sound. The critical issues are concentrated in two areas: (1) an unvalidated `soundcloudUrl` value being interpolated directly into an `iframe src` in both `page.tsx` and `PsalmTabs.tsx`, and (2) `innerHTML` assignment in `AbcRenderer.tsx` (referenced by these files) used to clear the abcjs container — while clearing is necessary, the pattern is flagged because it interacts with user-supplied ABC content. Additional warnings cover a missing de-duplication step on backup tunes, an unsafe `generateMetadata` that can feed an unvalidated ID into a DB query, a localStorage read that causes a hydration flash, stanza logic that silently renders nothing when lyrics are empty, and two missing `sandbox` attributes on SoundCloud iframes.

#### CR-01: Unsanitised `soundcloudUrl` interpolated into `iframe src` — stored-data injection risk

**Files:**
- `src/app/psalms/[id]/page.tsx:104`
- `src/components/PsalmTabs.tsx:77`

**Issue:**
`primaryTune.soundcloudUrl` is a database-sourced string concatenated directly into the iframe `src` attribute with only `encodeURIComponent` around the URL portion. `encodeURIComponent` is insufficient protection here: if the stored value is a `javascript:` URI or a data URI, `encodeURIComponent` will encode it verbatim and embed it as the query-string value of `url=`, but a malicious base URL (e.g., the outer `https://w.soundcloud.com/player/?url=` part) is hardcoded — so the SoundCloud domain is safe for the outer frame origin. However, the actual risk is that **no validation ensures the stored value is a valid HTTPS URL before it is passed to the browser**. If an admin (or a future migration script) stores a `javascript:…` or `data:…` string, it will be interpolated literally into the attribute — iframes with a `javascript:` or `data:` src can execute arbitrary JS in older browsers or certain render contexts.

Additionally, neither iframe has a `sandbox` attribute. A SoundCloud embed that has been compromised or whose URL has been tampered with in the database can navigate the top frame (`allow-top-navigation` is the default without `sandbox`).

**Fix:**

Add a URL validator before rendering the iframe, and add `sandbox` to both iframes:

```tsx
// Utility (e.g. src/lib/url.ts)
export function isSafeHttpsUrl(url: string): boolean {
  try {
    const parsed = new URL(url)
    return parsed.protocol === 'https:'
  } catch {
    return false
  }
}
```

```tsx
// In page.tsx and PsalmTabs.tsx — guard before rendering the iframe
{primaryTune?.soundcloudUrl && isSafeHttpsUrl(primaryTune.soundcloudUrl) && (
  <iframe
    sandbox="allow-scripts allow-same-origin"
    title={`SoundCloud: ${primaryTune.name}`}
    width="100%"
    height="96"
    allow="autoplay"
    src={`https://w.soundcloud.com/player/?url=${encodeURIComponent(primaryTune.soundcloudUrl)}&auto_play=false&hide_related=true&show_comments=false&show_user=false&show_reposts=false`}
    className="rounded-md border border-border"
  />
)}
```

#### CR-02: `generateMetadata` calls `fetchPsalmDetail(Number(id))` without the integer guard that `PsalmPage` applies

**File:** `src/app/psalms/[id]/page.tsx:16–24`

**Issue:**
`PsalmPage` (line 29) correctly validates the parsed integer before hitting the database:
```ts
if (!Number.isFinite(psalmId) || psalmId < 1 || psalmId > 150) notFound()
```
`generateMetadata` (line 18) does not apply this guard. It calls `fetchPsalmDetail(Number(id))` directly. If a bot or crawler hits a crafted URL such as `/psalms/99999999999999999` or `/psalms/abc`, `Number('abc')` yields `NaN`, and Drizzle's `eq(psalms.id, NaN)` will send `WHERE id = NaN` to PostgreSQL. PostgreSQL treats a NaN comparison as always-false for numeric types, so the query returns nothing harmlessly — but the behaviour is unintentional. More concretely, an arbitrarily large integer like `Number('99999999999999999999')` becomes `Infinity` (or a very large float) which will be sent as a floating-point literal in the SQL, which could trigger a Postgres type-cast error depending on the driver.

**Fix:**

```ts
export async function generateMetadata({ params }: PageProps): Promise<Metadata> {
  const { id } = await params
  const psalmId = Number(id)
  if (!Number.isFinite(psalmId) || psalmId < 1 || psalmId > 150) {
    return { title: 'Psalm Not Found | CPRC Psalter' }
  }
  const psalm = await fetchPsalmDetail(psalmId)
  return {
    title: psalm?.bibleTitle
      ? `${psalm.bibleTitle} | CPRC Psalter`
      : `Psalm ${psalmId} | CPRC Psalter`,
  }
}
```

#### WR-01: Backup tunes de-duplication is incomplete — the same tune can appear multiple times

**File:** `src/components/PsalmTabs.tsx:24–30`

**Issue:**
The backup-tunes list filters out the primary tune by id, but does not de-duplicate across non-primary entries. If the same non-primary tune is linked via multiple `psalmVersionTunes` rows (e.g., once per `psalmVersion`), it will appear in the rendered list more than once. The comment says "de-duped" but the implementation only excludes the primary tune.

```ts
const backupTunes = allPvts
  .filter((pvt) => !pvt.isPrimary)
  .map((pvt) => pvt.tune)
  .filter((t): t is NonNullable<typeof t> => !!t && t.id !== primaryTuneId)
  // ^^^ does NOT de-dup duplicates within the non-primary set
```

**Fix:**

```ts
const seen = new Set<number>()
const backupTunes = allPvts
  .filter((pvt) => !pvt.isPrimary)
  .map((pvt) => pvt.tune)
  .filter((t): t is NonNullable<typeof t> => {
    if (!t || t.id === primaryTuneId) return false
    if (seen.has(t.id)) return false
    seen.add(t.id)
    return true
  })
```

#### WR-02: `localStorage` read on mount causes hydration UI flash (scoreMode flickers from 'staff' to 'solfege')

**File:** `src/components/PsalmNotationPlayer.tsx:56–68`

**Issue:**
`scoreMode` is initialised to `'staff'` (line 58) and then updated in a `useEffect` (line 63–68). Because `useEffect` fires after the first render, the component always renders once with `scoreMode === 'staff'`, then re-renders with the stored preference. On a slow device this produces a visible layout shift: the Staff button appears active, then the Solfège button activates. Since this component is behind `ssr: false`, there is no SSR mismatch risk, but the flash is still a UX bug.

**Fix:**
Initialise state from a lazy initialiser that reads localStorage, which runs only on the client and only once:

```ts
const [scoreMode, setScoreMode] = useState<ScoreMode>(() => {
  if (typeof window === 'undefined') return 'staff'
  return localStorage.getItem('psalter-score-mode') === 'solfege' ? 'solfege' : 'staff'
})
// Remove the read useEffect entirely; keep only the write useEffect.
```

#### WR-04: `AbcRenderer` uses `el.innerHTML = ''` to clear the container — DOM clearing via innerHTML

**File:** `src/components/AbcRenderer.tsx:30`

**Issue:**
`el.innerHTML = ''` is used to clear the previously rendered abcjs SVG before each re-render. While the content being cleared is SVG generated by abcjs (not user input), this is a misuse of `innerHTML` as a DOM utility — it bypasses React's virtual DOM reconciliation and can cause issues if React holds references to child nodes. Additionally, abcjs itself might attach event listeners to the SVG nodes; clearing via `innerHTML` will orphan those listeners without triggering proper cleanup. The established safe pattern is `while (el.firstChild) el.removeChild(el.firstChild)` or `el.replaceChildren()`.

**Fix:**

```ts
useEffect(() => {
  const el = containerRef.current
  if (!el) return
  el.replaceChildren() // removes all children cleanly; no innerHTML
  abcjs.renderAbc(el, abc, {
    responsive: 'resize',
    add_classes: true,
  })
}, [abc])
```

#### WR-05: `buildAbcWithStanzas` regex strips ALL `w:` lines globally, including those inside repeated sections

**File:** `src/components/PsalmNotationPlayer.tsx:22–26`

**Issue:**
The regex `/^w:.*$/gm` removes every line starting with `w:` from the ABC string before injecting the new stanza group. In standard ABC notation, `w:` lines are expected to follow the music voice (`V:`) or measure groups they annotate. If the ABC string contains multiple voices or repeated sections each with their own `w:` lines, stripping all of them and appending a single block of `w:` lines at the end will produce malformed ABC that abcjs may misparse — misaligning lyrics with notes or silently dropping them.

**Fix:**
This requires a more careful ABC parser or a convention that ABC stored in the database never contains `w:` lines (letting the component always inject them). The fix for now is to document the constraint at the point of data entry and add an assertion:

```ts
function buildAbcWithStanzas(baseAbc: string, stanzaGroup: string[]): string {
  // Assumes baseAbc contains no w: lines (the DB stores bare notation).
  // If w: lines are found, strip them — but log a warning so DB data is corrected.
  if (/^w:/m.test(baseAbc)) {
    console.warn('[PsalmNotationPlayer] ABC string contains w: lines; they will be replaced.')
  }
  const withoutW = baseAbc.replace(/^w:.*$/gm, '').replace(/\n{3,}/g, '\n\n').trim()
  const wLines = stanzaGroup.map((s) => `w: ${s.replace(/\n/g, ' ')}`).join('\n')
  return `${withoutW}\n${wLines}`
}
```

Long-term, store only bare notation in the database and rely solely on the component for lyric injection.

#### WR-06: `stanzas.length <= 1` counter label is wrong when there are zero stanzas

**File:** `src/components/PsalmNotationPlayer.tsx:92–95`

**Issue:**

```ts
const counterLabel =
  stanzas.length <= 1
    ? `Stanza 1 / 1`
    : `Stanzas ${firstStanzaNum}–${lastStanzaNum} / ${stanzas.length}`
```

When `stanzas.length === 0` (no lyrics), this evaluates to `"Stanza 1 / 1"` which is incorrect — there are no stanzas. The navigation controls are gated on `stanzaGroups.length > 1` so they won't display, but `counterLabel` is still computed with a misleading value. If the guard condition ever changes, this label will surface.

**Fix:**

```ts
const counterLabel =
  stanzas.length === 0
    ? ''
    : stanzas.length === 1
    ? 'Stanza 1 / 1'
    : `Stanzas ${firstStanzaNum}–${lastStanzaNum} / ${stanzas.length}`
```

#### IN-03: `psalm.id` used raw in external URL hrefs — should be asserted as a safe integer

**File:** `src/components/PsalmTabs.tsx:204, 214, 224`

**Issue:**
`psalm.id` is typed as `number` (integer primary key) and is safe in practice, but it is interpolated directly into three external href strings without any conversion to `String()` or validation. TypeScript will coerce it to string in template literals, but an explicit `String(psalm.id)` or `psalm.id.toString()` makes the intent clear and prevents a future type change from silently producing `[object Object]` in the URL.

**Fix:**
```tsx
href={`https://www.sermonaudio.com/search/?keyword=psalm+${psalm.id}&keywordtype=4`}
// becomes:
href={`https://www.sermonaudio.com/search/?keyword=psalm+${String(psalm.id)}&keywordtype=4`}
```

#### IN-04: `PsalmNotationPlayer` is marked `'use client'` but is loaded via `dynamic(..., { ssr: false })` — redundant directive is not harmful but is misleading

**File:** `src/components/PsalmNotationPlayer.tsx:1`

**Issue:**
The component is correctly loaded via `next/dynamic({ ssr: false })` in `PsalmNotationPlayerClient.tsx`, which already ensures it never runs on the server. The `'use client'` directive on the component itself is redundant — `dynamic` with `ssr: false` already guarantees client-only execution. While not a bug, new contributors may be confused about which mechanism is actually responsible for the client boundary.

**Fix:**
Keep `'use client'` — it is harmless and ensures the file is correctly treated as a client module if ever imported differently. Add a comment:

```tsx
'use client'
// Note: this component is also loaded via dynamic({ ssr: false }) in
// PsalmNotationPlayerClient.tsx. The 'use client' directive is retained
// so that direct imports (e.g. in tests) also work correctly.
```
