<root_cause>
ROOT CAUSE (already diagnosed — do NOT re-investigate from scratch; verify and fix):

Path: `/psalms/62` → `SingingView` (chromeless=true) → `NotationRendererClient` →
`NotationRenderer` Staff view (viewMode='staff', NOT split-leaf) → `buildUnifiedAbc`.

St Agnes, Durham (tune id 155) ABC (M:C, L:1/8, K:G), 4 CM phrases:
  P0: `b2b2b2a4 | b2c'4f2 | g6`
  P1: `d2 | d2d2b4 | a2a6`
  P2: `| c'2c'2b2a4 | g2f4e2 | d6`
  P3: `d2 | e2g2b4 | a2g6`
Its `melisma_positions` column is `[]` (empty) → the Phase-04.9.12 melisma branch
in buildUnifiedAbc is SKIPPED (`phrasePositions != null` is false), so the tune
flows through the standard w:-line path.

Desktop (viewport ≥1280): `baseSubdivisions = 1` → each phrase renders as ONE
sub-staff → `needsProportionalSplit` is false → the `else` branch uses
`wLineForSyllables` for structured 1:1 syllable-to-note alignment. PERFECT.

Mobile (chromeless && viewport <768): `baseSubdivisions = 2` → each phrase is split
into 2 sub-staves by `splitMusicIntoSubLines` at MEASURE boundaries. Because these
phrases end with a long held note in its own measure, the split is lopsided by
NOTE COUNT, e.g. P0 → sub-staff A = `b2b2b2a4 | b2c'4f2 |` (7 notes),
sub-staff B = `g6 |` (1 note).

The bug: the mobile branch (`needsProportionalSplit === true`) distributes the
8 syllables with `splitWLineIntoChunks(syllabified, actualSubdivisions)`, which
splits by EQUAL TOKEN COUNT → 4 syllables to sub-staff A, 4 to sub-staff B.
Result on mobile: the 1-note held final note `g6` gets 4 syllables crammed under
it, and the 7-note melody line is padded with 3 placeholder `·` dots. Every phrase
of this tune is misaligned. "A few other tunes" = other non-melisma tunes whose
final phrase note is a long held note in its own measure (same lopsided split).

THE FIX: distribute syllables by each sub-staff's actual NOTE-HEAD COUNT instead of
equal token count. For P0 that yields sub-staff A = first 7 syllables, sub-staff B =
last 1 syllable — a strict 1:1 syllable-to-note mapping that matches the desktop
single-staff rendering. This obeys lyric-to-note-alignment.md's core rule (1:1
mapping; `_` only for melismas — and this tune has none).

Scope guard: the fix must ONLY affect the `needsProportionalSplit` branch
(non-melisma, mobile sub-divided, single-metrical-line phrases). Desktop
(subdivisions=1, no split), melisma tunes (different branch), multi-line phrases
(structured else branch), and split-leaf must be byte-identical afterwards.
</root_cause>

  <name>Task 1: Add pure note-count-weighted syllable splitter + tests</name>
  <files>src/components/notation/splitWLineByNoteCounts.ts, src/components/notation/__tests__/splitWLineByNoteCounts.test.ts</files>
  <behavior>
    `splitWLineByNoteCounts(payload: string, noteCounts: number[]): string[]`
    returns one syllable-chunk string per entry in `noteCounts`.
    - Splits `payload` on whitespace into tokens.
    - Chunk i receives the next `noteCounts[i]` tokens (in order); tokens are
      consumed cumulatively across chunks (chunk 0 first, then chunk 1, ...).
    - The LAST chunk absorbs any remaining tokens (so no syllable is ever dropped
      when token count exceeds sum(noteCounts)).
    - If tokens run out, later chunks are `''` (empty) — never negative slices.
    - Chunk strings are space-joined tokens (matching splitWLineIntoChunks output shape).

    Tests (write FIRST, must fail before implementation):
    - `splitWLineByNoteCounts('a b c d e f g h', [7, 1])` → `['a b c d e f g', 'h']`
      (the St Agnes P0 case — proves the held-final-note gets exactly ONE syllable).
    - `splitWLineByNoteCounts('one two three four', [2, 2])` → `['one two', 'three four']`
      (even split, regression sanity).
    - `splitWLineByNoteCounts('a b c', [1, 1, 1])` → `['a', 'b', 'c']`.
    - `splitWLineByNoteCounts('a b c d e', [2, 2])` → `['a b', 'c d e']`
      (extra tokens beyond sum land in the last chunk — no drop).
    - `splitWLineByNoteCounts('a b', [3, 1])` → `['a b', '']`
      (fewer tokens than notes → chunk 0 takes all available, chunk 1 empty).
  </behavior>
